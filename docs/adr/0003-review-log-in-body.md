# 0003. 人の判断はカード本文の追記専用の `## レビュー` に書き、ゲートの状態はそこから読む

- 状態: 採用
- 日付: 2026-09-11
- 置き換え元: なし
- 置き換え先: なし

## 状況

ステージを保存せず実態から導出する（[0002](0002-derive-stage.md)）には、人の判断にも痕跡が要った。
当時、人が下した判断（承認した・否決した・その理由）はどこにも残らず、
`explored` フラグは「探索が済んだ」ことは言えても「人が見て良しとした」ことは言えなかった。
否決の理由を記録する場所そのものが無かった。

カードは `.ai-board/cards/<id>.md` のファイルで、ai-board サーバが書ける唯一の場所だった。
AI エージェントも CLAUDE.md の書き込み境界で本文の編集を許されており、人はエディタで直接読み書きしていた。
board-lanes の計画は「新しいファイル形式・新しい保存場所を増やさない」「否決の理由を、AI が次の周回で読める形で残す」を目標にした。

## 決定

- **人の判断はカード本文の `## レビュー` に追記専用のログとして書く。** エントリは
  `### <ISO 8601> <ゲート> <種別>` の見出し 1 行と、それに続く理由文で表す。
  種別は 提出 / 再提出（AI が書く）と 承認 / 否決 / 中止（人が書く）。否決には理由文を必須とする。
- **各ゲートの状態は、そのゲートの最新のエントリから決める。** 無ければ未提出、提出 / 再提出なら判断待ち、
  承認なら通過、否決なら差し戻し。別のゲートのエントリを混ぜない。同時刻ならログの後ろにあるほうを最新とする。
- **書式の壊れた見出しは黙って無視する。** ボード全体が読めなくなるより、1 件が無視されるほうが害が小さい。
- 否決からの復帰は、AI が成果物を直して `再提出` を追記することで表す。
- PR のゲートはレビューログを持たない。承認とマージは PR 側の実態が正である。
- **中止は工程の進捗と直交する終端の軸として扱い、ゲートの通過判定に含めない。** 中止しても通過済みのゲートを巻き戻さず、
  ステージは動かない。中止の後に再提出があれば中止ではなくなる。

## 検討した代案

- **frontmatter に `reviews:` 配列を持つ** — frontmatter が重くなり、理由文が複数行になると手編集が辛い。
- **`.ai-board/reviews/<id>.jsonl` に分離する** — カードをエディタで開いたときに理由が見えない。
  カードを 1 ファイルで完結させる設計と食い違う。

## 結果

- 最初の実装は中止もゲートの判定に含めており、中止を追記した瞬間にステージが前の列へ戻っていた。
  同じ日に `af16618` で判定から外し、仕様のシナリオで固定した。
- API・AI・人の 3 者が同じ場所を読み書きし、否決の理由が AI の次の周回の入力になった。
- 承認 / 否決 / 中止は `POST /api/cards/:id/reviews` のボタンから正しい書式で追記し、手書きは例外的な経路になった。
- 追記専用であることから、廃止したゲートの記録は書き換えず、解釈だけをやめる扱いになった（[0004](0004-drop-explore-lanes.md)）。
- レビューの履歴を構造化データとして検索・集計することと、複数人のレビューの記録はしない（計画の Non-Goals）。
- 後に、ゲートに verify が加わり（[0013](0013-verify-gate.md)）、AI が書ける種別に 保留 が加わり（[0014](0014-ai-review-entries-and-hold.md)）、
  飛ばす宣言のあるゲートでは 提出 / 再提出 を承認と読むようになった（[0018](0018-skip-gate-reads-submit-as-approval.md)）。
  カードの置き場所はファイルから SQLite（[0009](0009-cards-in-sqlite.md)）、データ用ブランチ（[0019](0019-cards-on-data-branch.md)）へ移ったが、
  判断の置き場所は本文の `## レビュー` のままである。追記は本文の文字列の往復ではなく
  リポジトリの専用の口で行うようになった（[0022](0022-review-append-port.md)）。
