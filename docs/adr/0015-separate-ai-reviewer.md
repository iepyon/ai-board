# 0015. AI レビューを実装とは別の作業者に任せ、重要な指摘だけを直して見送りを PR の本文に写す

- 状態: 採用（一部を [0021](0021-flat-subagents.md)・[0023](0023-three-loop-roles.md) が置き換え）
- 日付: 2026-10-30
- 置き換え元: なし
- 置き換え先: [0021](0021-flat-subagents.md)・[0023](0023-three-loop-roles.md)（一部）

## 状況

`implement` の 1 手は計画のタスクを 1 つだけ倒し、次の手は次の cron の周が選んでいた（[0012](0012-loop-supervisor-and-fresh-subagent.md)）。
2026-10-30 に `verify-gate`（タスク 16 件）をループで実装したところ、1 手は 3〜5 分で終わるのに、タスクごとに 5 分の周を待ち、
PR中 になるまでの時間の半分以上が待ち時間だった。実装中は人の判断を挟まない区間で、タスクの境目で周を待つ理由は無かった。

AI レビューは、`implement` の最後の手で作業者が自分で `/code-review` にかけ、指摘を自分で直していた。
新しい文脈で読むとはいえ、何を直すかを決めるのは実装した作業者自身だった。

監視役は計画を読まず、計画は作業用のブランチにあってメインのチェックアウトからは読めないことが多い。
そのため `next-action.ts` は実装中のカードの手を計画の進み具合で分けていなかった。

## 決定

- **AI レビューは実装とは別の作業者（`board-reviewer`）に任せる。** レビューの作業者は指摘を計画の `## AI レビュー` 節に書くだけで、コードは直さない。
- **直すか見送るかはレビューの作業者が決める。** 直す指摘は `- [ ]` のチェックボックスで、見送る指摘はチェックボックスの無い `### 見送った指摘` の箇条で理由を添えて書く。
  直すのは、誤った振る舞い・セキュリティ・データの破損や消失・計画の決定やハードルールとの食い違い・振る舞いを足したのにテストが無いこと。
  名前や書き方の好み、振る舞いを変えない整理、PR の目的の外の改善は見送る。直し方に人の判断が要る指摘は `### 人に判断してほしいこと` に書く。
- 直す指摘は普通のタスクとして実装の側が倒す。**見送った指摘は PR の本文の `## 見送った AI レビューの指摘` 節に写す。**
- **AI レビューは 1 回だけ。** 指摘を直した後にもう一度レビューはしない。その先は人が動作確認と PR で見る。
- レビュー済みかどうかは計画の `## AI レビュー` 節の有無だけで決め、専用の状態は持たない。
- `next.action` に `review` を足さない。`implement` の手を受けた作業者がワークツリーの計画を読んで段（タスクを倒す / レビュー / 締め）を決め、1 手で 1 段だけ進める。
- タスクを倒す段では、作業者が取りまとめ役となり、タスクごとに新しいタスクの作業者（`board-task`）を入れ子で立てて最後まで倒す。
- 監視役は作業者の完了の通知を受けたら、次の cron の周を待たずに次の手を選んで渡す。
- `revise-impl` の AI レビューは今のまま作業者が自分でかけるが、直すのは同じ基準で「直す」に当たる指摘だけにし、見送りを PR の本文の同じ節に足す。

## 検討した代案

- **全部の指摘を直す（最初の計画）** — 計画は一度否決された。理由は「AIのレビューは重要なものだけ直し、見送ったのが何かを プルリクに記載するようにして欲しい」。これを受けて直す・見送るの区別と PR の本文への写しを足した。
- **実装の側に直すか見送るかを選ばせる** — 書いた者が自分の書いたものへの指摘を取捨することになり、レビューを分けた意味が薄れる。
- **見送る指摘もチェックボックスで書く** — 進捗バーと段の判定は `- [ ]` を全部数えるので、未チェックのまま残り締めの段へ進めなくなる。
- **見送りを PR のコメントに写す** — コメントは動作確認の否決や議論で流れていく。人は PR を開くと本文をまず読む。
- **`review` を監視役が渡す新しい手にする** — 監視役は「タスクを倒し終えたか」「レビュー済みか」を見分けられない。
- **`status` にブランチの計画を `git show` で読ませる** — サーバと `status` に git の読み取りを持ち込み、「ファイルがあれば列が立つ」今の読み方とも二重になる。
- **1 手でタスク・レビュー・直し・動作確認の提出までを続けて行う** — 手は短くならず、段ごとに文脈を新しくする利点も失う。
- **`revise-impl` の AI レビューもレビューの作業者に分ける** — 人の否決を受けた直しは小さいことが多く、1 手で頼み直す形が崩れる（Non-Goals）。
- **見送った指摘を別のカードとして起票する** — PR の本文に残すだけにし、拾うかは人が決める（Non-Goals）。

## 結果

- 書いた者が自分の書いたものを審査する形を避けられた。レビューの作業者がコードを直さないことは道具の制限では守れず、取りまとめ役がそのコミットが計画ファイルだけを変えていることを確かめる。
- タスクの境目の待ち時間が無くなった。1 手はタスクの数だけ長くなる。
- 人は PR の本文で、AI が何を見送ったかを読める。
- 入れ子のサブエージェントの完了を取りまとめ役が待てることは確かめたが、`ListAgents` での見え方と `TaskStop` の連鎖は確かめないまま入れた。
- 入れ子で `board-task` / `board-reviewer` を立てる形は、クラウドのセッションでサブエージェントが `Agent` を持てず止まったため、[0021](0021-flat-subagents.md) が置き換えた。
  監視役が `next.step` を見て直接立て、`status` がブランチの計画を `git show` で読んで段を決めるようになった。
- タスクごとに `board-task` を立てる形は、[0023](0023-three-loop-roles.md) が置き換えた。`board-task` は無くなり、`board-worker` が計画の節を 1 回でまとめて倒す。
- 実装する役とレビューする役を分けること、直す・見送るの基準、見送りを PR の本文に写すこと、レビューを 1 回だけにすることは変わっていない。
