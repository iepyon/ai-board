# 0004. 探索中と探索レビューの列を削る

- 状態: 採用
- 日付: 2026-09-11
- 置き換え元: なし
- 置き換え先: なし

## 状況

board-lanes でステージを 9 段にした（[0002](0002-derive-stage.md)）。そのうち `exploring`（探索中）と
`explore-review`（探索レビュー）は、本文に `## 探索メモ` の見出しがあれば探索レビューが立ち、
explore ゲートの承認で `planning` へ進む作りだった。

同じ日のうちに、この 2 列は実運用で列として機能していないと判断された。探索は計画提案と一体で進み、
explore ゲートの承認は `planning` へ進むためだけの通過儀礼になっていた。
人が見るべき判断点は計画レビューと PR の 2 つで足りた。

レビューログ（[0003](0003-review-log-in-body.md)）は書式の壊れた見出しを黙って無視する作りで、
カードには explore のレビュー記録がすでに残っていた。

## 決定

- **`exploring` と `explore-review` を削り、ステージを 7 段にする。**
  `idea` → `planning` → `plan-review` → `impling` → `verifying` → `pr` → `merged`。
- `startedAt` の打刻が立てるステージを `planning` にする。人が動かせる 1 遷移は アイデア ⇄ 計画提案中 になる。
- **explore ゲートを廃止し、レビューゲートを `plan` の 1 つにする。** `## 探索メモ` は導出の入力ではなくなり、
  本文の自由記述として残る。`skipGates` に `explore` は宣言できない。
- **既存カードに残る explore のレビュー記録は消さず、規定外のゲートとして黙って無視する。** データ移行は行わない。

## 検討した代案

- **`explore-review` だけを削り、`exploring` を残す** — `exploring` は「AI が探索している」列であり、
  探索の成果物を人が見ないなら `planning` と区別する意味が無い。2 つまとめて落とすほうが列の意味が濁らない。
- **既存カードから explore の記録を一括削除する** — レビューログは人の判断の履歴であり、列の定義が変わったことを理由に
  過去の記録を書き換えるのは追記専用の原則に反する。記録は残し、解釈だけをやめる。
- **ステージの列挙を `src/shared/` に寄せて 1 か所にする** — web 側の型は UI 固有の対応表と一体で書かれており、
  共有化は今回の削除より大きい。サーバと web の 2 か所を同時に直した。

## 結果

- `RULES` から 2 本を落とし、`planning` の条件を「explore 承認済み」から「`startedAt` が非 null」へ差し替えるだけで済んだ。
  差し戻しのための `if` は増えていない。
- 探索の成果物を人が見る機会が計画レビューの 1 回だけになった。探索が的外れなまま計画まで進むと手戻りが大きくなるので、
  重いカードは人が `startedAt` を打つ前に口頭で握る運用で受ける（計画の Risks）。
- `skipGates` は Zod で検証されるため、`explore` を含むカードは読み取りエラーになる。
  そのようなカードが 1 枚も無いことを確かめて、検証を緩めずに受け入れた。
- ロールバックは revert で足りる。explore の記録を消していないので、戻せば探索レビューの列も復元される。
- 後に `## 探索メモ` は、ループのサブエージェントに伝えたい補足を書く自由記述の場所として使われている（CLAUDE.md）。
