# 12. ループは auto モードで回す前提で、許可ルールは分類器に任せると困るものだけを同梱し、境界の本体にはしない

- 状態: 採用
- 日付: 2026-11-03

## 背景

ループ（当時は監視役とサブエージェント、今は本筋のセッション）は 1 手のあいだに git・npm・`ai-board` の CLI を何度も呼ぶが、`.claude/settings.json` には deny しか無かった。
確認の応答を待つ間ループは止まって見え、確認が多すぎると人は場当たりで何でも許しがちになる。
計画レビューでは、リベースしたブランチを push するために force push を許したいという否決があった。
最初は手順書の操作を `allow` に網羅したが、動作確認で「auto モードで進むなら allow は最小にしたい」という否決があった。
auto モードでは、許可ルールに当たらない操作を自動許可の分類器が判定し、手順書のふつうの操作はそのまま通す。

## 決定

- **ループは auto モードで回すことを前提にする。** 手順書のふつうの操作（品質ゲート、`ai-board` の CLI、`git` の commit / push など、ワークツリーの下の編集）は
  分類器に任せ、`allow` に重ねない。
- **`allow` には、手順書が使うのに分類器が既定で止める操作だけを置く。** 今は `main` 以外への `git push --force-with-lease origin <branch>` と、
  カードのワークツリーの中の `git -C <path>/.claude/worktrees/<id> checkout -- .` / `clean -fd` だけである。
- **`ask`（戻しにくく、人が 1 回だけ行う）と `deny`（境界を壊す）は、モードによらず効くので残す。**
  `deny` には `--force` / `-f` / `+` の refspec と `--mirror` の push、`main` への push を置き、
  `--force` の後ろを空白か行の終わりで区切って `--force-with-lease` に当たらないようにする。
- **許可ルールはうっかりの事故を止める保険で、境界の本体ではない。** 本体はカードの CLI の構造、`board-decide` と人の API を使わない決まり、GitHub のブランチ保護に置く。
- 形は `src/__tests__/claude-settings.test.ts` で、`*` を任意の文字列とみなす照合の近似で守る（`allow` の中身もそこで固定する）。

## 結果

- auto モードでは、手順書の操作は分類器を通って流れ、分類器が止める force push とワークツリーの取り消しは `allow` で通り、境界を壊す操作は `deny` で拒まれる。
- `allow` が小さいので、分類器が危ないと見る操作を許可ルールが黙って通すことがない。
- auto モード以外で回すと、`allow` に無い操作のたびに確認が出る。
- 手順書に操作を足して分類器がそれを止めるなら、その操作だけを `allow` に足す見直しが要る。
- 前方一致の照合なので `git -c x push --force` や `bash -c` で迂回できる。`main` の保護は人がブランチ保護で入れる必要がある。
- 手順書の push は `git -C "$WT" push origin <branch>` の明示の形に揃えた（上流が `origin/main` のまま `main` へ向かうのを避けるため）。

## 退けた案

- **手順書の操作を `allow` に網羅する** — どのモードでも確認が出なくなるが、分類器が止めるはずの操作まで許可ルールが黙って通す。
  手順書を変えるたびに `allow` の足し忘れが起き、`node -e` のような形を許すかで迷う（動作確認の否決）。
- **force push をすべて禁じる** — リベースした後の push が止まる（計画レビューの否決）。
- **戻しにくい操作も `deny` にする** — 人がチャットで頼んだ `git reset --hard` などの正当な操作まで止まる。
