# 0020. 動かす下限を Node の LTS（24）にする

- 状態: 採用
- 日付: 2026-11-01
- 置き換え元: なし
- 置き換え先: なし

## 状況

研修の受講者には、Node 26 を入れにくい人がいた（会社の PC で入れられる版が決まっている、など）。

`package.json` の `engines` は `>=26.0.0` で、CI も 26 だけで回していた。
カードを SQLite に移したとき（`b97280b`）の `engines` は `>=22.13` で、2026-10-31 の `8fc30eb` で CI を 22 / 24 / 26 のマトリクスにした。
同じ日の `c12a324` で、「個人用のローカルツールとして CI と engines を揃える」ために 26 以上へ絞り、マトリクスを外し、`@types/node` も 26 系に上げた。
絞った理由は技術的なものではなかった。

カードの保存（と移行前の DB の読み込み）に使う `node:sqlite` は 24 でも使える。
計画を書く前に、`main`（`7b37ad3`）のまま Node 24.22.1 で `npx vitest run` を走らせ、38 ファイル 835 件が通ることを確かめた。
`src/cli.ts` は、`node:sqlite` が 24 では実験的扱いで出す `ExperimentalWarning` を黙らせる処理を持っていた。

## 決定

**`engines.node` を `>=24.0.0` にし、CI を 24 と 26 のマトリクスで回す。**

- 下限は 24.0.0 にする。22 は戻さない。24 の中の細かい下限（`24.x.y`）は、`node:sqlite` の `DatabaseSync` が 24.0 で使えるので切らない
- CI は下限（24）と手元で使う版（26）の両方を通す。`test:coverage` と `build` も両方の行で走らせる
- **`@types/node` は下限の 24 系に合わせる。** 26 にだけある API を使えば `typecheck` で先に落ちるようにする。実行時に 26 で動くことは 26 の行の CI で確かめる
- `src/cli.ts` の `ExperimentalWarning` を黙らせる処理は残す。エージェントが CLI の出力を読むため
- README の「使い方」の先頭に、動かす前提（Node 24 以上、なるべく 24 系の最新）を書く

## 検討した代案

- **22 も戻す** — 依頼は「LTS（24）で動かしたい」である。2026-11 の時点で 22 は保守の終わりが近く、戻すと CI の行が増えるだけで得が無い
- **`@types/node` を上限の 26 系のままにする** — 26 にだけある API を使っても `typecheck` が通り、24 で動かしたときに初めて落ちる
- **CI の行ごとに `test:coverage` や `build` を省く** — 片方でしか落ちない壊れ方を見逃す
- **`.nvmrc` / `.node-version` / Volta などで版を固定する** — 研修の PC の事情に合わせ、版の選び方は使う人に任せる（Non-Goals）
- **`engine-strict` で `engines` を守らせる** — Non-Goals として入れなかった

## 結果

- Node 24 の環境で `npm install` しても `engines` の不一致の警告が出ない
- **型の検査は下限の版で行う**ことになった。上の版の API を使うには下限を上げる判断が要る
- CI はマトリクスの 2 行が並列に走るので待ち時間はほぼ変わらないが、使う分は倍になった
- 24.0 そのものは CI で確かめない。CI は 24 系の最新で走るので、古い 24 でだけ壊れる API を使っても気づけない。README に「なるべく 24 系の最新」と書いて補う
- `node:sqlite` は、カードをデータ用ブランチに移した後（[0019](0019-cards-on-data-branch.md)）は `ai-board migrate` で古い DB を読むためだけに使っている
