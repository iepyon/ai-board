# 0022. 判断は本文の文字列で往復させず、リポジトリの専用の口（appendReview）で値のまま追記する

- 状態: 採用
- 日付: 2026-11-02
- 置き換え元: なし
- 置き換え先: なし

## 状況

2026-10-30、`loop-respect-human` の作業者が動作確認を頼む理由に `##` の見出しを入れたところ、本文が `## レビュー` の節からはみ出した。
監視役が確認用の DB で試すと、理由に `### 2099-01-01T00:00:00.000Z plan 承認` の行を混ぜた `card submit` で、
その行が人の `plan 承認` として読まれ、カードが実装中に進んだ（`startedAt` も無いのに）。AI が CLI の `--reason` だけで承認・否決・中止を偽造できた。

カードをデータ用ブランチに移した後（[0019](0019-cards-on-data-branch.md)）も、書き方は同じ形だった。
usecase が組み立てた本文の末尾に `appendReviewEntry` で判断の見出しと理由の文字列を足し、
リポジトリ（`planCardWrite`）が前の本文と比べて、足された部分を Markdown として読み直して判断のファイルを作っていた。
`planCardWrite` の docstring にも「足した判断が本文の差し替えなのか判断の追記なのかは、ここでは区別できない」とあった。
理由（自由な文）と判断の見出し（構造）が同じ文字列に乗ることが、偽造の穴の根っこだった。

塞ぎ方は 2 段で進んだ。

1. `issue-store` の AI レビューで同じ穴が見つかり、`1108fec` で `card submit` / `card hold` の `--reason` に判断の見出しとして読める行があれば CLI が拒むようにした
2. `review-reason-escape`（PR #61）で、その検査を usecase に寄せ、人の API（400）と本文の差し替え（409）にも効かせた。
   無害化（字下げ・引用・`####` へ下げて書く）はファイルに残る文と入力した文が食い違うので採らず、拒むことにした。
   拒む行は `parseEntryHeading` が判断の見出しとして読む行だけにした（`## 手順` のような節は読むときに `demoteHeadings` が `####` へ下げるので守られる）

PR #61 の AI レビューでは、「リポジトリに判断の追記の口を分けるべき」「拒まず下げて書くべき」という指摘が出たが、作りの変更は目的の外として見送った。
`CLAUDE.md` は書き込み境界を構造で強制すると決めていた。

## 決定

**判断は値（`ReviewEntry`）のまま、`CardRepository.appendReview` で `log/` のファイルを 1 つ書く。本文の保存（`save`）は判断のファイルを決して作らない。**

- 理由はファイルの中身になるだけで、どこでも見出しとして読み直さない
- `planCardWrite` から、本文の形で判断の追記を推し量る道（`appendedEntries` など）を消す。判断を足した本文の `save` は `ReviewEntriesChanged` で拒む
- **理由の検査（判断の見出しとして読める行を拒む）を外す。** 理由に何が書かれていても判断は指定した 1 件しか増えない。「偽造できない」テストは「判断が 1 件だけ増える」を確かめる形で残す
- 本文の保存は、`## レビュー` の節が無ければ「判断は変えない」と読み、節があってエントリが今と違えば拒む
- API の応答は `body`（節を除いた本文）と `reviews`（判断の一覧）に分ける。詳細パネルは本文と「判断の記録」を分けて出し、判断の見出しは画面が値から描く
- 理由は Markdown として整形して描くが、見出しの行だけは見出しにせず、記号の付いた普通の行として出す
- `Card` の形（`body` は組み立てた本文）と、読む側（`stage-resolver` などの `parseReviewLog(card.body)`）と `card show` の出力は変えない

## 検討した代案

- **理由に見出しの行があれば拒む（`1108fec`・PR #61）** — 作りが文字列を経由したままで、入口ごとの検査に頼る。「理由に貼れない行がある」という制約が人に残る（前の判断の見出しを引用して貼ると 400）
- **無害化して書く** — PR #61 で、ファイルに残る文と入力した文が食い違うとして採らなかった
- **理由の検査を多層の守りとして残す** — 作りが将来また文字列を経由するように戻ったときの保険になる。「偽造できない」テストを残すことで代えた
- **書く口だけを分け、画面は組み立てた本文を 1 つの Markdown として描いたままにする** — 最初の計画で、動作確認の後に人が否決した。
  理由の見出しの行が `####` の太字の見出しとして出て、本物の判断の見出しと色が少し違うだけだった。人は「本文とログは分けた表示が良さそう」とした
- **理由を文字のまま出す** — 2 回目の否決で、人は Markdown として整形し、見出しの行だけは見出しにしないよう求めた
- **`parseBlocks` に見出しを読まない引数を足す** — 見出しの行は段落の続きを切るので、読み方を変えると本文の描き方に触れる危険がある。木を作った後に置き換える
- **`Card` に判断の配列を持たせ、読む側も文字列を経由しない** — 組み立てるテストや偽のリポジトリ（10 を超える所）と読む側のすべてに及ぶ。読む側は `demoteHeadings` で守られている（Non-Goals）
- **節を持つ本文で判断を変えたときに黙って無視する** — CLI で判断の節を書き換えたエージェントの編集が、何も言わずに消える

## 結果

- **判断を書けるのは `appendReview` の口だけになった。** 本文の差し替えから判断が増える道は作りの上で無い
- 人の API で見出しの形の行を含む理由は 400 から 200 に変わった
- 1 回の書き込みで本文と判断を同時に変える道は無くなった
- 応答の `reviews` の理由は組み立てた本文から読むので、`#`〜`###` の段の違いが `####` にそろって失われる。`card show` では `####` の見出しとして読める
- 画面の本文の編集は節の無い本文を送る。CLI で節ごと消して `card body` に送っても拒まれず、判断は `log/` に残る
- データ用ブランチのファイルの形と版は変えていない。移行の道（`legacyCardFiles`）は本文から判断を読む形のまま残る
