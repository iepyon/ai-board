# 0013. 動作確認の列（verify ゲート）を足し、PR を見る前に人が実装を動かして確かめる

- 状態: 採用
- 日付: 2026-10-30
- 置き換え元: なし
- 置き換え先: なし

## 状況

人がカードを確かめる場面は、計画レビューで計画を読むときと、PR中 でコードの差分を読むときの 2 つだった。
どちらも読む確認で、実装を動かす場面はボードの流れに無かった。
動かしたければ人が自分でブランチを手元で起動するしかなく、ボードはそれを「人の番」として示さなかった。
差分を読み終えてから動かし、意図と違う振る舞いに気づき、直った後にもう一度差分を読む、という二度手間が起きやすかった。

以前（2026-09-25、`cecbf0b`）、実装中 と PR中 の間には「検証中」（`verifying`）の列があった。
これは tasks を全部倒して MR がまだ無い状態、つまり AI が品質ゲートを回している最中を表す AI の列だった。
`cecbf0b` は AI レビューを実装中の内部工程として扱い、この列を廃止して 6 列にした。
今回足す列は、同じ位置に入るが人が動かして確かめる番の列で、意味が違う。

AI の次の一手は、実装中のカードに対して `implement` の 1 種類だけだった。

## 決定

- 実装中 と PR中 の間に「動作確認」の列を足す。ゲートに `verify` を、ステージに `verifying` を足す。人の列で、判断待ちの区画に出る。
- **導出の規則は 1 本だけ足す。** 「plan 承認済み かつ verify が提出済み → 動作確認」を PR中 と 実装中 の間に置く。
  否決・承認・飛ばす宣言のための規則は足さない。否決や承認でゲートが「提出済み」でなくなれば、1 つ下の 実装中 に自然に落ちる。
- AI は実装を終えたら PR を Draft のまま `verify` に提出する。本文には人が動かす手順と、AI 自身が動かした結果を書く。確かめられなかった部分はそう書く。
- 計画に `## 動作確認の手順` の節を足し、計画レビューの時点で後で何を動かすかを読めるようにする。
- 次の一手に、否決を直して頼み直すまでを 1 手にした `revise-impl` と、人の承認の後に Ready にする `ready` を足す。
  飛ばす宣言による承認と人の承認を見分けるため、次の一手の入力に `skipGates` を渡す。
- AI レビューは動作確認を頼む前に済ませる。`ready` の手ではコードに触らない。
- `latestReview` は 1 つのまま「その列が待っているゲートの最新の記録」とし、`gate` を足す。
- 動作確認を飛ばす入口は詳細パネルのチェックボックスにする。**CLI には足さない**（AI が自分で飛ばす宣言を書けないことを、入口が無いことで守る）。
- verify の承認 / 否決も人だけが書く。

## 検討した代案

- **列を足さず「Ready にする前に動作確認の承認が要る」という決まりだけを足す** — 動かして確かめる番が判断待ちの区画に出ず、ボードが人の番を示さないという元の問題が残る。
- **否決・承認・飛ばす宣言のための専用の規則を足す** — 計画レビューと同じしくみで足りる。専用の規則を足すと、計画と動作確認で差し戻しの扱いが食い違いやすい。
- **`revise-impl` を `implement` に混ぜる** — 「この否決への直しは済んだか」の印が要り、印が無ければ毎周同じ直しを繰り返しかねない。1 手で頼み直せばカードは動作確認へ上がる。
- **`latestReview` をゲートごとに持つ** — 画面の側で「このステージならどのゲートの記録を読むか」を毎回分け直すことになる。
- **飛ばす宣言の入口を CLI に足す** — CLI は AI も使う入口である。
- **ボードの画面からブランチのコードを起動する** — 書き込み境界と信頼の議論が別に要るので、別カードにした（Non-Goals）。

計画は一度否決された。理由は「計画の文書を初心者にもわかりやすく書き直して」で、文章を書き直して再提出した。設計の判断とタスクは変えていない。

## 結果

- 動作確認では振る舞いだけを、PR中 ではコードの質と設計を見るように役割が分かれた。
- 列は 7 つになった。動作確認を頼んでいない実装中のカードと Ready の PR を持つカードは列が変わらない。
- 承認の後に Ready にするのは AI の作業なので、承認されたカードはいったん 実装中 に戻る。動作確認 の列は「人が動かす番」だけを表す。
- すべてのカードで人を 1 回待つことになる。小さな変更はチェックボックスで飛ばして和らげる。
- 画面の見た目などは AI が動かした結果を書けないことがある。推測で「確認した」と書かせない。
- `verifying` という名前は廃止した「検証中」と同じだが、ステージは保存しないので古い値とはぶつからない。古い意味が残るのは archive の計画だけである。
- 作業者が否決を直しきれずに止まったとき、同じ `revise-impl` が毎周選ばれ続ける問題が AI レビューで見つかり、[0014](0014-ai-review-entries-and-hold.md) で扱った。
- 飛ばす宣言のあるゲートで提出をどう読むかは、後に [0018](0018-skip-gate-reads-submit-as-approval.md) で決め直した。
