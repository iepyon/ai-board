# board-timeline Specification

## Purpose

カードが各工程にいた時間を、残った痕跡から区間の並びとして導出する。
どの工程で、人と AI のどちらを待って時間を使ったかを後から見られるようにする。

## Requirements

### Requirement: 各工程にいた時間は区間の並びとして導出する

システムは カードが各工程にいた時間を、区間の並びとして示さなければならない (MUST)。
区間は種類・担当（人 / AI）・始まり・終わりを持ち、時刻の順に並ぶ。
区間の並びはステージと同じく保存しては SHALL NOT、残った痕跡から毎回導出しなければならない (MUST)。
導出は今の時刻を受け取っては SHALL NOT。同じ痕跡からは常に同じ並びを返す。

痕跡は、起票の時刻、着手の時刻、`## レビュー` のすべてのエントリ、PR を最後に Ready にした時刻・
最後に Draft へ戻した時刻・マージした時刻である。
Draft へ戻した時刻は、PR が今 open で Draft のときだけ痕跡に数える。
`## レビュー` は今効いている判断だけでなく、すべてのエントリを時刻の順に読まなければならない (MUST)。
差し戻しの前のエントリこそが区間の境目になるからである。

区間の種類と担当は次の 9 種類とする。

| 種類             | 区間             | 担当 | 始まり                                                 |
| ---------------- | ---------------- | ---- | ------------------------------------------------------ |
| `idea`           | アイデアの滞留   | 人   | 起票                                                   |
| `planning`       | 計画を書く       | AI   | 着手                                                   |
| `plan-review`    | 計画レビュー     | 人   | plan 提出 / 再提出                                     |
| `plan-rework`    | 計画の差し戻し   | AI   | plan 否決                                              |
| `plan-held`      | 計画の保留       | 人   | plan 保留                                              |
| `implementing`   | 実装             | AI   | plan 承認（plan を飛ばすカードは plan 提出 / 再提出）  |
| `readying`       | Ready にする     | AI   | （今は始まらない。廃止した verify の承認が始めていた） |
| `pr-review`      | PR レビュー      | 人   | PR を Ready にした                                     |
| `draft-returned` | Draft に戻された | 人   | PR を Draft に戻した                                   |

着手は飛ばす宣言によらず `planning` を始める。
飛ばす宣言のあるゲートの 提出 / 再提出 は、そのゲートの承認と同じ区間を始める（card-gate-skip と同じ読み替え）。
宣言は今の値で過去のエントリを読むので、宣言を後から出し入れすると、過去の区間の種類も変わる。

廃止した verify ゲートのエントリは痕跡に数えない。動作確認の列を通ったマージ済みのカードも、
`implementing` が PR を Ready にした時刻まで続き、そこから `pr-review` が始まる区間として読む。

区間の終わりは次の区間の始まりとする。マージと中止は今の区間を閉じるだけで、次の区間を始めない。
マージの後の痕跡は読まない。中止で閉じた後は、`## レビュー` のエントリが来るまで区間を開かず、
PR の痕跡（Ready にした・Draft へ戻した）でも開かない。そのため中止の後に再開したカードだけは、
中止から再開までのあいだが区間の隙間になる。

今いる区間は終わりを持たない。PR のマージで終わったカードと中止のカードは、終わりを持たない区間を持っては SHALL NOT。
計画の archive は痕跡に含めないので、PR のマージ時刻を引けずに archive だけでマージ済みになったカードは、
最後の区間が終わりを持たないまま残る。
長さ 0 の区間は落とし、同じ種類の区間が隣り合ったら 1 つにつながなければならない (MUST)。

PR を最後に Ready にした時刻は、PR のイベントの最後の Ready から取る。
作成時から Ready の PR はそのイベントを残さないので、Draft でない PR でイベントが無ければ PR の作成時刻とする。
今 Draft で一度も Ready にしていない PR は、Ready にした時刻を持たない。

#### Scenario: アイデアのまま

- **WHEN** 着手されていないカードを見る
- **THEN** 区間は起票から始まる `idea` の 1 つだけで、終わりを持たない

#### Scenario: 計画の否決と再提出

- **WHEN** plan が提出・否決・再提出・承認され、PR が Ready になってマージされた
- **THEN** 区間は `idea` → `planning` → `plan-review` → `plan-rework` → `plan-review` → `implementing` → … と並び、
  最後の `pr-review` はマージの時刻で閉じる

#### Scenario: 計画から立て直させた

- **WHEN** 承認済みの計画に plan の否決が記録され、計画が再提出されて承認し直された
- **THEN** `implementing` は否決の時刻で閉じて `plan-rework` が始まり、承認し直した時刻から再び `implementing` が始まる

#### Scenario: 実装を終えて Ready にした

- **WHEN** plan が承認され、AI が PR を Ready にした
- **THEN** `implementing` は Ready にした時刻で閉じ、そこから `pr-review` が始まる

#### Scenario: 廃止した verify のエントリが残っている

- **WHEN** plan の承認の後に verify の提出と承認が残り、その後 PR が Ready になってマージされた
- **THEN** `verifying` と `readying` は現れず、`implementing` が Ready にした時刻まで続く

#### Scenario: 計画レビューを飛ばした

- **WHEN** plan ゲートをスキップすると宣言したカードが着手され、plan の提出が記録された
- **THEN** 区間は `idea` → `planning` → `implementing` と並び、`plan-review` は現れない

#### Scenario: 着手のボタンを押さずに進めた

- **WHEN** 着手時刻が無い、または最初の `## レビュー` のエントリより後にあるカードを見る
- **THEN** 着手時刻は無いものとして扱われ、`idea` が最初のエントリまで続き、`planning` は現れない

#### Scenario: GitHub につながっていない

- **WHEN** PR の Ready・マージの時刻が引けないカードで、最後の記録が plan の承認である
- **THEN** 最後の `implementing` は終わりを持たないまま残る

#### Scenario: 中止の後に再開した

- **WHEN** plan の提出の後に中止され、しばらくして plan の再提出が記録された
- **THEN** `plan-review` は中止の時刻で閉じ、再提出の時刻から新しい `plan-review` が始まる。そのあいだに区間は無い

#### Scenario: マージの後にエントリがある

- **WHEN** PR がマージされた後に、`## レビュー` のエントリが書き足された
- **THEN** 区間はマージの時刻で終わり、そのエントリは区間を始めない

### Requirement: AI の区間はループの 1 手の記録で待ちと作業に分ける

システムは AI の区間を、ループの 1 手の記録（loop-activity）を使って「ループが拾うまでの待ち」と「作業者が動いていた時間」の小区間に分けて示さなければならない (MUST)。
「AI が遅い」のうち、ループの間隔や並列度で拾われるまで待っていたのか、作業そのものに時間がかかったのかを見分けるためである。

小区間は区間の並びの導出とは別に付け、区間の並びの導出そのものは 1 手の記録を読んでは SHALL NOT。
AI の区間では、そのカードの 1 手の記録を区間の範囲で切り取り、重なった部分を作業、区間の中のそれ以外を待ちとする。
重なる記録は 1 つの作業につながなければならない (MUST)。
人の区間には小区間を付けては SHALL NOT。
1 手の記録が 1 つも重ならない AI の区間には、小区間を付けては SHALL NOT（記録を始める前の区間や、ループを使わずに進めた区間を、すべて待ちと言い張らないため）。
今いる区間と終わっていない記録は終わりを持たないまま扱い、今の時刻を受け取っては SHALL NOT。

#### Scenario: 拾われるまで待ってから作業した

- **WHEN** 着手から 6 時間後にループが `plan` を渡し、1 時間で終わり、その 5 時間後に計画を提出した
- **THEN** `planning` の区間は 待ち（6 時間）→ 作業（1 時間）→ 待ち（5 時間）に分かれる

#### Scenario: 記録の無い区間

- **WHEN** 1 手の記録を書き始める前に実装を終えたカードを見る
- **THEN** その `implementing` の区間には小区間が付かない

#### Scenario: 作業中

- **WHEN** 今いる AI の区間で、ループの手がまだ終わっていない
- **THEN** 最後の小区間は作業で、終わりを持たない
