# card-review Specification

## Purpose

人がカードに下した判断（承認・否決・中止）と、AI が成果物を出した事実を、
カード本文の追記専用ログとして残す。否決の理由は AI が次の周回で読む唯一の入力になる。

## Requirements

### Requirement: レビューログの書式

システムは カード本文のレビュー見出し配下を追記専用のログとして解釈しなければならない (MUST)。

1 件のエントリは 1 つの見出し行で始まり、書式は `### <ISO 8601 の時刻> <ゲート> <種別>` とする。
見出しに続く本文はそのエントリの理由文として扱わなければならない (MUST)。

ゲートは `plan` の 1 つとする。
種別は 提出 / 再提出 / 承認 / 否決 / 中止 の 5 つとする。

#### Scenario: エントリを読み取る

- **WHEN** レビュー見出しの下に規定の書式の見出し行がある
- **THEN** 時刻・ゲート・種別・理由文を持つエントリとして読み取られる

#### Scenario: 次の見出しでセクションが終わる

- **WHEN** レビュー見出しの後ろに別の同レベル見出しが現れる
- **THEN** そこから先はレビューログとして読み取られない

#### Scenario: 書式の壊れた見出しは無視する

- **WHEN** 見出し行の時刻が日付として解釈できない、またはゲートや種別が規定外である
- **THEN** そのエントリは無視され、他のエントリの読み取りは続行される

#### Scenario: レビュー見出しが無い

- **WHEN** カード本文にレビュー見出しが無い
- **THEN** エントリは 0 件として扱われる

### Requirement: ゲートの通過判定

システムは 各ゲートの状態を、そのゲートに属するエントリのうち最も時刻の新しいものから
決めなければならない (MUST)。

- エントリが無い場合は未提出とする
- 最新が 提出 または 再提出 なら人の判断待ちとする
- 最新が 承認 なら通過済みとする
- 最新が 否決 なら差し戻し中とする

別のゲートのエントリを判定に混ぜては SHALL NOT。

中止のエントリを判定に含めては SHALL NOT。中止は工程の進捗とは直交する終端の軸であり、
通過済みのゲートを未通過へ巻き戻しては SHALL NOT。

#### Scenario: 否決のあとに再提出された

- **WHEN** plan ゲートの記録が 提出 → 否決 → 再提出 の順に並んでいる
- **THEN** plan ゲートは人の判断待ちになる

#### Scenario: 他のゲートは影響しない

- **WHEN** 廃止された `explore` など規定外のゲート名のエントリだけが並んでいる
- **THEN** plan ゲートは未提出のままである

#### Scenario: 中止はゲートの通過を巻き戻さない

- **WHEN** plan ゲートの記録が 承認 → 中止 の順に並んでいる
- **THEN** plan ゲートは通過済みのままである

### Requirement: plan ゲートの事前スキップ

システムは カードに事前に宣言されたゲートを、レビューログを見ずに通過済みとして
扱わなければならない (MUST)。宣言できるのは人だけとする (MUST)。

宣言できるのは規定のゲートだけとする。規定外のゲート名の宣言は受け付けては SHALL NOT。

#### Scenario: 計画レビューを飛ばす

- **WHEN** カードが plan ゲートをスキップすると宣言している
- **THEN** 計画ファイルの有無やレビュー記録によらず plan ゲートは通過済みになる

#### Scenario: スキップしたカードは待ちの列に滞留しない

- **WHEN** 着手済みのカードが plan ゲートをスキップすると宣言し、計画ファイルが存在する
- **THEN** そのカードは `plan-review` に留まらない

#### Scenario: 廃止されたゲートは宣言できない

- **WHEN** カードのスキップ宣言に `explore` が含まれている
- **THEN** そのカードの読み取りは規定外の値として拒否される

### Requirement: 書ける主体の分離

システムは 提出 と 再提出 のエントリを AI エージェントが書くことを許さなければならない (MUST)。
承認 / 否決 / 中止 は人だけが書けるものとし、AI エージェントがこれらを書くことを
許して SHALL NOT。

#### Scenario: AI が成果物の提出を記録する

- **WHEN** AI エージェントが計画ファイルを書き終えて提出を記録する
- **THEN** そのエントリは受け付けられ、カードは人の判断待ちの列へ進む

### Requirement: 計画の判断を追記する API

システムは カードを指定してレビューエントリを追記する手段を提供しなければならない (MUST)。
入力はゲート・種別・理由文とし、時刻はサーバが付けなければならない (MUST)。

規定外のゲートを指定した追記は 400 で拒否しなければならない (MUST)。

否決には空でない理由文を要求しなければならない (MUST)。
理由が無い否決は 400 で拒否しなければならない (MUST)。

存在しないカードへの追記は 404 で拒否しなければならない (MUST)。

追記の結果ステージが変わる場合、次にボードを取得したときに新しい列が返らなければならない (MUST)。

#### Scenario: 計画を承認する

- **WHEN** 計画ファイルのあるカードに plan の承認を追記する
- **THEN** 追記が成功し、そのカードのステージは `impling` になる

#### Scenario: 理由なしで否決する

- **WHEN** 理由文を付けずに否決を追記する
- **THEN** 400 が返り、カード本文は変更されない

#### Scenario: 理由付きで否決する

- **WHEN** 理由文を付けて plan の否決を追記する
- **THEN** ステージは `planning` に戻り、理由文がカード本文に残る

#### Scenario: 廃止されたゲートを指定する

- **WHEN** `explore` を指定して追記する
- **THEN** 400 が返り、カード本文は変更されない

#### Scenario: 存在しないカード

- **WHEN** 存在しない ID のカードへ追記する
- **THEN** 404 が返る

### Requirement: 中止

システムは 全エントリを通じて最新のものが 中止 であるカードを、終端に達したものとして
示さなければならない (MUST)。

中止は専用のステージとして扱っては SHALL NOT。マージ済みとは意味が異なるため、
同じ列に混ぜて SHALL NOT。

中止されたカードは既定でボードに表示しないが、明示的な操作で表示できなければならない (MUST)。

#### Scenario: カードを中止する

- **WHEN** カードに中止を追記する
- **THEN** そのカードは中止として示され、既定のボード表示から外れる

#### Scenario: 中止してもステージは動かない

- **WHEN** 計画提案中のカードに中止を追記する
- **THEN** ステージは計画提案中のままで、中止として示される

#### Scenario: 中止のあとに再開する

- **WHEN** 中止のあとに再提出のエントリが追記される
- **THEN** そのカードは中止ではなくなる
