# ai-board

プランニングファイル駆動の開発のためのボード。`ai-board` の CLI とチャット（Claude Code のスキル）で扱う。

`.ai-board/plans/` とレビュー要求（GitHub の Pull Request）を読んで各カードのステージを自動導出する。
`stage` という値はどこにも保存しない。人の判断（着手・承認・否決・中止）も
カード上の痕跡として残り、それも導出の入力になる。

```
[ アイデア ] [ 計画提案中 ] [ 計画レビュー ] [ 実装中 ] [ PR中 ] [ マージ済み ]
     人            AI            人 ★          AI        人 ★        —
```

★ が人の判断を待つゲート。計画レビューでは計画を読む。PR中 では、AI が PR の本文に書いた動作確認の結果（動かした手順と結果）を読み、
必要ならブランチを動かして振る舞いを確かめ、それからコードの差分を読む。
PR に指摘（コメント）を書くと、AI が Ready のまま修正を push するか、直すものが無い理由を返信して、また人の番に戻る。
人が動かすのは `アイデア ⇄ 計画提案中` の 1 遷移だけ（着手）で、あとは AI が右へ進め、★ で止まる。

画面・サーバ・ダッシュボードはいったん外した（[ADR 0017](docs/adr/0017-remove-web-and-server.md)）。
実装の細部は [`docs/architecture.md`](docs/architecture.md)、設計判断の理由は [`docs/adr/`](docs/adr/) にある。

## なぜ必要か

AI エージェントと開発を回すとき、作業の実態は複数の場所に散らばる。

| 情報               | 所在                                        |
| ------------------ | ------------------------------------------- |
| アイデア・調査メモ | `origin` の `ai-board/data` ブランチ（git） |
| 計画とタスクの進捗 | `.ai-board/plans/<id>.md`                   |
| PR のレビュー      | GitHub                                      |
| 完了               | `.ai-board/plans/archive/`                  |

どれも見ようと思えば見られるが、アイデアから完了までを一本のパイプラインとして俯瞰する手段がない。
ai-board はその欠けたビューを埋め、**「いま誰の番か」を可視化する。**

## 使い方

動かすには Node 24 以上が要る（なるべく 24 系の最新を使う）。

```bash
npm install
npm run build

# .ai-board/ を持つプロジェクトのルートで読む
node dist/cli.js status --root /path/to/your-project
```

```
使い方: ai-board <command> [--root <path>]

Commands:
  card <command>      カードの読み書き
  status [--json [--only <項目,...>]]
                      ボードの状態と次の一手
  init                空のデータ用ブランチを作る
  pr <command>        PR の読み書き（gh api の REST）
  decide <command>    人の判断を書く（人と、人が会話で頼んだ Claude だけ）
  loop <start|finish> ループの 1 手の記録を書く（ループだけが使う）
  dist-check          dist/ が HEAD のコミットより古いかを確かめる
```

引数なしの `ai-board` は使い方を出して終わる。常駐するサーバは無い。

## ボードの見方

ボードは `ai-board status` で読む。人向けの数行（`status`）と、ループや手順書が読む JSON（`status --json`）の 2 つの形がある。
どちらも同じ導出の結果を、次の区画に振り分けて出す。区画はステージの見せ方の振り分けで、導出の規則には関わらない。

| 区画                   | 入るカード                                                                       | 並び                   |
| ---------------------- | -------------------------------------------------------------------------------- | ---------------------- |
| 判断待ち（`waiting`）  | 計画レビュー / PR中、止まっている 計画提案中 / 実装中                            | 待ち始めた時刻の古い順 |
| AI 作業中（`working`） | 計画提案中 / 実装中（止まっているものを除く）と、人の指摘に AI が応える番の PR中 | PR中 を先頭に、`rank`  |
| アイデア（`ideas`）    | アイデア（区切り線で上下に分ける）                                               | `rank`                 |
| マージ済み             | マージ済み                                                                       | マージの新しい順       |
| 中止                   | 最新のレビューエントリが中止のカード                                             | `rank`                 |

判断待ちのカードには、止まった理由（人が何をすればよいか）と、出せる判断（`decisions`）が付く。
AI 作業中のカードは、計画ファイルが 3 日更新されないと「動きなし」（`stale`）になる。
ループの様子は「ループ: <カード> を <手> 中（12 分）」「ループ: 最後の手から 40 分」「ループ: 記録なし」の 1 行で出る。

出せる判断はカードによって変わる。

| カード                                       | 出せる判断                     |
| -------------------------------------------- | ------------------------------ |
| アイデア                                     | 中止                           |
| 計画レビュー                                 | 承認 / 否決して差し戻す / 中止 |
| 実装中で止まっている（Draft へ戻された）     | 計画から立て直させる / 中止    |
| 計画提案中で止まっている（plan 保留）        | 計画を直させる / 中止          |
| 計画提案中で止まっている（成果物が見えない） | 中止                           |
| PR の状態を引けない                          | 出さない                       |

「否決して差し戻す」「計画から立て直させる」「計画を直させる」はどれも plan の否決として `## レビュー` に追記され、理由が必須。
PR中 のカードは GitHub で PR をマージして判断するので、判断は出さない。

## ステージの決まり方

以下を**上から評価し、最初に真になったもの**を採用する（＝最も進んだステージ）。手動上書きの仕組みは無い。

| #   | stage         | 条件                                                                 |
| --- | ------------- | -------------------------------------------------------------------- |
| 1   | `merged`      | 計画が `.ai-board/plans/archive/` にある、**または** PR が merged    |
| 2   | `pr`          | PR が存在し opened、かつ Draft でない                                |
| 3   | `impling`     | plan ゲート通過済み                                                  |
| 4   | `plan-review` | `.ai-board/plans/<id>.md` か Draft の PR があり、plan ゲートが未判断 |
| 5   | `planning`    | `startedAt` が非 null                                                |
| 6   | `idea`        | 既定                                                                 |

計画と実装は同じ 1 本の PR に載る。AI は計画をコミットした時点で Draft の PR を出し、
人はその PR で計画を読んで、チャットで頼むか `ai-board decide` で承認 / 否決する。
実装と AI レビューを終えた AI は、PR の CI が通るのを確かめ（赤なら直す）、動かした手順と結果を PR の本文の `## 動作確認の結果` に表で書き、計画を archive して PR を Ready にする（`pr` へ）。
人は PR中 で、その証拠を読み、必要ならブランチを動かし、差分を読んでマージする。

実装中の PR も Draft だが、計画レビューへは巻き戻らない。plan が承認済みのカードは 3 で決まるため。
**否決の差し戻しに専用のルールは無い。** ゲートが「差し戻し中」のとき、その工程のレビュー行と承認行が両方外れ、1 つ手前の列へ自然に落ちる。

### レビューログ

人の判断はカード本文の `## レビュー` に追記される。ゲートは計画を読む `plan` の 1 つ。
種別は 提出 / 再提出 / 保留（AI が書く）と 承認 / 否決 / 中止（人が書く）の 6 つ。

```markdown
## レビュー

### 2026-09-11T04:00:00.000Z plan 提出

### 2026-09-11T05:12:00.000Z plan 否決

既存の stage-resolver を見ていない。導出ルールとの整合を調べ直して。

### 2026-09-11T09:30:00.000Z plan 再提出

### 2026-09-11T10:00:00.000Z plan 承認
```

ゲートの状態は、そのゲートの最新エントリ 1 件で決まる。書式の壊れた見出しは黙って無視する。
中止のエントリはゲートの判定から除く（中止は工程の進捗とは直交する終端の軸で、通過済みのゲートを巻き戻さない）。
最新が 保留 のゲートは先へ進まないので、保留のカードは AI の列に留まり、人が後から承認 / 否決 / 中止を書けば外れる。
`pr` ゲートはレビューログを持たない。PR の承認とマージは GitHub 側の実態そのものであるため。

### 止まり

AI の列（計画提案中 / 実装中）にいても、人の判断を待っているカードがある。これを**止まり**と呼ぶ。
止まりはステージとは別の軸の派生値で、どこにも保存しない。止まっているカードは判断待ちの区画に出て、AI ループはそのカードを選ばずに後ろのカードへ進む。

| 止まり                                                  | 列         | 人がすること                                         |
| ------------------------------------------------------- | ---------- | ---------------------------------------------------- |
| 人の判断の後に、PR が Draft に戻された                  | 実装中     | GitHub で Ready に戻す / 計画から立て直させる / 中止 |
| AI が `plan 保留` を書いた                              | 計画提案中 | 計画を直させる / 中止                                |
| 計画を提出したのに計画ファイルも Draft の PR も見えない | 計画提案中 | 中止                                                 |
| そのカードの PR の状態だけを GitHub から引けない        | どの列でも | 時間を置く。続くなら GitHub で PR を確かめる         |

人が承認 / 否決 / 中止を書けばそのエントリが最新になり、止まりは外れる（PR の状態を引けない止まりは、次に引ければひとりでに外れる）。
止まりを解く専用の操作は無い。立つ条件の細部は [`docs/architecture.md`](docs/architecture.md) の「止まり（hold）」にある。

PR中 で小さな指摘を AI に直させたいときは、PR にコメントを書けばよい。
カードは AI 作業中の区画の先頭に移り、ループが `fix-pr` の手で、Ready のまま修正を push するか、直すものが無い理由を 1 件返信して、判断待ちに戻す
（[ADR 0016](docs/adr/0016-pr-feedback-ai-turn.md)）。計画から作り直させたいときは、PR を Draft に戻して「計画から立て直させる」を頼む。

### スキップ

frontmatter の `skipGates` に書いたゲートでは、AI の 提出 / 再提出 を人の承認と同じに読む。
小さいカードを夜間に `/loop` で流したいときに使う。否決 / 保留 / 承認 はふつうに効き、人は後から否決して差し戻すこともできる。

宣言は人が書くもので、チャットで頼むか `ai-board decide skip <id> --gate plan [--remove]` で出し入れする（`ai-board card` には入口が無い）。
宣言を入れても着手するまではアイデアに留まり、着手後に AI が `plan 提出` を書いた時点で計画レビューを通らずに実装中へ進む。

### 誰が動かせるか

| 列                    | ステージを立てるもの                                                   | 誰の領分か                     |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------ |
| アイデア / 計画提案中 | `startedAt` の打刻                                                     | 人                             |
| 計画レビュー          | 計画ファイル / Draft の PR                                             | AI                             |
| 実装中                | `## レビュー` の plan 承認（plan を飛ばすカードは plan 提出 / 再提出） | 人（plan を飛ばすカードは AI） |
| PR中                  | PR が Ready で opened                                                  | AI                             |
| マージ済み            | 計画の archive / PR の merged                                          | AI                             |

**人が動かせるのは `アイデア ⇄ 計画提案中` の 1 遷移だけ。**
`ai-board decide start`（着手）と `ai-board decide unstart`（着手を戻す）がこれにあたり、`startedAt` を書き換える。
AI の成果物か人のレビュー記録があるカード（計画レビュー以降）は、着手を戻せない。

## カード

カードの正本は `origin` の `ai-board/data` ブランチ（データ用ブランチ）にあり、`cards/<id>/` の 1 ディレクトリが 1 カード。
データ用ブランチはコードの履歴と交わらない orphan のブランチで、clone した時点でカードが揃う。
手元では、CLI がメインのチェックアウトの `.ai-board/data/` にデータのワークツリーとして展開し、書き込みのたびにコミットと push をする。
`id` は不変で、`branch` / `mr` が進行に応じて後から埋まる。

`ai-board card show <id>` は、カードを次の Markdown の形で出す。

```markdown
---
id: refresh-token # 不変。生成後は変えない
title: リフレッシュトークン対応
created: 2026-09-01T09:00:00.000Z
startedAt: '2026-09-01T10:00:00.000Z' # 人が着手を指示した時刻
skipGates: [] # 人が事前に見ないと宣言したゲート（plan）
branch: feat/refresh-token
mr: 42 # GitHub の PR 番号（branch から自動解決して書き戻す）
rank: 1500 # 並び順。小さいほど上。並べ替えたときだけ書かれる
---

## アイデア

## レビュー
```

### カードを書く経路

人は `ai-board decide`（チャットからは `board-decide`）で、エージェントは `ai-board card` の CLI から書く。
書き込みは「取り直す → 検査する → コミットする → push する」を 1 つの操作として行い、push が拒否されたら取り直して頭からやり直す。
データのワークツリーのファイルを直接書き換えたり、データ用ブランチへ直接 push したりはしない（`.claude/settings.json` の deny ルールでも止めている）。

```bash
ai-board card list                         # 一覧（JSON、本文なし、rank 順）
ai-board card show <id>                    # 1 枚を Markdown で
ai-board card create --title <t> [--id <id>] < body.md
ai-board card seed --from <dir>            # <dir> の *.md のうち、まだ無いカードだけを起票（既にある ID は飛ばす）
ai-board card body <id> < body.md          # 本文の差し替え
ai-board card branch <id> <name>           # ブランチの紐付け（--clear で外す）
ai-board card submit <id> [--gate plan] [--resubmit] [--reason <text>]   # 提出 / 再提出（ゲートは plan だけ）
ai-board card hold <id> --gate plan --reason <text>   # 保留（否決された計画を直しきれずに止まるとき。理由は必須）
```

`ai-board card` にはエージェントに許す操作しか無い。`startedAt`・`rank`・`skipGates` の書き換えと、
承認 / 否決 / 中止の追記は、`ai-board decide` からだけ行える。逆に、`ai-board decide` からは AI の種別（提出 / 再提出 / 保留）を書けない。
`hold` は最新の判断が否決のときだけ、`submit` は着手したカードで plan が未提出か否決のときだけ書ける。
`body` は `## レビュー` のエントリが変わる差し替えを拒否する。

### チャットから判断する

`board-decide` のスキル（`.claude/skills/board-decide/SKILL.md`）は、人がチャットで頼んだ判断を、Claude が `ai-board decide` の CLI で代わりに書く。
「chat-decide の計画を承認して」「否決して、理由は〜」「loop-activity を一番上へ」のように頼むか、`/board-decide` で呼ぶ。

```bash
ai-board decide approve <id> [--reason <text>]     # plan を承認する
ai-board decide reject <id> --reason <text>        # plan を否決する（理由は必須）
ai-board decide abort <id> [--reason <text>]       # 中止する
ai-board decide start <id> / unstart <id>          # 着手する / 着手を戻す
ai-board decide skip <id> --gate plan [--remove]   # 計画レビューを飛ばす宣言を入れる / 外す
ai-board decide move <id> --after <ref> --before <ref>   # アイデアの並べ替え（<ref> はカード ID・:divider・none）
ai-board decide move-divider --after <ref> --before <ref>   # 区切り線を動かす
```

書く前にボードを導出し、出せない判断は拒む。GitHub に繋がらないときは、承認 / 否決 / 中止と着手 / 着手を戻すを拒む（宣言・並べ替えは書く）。
誰が呼んでも書けるので、人の判断の守りは「人がこの会話で自分の言葉で頼んだときだけ使う」という手順書の決まりにある（[ADR 0007](docs/adr/0007-board-decide.md)）。

- 中止 / 着手を戻す は、送る中身を見せて 1 回確かめてから書く。承認 / 否決は、対象が 1 つに決まれば確かめずに書く
- 対象を言わずに頼むと（「判断待ちを見せて」）、判断待ちのカードと出せる判断を並べて選ばせる
- 書いた判断で AI の番ができたら、頼み直さなくても同じセッションで `board-loop` の 1 周が続く（[ADR 0013](docs/adr/0013-continue-loop-after-decide.md)）。
  否決は「続けて直す / 待つ」を 1 回聞く。「書くだけ」と言えば続けない

### 並び順

アイデアの表の行は `ai-board decide move` で並べ替えられ（チャットからは「<カード> を一番上へ」）、上にあるものほど優先度が高い。
並べ替えると、動かしたカードの `rank` だけが書き換わる。`rank` の無いカードは作成順に並び、新しいカードは末尾に付く。

アイデアの表には区切り線が 1 本あり、線より上が「次にやる」、下が「あとで考える」。
区切り線は `ai-board decide move-divider` で動かせる。新しく起票したアイデアは末尾に付くので「あとで考える」に入る。
並び順も区切り線も人が決める優先度なので、`ai-board card` から書く入口は無い。

## 計画ファイル

`.ai-board/plans/<card-id>.md` の 1 ファイルがそのカードの計画。
**ファイル名がカード ID と一致することで紐付く**ので、カードの frontmatter に紐付け用のフィールドは無い。

```markdown
# リフレッシュトークン対応

## 方針

...

## 動作確認の手順

1. `npm run build` の後、トークンの期限を切らした状態で API を呼ぶ
2. 応答が 200 になり、保存したトークンが入れ替わっていることを見る

## タスク

- [x] トークンの保存先を決める
- [ ] 更新エンドポイントを足す
```

チェックボックスはカードのタスクの進み（`plan.tasks`）になる。**タスクの進捗はステージを立てない。**
フェンスで囲んだコードブロックの中のチェックボックスは数えないので、計画に書き方の例として載せてよい。

`## 動作確認の手順` には、動かして確かめるときのコマンドと、期待する結果を書く。
実装と AI レビューを終えた AI は、これをもとに動かせるところを動かし、
「確かめたこと / コマンド / 結果（`通った` / `落ちた` / `走らせていない`）」の表を PR の本文の `## 動作確認の結果` に書く。
Ready にする前に `ai-board pr checks <n> --wait` で CI を確かめ、赤なら直して push する（2 回まで）。直せなければ Ready にせず止まる。
PR を Ready にする直前に、同じ PR の中で計画を `.ai-board/plans/archive/<card-id>.md` へ移す。マージと同時に archive も main に入り、これがマージ済みの実態になる。

計画を書くのは AI エージェントで、**`ai-board` の CLI は計画を read-only** に扱う。
**計画ファイルが存在するだけで計画レビューの列が立つ。** 本来のゲートは `plan 提出` だが、ファイルの存在は人待ちを取りこぼさないための保険である。

## AI ループ

`board-loop` のスキル（`.claude/skills/board-loop/SKILL.md`）は、ボードを読んで AI が進めてよいカードの次の 1 手を、動かしたセッションが自分で進める。
手ごとの手順は隣の `plan.md` / `implement.md` / `fix-pr.md`、共通の決まりは `rules.md` にある。`/loop 5m /board-loop` で間隔運転する。

- 何をするかは `ai-board status --json` の `next` が決める。優先順は PR中（人の指摘に AI が応える番のものだけ）→ 実装中 → 計画提案中、同じ列の中は `rank` の順
- 1 手は次の 4 種類のどれか

  | 手            | 選ばれるとき                   | すること                                                                                                          |
  | ------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
  | `plan`        | 計画提案中で、計画がまだ無い   | 計画を書いて Draft の PR を出し、`plan 提出` を書く                                                               |
  | `revise-plan` | 計画提案中で、計画が否決された | 否決の理由を読んで計画を直し、`plan 再提出` を書く。直しきれなければ `plan 保留` を書いて止まる                   |
  | `implement`   | 実装中で、止まっていない       | 計画の状態から決まる段（下の表）を進める                                                                          |
  | `fix-pr`      | PR中 で、人の指摘に応える番    | PR を Ready のまま修正を push する（CI も確かめる）か、直すものが無い理由を `ai-board pr comment` で 1 件返信する |

- `implement` の手では、`status` がカードのブランチの計画を読んで段を決め、`next.step` に載せる

  | 計画の状態                                | `next.step` | 進める者         | すること                                                                                               |
  | ----------------------------------------- | ----------- | ---------------- | ------------------------------------------------------------------------------------------------------ |
  | `plans/archive/` にある                   | `close`     | 本筋のセッション | 前の周で `ai-board pr ready` だけが失敗している。それだけをやり直す                                    |
  | 未チェックのタスクがある                  | `task`      | 本筋のセッション | 残りの節を上から順に倒し、節ごとに 1 つのコミットにする                                                |
  | 全部倒れていて、`## AI レビュー` 節が無い | `review`    | `board-reviewer` | 計画の末尾に `## AI レビュー` 節を書き足す。コードは直さない                                           |
  | 全部倒れていて、`## AI レビュー` 節がある | `close`     | 本筋のセッション | 動かして確かめ、PR の本文に `## 動作確認の結果` などを書き、計画を archive して Ready                  |
  | 読めなかった（ブランチが無い など）       | `null`      | 本筋のセッション | ワークツリーに入って計画を読み、タスクを倒す段か締めの段なら進める。レビューの段なら何も変えずに止まる |

- 止まっているカードは選ばない。計画レビューのカードには触らない。PR中 のカードには `fix-pr` の手でだけ触る。
  着手・承認・否決・中止・並び順・マージは人に任せる
- GitHub に接続できないとき（`github:` が無いときも含む）は何もせずに止まる。PR の状態が引けないと、人を待つカードが AI の列に落ちて見えるため
- 手を終えたら、次の cron の周を待たずに同じ手番で次の手へ進む。`止まった` か `next` が null になるまで続く
- 同じ手で 2 回以上止まり続けているカードには、次の一手に `止まった ×N` の印が付く（数えて見せるだけで、止めはしない）

ループを回すセッション（本筋のセッション）が、計画・実装・締めの手を自分で進める。
別の文脈に切り分けるのは AI レビューだけで、`next.step` が `review` のときに `.claude/agents/board-reviewer.md` のサブエージェントを 1 つ前景で立てる。
実装を書いたセッションが、自分の差分を審査しないためである（[ADR 0011](docs/adr/0011-loop-single-session.md)）。

### ループの 1 手の記録

ループは、手を始める前に `ai-board loop start` で開始を、手を終えたら `ai-board loop finish` で終了・結果を書く。
記録はデータ用ブランチの `loop/` に 1 件 1 ファイルで置かれ、時間・トークン・手順書の版（`.claude/HARNESS_VERSIONS.md` の先頭の版）を持つ。
ボードはこれを読んで、`status` の「ループ: …」の行とカードの `loopSteps` を出す。記録はステージの導出にも次の一手にも使わない。
細部は [`docs/architecture.md`](docs/architecture.md) の「ループの 1 手の記録」と [ADR 0014](docs/adr/0014-loop-step-record.md) にある。

```bash
ai-board loop start  --loop <id> --card <cardId> --action <手> [--step <task|review|close>] [--agent <name>]
ai-board loop finish --loop <id> --card <cardId> --result <advanced|held|stopped|failed|unknown> [--tokens <n>] [--duration-ms <n>]
```

### ループの許可ルール

**ループは auto モードで回すことを前提にしている。** auto モードでは、許可ルールに当たらない操作を自動許可の分類器が判定し、
読み取り・品質ゲート・`ai-board` の CLI・ふつうの commit や push はそのまま通す。
そこで `.claude/settings.json` の `permissions` には、分類器に任せると困るものだけを書いて同梱している。理由と退けた案は [ADR 0012](docs/adr/0012-loop-permissions.md) にある。

| 段      | 入れるもの                                            | 当たったとき         |
| ------- | ----------------------------------------------------- | -------------------- |
| `allow` | 手順書が使うのに、分類器が既定で止める操作            | 確認なしで走る       |
| `ask`   | 手順書が使わないか、人が 1 回だけ行う、戻しにくい操作 | 毎回人に確かめる     |
| `deny`  | ハーネスの境界を壊す。人もループ中には使わない        | 確認を経ずに拒まれる |

- **`allow`:** `main` 以外への `git push --force-with-lease origin <branch>`、カードのワークツリーの中の取り消し（`checkout -- .` / `clean -fd`）
- **`ask`:** `git reset --hard`、`git branch -D` / `-d`、`git worktree remove`、`ai-board init`
- **`deny`:** データのワークツリーの編集とデータ用ブランチへの push、`main` への push、`--force` / `-f` / `+` の refspec での force push、`--mirror` の push、
  DB の直接操作（`sqlite3`）、メインのチェックアウトの `.claude/settings*.json` の編集
- **どこにも書かないもの:** 品質ゲート、`ai-board` の CLI、手順書が使うふつうの `git` の操作。分類器がそのまま通すので重ねない

許可ルールは**うっかりの事故を止める保険で、境界そのものではない。** 前方一致の文字列の照合なので迂回できる。
境界の本体は、カードの書き込みは `ai-board card` の CLI の構造、人の判断は手順書の決まりに置く。
`main` には、リポジトリの Settings → Branches でブランチ保護（直接の push と force push の禁止）を入れることを勧める。

### クラウドのセッションで回す

Claude Code のアプリから立ち上げたクラウドのセッションでもボードを回せる。カードはデータ用ブランチにあるので、clone した時点で手元と同じカードが見える。

1. セッションを立ち上げたら、まず `npm ci && npm run build` で `dist/` を作る（clone には `dist/` が無い）
2. 会話で `/loop 5m /board-loop` を回す。これが主な回し方である
3. ボードを読むときは、会話で「ボードを見せて」と頼むか、`ai-board status` を走らせる
4. 判断は会話で頼む（「〜の計画を承認して」など）。判断で AI の番ができたら、頼み直さなくてもそのまま次の 1 手が渡る

クラウドでは GitHub の GraphQL が 403 になり、`gh pr` と `gh auth status` が動かない。
そのため手順書は PR の読み書きに `ai-board pr ...`（`gh api` の REST）を使う。

人が会話を開いていない間も動かしたいときは、ルーティン（cron で動くクラウドのエージェント）で `/board-loop` を定期に走らせてもよい。
ルーティンが重なって同じ手が 2 つ同時に走っても、カードの書き込みは push の拒否で 1 つにまとまる。

クラウドのセッションからはブランチを消せない。リポジトリの Settings → General の「Automatically delete head branches」を有効にしておく
（データ用ブランチは PR の head にならないので消えない）。

### Windows で使う

Windows では、Windows の Claude Code が使う Git Bash（Git for Windows に同梱）で、手順書を書き換えずに回せる。PowerShell や cmd は想定しない。

- `jq` は要らない。手順書は `ai-board status --json --only <項目,...>` で要る項目だけを出す
- 改行コードは `.gitattributes`（`* text=auto eol=lf`）で LF に揃える。`.gitattributes` が入る前に clone した作業ツリーは、
  未コミットの変更が無いことを確かめてから `git rm --cached -r . && git reset --hard` で取り出し直す
- テストは Windows を対象にしていない（POSIX 形式のパスや `chmod` を使うテストがある）

### ワークツリーではデータのワークツリーを共有する

`--root` がリンクされたワークツリーなら、git に載らない各自のファイルはメインのチェックアウトのものを使う。カードの変更が散らばらないようにするため。

| ファイル                                  | 置き場所                                                          |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `.ai-board/data/`（データのワークツリー） | メインのチェックアウト                                            |
| `data.lock`・`cache/`                     | メインのチェックアウトの `.ai-board/`（データのワークツリーの隣） |
| `config.yaml`                             | データ用ブランチの根（無ければメインの `.ai-board/config.yaml`）  |
| `.ai-board/plans/`                        | ワークツリー（`--root`）                                          |

環境変数 `AI_BOARD_DATA` を指定すると、データのワークツリーの代わりにそのディレクトリ（git のリポジトリ）を使う。
カードに書くコードやデータ用ブランチの形を変えるコードをワークツリーで動かすときは、スクラッチパッドなどに作った bare リポジトリを `origin` にした clone を指す。
指さなければ、試しの書き込みが本物の `origin` の `ai-board/data` に push される。

### board.db からの切り替え

カードの正本は、かつて `.ai-board/board.db`（SQLite）にあった。今の版は `board.db` を読まない。

- **新しいリポジトリ:** メインのチェックアウトで `node dist/cli.js init` を走らせる。
  空のデータ用ブランチ `ai-board/data` を作って `origin` へ push し、`.ai-board/config.yaml` があればデータ用ブランチの根へ写す
- **`board.db` しか持たない手元:** SQLite を消す前の版（main のコミット `d2380ce`）を checkout し、
  `npm ci && npm run build && node dist/cli.js migrate` で移行してから今の版に戻す

ほかのマシンやクラウドのセッションでは `init` は要らない。最初に CLI を動かしたときに、`origin` のデータ用ブランチからデータのワークツリーが作られる。

## GitHub との接続

`PR中` / `マージ済み` の列は、カードに紐付いた GitHub の Pull Request の状態で決まる。
接続設定はデータ用ブランチの根の `config.yaml` から読み、無ければメインのチェックアウトの `.ai-board/config.yaml` を読む。
`ai-board init` は `.ai-board/config.yaml` をデータ用ブランチへ写すので、`init` の前に用意しておく。

```bash
cp .ai-board/config.example.yaml .ai-board/config.yaml
```

```yaml
github:
  repository: iepyon/ai-board # owner/repo
```

ai-board はアクセストークンを受け取らない。問い合わせは `gh api` の実行として行い、**認証はログイン済みの CLI に委ねる**（`gh auth login`）。
CLI が入っていない・未ログイン・設定が無いときは連携が無効になり、理由が `ai-board status` の「GitHub:」の行に出る。
問い合わせるのは `branch` か `mr` が書かれたカードだけで、`mr` が無ければ `branch` から PR を解決して番号を書き戻す。
取得の細部は [`docs/architecture.md`](docs/architecture.md) の「GitHub の PR の取得」にある。
