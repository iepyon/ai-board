# ai-board

プランニングファイル駆動の開発のためのローカル Web ダッシュボード。

`.ai-board/plans/` とレビュー要求（GitHub の Pull Request）を読んで各カードのステージを自動導出する。
`stage` という値はどこにも保存しない。人の判断（着手・承認・否決・中止）も
カード上の痕跡として残り、それも導出の入力になる。

```
[ アイデア ] [ 計画提案中 ] [ 計画レビュー ] [ 実装中 ] [ 動作確認 ] [ PR中 ] [ マージ済み ]
     人            AI            人 ★          AI        人 ★       人 ★        —
```

★ が人の判断を待つゲート。計画レビューでは計画を読み、動作確認ではブランチを動かして振る舞いを確かめ、
PR中 ではコードの差分を読む。人が動かすのは `アイデア ⇄ 計画提案中` の 1 遷移だけ（「着手」ボタン）で、
あとは AI が右へ進め、★ で止まる。

## 画面

横幅固定（1040px）で縦にスクロールする 1 ページ。上の件数帯に 7 段の件数を出し、
その下に区画を積む。区画はステージの見せ方の振り分けで、導出の規則には関わらない。

| 区画                     | 入るカード                                                       | 並び                   |
| ------------------------ | ---------------------------------------------------------------- | ---------------------- |
| あなたの判断を待っている | 計画レビュー / 動作確認 / PR中、止まっている 計画提案中 / 実装中 | 待ち始めた時刻の古い順 |
| AI が進めている          | 計画提案中 / 実装中（止まっているものを除く）                    | `rank`                 |
| アイデア                 | アイデア（区切り線で上下に分ける）                               | `rank`（ドラッグ可）   |
| マージ済み（折りたたみ） | マージ済み                                                       | マージの新しい順       |
| 中止（折りたたみ）       | 最新のレビューエントリが中止のカード                             | `rank`                 |

計画レビューのカードには `plan 提出` に書かれた判断待ちの点を出し、その場で計画を開いて
承認 / 否決 / 中止できる。動作確認のカードには `verify 提出` に書かれた動かす手順と AI が動かした結果を出し、
「PR #n を開く」のリンクと同じボタンを置く。AI が進めているカードは、計画ファイルが 3 日更新されないと
「動きなし」の印が付く。タイトルを押すと、本文の表示・編集と branch / PR の紐付けを行う詳細パネルが開く。
本文は Markdown を整形して表示し（見出し・段落・箇条書き・コードブロック・強調・インラインコード・http(s) のリンク）、
「編集」を押したときだけ textarea に切り替わる。段落の中の改行は改行のまま出し、表は等幅のまま出す。
本文の欄（表示と編集）には `## レビュー` の節を出さず、判断はその下の「判断の記録」の欄に書かれた順で出す（判断が無ければ欄ごと出さない）。
判断ごとの見出し（ゲート・種別・時刻）は画面が値から描き、理由はその下に Markdown として整形して出す（空なら「（理由なし）」）。
ただし理由の中の見出しの行（`#`〜`######`）だけは見出しにせず、`#### …` と記号の付いた普通の行として出すので、理由に何を書いても判断の見出しには見えない。
編集で保存するのは節の無い本文で、判断は変わらない。
詳細パネルは画面の幅に合わせて広がり（560〜880px）、本文を先頭に置く。タイトルの下にはステージ・タスクの進み・PR へのリンクを 1 行で出し、
ステージの理由・計画・ゲート・紐付けの欄は本文の後ろに並ぶ。計画レビューと動作確認のカード、止まっているカード（どれも中止したものを除く）だけは、判断のボタンを本文より前に置く。PR中 のカードは GitHub で PR をマージして判断するので、ボタンは出さない。
ゲートの欄には「計画レビューを飛ばす」と「動作確認を飛ばす」のチェックボックスがあり、`skipGates` の `plan` と `verify` を出し入れする（後述のスキップ）。
「動作確認を飛ばす」は、動作確認の列をまだ通っていない、中止でないカード（アイデア〜動作確認）にだけ出す。

**止まっているカード**は、AI の列（計画提案中 / 実装中）にいるが人の判断を待っているカードである（後述の「止まり」）。
判断待ちの区画に、止まった理由（人が何をすればよいか）と、AI が書いた 保留 の本文を出す。
ボタンはカードによって変わる。

| カード                                        | ボタン                                                |
| --------------------------------------------- | ----------------------------------------------------- |
| 計画レビュー                                  | 承認 / 否決して差し戻す / 中止                        |
| 動作確認                                      | 承認 / 否決して差し戻す / 計画から立て直させる / 中止 |
| 実装中で止まっている（verify 保留、Draft へ） | 実装を直させる / 計画から立て直させる / 中止          |
| 計画提案中で止まっている（plan 保留）         | 計画を直させる / 中止                                 |
| 計画提案中で止まっている（成果物が見えない）  | 中止                                                  |

「実装を直させる」は verify の否決、「計画から立て直させる」と「計画を直させる」は plan の否決として `## レビュー` に追記され、どれも理由が必須。
飛ばす宣言のあるゲートでも同じボタンを出す（宣言があっても、人の否決はふつうに差し戻しになるため。後述のスキップ）。

## なぜ必要か

AI エージェントと開発を回すとき、作業の実態は複数の場所に散らばる。

| 情報               | 所在                                        |
| ------------------ | ------------------------------------------- |
| アイデア・調査メモ | `origin` の `ai-board/data` ブランチ（git） |
| 計画とタスクの進捗 | `.ai-board/plans/<id>.md`                   |
| PR のレビュー      | GitHub                                      |
| 完了               | `.ai-board/plans/archive/`                  |

どれも見ようと思えば見られるが、アイデアから完了までを一本のパイプラインとして
俯瞰する手段がない。ai-board はその欠けたビューを埋める。

**そして「いま誰の番か」を可視化する。** 人が判断すべき 3 点（計画レビュー・動作確認・PR）で
列が止まり、それ以外は AI が右へ進める。

## 使い方

動かすには Node 24 以上が要る（なるべく 24 系の最新を使う）。

```bash
npm install
npm run build

# .ai-board/ を持つプロジェクトのルートで起動する
node dist/cli.js --root /path/to/your-project
```

```
使い方: ai-board [options]

  --root <path>          対象プロジェクトのルート (既定: カレントディレクトリ)
  --port <n>             待ち受けポート (既定: 5673、使用中なら自動で繰り上げ)
  --no-open              ブラウザを自動で開かない
  --poll-interval <ms>   GitHub のポーリング間隔 (既定: 60000)
  -h, --help             ヘルプを表示
```

サーバは `127.0.0.1` にのみ bind する。

## ステージの決まり方

以下を**上から評価し、最初に真になったもの**を採用する（＝最も進んだステージ）。
手動上書きの仕組みは無い。

| #   | stage         | 条件                                                                 |
| --- | ------------- | -------------------------------------------------------------------- |
| 1   | `merged`      | 計画が `.ai-board/plans/archive/` にある、**または** PR が merged    |
| 2   | `pr`          | PR が存在し opened、かつ Draft でない                                |
| 3   | `verifying`   | plan ゲート通過済み、かつ verify ゲートが判断待ち                    |
| 4   | `impling`     | plan ゲート通過済み                                                  |
| 5   | `plan-review` | `.ai-board/plans/<id>.md` か Draft の PR があり、plan ゲートが未判断 |
| 6   | `planning`    | `startedAt` が非 null                                                |
| 7   | `idea`        | 既定                                                                 |

計画と実装は同じ 1 本の PR に載る。AI は計画をコミットした時点で Draft の PR を出し、
人はその PR で計画を読んで、ボードのボタンで承認 / 否決する。
実装を終えた AI は、PR を Draft のまま `verify 提出` を書いて動作確認を頼む（`verifying` へ）。
人がブランチを動かして承認すると、AI が PR を Ready にして `pr` へ進む。

動作確認を頼む時点の PR も Draft だが、計画レビューへは巻き戻らない。
Draft の PR が立てる `plan-review` のルールは plan ゲートが未判断のときにしか当てはまらず、
plan が承認済みのカードは 3 か 4 で決まるため。

**否決の差し戻しに専用のルールは無い。** ゲートが「差し戻し中」のとき
その工程のレビュー行と承認行が両方外れ、1 つ手前の列へ自然に落ちる。
verify も同じで、否決・承認・スキップのどれでも `verifying` が外れて `impling` に落ちる。
承認の後に Ready にするのは AI の作業なので、AI の列（実装中）で待つ。

### レビューログ

人の判断はカード本文の `## レビュー` に追記される。ゲートは計画を読む `plan` と、
実装を動かして確かめる `verify` の 2 つ。
種別は 提出 / 再提出 / 保留（AI が書く）と 承認 / 否決 / 中止（人が書く）の 6 つ。
保留は、AI が否決を自分では直しきれずに止まった痕跡である（後述の「止まり」）。

```markdown
## レビュー

### 2026-09-11T04:00:00.000Z plan 提出

### 2026-09-11T05:12:00.000Z plan 否決

既存の stage-resolver を見ていない。導出ルールとの整合を調べ直して。

### 2026-09-11T09:30:00.000Z plan 再提出

### 2026-09-11T10:00:00.000Z plan 承認

### 2026-09-12T03:00:00.000Z verify 提出

npm run dev で起動し、カードの詳細パネルで「更新」を押すとトークンが入れ替わる。
```

ゲートの状態は、そのゲートの最新エントリ 1 件で決まる。書式の壊れた見出しは黙って無視する
（カードは人が直接編集してよいファイルなので、手書きの揺れでボードが読めなくなるほうが害が大きい）。

中止のエントリはゲートの判定から除く。中止は工程の進捗とは直交する終端の軸であり、
通過済みのゲートを巻き戻さない。

最新が 保留 のゲートは `held` になる。どの規則も `held` でゲートを先へ進めないので、
保留のカードは AI の列（計画提案中 / 実装中）に留まる。
人が後から承認 / 否決 / 中止を書けばそれが最新になり、保留は自然に外れる。

後ろのゲート（`verify`）は、前のゲート（`plan`）の最新の承認より古いエントリを数えない。
計画を承認し直したなら、前の計画に対する動作確認の判断（否決・保留）はもう効かない、という意味である。
計画から立て直したカードは、計画をもう一度承認すると verify が未提出に戻り、AI はタスクを倒すところから始め直す。
通常の流れでは verify のエントリはすべて plan の承認より後にあるので、何も外れない。

`pr` ゲートはレビューログを持たない。PR の承認とマージは GitHub 側の実態そのもので、
カード本文に写す必要が無いため。

かつては `explore` ゲートもあったが、探索レビューの列とともに廃止した。
既存のカードに残る `explore` のエントリは規定外のゲートとして黙って無視される。

### 止まり

AI の列（計画提案中 / 実装中）にいても、人の判断を待っているカードがある。これを**止まり**と呼ぶ。
止まりはステージとは別の軸の派生値で、どこにも保存しない。ステージは「工程のどこにいるか」、止まりは「その工程で誰を待っているか」を表す。
止まっているカードは判断待ちの区画に出て、AI ループはそのカードを選ばずに後ろのカードへ進む。

| 止まり                                                  | 列         | 人がすること                                                          |
| ------------------------------------------------------- | ---------- | --------------------------------------------------------------------- |
| AI が `verify 保留` を書いた                            | 実装中     | 実装を直させる / 計画から立て直させる / 中止                          |
| 人の判断の後に、PR が Draft に戻された                  | 実装中     | GitHub で Ready に戻す / 実装を直させる / 計画から立て直させる / 中止 |
| AI が `plan 保留` を書いた                              | 計画提案中 | 計画を直させる / 中止                                                 |
| 計画を提出したのに計画ファイルも Draft の PR も見えない | 計画提案中 | 中止                                                                  |

最後の止まりは、PR の状態を引けているとき（GitHub に接続し、初回の取得を終えたとき）にだけ立つ。
引けていなければ、PR が無いのか分からないためである。
Draft に戻された止まりで出るボタンは、飛ばす宣言の有無で変わらない（`skipGates` に `verify` があっても「実装を直させる」を出す）。

PR の `draft` だけでは「まだ一度も Ready にしていない」と「人が Draft に戻した」を見分けられない。
そこで GitHub の PR のイベントから、最後に Draft へ戻された時刻（`convert_to_draft`）を引く。
作成時から Draft の PR はこのイベントを残さないので、動作確認を頼むあいだの Draft では止まらない。
戻された時刻がカードの最新のレビューエントリより新しいときに止まる。

人が承認 / 否決 / 中止を書けばそのエントリが最新になり、止まりは外れる。止まりを解く専用の操作は無い。

### スキップ

frontmatter の `skipGates` に書いたゲートでは、AI の 提出 / 再提出 を人の承認と同じに読む。
小さいカードを夜間に `/loop` で流したいときに使う。AI が提出した時点でゲートを通るので、カードはそのレビュー列に滞留しない。
否決 / 保留 / 承認 はふつうに効き、人は後から否決して差し戻すこともできる。エントリが無ければ、宣言があっても未提出のままである。

宣言は、詳細パネルのゲートの欄の 2 つのチェックボックスから出し入れする。

- **計画レビューを飛ばす**（`plan` を入れる）: 印を入れても、着手するまではアイデアに留まる。
  着手すると計画提案中に入り、AI が計画を書いて Draft の PR を出す。AI が `plan 提出` を書いた時点で、計画レビューを通らずに実装中へ進む。
  提出済みのカードに印を入れるとその場で実装中へ進み、実装中のカードから外すと plan ゲートが提出済みに戻って実装中から外れる
- **動作確認を飛ばす**（`verify` を入れる）: AI は実装を終えても動作確認を頼まず、AI レビューの後にそのまま PR を Ready にする。
  人が否決して直させたときも、AI の `verify 再提出` が承認と読まれ、そのまま Ready にする（判断してほしい点は PR のコメントに書く）
  このチェックボックスは、アイデア・計画提案中・計画レビュー・実装中・動作確認のカード（中止したものを除く）にだけ出す。
  PR中・マージ済み・中止のカードはもう動作確認の列を通らず、入れても何も変わらないので出さない（既に入っている宣言は値として残る）。
  動作確認のカードでは、印を入れると提出済みの `verify 提出` が承認と読まれて実装中へ戻り、AI が PR を Ready にする旨の説明文に差し替わる

どちらの宣言も人が書くもので（画面と `PATCH /api/cards/:id`。チャットからは後述の `board-decide`）、CLI には入口が無い。
AI の `plan 提出` / `plan 再提出` は着手したカードにしか書けないので、AI が宣言を使って人の着手を飛ばすこともできない。
また、plan ゲートが未提出か否決のときにしか書けないので、AI が計画を出し直して人の `verify 否決` を打ち消すこともできない。

### 誰が動かせるか

| 列                    | ステージを立てるもの                                                   | 誰の領分か                     |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------ |
| アイデア / 計画提案中 | `startedAt` の打刻                                                     | 人                             |
| 計画レビュー          | 計画ファイル / Draft の PR                                             | AI                             |
| 実装中                | `## レビュー` の plan 承認（plan を飛ばすカードは plan 提出 / 再提出） | 人（plan を飛ばすカードは AI） |
| 動作確認              | `## レビュー` の verify 提出                                           | AI                             |
| PR中                  | PR が Ready で opened                                                  | AI                             |
| マージ済み            | 計画の archive / PR の merged                                          | AI                             |

**人が動かせるのは `アイデア ⇄ 計画提案中` の 1 遷移だけ。**
アイデアの行の「着手」と、計画提案中のカードの「着手を戻す」がこれにあたり、`startedAt` を書き換える。
承認 / 否決 / 中止 は判断待ちの区画（または詳細パネル）のボタンから行い、`## レビュー` への追記になる。
否決には理由文が必須（空の否決は AI が次の周回で読むものを持たない）。

さらに、**動かせる先はカードごとに違う**。`startedAt` を外したときに残るステージ
（AI の成果物と人のレビュー記録が課す下限）より前へは戻せない。

| 下限               | 手で入れられる列         |
| ------------------ | ------------------------ |
| `idea`             | アイデア / 計画提案中    |
| `plan-review` 以降 | なし（カードを掴めない） |

### その他の設計上の判断

- **AI レビューに専用の列は作らない。** 実装中の内部工程として扱う。tasks の進捗は
  カード上のプログレスバーに出るだけで、ステージを立てる入力には使わない。
  AI レビューの直す指摘も計画のチェックボックスとして書かれるので、進捗に数えられるだけでステージは動かさない。
- **レビュー後の修正は `pr` 列内のバッジ。** 「AI が指摘を受けて修正を push した」を
  最新コミットと最新レビューコメントの時刻比較で判定し、再提出済みとして示す。
  新しいレビューコメントが来れば日時比較が逆転し、自然にバッジが消える。
- **否決からの復帰は AI の「再提出」追記で表す。** ファイルの mtime 比較は成立しない
  （レビュー記録を書く行為そのもので mtime が動くため）。
- **中止に専用の列は作らない。** マージ済みとは意味が違うので混ぜない。
  既定でボードから畳み、トップバーのトグルで掘り起こせる。

## カード

カードの正本は `origin` の `ai-board/data` ブランチ（データ用ブランチ）にあり、`cards/<id>/` の 1 ディレクトリが 1 カード。
データ用ブランチはコードの履歴と交わらない orphan のブランチで、clone した時点でカードが揃う。
判断は `cards/<id>/log/` に 1 件 1 ファイルで、並び順と区切り線は `order.yaml` に置く。
手元では、CLI とサーバがメインのチェックアウトの `.ai-board/data/` にデータのワークツリーとして展開し、
書き込みのたびにコミットと push をする（全ワークツリーで 1 つのバックログを共有する。後述）。
`id` は不変で、`branch` / `mr` が進行に応じて後から埋まる。
これによりアイデアメモ → 計画 → ブランチ → PR → archive が 1 本の線でつながる。

`ai-board card show <id>` は、カードを次の Markdown の形で出す。

```markdown
---
id: refresh-token # 不変。生成後は変えない
title: リフレッシュトークン対応
created: 2026-09-01T09:00:00.000Z
startedAt: '2026-09-01T10:00:00.000Z' # 人が着手を指示した時刻
skipGates: [] # 人が事前に見ないと宣言したゲート（plan / verify）
branch: feat/refresh-token
mr: 42 # GitHub の PR 番号（branch から自動解決して書き戻す）
rank: 1500 # 並び順。小さいほど上。並べ替えたときだけ書かれる
---

## アイデア

## レビュー
```

### カードを書く経路

人は画面から、エージェントは `ai-board card` の CLI から書く。
CLI はデータ用ブランチを取り直してから読み書きするので、サーバが止まっていても書ける。
書き込みは「取り直す → 検査する → コミットする → push する」を 1 つの操作として行い、push が拒否されたら取り直して頭からやり直す。
サーバが動いていれば、データのワークツリーの変化を拾って SSE でブラウザへ即座に反映される。
クラウドのセッションなどほかの場所からの書き込みは、ポーリングと同じ間隔（既定 60 秒）の取り直しで拾う。
データのワークツリーのファイルを直接書き換えたり、データ用ブランチへ直接 push したりはしない（`.claude/settings.json` の deny ルールでも止めている）。

```bash
ai-board card list                         # 一覧（JSON、本文なし、rank 順）
ai-board card show <id>                    # 1 枚を Markdown で
ai-board card create --title <t> [--id <id>] < body.md
ai-board card body <id> < body.md          # 本文の差し替え
ai-board card branch <id> <name>           # ブランチの紐付け（--clear で外す）
ai-board card submit <id> [--gate <plan|verify>] [--resubmit] [--reason <text>]   # 提出 / 再提出（既定は plan）
ai-board card hold <id> --gate <plan|verify> --reason <text>   # 保留（否決を直しきれずに止まるとき。理由は必須）
ai-board status [--json | --html]          # 導出したステージ・判断待ち・次の一手（サーバ不要）
```

CLI にはエージェントに許す操作しか無い。`startedAt`・`rank`・`skipGates` の書き換えと、
承認 / 否決 / 中止の追記は画面（HTTP API）からだけ行える（人がチャットで頼んだときは、後述の `board-decide` が同じ API を叩く）。
逆に、画面（HTTP API）からは AI の種別（提出 / 再提出 / 保留）を書けない。
`hold` は、そのゲートの最新の判断が 否決 のときにしか書けない（否決を直す手で止まるときだけ使うため）。
承認済みのゲートに保留を書いて人の承認を打ち消したり、計画レビュー / 動作確認 で人を待つカードを AI の列へ落としたりはできない。
`submit` の plan ゲートは、着手したカードで、plan が未提出か否決のときにしか書けない。
`body` は `## レビュー` のエントリが変わる差し替えを拒否するので、本文の差し替えで
人の判断を書き換えることもできない。`## レビュー` の節の無い本文は「判断は変えない」として受け付け、本文だけを書く。
`submit` / `hold` の `--reason` に判断の見出し（`### <時刻> <gate> <種別>`）の形の行を書いても、判断は指定した 1 件だけが増える
（判断は値のまま `log/` に書かれ、その行は `####` へ下がって理由の一部として見える）。画面（HTTP API）の判断の理由と本文の編集でも同じである。

### チャットから判断する

`.claude/skills/board-decide/SKILL.md` は、人がチャットで頼んだ判断を、Claude が画面と同じ人の API で代わりに書くスキル。
「chat-decide の計画を承認して」「否決して、理由は〜」「loop-activity を一番上へ」のように頼むか、`/board-decide` で呼ぶ。

- できること: 承認 / 否決 / 中止、着手 / 着手を戻す、計画レビューを飛ばす、動作確認を飛ばす、アイデアの並べ替え（区切り線の移動を含む）
- 承認 / 否決 は、頼まれたカードと判断が 1 つに決まれば確かめずに書き、書いた中身を伝える。否決の理由は人の言葉をそのまま送る。
  中止 / 着手を戻す は、送る中身を見せて 1 回確かめてから書く。
  計画レビューのカードに「計画レビューを飛ばす」、動作確認のカードに「動作確認を飛ばす」を入れるときも、待っている提出がその場で承認と読まれるので確かめる
- 対象を言わずに頼むと（「判断待ちを見せて」、引数なしの `/board-decide`）、判断待ちのカードと出せる判断を並べて選ばせる
- 出せる判断・アイデアの並び・サーバの URL は `ai-board status --json` から読む（`decisions` / `ideas` / `server`）。
  書き込みはサーバを通す。サーバは起動時にデータのワークツリーの隣（既定は `.ai-board/server.json`）に自分の場所を書く。
  サーバが動いていなければ、書く直前にそのセッションの中で `ai-board --no-open` を起動し、書き終えたら止める（クラウドのセッションには常駐のサーバが無い）
- 使うのは人が頼んだときだけ。ループのサブエージェントは使わず、監視役も周の中では使わない

### AI ループ

`.claude/skills/board-loop/SKILL.md` は、ボードを読んで AI が進めてよいカードの次の 1 手を、サブエージェント
（計画の手は `board-planner`、実装の手は段が `review` なら `board-reviewer`、それ以外は `board-worker`）に直接渡すスキル。
`/loop 5m /board-loop` で間隔運転する。

- 何をするかは `ai-board status --json` の `next` が決める。優先順は 実装中 → 計画提案中、同じ列の中は `rank` の順
- 1 手は次の 5 種類のどれか。計画提案中のカードには `plan` / `revise-plan`、実装中のカードには `implement` / `revise-impl` / `ready`

  | 手            | 選ばれるとき                   | すること                                                                                                               |
  | ------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
  | `plan`        | 計画提案中で、計画がまだ無い   | 計画を書いて Draft の PR を出し、`plan 提出` を書く                                                                    |
  | `revise-plan` | 計画提案中で、計画が否決された | 否決の理由を読んで計画を直し、`plan 再提出` を書く                                                                     |
  | `implement`   | 実装中で、verify が未提出      | 計画の状態から決まる 1 段を進める（下の表）。最後の段で PR を Draft のまま `verify 提出` を書く（飛ばすなら Ready に） |
  | `revise-impl` | 実装中で、verify が否決された  | 否決の理由と PR のコメントを読んで直し、`verify 再提出` を書く                                                         |
  | `ready`       | 実装中で、verify を通った      | 計画を archive へ移してコミットし、`ai-board pr ready` で Ready にする                                                 |

  verify を飛ばすカードでは `gateState` が `verify 提出` / `verify 再提出` を承認と同じに返すので、人の承認と同じく `ready` が選ばれる。
  動作確認で否決された実装を `revise-impl` が直して再提出した後は、締めの段を通さずに Ready にする（`revise-impl` が PR の本文に足した見送りを消さない）

  `revise-plan` / `revise-impl` で否決を直しきれないとき、サブエージェントは何も直さず `ai-board card hold` で 保留 を書いて止まる。
  前の plan 承認がある否決（人が「計画から立て直させる」を選んだもの）の `revise-plan` では、作り直すタスクの `[x]` を外すか新しいタスクを足し、
  計画の `## AI レビュー` 節を消す（残っていると、作り直した実装の AI レビューが飛ばされる）

- `implement` の手では、`status` がカードのブランチの計画を `git show` で読んで段を決め、`next.step` に載せる。
  監視役は計画を読まず、`next.step` で渡す先を決める。段は手の種類（`next.action`）を増やさず、`implement` の中の区切りとして扱う

  | 計画の状態                                | `next.step` | 段             | 渡す先           | すること                                                                                                                   |
  | ----------------------------------------- | ----------- | -------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------- |
  | `plans/archive/` にある                   | `close`     | archive 済み   | `board-worker`   | 前の周で `ai-board pr ready` だけが失敗している。`ai-board pr ready` だけをやり直す                                        |
  | 未チェックのタスクがある                  | `task`      | タスクを倒す段 | `board-worker`   | 残りの節を上から順に倒し、節ごとに 1 つのコミットにする。`## AI レビュー` 節が無ければレビューの段の前で止まり、あれば同じ起動で締めの段へ進む |
  | 全部倒れていて、`## AI レビュー` 節が無い | `review`    | レビューの段   | `board-reviewer` | 計画の末尾に `## AI レビュー` 節を書き足す。コードは直さない                                                               |
  | 全部倒れていて、`## AI レビュー` 節がある | `close`     | 締めの段       | `board-worker`   | 見送った指摘を PR の本文の `## 見送った AI レビューの指摘` 節に写し、動作確認を頼む。飛ばす宣言があれば archive して Ready |
  | 読めなかった（ブランチが無い など）       | `null`      | —              | `board-worker`   | ワークツリーに入って計画を読み、タスクを倒す段か締めの段なら進める。レビューの段なら何も変えずに止まる                     |

  ブランチはローカルのものがあればそれを、無ければ `origin` の追跡ブランチを読む。`status` は `git fetch` をしないので、段が古いことがある。
  受けたサブエージェントはワークツリーで計画を読み直し、自分の受け持つ段でなければ何も変えずに `止まった` と報告する（監視役は次の周で読み直す）。
  サブエージェントがサブエージェントを立てる入れ子は使わない。クラウドのセッションではサブエージェントが `Agent` の道具を持てないため、手元でも同じ手順で回す

  節は、計画の `## タスク` を `### <番号>. <題>` の見出しで区切った範囲で、最初の未チェックのタスクから上へたどった最初の見出しから、次の見出しの手前までである。
  `board-planner` は、その節までを倒し終えたら品質ゲートが通るところで区切り、どこで区切るかは計画レビューで人が確かめる。
  `board-worker` は 1 回の起動で残りの節を上から順に倒す。節の途中ではゲートを走らせず（テストが落ちていてもよい）、節の終わりごとにゲートを通して 1 つのコミットにし、push する。
  節は止まってよい区切りで、起動の中で自動の要約が入ったら、`board-worker` は節の区切りで止まり、次の起動が計画の `[x]` とコミットから続きの節を選ぶ。
  節の終わりでゲートが通らず、原因がタスクの順番なら、未チェックのタスクを別の節へ移す・隣り合う節を合わせる・節の中で並べ替える、だけをしてよい（タスクの文は変えない）。
  節に区切っていない計画では `## タスク` 全体が 1 つの節になり、`## AI レビュー` 節の直す指摘も 1 つの節として 1 回でまとめて倒れる

  `board-reviewer` は、指摘を「直す」（`- [ ]`）と「見送る」（チェックボックスの無い `### 見送った指摘`、理由付き）と「人に判断してほしい」（`### 人に判断してほしいこと`）に分ける。
  直す指摘は普通のタスクとして次のタスクを倒す段で `board-worker` に倒され、ボードの進捗バーにも乗る。倒し終えた `board-worker` は、同じ起動のまま締めの段へ進む。指摘が無ければ「指摘なし」と書く。
  AI レビューは 1 回だけで、指摘を直した後にもう一度レビューはしない。
  `revise-impl` では `board-worker` が自分で AI レビューをかけ、同じ基準で重要な指摘だけを直して、見送った指摘を PR の本文の同じ節に足す

- 止まっているカード（前述の「止まり」）は選ばず、後ろのカードへ進む。止まっているカードは `status` の `waiting` に出る。
  人が PR を Draft に戻したカードを、ループが Ready にし直すことは無い
- 計画レビュー / 動作確認 / PR中 のカードには触らず、着手・承認・否決・中止・並び順・マージは人に任せる
- GitHub に接続できないとき（`github:` が無いときも含む）は何もせずに止まる。PR の状態が引けないと、人を待つカードが AI の列に落ちて見えるため

ループを回すセッションは監視役で、カードの作業は自分でしない。
1 手ごとに、まっさらな文脈のサブエージェント（`.claude/agents/board-planner.md` / `board-worker.md` / `board-reviewer.md`）へ、カード ID と手の種類だけを渡す。
前のカードで読んだコードや決めた事柄が、次のカードの作業に紛れ込まないようにするためである。
同じカードの中で、1 つの `board-worker` が節をまたいで文脈を持つのは構わない（読み直しが減る）。実装とレビューの間だけは、別の起動に分ける。

- サブエージェントはカード本文・計画・PR を自分で読み直し、何をしたかと PR の URL を数行で返す。監視役はそれを伝えるだけ
- サブエージェントの完了の通知を受けたら、次の cron の周を待たずに次の手を選んで渡す。実装 → AI レビュー → 指摘の修正 → 動作確認の提出が続けて流れる
- サブエージェントが動いている間の周は、何もせずに「作業中」と伝える。作業中かは、名前が `board-planner-` / `board-worker-` / `board-reviewer-`
  のどれかで始まるサブエージェントが動いているかで見る。3 つとも監視役が直接立てる
- サブエージェントには会話が見えない。ループに伝えたい補足は、会話ではなくカード本文の `## 探索メモ` に書く

`status` を読むには、メインのチェックアウトのコードが `ai-board status` を持っている必要がある。

### クラウドのセッションで回す

手元の Mac を動かし続けなくても、Claude Code のアプリから立ち上げたクラウドのセッションでボードを回せる。
クラウドのセッションは毎回新しい clone から始まるが、カードはデータ用ブランチにあるので、clone した時点で手元と同じカードが見える。
常駐のサーバは無く、ボードの画面（React）も動かさない。

1. セッションを立ち上げたら、まず `npm ci && npm run build` で `dist/` を作る（clone には `dist/` が無い）
2. 会話で `/loop 5m /board-loop` を回す。これが主な回し方である。監視役とサブエージェントの動きは手元と同じ
3. ボードを読むときは、会話で「ボードを見せて」と頼む。`board-loop` のスキルが `ai-board status --html` の出力を Artifact として公開する。
   同じ会話で頼み直すと、同じ URL のまま新しいボードに書き直される
4. 判断は会話で頼む（「〜の計画を承認して」など）。`board-decide` のスキルが、そのセッションの中でサーバを起動して人の API で書き、書き終えたら止める

クラウドでは GitHub の GraphQL が 403 になり、`gh pr` と `gh auth status` が動かない。
そのため手順書は PR の読み書きに `ai-board pr ...`（`gh api` の REST）を使い、GitHub の接続も `gh api` のリポジトリの取得で確かめる。
`ai-board pr ready` は、`gh pr ready` が失敗したらクラウドの `ccr/ready_for_review` の経路で Draft を外す。

人が会話を開いていない間も止まっているカードを動かしたいときは、ルーティン（cron で動くクラウドのエージェント。間隔は最短 1 時間）で `/board-loop` を定期に走らせてもよい。
これは会話の `/loop` の保険で、主には使わない。ルーティンからの通知の設定はこのリポジトリでは扱わない。
ルーティンが重なって同じ手が 2 つ同時に走っても、カードの書き込みは push の拒否で 1 つにまとまる（後から来た提出は、取り直した状態で検査されて拒まれる）。

クラウドのセッションからはブランチを消せない。マージした PR のブランチが残らないよう、
人がリポジトリの Settings → General の「Automatically delete head branches」を有効にしておく。
これが消すのはマージした PR の head のブランチだけで、データ用ブランチ `ai-board/data` は PR の head にならないので消えない。

### ワークツリーではデータのワークツリーを共有する

`--root` がリンクされたワークツリー（`.git` がファイル）なら、git に載らない各自のファイルは
メインのチェックアウトのものを使う。ワークツリーごとにデータのワークツリーが分かれて、カードの変更が散らばらないようにするため。

| ファイル                                  | 置き場所                                                          |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `.ai-board/data/`（データのワークツリー） | メインのチェックアウト                                            |
| `server.json`・`data.lock`・`cache/`      | メインのチェックアウトの `.ai-board/`（データのワークツリーの隣） |
| `config.yaml`                             | データ用ブランチの根（無ければメインの `.ai-board/config.yaml`）  |
| `.ai-board/plans/`                        | ワークツリー（`--root`）                                          |

計画ファイルは git でブランチに乗るので、ワークツリーのものを読む。
ワークツリーでボードを起動すれば、そのブランチの計画を、メインと同じカードの上で判断できる。
起動ログの `データ` の行に、どのデータのワークツリーを使っているかが出る。

環境変数 `AI_BOARD_DATA` を指定すると、データのワークツリーの代わりにそのディレクトリ（git のリポジトリ）を使う。
ai-board 自身をワークツリーで開発し、カードに書くコードやデータ用ブランチの形を変えるコードを動かすときは、これで別のディレクトリを指す。
指さなければ、試しの書き込みが本物の `origin` の `ai-board/data` に push される。
そのディレクトリの `origin` へ push するので、スクラッチパッドなどに作った bare リポジトリを `origin` にした clone を指す。
`server.json`・`data.lock`・`cache/` は、そのディレクトリの隣に置かれ、本物のものと混ざらない。

### board.db からの切り替え

カードの正本は、かつて `.ai-board/board.db`（SQLite）にあった。
データ用ブランチへの切り替えは、人が 1 回だけ次の順で行う。

1. 動いている ai-board のサーバと、`/loop` を回しているセッションを止める。
   `migrate` の後に `board.db` へ書かれた変更はデータ用ブランチに移らず、`migrate` は 2 回目を走らせられない
2. データ用ブランチに切り替える PR をマージし、メインのチェックアウトを最新の main にする
3. メインのチェックアウトで `npm run build` を走らせ、`dist/` を作り直す
4. メインのチェックアウトで `node dist/cli.js migrate` を走らせる

`migrate` は `.ai-board/board.db` を読み、データ用ブランチ `ai-board/data` を作って `origin` へ push する。
`## レビュー` のエントリは元の時刻のまま `log/` の 1 件 1 ファイルに分かれ、`startedAt` は着手の 1 件に、`rank` と区切り線は `order.yaml` に、`.ai-board/config.yaml` は `config.yaml` に移る。
書き出したカードを組み立て直して `board.db` のカードと比べ、食い違えば push せずに止まる。
`--from <db>` で読む DB を変えられる。`board.db` の無いリポジトリでは、`--empty` で空のデータ用ブランチを作る。
`origin` に `ai-board/data` が既にあれば、何もせずに止まる。

マージしてから `migrate` を走らせるまでの間、CLI とサーバはカードを読めずに止まり、`ai-board migrate` を走らせるよう案内する。
`migrate` の後は `ai-board card list` や `ai-board status` でカードが見えることを確かめ、サーバを起動し直す。
ほかのマシンやクラウドのセッションでは `migrate` は要らない。最初に CLI かサーバを動かしたときに、`origin` のデータ用ブランチからデータのワークツリーが作られる。

### 並び順

アイデアの表の行はドラッグで並べ替えられ、上にあるものほど優先度が高い。
並び順は全カードで 1 本で、各区画はそれを自分のカードだけに絞って見せる。
ステージが進んで区画を移っても、優先度はそのまま持ち越される（判断待ちとマージ済みの区画だけは時刻で並べ直す）。

並べ替えると、動かしたカードの `rank` だけが書き換わる。`rank` の無いカードは
`created` のエポックミリ秒を `rank` とみなすので、並べ替えたことの無いカードは作成順に並び、
新しいカードは末尾に付く。`rank` を決めるのは人で、エージェントは読むだけにする。

アイデアの表には区切り線が 1 本あり、線より上が「次にやる」、下が「あとで考える」。
区切り線もカードと同じくドラッグで動かせ、カードを線の向こうへドラッグすれば区分が変わる。
区切り線は `rank` と同じ物差しの値を 1 つ持つだけで（データ用ブランチの `order.yaml` の `divider`）、カードに区分の値は無い。
一度も動かしていなければ末尾にあり、すべてのアイデアが「次にやる」に入る。
新しく起票したアイデアは末尾に付くので「あとで考える」に入る。
区切り線も人が決める優先度なので、`ai-board card` から読み書きする入口は無い。

## 計画ファイル

`.ai-board/plans/<card-id>.md` の 1 ファイルがそのカードの計画。
**ファイル名がカード ID と一致することで紐付く**ので、カードの frontmatter に
紐付け用のフィールドは無い。

```markdown
# リフレッシュトークン対応

## 方針

...

## 動作確認の手順

1. npm run dev で起動する
2. カードの詳細パネルで「更新」を押し、トークンが入れ替わることを見る

## タスク

- [x] トークンの保存先を決める
- [ ] 更新エンドポイントを足す
```

チェックボックス（`- [ ]` / `- [x]`）はカード上のプログレスバーになる。
インデントされたサブタスクも親と同じように数える（列 0 に固定すると
`  - [ ] 1.1.1 …` が進捗から消えるため）。**タスクの進捗はステージを立てない。**
フェンス（` ``` ` / `~~~`）で囲んだコードブロックの中のチェックボックスは数えないので、計画に書き方の例として載せてよい
（閉じていないフェンスは無いものとして後ろの行を数える。4 つの空白で字下げしたコードブロックは外さない）。

`## 動作確認の手順` には、人が動かして確かめるときの起動のコマンド、見る画面、期待する結果を書く。
計画レビューの時点で、後で何を確かめることになるかを読めるようにするため。
実装を終えて `verify 提出` を書くときは、これをもとに、実装を経て変わった手順、AI が実際に動かした結果、
確かめられなかった点を本文に書く。

動作確認が承認されたら（飛ばす宣言があればタスクを倒し終えたら）、PR を Ready にする直前に同じ PR の中で `.ai-board/plans/archive/<card-id>.md` へ移す。
マージと同時に archive も main に入り、これがマージ済みの実態になる
（GitHub が引けないときや、`github:` の無いリポジトリでも マージ済み が立つ）。

計画を書くのは AI エージェントで、**ai-board サーバは read-only** に徹する。
ボードは計画の本文を持たず、タスクの進捗と archive の有無だけを読む。
人は計画を Draft の PR で読み、ボードには PR へのリンクだけが出る
（計画ファイルはブランチにあり、ボードを動かすチェックアウトからは見えないことが多い）。

**計画ファイルが存在するだけで計画レビューの列が立つ。** エージェントが書き始めた時点で
列が動くが、本来のゲートは本文の `## レビュー` に書かれる `plan 提出` であり、
ファイルの存在は「ログの欠落で人待ちを取りこぼさない」ための保険である。

## レビュー要求の取得先

`PR中` / `マージ済み` の列は、カードに紐付いた GitHub の Pull Request の状態で決まる。

接続設定はデータ用ブランチの根の `config.yaml` から読む。クラウドのセッションの clone には、git に載らない各自のファイルが無いためである。
データ用ブランチに無ければ、メインのチェックアウトの `.ai-board/config.yaml`（git の追跡外）を読む。
`ai-board migrate` は `.ai-board/config.yaml` をデータ用ブランチへ写すので、切り替えの前に用意しておく。

```bash
cp .ai-board/config.example.yaml .ai-board/config.yaml
```

```yaml
github:
  repository: iepyon/ai-board # owner/repo
```

### アクセストークンは要らない

ai-board はトークンを受け取らない。問い合わせは `gh api` の実行として行い、
**認証はログイン済みの CLI に委ねる。**

```bash
gh auth login
```

CLI が入っていない、または未ログインなら連携は無効になり、理由が画面に出る。
設定そのものが無い場合も同じく無効になり、`PR中` / `マージ済み` の列が
レビュー要求由来の情報を失うだけでボードは動く。取得先がダウンしてもボードは落ちず、
直近のキャッシュを保ったまま接続状態だけを error にする。

CLI の有無とログイン状態は起動時に 1 度だけ確かめる。ログインし直したら ai-board を再起動する。

PR 一覧の全件取得はページングで取りこぼすため使わず、カード単位で問い合わせる。
問い合わせるのは `branch` か `mr` が書かれたカードだけ。
`mr` が無ければ `branch` から PR を解決し、得られた番号を書き戻す。

GitHub はレビューコメントが 2 か所（PR 全体への返信とコード行への指摘）に分かれるため、
両方を合算して「人が書いた最新のコメント」とする。

PR のイベント（`issues/{n}/events`）は PR の状態を問わず引き、2 つの時刻を取る。
最後に Ready にした時刻（`ready_for_review`。作成時から Ready の PR は作成時刻）は、区間の並び（`timeline`）の PR レビューの始まりになる。
最後に Draft へ戻された時刻（`convert_to_draft`）は、今 open かつ Draft の PR でだけ値を持ち、前述の「止まり」に使う。

### GitLab 連携の廃止

かつては GitLab の Merge Request も取得先に選べた。
GitLab の MR !1 と GitHub の PR #1 は別物なので、GitLab 時代の番号を GitHub で引くと
**列は正しく埋まったままリンクだけが別の PR を指す**。
これを避けるため、番号の出どころを記録していた `forge` 列をもとに、
GitHub のものと確かめられない番号を当時の DB のマイグレーションで消してから列を落とし、
`branch` から解決し直させた。かつての `ai-board import` も `forge: gitlab` の番号は捨てていた。

## 設計

**ステージはどこにも保存しない。** 3 つの実態（カード・計画ファイル・レビュー要求）
から純関数で導出する。列を動かしたければ、その列を成立させる実態を作る。
手動で上書きする入力口は無い。

計画ファイルはディレクトリを直接読む。ファイル名がそのままカード ID なので、
ID として不正な名前のファイルは警告して読み飛ばす（ここで例外を投げるとボード全体が
500 になり、置き場所を間違えた 1 ファイルで画面が死ぬ）。

かつては OpenSpec の `openspec/changes/` を読んでいたが、Plan モードで立てた計画を
そのまま成果物にするほうが工程が短いため、計画ファイル 1 本に寄せた。
移行前の change は `.ai-board/plans/archive/` に計画として残してある。

### レイヤー構成

```
src/
  app.ts                Express アプリケーションファクトリ
  server.ts / cli.ts    起動
  shared/               Result<T,E>・Branded Types・設定・ミドルウェア
  cards/                カードの CRUD コンテキスト
    models/ errors/ repositories/ usecases/ controllers/ composition.ts
  board/                3ソース統合・ステージ導出コンテキスト
    services/stage-resolver.ts    ← 核となる純関数
    repositories/plan.repository.ts
    services/github-client.ts
  infrastructure/       ファイル監視・SSE・GitHub ポーリング
  web/                  React + Vite のダッシュボード UI
```

- usecase はすべて `Result<T, E>` を返し、例外を投げない
- エラーは discriminated union（`{ type: 'CardNotFound' }`）で表し、
  controller が `*-error-mappings.ts` で HTTP ステータスへ変換する
- 依存はコンテキストごとの `composition.ts`（Composition Root）で構成する

### API

| メソッド | パス                     | 用途                                                    |
| -------- | ------------------------ | ------------------------------------------------------- |
| `GET`    | `/api/board`             | 全カード＋導出ステージ＋計画の進捗 / レビュー要求の情報 |
| `POST`   | `/api/cards`             | 新規アイデアカード作成                                  |
| `PATCH`  | `/api/cards/:id`         | frontmatter の部分更新                                  |
| `PUT`    | `/api/cards/:id/body`    | 本文の差し替え                                          |
| `POST`   | `/api/cards/:id/reviews` | `## レビュー` へのエントリ追記                          |
| `POST`   | `/api/cards/:id/move`    | 直前・直後のカード（`after` / `before`）の間へ並べ替え  |
| `POST`   | `/api/idea-divider/move` | アイデアの表の区切り線を直前・直後のカードの間へ動かす  |
| `GET`    | `/api/events`            | SSE。ファイル変更・ポーリング結果を push                |

`PATCH` では `undefined`（未指定＝変更しない）と `null`（値を消す）を区別する。

`GET /api/board` の各カードは、画面が本文や計画を解析し直さずに済むよう、次の値も持つ。

- `latestReview` — その列が待っているゲート（計画レビューなら plan、動作確認なら verify）の最新エントリ。
  待ちの列でなければゲートを問わず最新のエントリ（どちらも中止を除く）。`{ at, gate, kind, reason }` か `null`。
  判断待ちの区画が出す提出の本文と、待ち始めた時刻はここから取る
- `plan.updatedAt` — 計画ファイルの mtime。「動きなし」の目安と、PR の無いマージ済みカードの日付
- `mrState.mergedAt` — PR の `merged_at`
- `mrState.readyAt` — 最後に Ready にした時刻（`ready_for_review` のイベント）。作成時から Ready の PR は作成時刻。
  今 Draft で一度も Ready にしていなければ `null`
- `mrState.convertedToDraftAt` — 最後に Draft へ戻された時刻。今 open かつ Draft でなければ `null`
- `hold` — 止まり（前述）。`{ reason, since }` か `null`。`reason` は人が何をすればよいか、`since` は人を待ち始めた時刻。
  判断待ちの区画への振り分けと、AI ループが選ばないことの両方がこの値を読む
- `timeline` — カードが各工程にいた時間を区間として時刻の順に並べたもの（区間の並び）。
  各区間は `{ kind, owner, start, end }` で、`owner` は `human` / `ai`、今いる区間は `end: null`。
  起票・着手・`## レビュー` の各エントリ・PR の Ready / Draft へ戻す / マージの時刻から毎回導出し、保存しない。
  差し戻しがあれば同じ `kind` が何度も現れる。`ai-board status --json` の `cards[]` も同じものを持つ

ステージを直接指定する入力口は無い。`POST /api/cards/:id/reviews` はゲート（`plan` / `verify`）・種別・理由文を
受け取って本文へ追記するだけで、列は次の `GET /api/board` で導出し直される。
種別は 承認 / 否決 / 中止 だけを受け付け、AI の種別（提出 / 再提出 / 保留）は 400 を返す。
否決に理由文が無ければ 400 を返す。

## 開発

```bash
npm test              # vitest（unit + supertest による API e2e）
npm run test:coverage # カバレッジ（閾値 80%）
npm run lint
npm run typecheck
npm run format:check  # Prettier（崩れていたら npm run format）
npm run build
npm run dev           # サーバのみ（tsx watch）
npm run dev:web       # Vite dev サーバ（/api を 5673 へプロキシ）
```

CI（`.github/workflows/ci.yml`）は PR と main への push で typecheck / lint / format:check /
test:coverage / build を走らせる。PR のレビューだけに効く指示は `REVIEW.md` にある。

### Claude Code のプレビュー

Claude Code のプレビューが読む `.claude/launch.json` は各自の設定で、git に載せない。
`.claude/launch.example.json` をコピーして使う。

```bash
cp .claude/launch.example.json .claude/launch.json
```

サンプルには 3 つの起動設定がある。

| 名前       | 起動するもの                                   | ポート     |
| ---------- | ---------------------------------------------- | ---------- |
| `server`   | `npm run dev`（サーバのみ）                    | 5673       |
| `web`      | `npm run dev:web`（Vite）                      | 5674       |
| `worktree` | `node dist/index.js`（ビルド済みの画面を配信） | 空きポート |

`worktree` は、他のセッションが 5673 / 5674 を使っているときのためのもの。
Vite のプロキシ先は 5673 に固定されているので、サーバ 1 本で画面まで配信する。
`tsx` で起動すると `src/web`（ビルド前のソース）を配信して画面が白くなるため、
先に `npm run build` を走らせる。コードを直したら、ビルドし直すまで画面には反映されない。
