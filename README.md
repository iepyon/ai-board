# ai-board

プランニングファイル駆動の開発のためのボード。`ai-board` の CLI とチャット（Claude Code のスキル）と、`ai-board status --html` のダッシュボードで扱う。

`.ai-board/plans/` とレビュー要求（GitHub の Pull Request）を読んで各カードのステージを自動導出する。
`stage` という値はどこにも保存しない。人の判断（着手・承認・否決・中止）も
カード上の痕跡として残り、それも導出の入力になる。

```
[ アイデア ] [ 計画提案中 ] [ 計画レビュー ] [ 実装中 ] [ PR中 ] [ マージ済み ]
     人            AI            人 ★          AI        人 ★        —
```

★ が人の判断を待つゲート。計画レビューでは計画を読む。PR中 では、AI が PR の本文に書いた動作確認の結果（動かした手順と結果）を読み、
必要ならブランチを動かして振る舞いを確かめ、それからコードの差分を読む。
PR に指摘（コメント）を書くと、AI が Ready のまま修正を push するか、直すものが無い理由を返信して、また人の番に戻る。
人が動かすのは `アイデア ⇄ 計画提案中` の 1 遷移だけ（着手）で、あとは AI が右へ進め、★ で止まる。

かつては React の画面と、それを配るサーバ（HTTP API・SSE・GitHub のポーリング）があったが、考えることを減らすためにいったん外した。
画面は後でゼロから作り直す（[ADR 0017](docs/adr/0017-remove-web-and-server.md)）。

## ボードの見方

ボードは `ai-board status` で読む。人向けの数行（`status`）、ループや手順書が読む JSON（`status --json`）、
ダッシュボードの 1 枚の HTML（`status --html`。チャットで「ボードを見せて」と頼むと `board-dashboard` のスキルが Artifact として公開する）の 3 つの形がある。
どれも同じ導出の結果を、次の区画に振り分けて出す。区画はステージの見せ方の振り分けで、導出の規則には関わらない。

| 区画                   | 入るカード                                                                       | 並び                   |
| ---------------------- | -------------------------------------------------------------------------------- | ---------------------- |
| 判断待ち（`waiting`）  | 計画レビュー / PR中、止まっている 計画提案中 / 実装中                            | 待ち始めた時刻の古い順 |
| AI 作業中（`working`） | 計画提案中 / 実装中（止まっているものを除く）と、人の指摘に AI が応える番の PR中 | PR中 を先頭に、`rank`  |
| アイデア（`ideas`）    | アイデア（区切り線で上下に分ける）                                               | `rank`                 |
| マージ済み             | マージ済み                                                                       | マージの新しい順       |
| 中止                   | 最新のレビューエントリが中止のカード                                             | `rank`                 |

判断待ちのカードには、止まった理由（人が何をすればよいか）と、出せる判断（`decisions`）が付く。
AI 作業中のカードは、計画ファイルが 3 日更新されないと「動きなし」（`stale`）になる。
ループの様子は「ループ: <カード> を <手> 中（12 分）」「ループ: 最後の手から 40 分」「ループ: 記録なし」の 1 行で出る（後述の「ループの 1 手の記録」）。

**止まっているカード**は、AI の列（計画提案中 / 実装中）にいるが人の判断を待っているカードである（後述の「止まり」）。
人の判断は、チャットで頼んで `board-decide` のスキルに書かせるか、`ai-board decide` で書く（後述の「チャットから判断する」）。
出せる判断はカードによって変わる。

| カード                                       | 出せる判断                     |
| -------------------------------------------- | ------------------------------ |
| アイデア                                     | 中止                           |
| 計画レビュー                                 | 承認 / 否決して差し戻す / 中止 |
| 実装中で止まっている（Draft へ戻された）     | 計画から立て直させる / 中止    |
| 計画提案中で止まっている（plan 保留）        | 計画を直させる / 中止          |
| 計画提案中で止まっている（成果物が見えない） | 中止                           |
| PR の状態を引けない                          | 出さない                       |

「否決して差し戻す」「計画から立て直させる」「計画を直させる」はどれも plan の否決として `## レビュー` に追記され、理由が必須。
飛ばす宣言のあるゲートでも同じ判断を出す（宣言があっても、人の否決はふつうに差し戻しになるため。後述のスキップ）。
PR中 のカードは GitHub で PR をマージして判断するので、判断は出さない。
アイデアの中止は判断を待っているのではなく、要らなくなったアイデアを中止の区画へ片付けるためのもので、判断待ちの区画には出ない。

## なぜ必要か

AI エージェントと開発を回すとき、作業の実態は複数の場所に散らばる。

| 情報               | 所在                                        |
| ------------------ | ------------------------------------------- |
| アイデア・調査メモ | `origin` の `ai-board/data` ブランチ（git） |
| 計画とタスクの進捗 | `.ai-board/plans/<id>.md`                   |
| PR のレビュー      | GitHub                                      |
| 完了               | `.ai-board/plans/archive/`                  |

どれも見ようと思えば見られるが、アイデアから完了までを一本のパイプラインとして
俯瞰する手段がない。ai-board はその欠けたビューを埋める。

**そして「いま誰の番か」を可視化する。** 人が判断すべき 2 点（計画レビュー・PR）で
列が止まり、それ以外は AI が右へ進める。

## 使い方

動かすには Node 24 以上が要る（なるべく 24 系の最新を使う）。

```bash
npm install
npm run build

# .ai-board/ を持つプロジェクトのルートで読む
node dist/cli.js status --root /path/to/your-project
```

```
使い方: ai-board <command> [--root <path>]

Commands:
  card <command>      カードの読み書き
  status [--json [--only <項目,...>] | --html]
                      ボードの状態と次の一手
  init                空のデータ用ブランチを作る
  pr <command>        PR の読み書き（gh api の REST）
  decide <command>    人の判断を書く（人と、人が会話で頼んだ Claude だけ）
  loop <start|finish> ループの 1 手の記録を書く（ループだけが使う）
  dist-check          dist/ が HEAD のコミットより古いかを確かめる
```

引数なしの `ai-board` は使い方を出して終わる。常駐するサーバは無い。

## ステージの決まり方

以下を**上から評価し、最初に真になったもの**を採用する（＝最も進んだステージ）。
手動上書きの仕組みは無い。

| #   | stage         | 条件                                                                 |
| --- | ------------- | -------------------------------------------------------------------- |
| 1   | `merged`      | 計画が `.ai-board/plans/archive/` にある、**または** PR が merged    |
| 2   | `pr`          | PR が存在し opened、かつ Draft でない                                |
| 3   | `impling`     | plan ゲート通過済み                                                  |
| 4   | `plan-review` | `.ai-board/plans/<id>.md` か Draft の PR があり、plan ゲートが未判断 |
| 5   | `planning`    | `startedAt` が非 null                                                |
| 6   | `idea`        | 既定                                                                 |

計画と実装は同じ 1 本の PR に載る。AI は計画をコミットした時点で Draft の PR を出し、
人はその PR で計画を読んで、チャットで頼むか `ai-board decide` で承認 / 否決する。
実装と AI レビューを終えた AI は、PR の CI が通るのを確かめ（赤なら直す）、動かした手順と結果を PR の本文の `## 動作確認の結果` に表で書き、計画を archive して PR を Ready にする（`pr` へ）。
人は PR中 で、その証拠を読み、必要ならブランチを動かし、差分を読んでマージする。

実装中の PR も Draft だが、計画レビューへは巻き戻らない。
Draft の PR が立てる `plan-review` のルールは plan ゲートが未判断のときにしか当てはまらず、
plan が承認済みのカードは 3 で決まるため。

**否決の差し戻しに専用のルールは無い。** ゲートが「差し戻し中」のとき
その工程のレビュー行と承認行が両方外れ、1 つ手前の列へ自然に落ちる。

かつては 実装中 と PR中 の間に「動作確認」（`verifying`、verify ゲート）の列があり、人を 2 回待っていた。
AI が動かした証拠を PR の本文に書けば、人は PR中 の 1 回の中で「動かす → 差分を読む」の順を守れるので、列をまとめた（`docs/adr/0005-verify-in-pr.md`）。

### レビューログ

人の判断はカード本文の `## レビュー` に追記される。ゲートは計画を読む `plan` の 1 つ。
種別は 提出 / 再提出 / 保留（AI が書く）と 承認 / 否決 / 中止（人が書く）の 6 つ。
保留は、AI が否決を自分では直しきれずに止まった痕跡である（後述の「止まり」）。

```markdown
## レビュー

### 2026-09-11T04:00:00.000Z plan 提出

### 2026-09-11T05:12:00.000Z plan 否決

既存の stage-resolver を見ていない。導出ルールとの整合を調べ直して。

### 2026-09-11T09:30:00.000Z plan 再提出

### 2026-09-11T10:00:00.000Z plan 承認
```

ゲートの状態は、そのゲートの最新エントリ 1 件で決まる。書式の壊れた見出しは黙って無視する
（カードは人が直接編集してよいファイルなので、手書きの揺れでボードが読めなくなるほうが害が大きい）。

中止のエントリはゲートの判定から除く。中止は工程の進捗とは直交する終端の軸であり、
通過済みのゲートを巻き戻さない。

最新が 保留 のゲートは `held` になる。どの規則も `held` でゲートを先へ進めないので、
保留のカードは AI の列（計画提案中 / 実装中）に留まる。
人が後から承認 / 否決 / 中止を書けばそれが最新になり、保留は自然に外れる。

`pr` ゲートはレビューログを持たない。PR の承認とマージは GitHub 側の実態そのもので、
カード本文に写す必要が無いため。

かつては `explore` ゲート（探索レビュー）と `verify` ゲート（動作確認）もあったが、どちらも列とともに廃止した。
既存のカードに残る `explore` / `verify` のエントリ（判断のファイルを含む）は規定外のゲートとして黙って無視され、
`skipGates` に残る `explore` / `verify` は読むときに落とす。記録は消さない。

### 止まり

AI の列（計画提案中 / 実装中）にいても、人の判断を待っているカードがある。これを**止まり**と呼ぶ。
止まりはステージとは別の軸の派生値で、どこにも保存しない。ステージは「工程のどこにいるか」、止まりは「その工程で誰を待っているか」を表す。
止まっているカードは判断待ちの区画に出て、AI ループはそのカードを選ばずに後ろのカードへ進む。

| 止まり                                                  | 列         | 人がすること                                         |
| ------------------------------------------------------- | ---------- | ---------------------------------------------------- |
| 人の判断の後に、PR が Draft に戻された                  | 実装中     | GitHub で Ready に戻す / 計画から立て直させる / 中止 |
| AI が `plan 保留` を書いた                              | 計画提案中 | 計画を直させる / 中止                                |
| 計画を提出したのに計画ファイルも Draft の PR も見えない | 計画提案中 | 中止                                                 |
| そのカードの PR の状態だけを GitHub から引けない        | どの列でも | 時間を置く。続くなら GitHub で PR を確かめる         |

成果物が見えない止まりは、PR の状態を引けているとき（GitHub に接続し、初回の取得を終えたとき）にだけ立つ。
引けていなければ、PR が無いのか分からないためである。
PR の状態を引けない止まりは、1 枚の PR だけが引けない（422 など）ときに、そのカードにだけ立つ。
GitHub の接続は「接続済み」のままで、ほかのカードは進む。列は前に引けた PR の状態で決め、出せる判断も戻せる列も無くし、`ai-board decide` もそのカードの判断と着手 / 着手を戻すを拒む。
理由にはカード・PR 番号・問い合わせ先・HTTP のステータスが出る（GitHub の応答の本文は資格情報が混じりうるので出さない）。次に引ければひとりでに外れる。
`gh` が無い・ネットワークが切れた・認証や上限（401 / 403 / 429）・GitHub の障害（5xx）は全体の失敗で、今までどおり接続がエラーになり、ループは止まる。
Draft に戻された止まりは、AI が Ready にした PR を人が PR中 で Draft に戻したときに立つ。止めないと、計画は archive 済みなので、ループが Ready に戻してしまう。
PR中 で小さな指摘を AI に直させたいときは、PR にコメントを書けばよい（後述の「PR の指摘に AI が応える」）。
計画から作り直させたいときは、PR を Draft に戻して「計画から立て直させる」を押す。

#### PR の指摘に AI が応える

PR中 のカードで、人の最新のコメントが、ブランチの最新コミットとも AI の最新のコメントとも後にあるとき、カードは「AI が進めている」区画の先頭に移る。
ステージは PR中 のままで、件数帯の PR中 のマスは今までどおり判断待ちの区画へ飛ぶ。
ループはこのカードを最優先で選び、`fix-pr` の手で、PR を Ready のまま修正を push するか、直すものが無い理由を 1 件だけ返信する。
どちらでも時刻が逆転し、カードは判断待ちの区画に戻る（push なら「再レビュー待ち」、返信なら「AI が指摘に返信しました」）。

- AI のコメントは、本文末尾の Claude Code のフッター（`_Generated by [Claude Code](https://claude.ai/code)_`）で見分ける。
  PR もコメントも人のアカウントで書かれるので、ユーザーでは見分けられない。フッター付きのコメントは指摘の件数に数えない。
  `ai-board pr comment` は、本文にフッターが無ければ末尾に足す
- 質問や「LGTM」のコメントも指摘として扱う（GitHub の Request changes は自分の PR に付けられず使えない）。直すものが無ければ AI が返信して戻す
- 理由と退けた案は [ADR 0016](docs/adr/0016-pr-feedback-ai-turn.md) にある

PR の `draft` だけでは「まだ一度も Ready にしていない」と「人が Draft に戻した」を見分けられない。
そこで GitHub の PR のイベントから、最後に Draft へ戻された時刻（`convert_to_draft`）を引く。
作成時から Draft の PR はこのイベントを残さないので、実装を進めるあいだの Draft では止まらない。
戻された時刻がカードの最新のレビューエントリより新しいときに止まる。

人が承認 / 否決 / 中止を書けばそのエントリが最新になり、止まりは外れる（PR の状態を引けない止まりを除く）。止まりを解く専用の操作は無い。

### スキップ

frontmatter の `skipGates` に書いたゲートでは、AI の 提出 / 再提出 を人の承認と同じに読む。
小さいカードを夜間に `/loop` で流したいときに使う。AI が提出した時点でゲートを通るので、カードはそのレビュー列に滞留しない。
否決 / 保留 / 承認 はふつうに効き、人は後から否決して差し戻すこともできる。エントリが無ければ、宣言があっても未提出のままである。

宣言は、チャットで頼むか `ai-board decide skip <id> --gate plan [--remove]` で出し入れする。

- **計画レビューを飛ばす**（`plan` を入れる）: 宣言を入れても、着手するまではアイデアに留まる。
  着手すると計画提案中に入り、AI が計画を書いて Draft の PR を出す。AI が `plan 提出` を書いた時点で、計画レビューを通らずに実装中へ進む。
  提出済みのカードに宣言を入れるとその場で実装中へ進み、実装中のカードから外すと plan ゲートが提出済みに戻って実装中から外れる

宣言は人が書くもので（`ai-board decide skip`。チャットからは後述の `board-decide` が書く）、`ai-board card` には入口が無い。
AI の `plan 提出` / `plan 再提出` は着手したカードにしか書けないので、AI が宣言を使って人の着手を飛ばすこともできない。
また、plan ゲートが未提出か否決のときにしか書けないので、AI が計画を出し直して人の否決や保留を打ち消すこともできない。

### 誰が動かせるか

| 列                    | ステージを立てるもの                                                   | 誰の領分か                     |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------ |
| アイデア / 計画提案中 | `startedAt` の打刻                                                     | 人                             |
| 計画レビュー          | 計画ファイル / Draft の PR                                             | AI                             |
| 実装中                | `## レビュー` の plan 承認（plan を飛ばすカードは plan 提出 / 再提出） | 人（plan を飛ばすカードは AI） |
| PR中                  | PR が Ready で opened                                                  | AI                             |
| マージ済み            | 計画の archive / PR の merged                                          | AI                             |

**人が動かせるのは `アイデア ⇄ 計画提案中` の 1 遷移だけ。**
`ai-board decide start`（着手）と `ai-board decide unstart`（着手を戻す）がこれにあたり、`startedAt` を書き換える。
承認 / 否決 / 中止 は `ai-board decide approve / reject / abort` で行い、`## レビュー` への追記になる。
否決には理由文が必須（空の否決は AI が次の周回で読むものを持たない）。

さらに、**動かせる先はカードごとに違う**。`startedAt` を外したときに残るステージ
（AI の成果物と人のレビュー記録が課す下限）より前へは戻せない。

| 下限               | 手で入れられる列       |
| ------------------ | ---------------------- |
| `idea`             | アイデア / 計画提案中  |
| `plan-review` 以降 | なし（着手を戻せない） |

### その他の設計上の判断

- **AI レビューに専用の列は作らない。** 実装中の内部工程として扱う。tasks の進捗は
  カードの `plan.tasks` に出るだけで、ステージを立てる入力には使わない。
  AI レビューの直す指摘も計画のチェックボックスとして書かれるので、進捗に数えられるだけでステージは動かさない。
- **レビュー後の修正は `pr` 列内のバッジ。** 「AI が指摘を受けて修正を push した」を
  最新コミットと最新レビューコメントの時刻比較で判定し、再提出済みとして示す。
  新しいレビューコメントが来れば日時比較が逆転し、自然にバッジが消える。
- **否決からの復帰は AI の「再提出」追記で表す。** ファイルの mtime 比較は成立しない
  （レビュー記録を書く行為そのもので mtime が動くため）。
- **中止に専用の列は作らない。** マージ済みとは意味が違うので混ぜない。
  判断待ち・AI 作業中・アイデアからは外し、中止の区画に寄せる。

## カード

カードの正本は `origin` の `ai-board/data` ブランチ（データ用ブランチ）にあり、`cards/<id>/` の 1 ディレクトリが 1 カード。
データ用ブランチはコードの履歴と交わらない orphan のブランチで、clone した時点でカードが揃う。
判断は `cards/<id>/log/` に 1 件 1 ファイルで、並び順と区切り線は `order.yaml` に置く。
手元では、CLI がメインのチェックアウトの `.ai-board/data/` にデータのワークツリーとして展開し、
書き込みのたびにコミットと push をする（全ワークツリーで 1 つのバックログを共有する。後述）。
`id` は不変で、`branch` / `mr` が進行に応じて後から埋まる。
これによりアイデアメモ → 計画 → ブランチ → PR → archive が 1 本の線でつながる。

`ai-board card show <id>` は、カードを次の Markdown の形で出す。

```markdown
---
id: refresh-token # 不変。生成後は変えない
title: リフレッシュトークン対応
created: 2026-09-01T09:00:00.000Z
startedAt: '2026-09-01T10:00:00.000Z' # 人が着手を指示した時刻
skipGates: [] # 人が事前に見ないと宣言したゲート（plan）
branch: feat/refresh-token
mr: 42 # GitHub の PR 番号（branch から自動解決して書き戻す）
```

### カードを書く経路

人は `ai-board decide`（チャットからは `board-decide`）で、エージェントは `ai-board card` の CLI から書く。
CLI はデータ用ブランチを取り直してから読み書きする。
書き込みは「取り直す → 検査する → コミットする → push する」を 1 つの操作として行い、push が拒否されたら取り直して頭からやり直す。
クラウドのセッションなどほかの場所からの書き込みは、次に CLI を動かしたときの取り直しで拾う。
データのワークツリーのファイルを直接書き換えたり、データ用ブランチへ直接 push したりはしない（`.claude/settings.json` の deny ルールでも止めている）。

```bash
ai-board card list                         # 一覧（JSON、本文なし、rank 順）
ai-board card show <id>                    # 1 枚を Markdown で
ai-board card create --title <t> [--id <id>] < body.md
ai-board card seed --from <dir>            # <dir> の *.md のうち、まだ無いカードだけを起票（研修の題材の取り込み。既にある ID は飛ばす）
ai-board card body <id> < body.md          # 本文の差し替え
ai-board card branch <id> <name>           # ブランチの紐付け（--clear で外す）
ai-board card submit <id> [--gate plan] [--resubmit] [--reason <text>]   # 提出 / 再提出（ゲートは plan だけ）
ai-board card hold <id> --gate plan --reason <text>   # 保留（否決された計画を直しきれずに止まるとき。理由は必須）
ai-board status [--json [--only <項目,...>] | --html [--session <id>]]   # 導出したステージ・判断待ち・次の一手（--html はダッシュボード）
ai-board dist-check                        # dist/ が HEAD のコミットより古いか（古ければ終了コード 1。手順書がビルドの要否に使う）
```

`ai-board card` にはエージェントに許す操作しか無い。`startedAt`・`rank`・`skipGates` の書き換えと、
承認 / 否決 / 中止の追記は、人の判断を書く `ai-board decide`（後述の「チャットから判断する」）からだけ行える。
逆に、`ai-board decide` からは AI の種別（提出 / 再提出 / 保留）を書けない。
`hold` は、そのゲートの最新の判断が 否決 のときにしか書けない（否決を直す手で止まるときだけ使うため）。
承認済みのゲートに保留を書いて人の承認を打ち消したり、計画レビューで人を待つカードを AI の列へ落としたりはできない。
`submit` の plan ゲートは、着手したカードで、plan が未提出か否決のときにしか書けない。
`body` は `## レビュー` のエントリが変わる差し替えを拒否するので、本文の差し替えで
人の判断を書き換えることもできない。`## レビュー` の節の無い本文は「判断は変えない」として受け付け、本文だけを書く。
`submit` / `hold` の `--reason` に判断の見出し（`### <時刻> <gate> <種別>`）の形の行を書いても、判断は指定した 1 件だけが増える
（判断は値のまま `log/` に書かれ、その行は `####` へ下がって理由の一部として見える）。`ai-board decide` の判断の理由でも同じである。

### チャットから判断する

`.claude/skills/board-decide/SKILL.md` は、人がチャットで頼んだ判断を、Claude が `ai-board decide` の CLI で代わりに書くスキル。
「chat-decide の計画を承認して」「否決して、理由は〜」「loop-activity を一番上へ」のように頼むか、`/board-decide` で呼ぶ。

```bash
ai-board decide approve <id> [--reason <text>]     # plan を承認する
ai-board decide reject <id> --reason <text>        # plan を否決する（理由は必須）
ai-board decide abort <id> [--reason <text>]       # 中止する
ai-board decide start <id> / unstart <id>          # 着手する / 着手を戻す
ai-board decide skip <id> --gate plan [--remove]   # 計画レビューを飛ばす宣言を入れる / 外す
ai-board decide move <id> --after <ref> --before <ref>   # アイデアの並べ替え（<ref> はカード ID・:divider・none）
ai-board decide move-divider --after <ref> --before <ref>   # 区切り線を動かす
```

`ai-board decide` はコミットして push する。
書く前にボードを導出し、出せない判断（判断を待っていないカードの承認、計画レビューのカードの着手を戻すなど）は拒む。
GitHub に繋がらないときは、PR の状態が引けず出せる判断や戻せる列を取り違えるので、承認 / 否決 / 中止と着手 / 着手を戻すを拒む（宣言・並べ替えは書く）。
誰が呼んでも書けるので、人の判断の守りは「人がこの会話で自分の言葉で頼んだときだけ使う」という手順書の決まりにある（[ADR 0007](docs/adr/0007-board-decide.md)）。

- できること: 承認 / 否決 / 中止、着手 / 着手を戻す、計画レビューを飛ばす、アイデアの並べ替え（区切り線の移動を含む）
- 承認 / 否決 は、頼まれたカードと判断が 1 つに決まれば確かめずに書き、書いた中身を伝える。否決の理由は人の言葉をそのまま送る。
  ただし人の言葉が会話の中にしか無いもの（Claude が示した案の記号、「さっきの」）を指すときは、Claude が会話を引き継がない者にも読める文面に起こし、
  その文面と「人の言葉のまま」を選択肢にして人に選んでもらってから送る。
  中止 / 着手を戻す は、送る中身を見せて 1 回確かめてから書く。
  計画レビューのカードに「計画レビューを飛ばす」を入れるときも、待っている提出がその場で承認と読まれるので確かめる
- 対象を言わずに頼むと（「判断待ちを見せて」、引数なしの `/board-decide`）、判断待ちのカードと出せる判断を並べて選ばせる
- 書いた判断で AI の番ができたら、頼み直さなくても同じセッションで `board-loop` の 1 周が続き、次の 1 手が進む。
  着手・承認（と、待っている提出を承認と読ませる宣言）は確かめずに続け、否決は「続けて直す / 待つ」を 1 回聞く
  （`## レビュー` は追記専用なので、理由を言い直したいときの間を残す）。中止・着手を戻す・並べ替えの後は続けない。
  「書くだけ」「進めないで」と言えば続けない。`next` が判断したカードと別のカードを指すときも `next` に従い、進めたカードの名前をはっきり伝える
- 出せる判断とアイデアの並びは `ai-board status --json` から読む（`decisions` / `ideas`）
- 使うのは人が頼んだときだけ。`board-reviewer` は `ai-board decide` もこのスキルも使わず、ループも周の中では使わない

### AI ループ

`.claude/skills/board-loop/SKILL.md` は、ボードを読んで AI が進めてよいカードの次の 1 手を、動かしたセッションが自分で進めるスキル。
手ごとの手順は隣の `plan.md`（計画の手）と `implement.md`（実装の手）と `fix-pr.md`（PR の指摘に応える手）にある。AI レビューの段だけは、`board-reviewer` のサブエージェントに切り分ける。
`/loop 5m /board-loop` で間隔運転する。

- 何をするかは `ai-board status --json` の `next` が決める。優先順は PR中（人の指摘に AI が応える番のものだけ）→ 実装中 → 計画提案中、同じ列の中は `rank` の順
- 1 手は次の 4 種類のどれか。計画提案中のカードには `plan` / `revise-plan`、実装中のカードには `implement`、人の指摘を受けた PR中 のカードには `fix-pr`

  | 手            | 選ばれるとき                   | すること                                                                                                                                                                                                                    |
  | ------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `plan`        | 計画提案中で、計画がまだ無い   | 計画を書いて Draft の PR を出し、`plan 提出` を書く                                                                                                                                                                         |
  | `revise-plan` | 計画提案中で、計画が否決された | 否決の理由を読んで計画を直し、`plan 再提出` を書く                                                                                                                                                                          |
  | `implement`   | 実装中で、止まっていない       | 計画の状態から決まる段を進める（下の表。タスクを倒す段から、AI レビューの後なら締めの段まで続けて進むことがある。レビューの段の前で手を終える）。最後の段で動かした証拠を PR の本文に書き、計画を archive して Ready にする |
  | `fix-pr`      | PR中 で、人の指摘に応える番    | PR を Ready のまま修正を push する（CI も確かめる）か、直すものが無い理由を `ai-board pr comment` で 1 件返信する                                                                                                           |

  かつては動作確認の否決を直す `revise-impl` と、動作確認の後に Ready にする `ready` もあったが、動作確認の列とともに廃止した（ループの記録に残る過去の手は、ログにそのまま出る）。

  `revise-plan` で否決を直しきれないとき、ループは何も直さず `ai-board card hold` で 保留 を書いて止まる。
  前の plan 承認がある否決（人が「計画から立て直させる」を選んだもの）の `revise-plan` では、作り直すタスクの `[x]` を外すか新しいタスクを足し、
  計画の `## AI レビュー` 節を消す（残っていると、作り直した実装の AI レビューが飛ばされる）

- `implement` の手では、`status` がカードのブランチの計画を `git show` で読んで段を決め、`next.step` に載せる。
  ループは `next.step` で、自分で進めるか `board-reviewer` を立てるかを決める。段は手の種類（`next.action`）を増やさず、`implement` の中の区切りとして扱う

  | 計画の状態                                | `next.step` | 段             | 進める者         | すること                                                                                                                                       |
  | ----------------------------------------- | ----------- | -------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
  | `plans/archive/` にある                   | `close`     | archive 済み   | 本筋のセッション | 前の周で `ai-board pr ready` だけが失敗している。`ai-board pr ready` だけをやり直す                                                            |
  | 未チェックのタスクがある                  | `task`      | タスクを倒す段 | 本筋のセッション | 残りの節を上から順に倒し、節ごとに 1 つのコミットにする。`## AI レビュー` 節が無ければレビューの段の前で手を終え、あれば同じ手で締めの段へ進む |
  | 全部倒れていて、`## AI レビュー` 節が無い | `review`    | レビューの段   | `board-reviewer` | 計画の末尾に `## AI レビュー` 節を書き足す。コードは直さない                                                                                   |
  | 全部倒れていて、`## AI レビュー` 節がある | `close`     | 締めの段       | 本筋のセッション | 動かして確かめ、PR の本文に `## 動作確認の結果`・`## 判断してほしいこと`・`## 見送った AI レビューの指摘` を書き、計画を archive して Ready    |
  | 読めなかった（ブランチが無い など）       | `null`      | —              | 本筋のセッション | ワークツリーに入って計画を読み、タスクを倒す段か締めの段なら進める。レビューの段なら何も変えずに止まる                                         |

  ブランチはローカルのものがあればそれを、無ければ `origin` の追跡ブランチを読む。`status` は `git fetch` をしないので、段が古いことがある。
  ループはワークツリーで計画を読み直し、段が食い違えば何も変えずに `止まった` で手を終える（次の周で読み直す）。
  `board-reviewer` は本筋のセッションが直接立てるので入れ子にならず、クラウドのセッションでも手元と同じ手順で回る

  節は、計画の `## タスク` を `### <番号>. <題>` の見出しで区切った範囲で、最初の未チェックのタスクから上へたどった最初の見出しから、次の見出しの手前までである。
  計画は、その節までを倒し終えたら品質ゲートが通るところで区切り、どこで区切るかは計画レビューで人が確かめる。
  `implement` の手は残りの節を上から順に倒す。節の途中ではゲートを走らせず（テストが落ちていてもよい）、節の終わりごとにゲートを通して 1 つのコミットにし、push する。
  節は止まってよい区切りで、自動の要約が入ったときなどは節の区切りで手を終え、次の周が計画の `[x]` とコミットから続きの節を選ぶ。
  節の終わりでゲートが通らず、原因がタスクの順番なら、未チェックのタスクを別の節へ移す・隣り合う節を合わせる・節の中で並べ替える、だけをしてよい（タスクの文は変えない）。
  節に区切っていない計画では `## タスク` 全体が 1 つの節になり、`## AI レビュー` 節の直す指摘も 1 つの節として 1 回でまとめて倒れる

  `board-reviewer` は、指摘を「直す」（`- [ ]`）と「見送る」（チェックボックスの無い `### 見送った指摘`、理由付き）と「人に判断してほしい」（`### 人に判断してほしいこと`）に分ける。
  直す指摘は普通のタスクとして次のタスクを倒す段で倒され、ボードの進捗バーにも乗る。倒し終えたら、同じ手のまま締めの段へ進む。指摘が無ければ「指摘なし」と書く。
  AI レビューは 1 回だけで、指摘を直した後にもう一度レビューはしない。

- 止まっているカード（前述の「止まり」）は選ばず、後ろのカードへ進む。止まっているカードは `status` の `waiting` に出る。
  人が PR を Draft に戻したカードを、ループが Ready にし直すことは無い
- 計画レビューのカードには触らない。PR中 のカードには `fix-pr` の手でだけ触り、修正の push と返信 1 件のほかはしない。
  着手・承認・否決・中止・並び順・マージは人に任せる
- GitHub に接続できないとき（`github:` が無いときも含む）は何もせずに止まる。PR の状態が引けないと、人を待つカードが AI の列に落ちて見えるため

ループを回すセッション（本筋のセッション）が、計画・実装・締めの手を自分で進める。
別の文脈に切り分けるのは AI レビューだけで、`next.step` が `review` のときに `.claude/agents/board-reviewer.md` のサブエージェントを 1 つ前景で立て、
カード ID と `$MAIN` の 2 行だけを渡す。実装を書いたセッションが、自分の差分を審査しないためである。
なぜこの形にしたか、退けた案（監視役と 3 役のサブエージェント、レビューを別のセッションで行う）は [ADR 0011](docs/adr/0011-loop-single-session.md) にある。

- 手を終えたら、次の cron の周を待たずに同じ手番で `status` を読み直し、次の手へ進む。実装 → AI レビュー → 指摘の修正 → 証拠を書いて Ready が続けて流れる。
  `止まった` か `next` が null になるまで続き、次の一手が別のカードでも同じセッションのまま続ける
- カードの前提は、カード本文・計画・PR から読み直す。前のカードで決めたことを持ち込まない
- 人がチャットで頼んだ判断（着手・承認など）で AI の番ができたときも、頼み直さなくても `board-decide` の後に 1 周が続く（「チャットから判断する」）。
  間隔運転（`/loop 5m /board-loop`）は、人のいない間に止まりを拾う保険として使う。間隔運転の周は手番が終わるまで待って届くので、手の途中には割り込まない
- 別のセッション（別の端末の間隔運転など）が同じカードの手を進めている（そのループの終わっていない記録がある）ときは、その周は何もせずに伝える

`status` を読むには、メインのチェックアウトのコードが `ai-board status` を持っている必要がある。

#### ループの 1 手の記録

ループは、手を始める前に `ai-board loop start` で開始を、手を終えたら `ai-board loop finish` で終了・結果を書く。
時間は `finish` が開始から終了までの時間で埋める（`--duration-ms` を渡したときはその値）。
トークンは、`--tokens` が無ければ `finish` が Claude Code の会話の記録（`~/.claude/projects/*/<セッション ID>.jsonl` とサブエージェントの記録。`CLAUDE_CONFIG_DIR` があればその下）から、
開始から終了までの assistant のメッセージの入力・キャッシュの書き込み・キャッシュの読み出し・出力を足して埋める。記録が見つからなければ「—」と出る。
`start` は、`--root` の `.claude/HARNESS_VERSIONS.md` の先頭の版（例: `v1`）を手順書の版として残す（無ければ「版なし」）。
作業者の欄は、レビューの段だけ `board-reviewer-…` の名前で、本筋のセッションが自分で進めた手は「—」である。理由は [ADR 0014](docs/adr/0014-loop-step-record.md)。
1 手の記録はデータ用ブランチの `loop/` に 1 件 1 ファイルで置かれ、書くたびにコミットして push される（クラウドのセッションが片付けられても残り、別の端末のボードからも見える）。
ボードはこれを読んで、`status` の「ループ: …」の行、カードの `loopSteps`、ダッシュボードのループの手の表を出し、AI の区間を「ループが拾うまでの待ち」と「手を進めていた時間」に分ける。

```bash
ai-board loop start  --loop <id> --card <cardId> --action <手> [--step <task|review|close>] [--agent <name>]
ai-board loop finish --loop <id> --card <cardId> --result <advanced|held|stopped|failed|unknown> [--tokens <n>] [--duration-ms <n>]
```

- `--loop` はループの識別子で、ループは自分のセッション ID（`CLAUDE_CODE_SESSION_ID`）を渡す。並べて回すループを見分けるために持たせる
- `start` は、同じループに終わっていない記録が残っていれば「途切れた」（`interrupted`）で閉じてから新しい記録を作る
- `finish` は、そのループの終わっていない記録を埋める。無いか、`--card` が食い違えば拒む
- 書くのはループ（本筋のセッション）だけで、`board-reviewer` は使わない。CLI は `loop/` だけを書き、カードには書けない
- 記録はステージの導出にも次の一手にも使わない。`ai-board loop` が失敗しても、ループは 1 行で知らせて手を進め続ける

### ループの許可ルール

ループは、1 手のあいだに git・npm・`ai-board` の CLI を何度も呼ぶ。
**ループは auto モードで回すことを前提にしている。** auto モードでは、許可ルールに当たらない操作を自動許可の分類器が判定し、
読み取り・品質ゲート・`ai-board` の CLI・ふつうの commit や push はそのまま通す。
そこで `.claude/settings.json` の `permissions` には、分類器に任せると困るものだけを書いて同梱している。
理由と退けた案は [ADR 12](docs/adr/0012-loop-permissions.md) にある。

Claude Code は `deny` → `ask` → `allow` の順に照合し、どれにも当たらなければ auto モードでは分類器が判定する（ほかのモードでは確認が出る）。

| 段      | 入れるもの                                            | 当たったとき         |
| ------- | ----------------------------------------------------- | -------------------- |
| `allow` | 手順書が使うのに、分類器が既定で止める操作            | 確認なしで走る       |
| `ask`   | 手順書が使わないか、人が 1 回だけ行う、戻しにくい操作 | 毎回人に確かめる     |
| `deny`  | ハーネスの境界を壊す。人もループ中には使わない        | 確認を経ずに拒まれる |

- **`allow`:** 分類器が既定で止める操作のうち、手順書が使うものだけを置く。広げると、分類器が止めてくれる操作まで黙って通るので最小にする
  - `main` 以外への `git push --force-with-lease origin <branch>`（`git -C <path> ...` の形も）。ブランチを `origin/main` にリベースし直したときに要る
  - カードのワークツリーの中の取り消し（`git -C <path>/.claude/worktrees/<id> checkout -- .` / `clean -fd` の形だけ）。
    `implement` の手が節の変更を戻すときに使う。`-C` の無い形やメインのチェックアウトでは分類器の判定に回る
- **`ask`:** `git reset --hard`、`git branch -D` / `-d`、`git worktree remove`、`ai-board init`。手順書の 1 手の中では使わず、使うなら人が意図して 1 回行う。
  `deny` にしないのは、人がチャットで頼んだ正当な操作（「Windows で使う」の取り出し直しなど）まで止めないためである
- **`deny`:** データのワークツリーの編集とデータ用ブランチへの push、`main` への push、`--force` / `-f` / `+` の refspec での force push、`--mirror` の push、
  DB の直接操作（`sqlite3`）、メインのチェックアウトの `.claude/settings*.json` の編集
- **どこにも書かないもの:** 品質ゲート、`ai-board` の CLI（`card` / `pr` / `status` / `loop` / `dist-check`）、`npm --prefix <path> run build`、
  手順書が使うふつうの `git` の操作（`status` / `diff` / `log` / `commit` / `push origin <branch>` など）、ワークツリーの下の編集。
  auto モードの分類器がそのまま通すので、許可ルールでは重ねない。`gh`・`node -e`・`curl`・`git push` だけの形・`git rebase` も書かず、分類器の判定に任せる。
  手順書は PR の読み書きに `ai-board pr` を使い、push は `git -C "$WT" push origin <branch>` の明示の形にそろえている
  （`git push` だけの形は、上流が `origin/main` のままのブランチで `main` へ向かいうるため）

`--force-with-lease` は、リモートのブランチが手元の知っている位置から動いていれば push を拒むので、人や別のセッションが積んだコミットを黙って消さない。
`--force` は相手の位置を確かめないので禁じたままにし、`main` へは `--force-with-lease` でも `deny` が先に効いて通らない。
照合は前方一致なので、`deny` の force push の形は `--force` の後ろを空白か行の終わりで区切って書き、`--force-with-lease` に当たらないようにしている（`src/__tests__/claude-settings.test.ts` が守る）。

許可ルールは**うっかりの事故を止める保険で、境界そのものではない。** 前方一致の文字列の照合なので、`git -c x push --force`、`bash -c '...'`、環境変数を前に付けた形などで迂回できる。
境界の本体は今どおり、カードの書き込みは `ai-board card` の CLI の構造、人の判断は `board-decide`・`ai-board decide`・人の API を周の中で使わないという手順書の決まりに置く。
`main` を守るには、リポジトリの Settings → Branches で `main` にブランチ保護（直接の push と force push の禁止）を入れることを勧める。

- auto モード以外（既定のモードなど）で回すと、`allow` に無い操作のたびに確認が出る。ループを止めずに回すなら auto モードを選ぶ
- 手順書（`.claude/skills/`、`.claude/agents/`）に新しい操作を足して分類器がそれを止めるなら、その操作だけを `allow` に足す。止めないものは足さない
- 人ごとの設定（`~/.claude/settings.json`、`settings.local.json`）と `defaultMode` には触らない。どのモードで回すかは人が選ぶ

### クラウドのセッションで回す

手元の Mac を動かし続けなくても、Claude Code のアプリから立ち上げたクラウドのセッションでボードを回せる。
クラウドのセッションは毎回新しい clone から始まるが、カードはデータ用ブランチにあるので、clone した時点で手元と同じカードが見える。
常駐のサーバは無い（手元でも同じ）。

1. セッションを立ち上げたら、まず `npm ci && npm run build` で `dist/` を作る（clone には `dist/` が無い）
2. 会話で `/loop 5m /board-loop` を回す。これが主な回し方である。手の進め方とレビューのサブエージェントの立て方は手元と同じ
3. ボードを読むときは、会話で「ボードを見せて」と頼む。`board-dashboard` のスキルが `ai-board status --html --session <自分のセッション ID>` の出力を、
   ダッシュボードの Artifact として公開する。ダッシュボードは 3 つのタブに分かれる。集計もページも CLI が作り、同じデータからは同じページができる
   - **今**: 判断待ち・AI 作業中（今の手）・残っているアイデア（ボードの並びと区切り線のまま）。開いたままにして、自分の番が来たかを確かめる
   - **ログ**: ループの手（時刻・カード・手・結果・時間・トークン）と判断の記録（提出・承認・否決・保留など）を、新しい順の 1 本にしたもの（新しい 200 件まで）
   - **振り返り**: 主な数字（マージ済みの枚数、着手からマージまでの中央値と最長、人の番の割合、否決、アイデアの残り）、工程ごとの滞在時間と日ごとのマージ数のグラフ、
     ループの手の表、手順書の版ごとの表（1 手の時間・トークン・止まった割合・やり直し、カードの否決率・人を待った時間。列は版で、最後に「版なし」）、マージ済み・中止のカード。
     同じ手で 2 回以上止まり続けているカードには、今のタブと `ai-board status` の次の一手に `止まった ×N` の印が付く（数えて見せるだけで、止めはしない）
   - カードのタイトルは、GitHub 上のデータ用ブランチのカードのファイル（`cards/<id>/card.md`）へのリンクになり、本文を読める（`config.yaml` に `github.repository` があるとき）
   - 右上の「更新」のボタンを押すと、ページを公開したセッションに `Claude Code Remote` の `send_message` で決まった 1 文が届き、
     セッションが出し直して同じ URL に公開し直す。チャットに何も打たなくてよい（初回はコネクタの許可を聞かれる）
   - ボタンが使えないとき（手元のセッションで公開した、コネクタを許していない、セッションが応えない）は、チャットで頼む案内が出る。
     同じ会話で頼み直すと、同じ URL のまま新しいボードに書き直される
   - 判断のボタンは無い。判断は次のとおり会話で頼む。なぜボタンからセッションに頼む形にしたかは [ADR 0015](docs/adr/0015-dashboard-refresh-via-session.md)
4. 判断は会話で頼む（「〜の計画を承認して」など）。`board-decide` のスキルが `ai-board decide` で書く。
   判断で AI の番ができたら、頼み直さなくてもそのまま次の 1 手が渡る

クラウドでは GitHub の GraphQL が 403 になり、`gh pr` と `gh auth status` が動かない。
そのため手順書は PR の読み書きに `ai-board pr ...`（`gh api` の REST）を使い、GitHub の接続も `gh api` のリポジトリの取得で確かめる。
`ai-board pr ready` は、`gh pr ready` が失敗したらクラウドの `ccr/ready_for_review` の経路で Draft を外す。
`ai-board pr checks` は、クラウドでは Commit Status API（`commits/{sha}/status`）が権限で読めない（HTTP 403）ので、そのときは `check-runs` だけで判定し、読めなかったことを出す。

人が会話を開いていない間も止まっているカードを動かしたいときは、ルーティン（cron で動くクラウドのエージェント。間隔は最短 1 時間）で `/board-loop` を定期に走らせてもよい。
これは会話の `/loop` の保険で、主には使わない。ルーティンからの通知の設定はこのリポジトリでは扱わない。
ルーティンが重なって同じ手が 2 つ同時に走っても、カードの書き込みは push の拒否で 1 つにまとまる（後から来た提出は、取り直した状態で検査されて拒まれる）。

クラウドのセッションからはブランチを消せない。マージした PR のブランチが残らないよう、
人がリポジトリの Settings → General の「Automatically delete head branches」を有効にしておく。
これが消すのはマージした PR の head のブランチだけで、データ用ブランチ `ai-board/data` は PR の head にならないので消えない。

### Windows で使う

Windows では、Windows の Claude Code が使う Git Bash（Git for Windows に同梱）で、手順書（`.claude/skills/` と `.claude/agents/`）を書き換えずに回せる。
PowerShell や cmd は想定しない。

- `jq` は要らない。手順書は `ai-board status --json --only <項目,...>` で要る項目だけを出し、判断は `ai-board decide` の引数で渡す。
  `sed`・`grep`・`diff`・`curl` などは Git for Windows に同梱されている
- 改行コードは `.gitattributes`（`* text=auto eol=lf`）で LF に揃える。Git for Windows の既定（`core.autocrlf=true`）で clone しても、`npm run format:check` は落ちない。
  データのワークツリー（`.ai-board/data/`）も、`ai-board` が git に `-c core.autocrlf=false -c core.eol=lf` を付けて触るので LF のまま取り出される
- `.gitattributes` が入る前に clone した作業ツリーは CRLF のまま残る。未コミットの変更が無いことを確かめてから、取り出し直す

  ```bash
  git rm --cached -r . && git reset --hard
  ```

- テストは Windows を対象にしていない。POSIX 形式のパスや `chmod` を使うテストがあり、手元の `npm test` は落ちうる。
  CI は Windows を走らせていない

### ワークツリーではデータのワークツリーを共有する

`--root` がリンクされたワークツリー（`.git` がファイル）なら、git に載らない各自のファイルは
メインのチェックアウトのものを使う。ワークツリーごとにデータのワークツリーが分かれて、カードの変更が散らばらないようにするため。

| ファイル                                  | 置き場所                                                          |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `.ai-board/data/`（データのワークツリー） | メインのチェックアウト                                            |
| `data.lock`・`cache/`                     | メインのチェックアウトの `.ai-board/`（データのワークツリーの隣） |
| `config.yaml`                             | データ用ブランチの根（無ければメインの `.ai-board/config.yaml`）  |
| `.ai-board/plans/`                        | ワークツリー（`--root`）                                          |

計画ファイルは git でブランチに乗るので、ワークツリーのものを読む。
ワークツリーで `ai-board status` を走らせれば、そのブランチの計画を、メインと同じカードの上で読める。

環境変数 `AI_BOARD_DATA` を指定すると、データのワークツリーの代わりにそのディレクトリ（git のリポジトリ）を使う。
ai-board 自身をワークツリーで開発し、カードに書くコードやデータ用ブランチの形を変えるコードを動かすときは、これで別のディレクトリを指す。
指さなければ、試しの書き込みが本物の `origin` の `ai-board/data` に push される。
そのディレクトリの `origin` へ push するので、スクラッチパッドなどに作った bare リポジトリを `origin` にした clone を指す。
`data.lock`・`cache/` は、そのディレクトリの隣に置かれ、本物のものと混ざらない。

### board.db からの切り替え

カードの正本は、かつて `.ai-board/board.db`（SQLite）にあった。今の版は `board.db` を読まない。

- **新しいリポジトリ:** メインのチェックアウトで `node dist/cli.js init` を走らせる。
  空のデータ用ブランチ `ai-board/data` を作って `origin` へ push し、`.ai-board/config.yaml` があればデータ用ブランチの根へ写す。
  `origin` か手元に `ai-board/data` が既にあれば、何もせずに止まる
- **`board.db` しか持たない手元:** SQLite を消す前の版（main のコミット `d2380ce`）の `ai-board migrate` で移行する。
  `/loop` のセッションを止め、`d2380ce` を checkout して `npm ci && npm run build && node dist/cli.js migrate` を走らせ、
  データ用ブランチができたら今の版に戻す。データ用ブランチの形の版は変わっていないので、今の版がそのまま読める

データ用ブランチが無いと、CLI はカードを読めずに止まり、`ai-board init` を走らせるよう案内する。
ほかのマシンやクラウドのセッションでは `init` は要らない。最初に CLI を動かしたときに、`origin` のデータ用ブランチからデータのワークツリーが作られる。

### 並び順

アイデアの表の行は `ai-board decide move` で並べ替えられ（チャットからは「<カード> を一番上へ」）、上にあるものほど優先度が高い。
並び順は全カードで 1 本で、各区画はそれを自分のカードだけに絞って見せる。
ステージが進んで区画を移っても、優先度はそのまま持ち越される（判断待ちとマージ済みの区画だけは時刻で並べ直す）。

並べ替えると、動かしたカードの `rank` だけが書き換わる。`rank` の無いカードは
`created` のエポックミリ秒を `rank` とみなすので、並べ替えたことの無いカードは作成順に並び、
新しいカードは末尾に付く。`rank` を決めるのは人で、エージェントは読むだけにする。

アイデアの表には区切り線が 1 本あり、線より上が「次にやる」、下が「あとで考える」。
区切り線は `ai-board decide move-divider` で動かせ、カードを線の向こうへ動かせば区分が変わる。
区切り線は `rank` と同じ物差しの値を 1 つ持つだけで（データ用ブランチの `order.yaml` の `divider`）、カードに区分の値は無い。
一度も動かしていなければ末尾にあり、すべてのアイデアが「次にやる」に入る。
新しく起票したアイデアは末尾に付くので「あとで考える」に入る。
区切り線も人が決める優先度なので、`ai-board card` から読み書きする入口は無い。

## 計画ファイル

`.ai-board/plans/<card-id>.md` の 1 ファイルがそのカードの計画。
**ファイル名がカード ID と一致することで紐付く**ので、カードの frontmatter に
紐付け用のフィールドは無い。

```markdown
# リフレッシュトークン対応

## 方針

...

## 動作確認の手順

1. `npm run build` の後、トークンの期限を切らした状態で API を呼ぶ
2. 応答が 200 になり、保存したトークンが入れ替わっていることを見る

## タスク

- [x] トークンの保存先を決める
- [ ] 更新エンドポイントを足す
```

チェックボックス（`- [ ]` / `- [x]`）はカードのタスクの進み（`plan.tasks`）になる。
インデントされたサブタスクも親と同じように数える（列 0 に固定すると
`  - [ ] 1.1.1 …` が進捗から消えるため）。**タスクの進捗はステージを立てない。**
フェンス（` ``` ` / `~~~`）で囲んだコードブロックの中のチェックボックスは数えないので、計画に書き方の例として載せてよい
（閉じていないフェンスは無いものとして後ろの行を数える。4 つの空白で字下げしたコードブロックは外さない）。

`## 動作確認の手順` には、動かして確かめるときのコマンドと、期待する結果を書く。
計画レビューの時点で、後で何を確かめることになるかを読めるようにするため。
実装と AI レビューを終えた AI は、これをもとに動かせるところを動かし、実装を経て変わった手順と、
「確かめたこと / コマンド / 結果（`通った` / `落ちた` / `走らせていない`）」の表を PR の本文の `## 動作確認の結果` に書く。
表には品質ゲートと CI（チェックごと）の行も入れ、走らせていないものには理由と何が要るかを書く。バグの直しでは、テストが直す前に落ちたことも行にする。
人は PR中 でそれを読み、必要なら手で動かす。

AI は Ready にする前に `ai-board pr checks <n> --wait` で PR の最新コミットの CI を確かめる。赤なら締めの段のまま直して push し（2 回まで）、
直せない・上限（既定 900 秒）まで待っても終わらないときは、Ready にせず止まって人に伝える。CI が無いリポジトリでは、表に `走らせていない` と書いて Ready にする。

締めの段で、PR を Ready にする直前に同じ PR の中で `.ai-board/plans/archive/<card-id>.md` へ移す。
マージと同時に archive も main に入り、これがマージ済みの実態になる
（GitHub が引けないときや、`github:` の無いリポジトリでも マージ済み が立つ）。

計画を書くのは AI エージェントで、**`ai-board` の CLI は計画を read-only** に扱う。
ボードは計画の本文を持たず、タスクの進捗と archive の有無だけを読む。
人は計画を Draft の PR で読み、ボードには PR の番号とリンクだけが出る
（計画ファイルはブランチにあり、ボードを動かすチェックアウトからは見えないことが多い）。

**計画ファイルが存在するだけで計画レビューの列が立つ。** エージェントが書き始めた時点で
列が動くが、本来のゲートは本文の `## レビュー` に書かれる `plan 提出` であり、
ファイルの存在は「ログの欠落で人待ちを取りこぼさない」ための保険である。

## レビュー要求の取得先

`PR中` / `マージ済み` の列は、カードに紐付いた GitHub の Pull Request の状態で決まる。

接続設定はデータ用ブランチの根の `config.yaml` から読む。クラウドのセッションの clone には、git に載らない各自のファイルが無いためである。
データ用ブランチに無ければ、メインのチェックアウトの `.ai-board/config.yaml`（git の追跡外）を読む。
`ai-board init` は `.ai-board/config.yaml` をデータ用ブランチへ写すので、`init` の前に用意しておく。

```bash
cp .ai-board/config.example.yaml .ai-board/config.yaml
```

```yaml
github:
  repository: iepyon/ai-board # owner/repo
```

### アクセストークンは要らない

ai-board はトークンを受け取らない。問い合わせは `gh api` の実行として行い、
**認証はログイン済みの CLI に委ねる。**

```bash
gh auth login
```

CLI が入っていない、または未ログインなら連携は無効になり、理由が `ai-board status` の「GitHub:」の行に出る。
設定そのものが無い場合も同じく無効になり、`PR中` / `マージ済み` の列が
レビュー要求由来の情報を失うだけでボードは動く。取得先がダウンしてもボードは落ちず、
直近のキャッシュを保ったまま接続状態だけを error にする。

CLI の有無とログイン状態は、`ai-board` の CLI を動かすたびに 1 度だけ確かめる。

PR 一覧の全件取得はページングで取りこぼすため使わず、カード単位で問い合わせる。
問い合わせるのは `branch` か `mr` が書かれたカードだけ。
`mr` が無ければ `branch` から PR を解決し、得られた番号を書き戻す。

GitHub はレビューコメントが 2 か所（PR 全体への返信とコード行への指摘）に分かれるため、
両方を合算して「人が書いた最新のコメント」とする。

PR のイベント（`issues/{n}/events`）は PR の状態を問わず引き、2 つの時刻を取る。
最後に Ready にした時刻（`ready_for_review`。作成時から Ready の PR は作成時刻）は、区間の並び（`timeline`）の PR レビューの始まりになる。
最後に Draft へ戻された時刻（`convert_to_draft`）は、今 open かつ Draft の PR でだけ値を持ち、前述の「止まり」に使う。

### GitLab 連携の廃止

かつては GitLab の Merge Request も取得先に選べた。
GitLab の MR !1 と GitHub の PR #1 は別物なので、GitLab 時代の番号を GitHub で引くと
**列は正しく埋まったままリンクだけが別の PR を指す**。
これを避けるため、番号の出どころを記録していた `forge` 列をもとに、
GitHub のものと確かめられない番号を当時の DB のマイグレーションで消してから列を落とし、
`branch` から解決し直させた。かつての `ai-board import` も `forge: gitlab` の番号は捨てていた。

## 設計

**ステージはどこにも保存しない。** 3 つの実態（カード・計画ファイル・レビュー要求）
から純関数で導出する。列を動かしたければ、その列を成立させる実態を作る。
手動で上書きする入力口は無い。

計画ファイルはディレクトリを直接読む。ファイル名がそのままカード ID なので、
ID として不正な名前のファイルは警告して読み飛ばす（ここで例外を投げるとボード全体が
読めなくなり、置き場所を間違えた 1 ファイルで `ai-board status` が止まる）。

かつては OpenSpec の `openspec/changes/` を読んでいたが、Plan モードで立てた計画を
そのまま成果物にするほうが工程が短いため、計画ファイル 1 本に寄せた。
移行前の change は `.ai-board/plans/archive/` に計画として残してある。

### レイヤー構成

```
src/
  cli.ts / cli-main.ts  CLI の入口
  shared/               Result<T,E>・Branded Types・設定・区画と判断の純関数
  cards/                カードの読み書きのコンテキスト
    models/ errors/ repositories/ usecases/ cli/ composition.ts
  board/                3ソース統合・ステージ導出コンテキスト
    services/stage-resolver.ts    ← 核となる純関数
    repositories/plan.repository.ts
    services/github-client.ts
    cli/                status / decide / pr / loop
  infrastructure/       外部コマンド・データのワークツリー・GitHub の問い合わせ
```

- usecase はすべて `Result<T, E>` を返し、例外を投げない
- エラーは discriminated union（`{ type: 'CardNotFound' }`）で表し、CLI が人に読める 1 行へ変換する
- 依存はコンテキストごとの `composition.ts`（Composition Root）で構成する

### `status --json` の各カード

`ai-board status --json` の `cards[]` は、本文や計画を解析し直さずに済むよう、次の値も持つ。

- `latestReview` — その列が待っているゲート（計画レビューなら plan）の最新エントリ。
  待ちの列でなければゲートを問わず最新のエントリ（どちらも中止を除く）。`{ at, gate, kind, reason }` か `null`。
  判断待ちの区画が出す提出の本文と、待ち始めた時刻はここから取る
- `plan.updatedAt` — 計画ファイルの mtime。「動きなし」の目安と、PR の無いマージ済みカードの日付
- `mrState.mergedAt` — PR の `merged_at`
- `mrState.readyAt` — 最後に Ready にした時刻（`ready_for_review` のイベント）。作成時から Ready の PR は作成時刻。
  今 Draft で一度も Ready にしていなければ `null`
- `mrState.convertedToDraftAt` — 最後に Draft へ戻された時刻。今 open かつ Draft でなければ `null`
- `mrState.noteCount` / `mrState.latestNoteAt` — 人のコメントの件数と最新の時刻。bot と AI（Claude Code のフッター付き）のコメントを除く
- `mrState.latestAiNoteAt` — AI が書いた最新のコメントの時刻。無ければ `null`
- `mrState.awaitingFix` — PR中 で、人の指摘に AI が応える番か。真なら AI 作業中の区画に出て、ループが `fix-pr` で選ぶ
- `hold` — 止まり（前述）。`{ reason, since }` か `null`。`reason` は人が何をすればよいか、`since` は人を待ち始めた時刻。
  判断待ちの区画への振り分けと、AI ループが選ばないことの両方がこの値を読む
- `timeline` — カードが各工程にいた時間を区間として時刻の順に並べたもの（区間の並び）。
  各区間は `{ kind, owner, start, end }` で、`owner` は `human` / `ai`、今いる区間は `end: null`。
  起票・着手・`## レビュー` の各エントリ・PR の Ready / Draft へ戻す / マージの時刻から毎回導出し、保存しない。
  差し戻しがあれば同じ `kind` が何度も現れる。
  各区間は `phases`（`{ kind: 'wait' | 'work', start, end }` の配列）も持ち、AI の区間をループの 1 手の記録で「待ち」と「作業」に分ける。
  人の区間と、記録が 1 つも重ならない AI の区間は空
- `loopSteps` — そのカードに渡されたループの手（1 手の記録）を開始の時刻の順に並べたもの

`ai-board status --json` は、ボード全体の `loop`（`{ running, lastFinishedAt }`。今触っている手と、最後に手を終えた時刻）も持つ。

ステージを直接指定する入力口は無い。`ai-board decide` はゲート（`plan`）・種別・理由文を
受け取って判断を追記するだけで、列は次の `ai-board status` で導出し直される。

## 開発

```bash
npm test              # vitest（unit）
npm run test:coverage # カバレッジ（閾値 80%）
npm run lint
npm run typecheck     # tsc を 2 回（本体・テスト）
npm run format:check  # Prettier（崩れていたら npm run format）
npm run build         # tsc で dist/ を作る
```

CI（`.github/workflows/ci.yml`）は PR と main への push で、Node 26 の typecheck / lint / format:check /
test:coverage / build を走らせる。PR のレビューだけに効く指示は `REVIEW.md` にある。

`typecheck` は、出力に使う `tsconfig.json`（テストを除く）と、テストまで含めた `tsconfig.test.json` の 2 つで `tsc` を走らせる。
vitest は型を見ずにテストを走らせるので、テスト用の値が本体の型とずれたら（本体に項目を足したのにテストの値に無い、など）ここで落ちる。
