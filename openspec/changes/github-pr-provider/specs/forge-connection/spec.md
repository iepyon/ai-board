## Purpose

カードに紐付くレビュー要求（GitLab の Merge Request、GitHub の Pull Request）の状態を、
どのホスティングサービスからどう取得するかを定める。取得先が変わっても、ステージ導出が
受け取る情報の意味は変わらないことを保証する。

## ADDED Requirements

### Requirement: 取得先は 1 つだけ選べる

システムは レビュー要求の取得先として GitLab と GitHub のうち高々 1 つを有効にしなければ
ならない (MUST)。設定に両方の取得先が書かれている場合は、起動を中止して設定の誤りを
利用者に示さなければならない (MUST)。いずれか一方を暗黙に優先しては SHALL NOT。
どちらが使われているか分からないまま動く状態を作らないためである。

#### Scenario: GitLab だけが設定されている

- **WHEN** 設定に GitLab の接続先だけが書かれ、対応するトークンが与えられている
- **THEN** 取得先は GitLab になる

#### Scenario: GitHub だけが設定されている

- **WHEN** 設定に GitHub の接続先だけが書かれ、対応するトークンが与えられている
- **THEN** 取得先は GitHub になる

#### Scenario: 両方が設定されている

- **WHEN** 設定に GitLab と GitHub の両方の接続先が書かれている
- **THEN** 起動は中止され、両方が設定されている旨が示される

### Requirement: 認証は CLI に委ねる

システムは レビュー要求の取得先へのアクセストークンを受け取っては SHALL NOT。
設定ファイル・環境変数・コマンドライン引数のいずれからもトークンを読んでは SHALL NOT。
問い合わせは利用者の環境に既にログイン済みの CLI（GitHub なら `gh`、GitLab なら `glab`）
の実行として行い、認証はその CLI に委ねなければならない (MUST)。

システムは CLI の出力に含まれ得る資格情報を記録しては SHALL NOT。
また CLI の標準エラー出力をそのまま利用者へ示す場合も、トークンを露出させては SHALL NOT。

選択された取得先に対応する CLI が存在しない、または未ログインの場合、
連携は無効として扱い、その理由を接続状態として示さなければならない (MUST)。

#### Scenario: CLI がログイン済み

- **WHEN** 設定に取得先が書かれ、対応する CLI がその取得先にログイン済みである
- **THEN** 連携は有効になり、問い合わせはその CLI を通して行われる

#### Scenario: CLI が入っていない

- **WHEN** 設定に取得先が書かれているが、対応する CLI が実行できない
- **THEN** 連携は無効になり、CLI が見つからない旨が接続状態として示される

#### Scenario: CLI が未ログイン

- **WHEN** 対応する CLI は存在するが、その取得先にログインしていない
- **THEN** 連携は無効になり、未ログインである旨が接続状態として示される

#### Scenario: トークンはどこからも読まれない

- **WHEN** 設定ファイルや環境変数にトークンらしき値が置かれている
- **THEN** システムはそれを読まず、接続の可否は CLI のログイン状態だけで決まる

### Requirement: 外部から与えられた値をコマンドとして解釈しない

システムは CLI を実行する際、カードに記録されたブランチ名や識別番号、設定ファイルの
リポジトリ指定を、シェルによって解釈される文字列へ連結しては SHALL NOT。
引数は個別の要素として渡さなければならない (MUST)。

カードファイルは人とエージェントが自由に編集でき、ブランチ名には任意の文字列が
入り得るためである。

#### Scenario: ブランチ名にシェルの特殊文字が含まれる

- **WHEN** カードのブランチ名にシェルが解釈し得る文字が含まれている
- **THEN** その文字はブランチ名の一部として CLI へ渡され、コマンドとしては解釈されない

### Requirement: 連携が無くてもボードは動く

システムは 取得先が未設定のとき、または取得先への問い合わせが失敗したときも、
ボードの取得を失敗させては SHALL NOT。接続状態を「無効」または「エラー」として
示したうえで、カードファイルと openspec 由来の情報だけでボードを返さなければならない (MUST)。

問い合わせが失敗した場合、システムは 直前に取得できていた状態を保持しなければならない (MUST)。
一時的な障害でステージが巻き戻ることを避けるためである。

#### Scenario: 取得先が未設定

- **WHEN** GitLab も GitHub も設定されていない
- **THEN** 接続状態は「無効」として示され、ボードは残りの情報で組み立てられる

#### Scenario: 取得先がダウンしている

- **WHEN** 取得先への問い合わせが失敗する
- **THEN** 接続状態は「エラー」として示され、直前に取得できていたレビュー要求の状態は保たれる

### Requirement: 問い合わせはカード単位で行う

システムは レビュー要求の一覧を全件取得しては SHALL NOT。
カードに記録された識別番号、または記録が無ければカードのブランチ名から、
カードごとに問い合わせなければならない (MUST)。
一覧取得はページングで取りこぼすためである。

ブランチから解決した識別番号は、カードへ書き戻さなければならない (MUST)。

#### Scenario: 識別番号が既にある

- **WHEN** カードにレビュー要求の識別番号が記録されている
- **THEN** その番号で直接問い合わせる

#### Scenario: ブランチから解決する

- **WHEN** カードに識別番号が無く、ブランチ名が記録されている
- **THEN** そのブランチのレビュー要求を解決し、得られた番号をカードへ書き戻す

### Requirement: 取得先が違っても情報の意味は揃える

システムは 取得先によらず、レビュー要求について同じ意味の情報を提供しなければならない (MUST)。
すなわち識別番号・状態・ソースブランチ・タイトル・Web URL・人が書いたレビューコメントの
件数と最終時刻・最新コミットの時刻である。

人が書いたレビューコメントの件数と最終時刻は、その取得先で人のコメントが複数の場所に
分かれて記録される場合、それらを合算しなければならない (MUST)。
取得先によって数字の意味がずれることを避けるためである。
システムが自動生成したコメントを件数に含めては SHALL NOT。

#### Scenario: コメントが複数の場所に分かれている

- **WHEN** 取得先がレビュー要求全体へのコメントとコード行へのコメントを別々に記録している
- **THEN** 件数は両方の合計になり、最終時刻は両方のうち最も新しいものになる

#### Scenario: 自動生成のコメントは数えない

- **WHEN** レビュー要求にシステムが自動生成したコメントだけが付いている
- **THEN** 人が書いたコメントの件数は 0 件になる
