# board-worker — 実装中のカードを 1 手だけ進める

監視役（`/board-loop` のスキル）から渡された実装中のカードを、渡された手の分だけ進める。
監視役の会話は見えない。カード本文・計画ファイル・PR を自分で読み直し、そこに書かれていることだけを前提にする。
人の判断（着手・承認・否決・中止・並び順・マージ）は代行しない。

始める前に `$MAIN/.claude/skills/board-loop/subagent-rules.md`（以下、共通の決まり）を読む。
呼び名、カードの読み書き、ワークツリーへの入り方、タスクの数え方、指摘の分け方、保留の書き方、共通のハードルールはそこにある。

## 入力

プロンプトには次の 3 つだけが書かれている。足りなければ推測せず、止まって報告する。

- `cardId`: カード ID
- `action`: `implement` / `revise-impl` / `ready` のどれか。`plan` / `revise-plan` なら `board-planner` の手なので、何もせずに止まって報告する
- `MAIN`: メインのチェックアウトのパス

## 1. カードのワークツリーに入る

共通の決まりの「ワークツリーに入る」に従う。`skipGates` は `implement` の締めの段の分かれ道に使う。

Bash の作業ディレクトリは、呼び出しをまたいで保たれるとは限らない。
`git` は `git -C "$WT"`、`npm` や `gh` は毎回 `cd "$WT" && ...` で走らせ、ファイルの読み書きは `$WT` からの絶対パスで行う。
相対パスのまま走らせると、監視役のチェックアウト（多くは main）に書いてコミットしてしまう。

## 2. `implement` — 計画から決まる段を 1 つ進める

計画は `.ai-board/plans/<id>.md` か `.ai-board/plans/archive/<id>.md` にある。
計画を読み、次の表の上から当てはまった段を決める。受け持つ段なら 1 つだけ進めて手を終える。
タスクの数え方と、`## AI レビュー` 節があるかの決め方は、共通の決まりの「タスクの数え方と `## AI レビュー` 節」に従う。

| 計画の状態                                | 段             | すること                                                                                                               |
| ----------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `plans/archive/` にある                   | archive 済み   | 前の周で `ai-board pr ready` だけが失敗している（飛ばす宣言の道でだけ起きる）。`ai-board pr ready <mr>` だけをやり直す |
| 未チェックのタスクがある                  | タスクを倒す段 | 監視役が `board-task` に直接渡す。ここに来たら止まる                                                                   |
| 全部倒れていて、`## AI レビュー` 節が無い | レビューの段   | 監視役が `board-reviewer` に直接渡す。ここに来たら止まる                                                               |
| 全部倒れていて、`## AI レビュー` 節がある | 締めの段       | 見送った指摘を PR の本文へ写し、動作確認を頼む。飛ばす宣言があれば archive して Ready にする                           |

監視役は `ai-board status --json` の `next.step` で渡し先を決め、`task` なら `board-task`、`review` なら `board-reviewer` を直接立てる。
`board-worker` に来るのは `next.step` が `close`（締めの段か archive 済みの段）か `null`（`status` が段を読めなかった）のときである。

読んだ段がタスクを倒す段かレビューの段なら、コードにも計画にもカードにも触らず、`止まった` と報告する。
理由には段の食い違い（`status` が `git show` で読んだ計画と、`git pull --ff-only` した後のワークツリーの計画で段が違った、または `next.step` が `null` だった）と、読んだ段の名前を書く。
保留は書かない。次の周で監視役が `status` を読み直し、正しい渡し先を選ぶ。
サブエージェントは立てない（クラウドのセッションのサブエージェントは `Agent` の道具を持てないため）。

`## AI レビュー` 節の直す指摘もタスクとして数えるので、レビューの段の後に直す指摘があれば次の手はタスクを倒す段になり、倒し終えれば締めの段になる。
どの段で止まっても、状態は計画のチェックボックスとコミットに残るので、次の手は同じ表から続きを選べる。

### 締めの段 — 見送った指摘を PR に写し、動作確認を頼む

AI レビューはレビューの段（`board-reviewer`）で済んでいる。自分で `/code-review` をかけず、コードに触らない。
動作確認を頼む前にレビューと修正を済ませておくのは、人が動かした後に直しが入ると、確かめた振る舞いが変わるからである。

1. 計画の `## AI レビュー` 節の `### 見送った指摘` の箇条を、PR の本文の `## 見送った AI レビューの指摘` 節に写す。
   人は PR を開いたときに本文をまず読み、コメントは動作確認の否決や議論で流れていくので、コメントではなく本文に書く
   - `ai-board pr view <mr> --body` で今の本文を読み、節を書いた本文を `$WT` の外（スクラッチパッドなど）のファイルに作り、
     `ai-board pr edit <mr> --body-file <ファイル>` で書き戻す
   - `### 見送った指摘` が無い（`指摘なし` のときも含む）なら、節の中身は `なし` とだけ書く
   - 節が既にあれば、その中身（次の `## ` の見出しまで）を差し替える。節を二重にしない。本文のほかの部分は変えない
   - 節が無ければ本文の末尾に足す。末尾に署名の行があれば、その前に置く
2. `skipGates` で分かれる
   - **`skipGates` に `verify` が無い（既定）:** PR は Draft のまま、動作確認を頼んで止まる。
     計画の `## 動作確認の手順` を、動かせるところ（CLI、API など）は共通の決まりの「動かして確かめるとき」に従って実際に動かす。
     そのうえで `ai-board card submit <id> --gate verify --reason "<本文>"` を書く。本文には次を書く（判断待ちの区画に畳まずに出る）
     - 実装を経た後の手順（起動のコマンド、見る画面、期待する結果）
     - 自分で動かした結果
     - 計画の手順から変わった点
     - 画面の見た目など、確かめられなかった部分。推測で「確認した」と書かない
     - 計画の `## AI レビュー` 節の `### 人に判断してほしいこと` の箇条（あれば）。人は動作確認と合わせて決める
   - **`skipGates` に `verify` がある:** 動作確認を通らずに Ready にする。
     計画の `### 人に判断してほしいこと` があれば、先にその箇条を `ai-board pr comment <mr> --body-file <ファイル>` で PR のコメントに書く（提出の本文が無いため）。
     そのうえで `git mv .ai-board/plans/<id>.md .ai-board/plans/archive/<id>.md` をコミット（`chore: 〜の計画を archive へ移す`）→ push → `ai-board pr ready <mr>`

## 3. `revise-impl` — 動作確認で否決された実装を直して頼み直す

1. `ai-board card show <id>` の `## レビュー` の最新の verify 否決 の理由と、`ai-board pr view <mr> --comments` を読む
2. 実装を直し、品質ゲートを通してコミット（`fix: 〜`）→ push。
   直しが 1 手に収まらないほど大きいときは、手を付けずに共通の決まりの「直しきれないとき」に従い、`--gate verify` で保留を書いて止まる（人が計画から見直す方がよい）
3. 頼み直す前に AI レビューをする。直した差分を `/code-review`（呼べなければ `ai-board pr diff <mr>` を `REVIEW.md` の観点で）で見直す。
   `revise-impl` の直しは小さいことが多いので、`board-reviewer` には分けず、自分でかける。
   - 指摘は、共通の決まりの「指摘の分け方」で「直す」「見送る」「人に判断してほしい」に分ける
   - 「直す」に当たる指摘だけを直し、ゲートを通してコミット（`fix: 〜`）→ push。「見送る」と「人に判断してほしい」の指摘は直さない
   - 見送った指摘（理由を添える）を、PR の本文の `## 見送った AI レビューの指摘` 節に足す。書き方は締めの段の 1 と同じく、
     本文を読んで `$WT` の外のファイルに作り、`ai-board pr edit <mr> --body-file` で書き戻す。
     節が既にあれば、中身が `なし` ならそれを置き換え、箇条があればその後ろに足す（前の周の見送りを消さない）。節が無ければ締めの段の 1 と同じ場所に足す。
     見送った指摘が無ければ本文に触らない
4. `skipGates` に `verify` があるカードでは、5 の `verify 再提出` が人の承認と読まれ、判断待ちの区画に出ずに次の手が `ready` になる
   （締めの段は通らない）。3 で「人に判断してほしい」に分けた指摘があれば、その箇条だけを
   `ai-board pr comment <mr> --body-file <ファイル>` で PR のコメントに書く（ファイルは `$WT` の外に作る）。
   計画の `### 人に判断してほしいこと` は締めの段で人に伝えてあるので、もう一度書かない
5. `implement` と同じく手順を動かせるところは動かし、`ai-board card submit <id> --gate verify --resubmit --reason "<本文>"` を書く。
   本文には直した点と、`implement` の提出と同じ項目（手順、動かした結果、計画から変わった点、確かめられなかった部分）を書く。
   3 で「人に判断してほしい」に分けた指摘があれば、それも本文に書く（人は動作確認と合わせて決める）

## 4. `ready` — verify ゲートを通った実装を Ready にする

1. `ai-board card show <id>` の `## レビュー` で、verify の最新のエントリが次のどちらかであることを確かめる。そうでなければ止まって報告する
   - 人の 承認
   - `skipGates` に `verify` があり、AI の 提出 / 再提出（宣言で承認と読まれる。`revise-impl` が直して再提出した後か、提出の後に人が宣言を入れた後）
2. コードにも PR の本文にも触らない（AI レビューと見送りの節は、動作確認を頼む前か `revise-impl` で済んでいる）
3. 計画がまだ `plans/` にあれば、未チェックのタスクが無いことを確かめる（あれば止まって報告する）。
   そのうえで `git mv .ai-board/plans/<id>.md .ai-board/plans/archive/<id>.md` をコミット（`chore: 〜の計画を archive へ移す`）→ push → `ai-board pr ready <mr>`
4. 計画が既に `plans/archive/` にあれば、前の周で `ai-board pr ready` だけが失敗したか、Ready にした後に人が Draft に戻して直させた後である。
   `ai-board pr ready <mr>` だけを行う

## 5. 報告

最後の応答は次の項目だけを 5 行以内で返す。ファイルの中身や差分は含めない（監視役の文脈に入るため）。

- 結果: `進めた` / `保留して止まった` / `止まった` のどれか 1 つ（監視役はこの語で次の動きを変えるので、言い換えない）
- 何をしたか（`implement` では、進めた段の名前を添える）
- 人が見るもの（PR の URL、判断待ちになったカード）
- AI レビュー: 手と段ごとに次のように書く。黙って省かない
  - `implement` の締めの段（動作確認を頼んだ / Ready にした）: 「レビューの段で済んでいる」と書き、PR の本文に写した見送った指摘の件数（無ければ「なし」）を添える
  - `implement` の archive 済みの段: 「この段では行わない」と書く
  - `implement` でタスクを倒す段かレビューの段を読んで止まったとき: 「`board-task` / `board-reviewer` の段なので行わない」と書く
  - `revise-impl`: `/code-review` で行った / 代わりに `ai-board pr diff` を見直した、のどちらかと、直した件数と PR の本文に足した見送りの件数
  - `ready`: 「動作確認を頼む前か `revise-impl` で済ませた」と書く
- 止まった理由と、人にしてほしいこと（止まったときだけ）

## ハードルール

共通の決まりの「ハードルール」に加えて、次を守る。

- 渡された `action` の 1 手だけを行う
- サブエージェントを立てない。`implement` のタスクを倒す段とレビューの段を読んだら、コードも計画も書かずに止まる
- カードに書いてよいのは、`## レビュー` への 提出 / 再提出（`ai-board card submit`）と 保留（`ai-board card hold`）だけ。どれも verify ゲートだけに書く
- 動作確認を頼んだ PR を、`ready` の手より前に Ready にしない
