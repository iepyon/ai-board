# board-task — 計画の節を 1 つ倒す

監視役（`/board-loop` のスキル）から、`implement` の手で `next.step` が `task`（タスクを倒す段）のカードを受け、
計画の上から最初の未チェックのタスクを含む節を倒し切る。節の中のタスクを上から順に実装し、節の終わりで品質ゲートを通してコミットし、push する。
監視役は節ごとに新しい `board-task` を立てる。まっさらな文脈で立てるのは別のカードの文脈を持ち込まないためで、
同じ節の中ではタスクをまたいで読んだコードや決めた事柄を持ち込んでよい（共通の決まりの「呼び名」）。

監視役の会話は見えない。前の節の要約も渡されない。
カード本文・計画・ワークツリーのコードを自分で読み、そこに書かれていることだけを前提にする。
人の判断（承認・否決・中止・マージ）は代行しない。

始める前に `$MAIN/.claude/skills/board-loop/subagent-rules.md`（以下、共通の決まり）を読む。
呼び名、カードの読み書き、ワークツリーへの入り方、タスクの数え方と節の決め方、動かして確かめるときの決まり、共通のハードルールはそこにある。

## 入力

プロンプトには次の 3 つだけが書かれている。足りなければ推測せず、止まって報告する。

- `cardId`: カード ID
- `action`: `implement` のはずである。ほかの手なら、何もせずに止まって報告する
- `MAIN`: メインのチェックアウトのパス

カードは `ai-board card show <cardId>`（書き方は共通の決まりの「カードの読み書き」）で読むだけにする。カードには何も書かない。

## 1. カードのワークツリーに入る

共通の決まりの「ワークツリーに入る」に従い、カードの `branch` のワークツリーに入って `git pull --ff-only` する。
`branch` が null、ワークツリーに未コミットの変更が残っている（前のサブエージェントが途中で止まっている）、`git pull --ff-only` が失敗した、のどれかなら、何も変えずに止まって報告する。

Bash の作業ディレクトリは、呼び出しをまたいで保たれるとは限らない。
`git` は `git -C "$WT"`、`npm` や `gh` は毎回 `cd "$WT" && ...` で走らせ、ファイルの読み書きは `$WT` からの絶対パスで行う。
相対パスのまま走らせると、監視役のチェックアウト（多くは main）に書いてコミットしてしまう。

## 2. 節を選ぶ

次のどれかに当たれば、何も変えずに止まって報告する。
監視役の段は `status` が `git show` で読んだ時点のもので、`git pull` した後の計画と食い違うことがある。食い違いなら、理由にそう書く。

- 計画が `$WT/.ai-board/plans/<cardId>.md` に無い（`plans/archive/` にあるなら、タスクを倒す段は済んでいる）
- 計画に未チェックのタスクが無い（段の食い違い。レビューの段か締めの段になっている）

節は、共通の決まりの「タスクの数え方と `## AI レビュー` 節」の節の決め方に従って選ぶ。
上から最初の未チェックのタスクの行（字下げされたサブタスクも 1 つと数える。`## AI レビュー` 節の直す指摘も含む）を見つけ、
その行から上へたどって最初に当たる見出しの行から、次の見出しの行の手前までを節とする。
以下、この範囲を「選んだ節」、選んだ節の中の未チェックのタスクの行を「節のタスク」と呼ぶ。節の中の `[x]` のタスクは飛ばす。

節に区切っていない計画では `## タスク` 全体が、`## AI レビュー` 節の直す指摘は `## AI レビュー` の見出しから次の見出しの手前までが、選んだ節になる。

`$WT/node_modules` が無ければ `cd "$WT" && npm ci` を走らせる。

## 3. タスクの範囲を決める

節のタスクのそれぞれについて、その行がタスクの書き出しである。次をそのタスクに含める。

- その行に続く、折り返しの行（行頭を字下げして続けた文）
- その行の下に字下げして並ぶ、チェックボックスの無い箇条（タスクの中身を細かく書いたもの）

字下げされていても `- [ ]` / `- [x]` で始まる行は別のタスクである。節の中にあれば節のタスクとして別に倒し、節の外にあればやらない。

節のタスクが `## AI レビュー` 節の行（`board-reviewer` が書いた直す指摘）でも、ほかのタスクと同じに扱う。
その 1 行に書かれた場所・起きること・直し方だけを直す。指摘の文は書き換えない。

## 4. 節のタスクを上から順に倒す

1. `ai-board card show <cardId>` のカード本文（アイデア / 背景 / 論点 / `## レビュー`）と、計画の全体を読む。
   特に `## 設計` の Decisions / Non-Goals と、`## タスク` の中での選んだ節の位置（前の節で何ができているはずか）を読む
2. 前の節で作られたはずのものは、要約に頼らずワークツリーのコードと `git -C "$WT" log` で確かめる
3. 節のタスクを上から 1 つずつ実装する。選んだ節の外（次の節）に書かれていることを先回りしてやらない。
   振る舞いを足したら、`src/**/__tests__/**/*.test.ts` にテストを足す
4. タスクを 1 つ倒すごとに、計画のその行の `- [ ]` を `- [x]` に変える（コミットはしない）。
   変えるのはその行のチェックボックスだけで、行の文、ほかの行、計画のほかの節は変えない。
   文脈が長くなって自動の要約が入っても、計画を読み直せばどこまで済んだかが分かる
5. 節の途中のタスクの後では、品質ゲートを走らせなくてよい。テストや型が落ちていてもよい（節の終わりで通す）
6. 計画の `## 動作確認の手順` や CLI・API を動かして確かめるときは、共通の決まりの「動かして確かめるとき」に従う

実装の途中で、次のどれかに当たると分かったら、それまでの変更（選んだ節の中で倒したタスクの分と、計画の `[x]` を含む）を
`git -C "$WT" checkout -- .` と `git -C "$WT" clean -fd` で戻し、止まって報告する。

- タスクの書き方から、何をすればよいかが一通りに決まらない
- タスクが計画の Decisions / Non-Goals、`CLAUDE.md` のハードルールと食い違う
- 選んだ節を倒し終えても品質ゲートを通せる形にならず、直すには 5 の「タスクの順番を直す」で許していない計画の変更（タスクの文の書き換え・追加・削除など）が要る

人の判断が要る止まりでも、`ai-board card hold` は書かない。`implement` に保留は無く、止まりは報告で監視役から人に届く。

## 5. 節の終わりで品質ゲートを通す

節のタスクをすべて倒し終えたら、品質ゲートを走らせる。

```bash
cd "$WT" && npm run typecheck && npm run lint && npm run format:check && npm test
```

整形が崩れていたら `cd "$WT" && npm run format` で直す。
落ちたら直して通し直す。落ちた原因がタスクの順番（後ろの節のタスクも一緒に入れないと通らない）なら、次の「タスクの順番を直す」に進む。
それ以外で直せなければコミットせず、変更を残したまま止まって報告する（どの段階で落ちたかを書く）。
計画ファイルやエージェントの定義だけの変更でも、ゲートは走らせる。

### タスクの順番を直す

節の終わりでゲートが通らず、その原因が「後ろの節のタスクも一緒に入れないと通らない」ことなら、計画の `## タスク` を直してから続けてよい。
人の判断は待たない（`implement` に保留は無い）。直してよいのは次の 3 つだけである。

- 未チェックのタスクの行を、別の節へ移す（後ろの節のタスクを今の節へ移す、など）。折り返しの行と、下に字下げして並ぶチェックボックスの無い箇条も一緒に移す
- 隣り合う節を 1 つに合わせる（後ろの節の `### <番号>. <題>` の見出しの行を 1 つ消す）
- 節の中で、未チェックのタスクの並びを入れ替える

次はしない。これが要るなら、それまでの変更（計画の `[x]` と順番の直しを含む）を
`git -C "$WT" checkout -- .` と `git -C "$WT" clean -fd` ですべて戻し、止まって報告する。

- タスクの文を書き換える、タスクを足す、消す
- `[x]` のタスクを動かす、チェックを外す
- 見出しを足す、見出しの文を書き換える
- 計画の `## タスク` 以外の節（`## 設計` の Decisions、`## 動作確認の手順`、`## AI レビュー` など）を変える

直した後は、移してきたタスクも選んだ節のタスクとして 4 の手順で倒し（倒したら `[x]` を付ける）、節の終わりでゲートを通し直す。
直しても通らなければ、変更を残したまま止まって報告する。
直したことは、6 のコミットの本文と 7 の報告に書く。

## 6. コミットと push

1. 次を確かめる。満たされなければコミットせず、変更を残したまま止まって報告する
   - 節のタスクがすべて `[x]` になっている
   - `git -C "$WT" status --porcelain` で、変わったファイルが選んだ節の実装と計画だけである
   - `git -C "$WT" diff -- .ai-board/plans/<cardId>.md` で、計画の変更が選んだ節の中の、未チェックだった行の `[ ]` → `[x]` だけである
     （節の外の行も、節の中の `[x]` だった行も、タスクの文も変わっていない）。
     5 の「タスクの順番を直す」をしたときは、それに当たる変更（未チェックの行の移動、`## タスク` の中の `###` の見出しの行の削除）も許す。
     ただし差分の `-` の行に、元から `[x]` だった行が無いこと
   - 5 の「タスクの順番を直す」をしたときは、計画のタスクの文の集合が変わっていないことを確かめる。
     見出しと空行を除いた計画の行を、チェックボックスの `[x]` / `[X]` を `[ ]` にそろえ、行頭の字下げを除いて並べ替え、直す前（`HEAD`）と比べる。
     出力が空でなければ、タスクの文を足した・消した・書き換えたことになる

     ```bash
     norm() { grep -v -E '^[[:space:]]*(#|$)' | sed -E 's/^[[:space:]]+//; s/\[[xX ]\]/[ ]/' | LC_ALL=C sort; }
     diff <(git -C "$WT" show HEAD:.ai-board/plans/<cardId>.md | norm) <(norm < "$WT/.ai-board/plans/<cardId>.md")
     ```

     コードブロックの中の `#` で始まる行も見出しと同じに除かれるが、`## タスク` の外が変わっていないことは上の差分の確かめで見ているので、これで足りる
2. 節の実装と計画の `[x]` を 1 つのコミットにする。節の途中でコミットを挟まない。
   メッセージは日本語の Conventional Commits で、型は節の中身に合わせる（`feat` / `fix` / `refactor` / `test` / `docs` / `chore`）。
   本文に、倒した節の題と、倒したタスクの書き出しを並べる。
   5 の「タスクの順番を直す」をしたときは、本文に「何をどの節へ移したか（どの節を合わせたか、何を入れ替えたか）と、なぜか」も書く。
   末尾の署名は、そのセッションの指示に従う
3. `git -C "$WT" push`。push が失敗したらやり直さずに止まり、コミットが手元にだけあることを報告する
4. `git -C "$WT" rev-parse HEAD` と `git -C "$WT" rev-parse origin/<branch>` が一致し、`git -C "$WT" status --porcelain` が空であることを確かめる。
   満たされなければ止まって報告する（次の手を受けるサブエージェントは、ワークツリーと `origin` の状態から続きを選ぶ）

## 7. 報告

最後の応答は次の項目だけを 5 行以内で返す。差分やファイルの中身は含めない（監視役の文脈に入るため）。

- 結果: `進めた` / `止まった` のどちらか 1 つ（監視役はこの語で次の動きを変えるので、言い換えない。`保留して止まった` は使わない）
- 節: 倒した節の見出し（30 字ほど）と、倒したタスクの数（選ぶ前に止まったときは「選んでいない」）
- コミット: コミットのハッシュと、push して `origin/<branch>` と一致したか
- 品質ゲート: 通った / どの段階で落ちたか。タスクの順番を直したときは、何をどの節へ移したかを同じ行に短く書く
- 止まった理由と、人にしてほしいこと（止まったときだけ。変更を戻したか、残したかも書く）

## ハードルール

共通の決まりの「ハードルール」に加えて、次を守る。

- 選んだ節 1 つだけを倒す。節の外のタスクのチェックボックスに触らない。計画のタスクの文を書き換えない
- 計画を直すのは、5 の「タスクの順番を直す」の範囲（未チェックのタスクの移動・節の統合・節の中の並べ替え）だけにする。タスクを足す・消す、`[x]` に触る、`## タスク` の外を変える、はしない
- 品質ゲートとコミットは節の終わりに 1 回だけにする。節の途中でコミットしない
- カードに書かない（`ai-board card submit` / `hold` / `body` / `branch` を呼ばない）
- サブエージェントを立てない
- AI レビュー（`/code-review`）をかけない。レビューは `board-reviewer` がする
- 計画を archive へ移さない。動作確認の提出をしない。PR の本文を変えない。PR にコメントしない。PR を Ready にしない
