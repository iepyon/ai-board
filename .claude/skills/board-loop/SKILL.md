# board-loop — 次の 1 手を作業者に渡す監視役

このスキルを動かすセッションは **監視役** である。監視役は次の一手を選んで作業者に渡し、返ってきた報告を人に伝えるだけで、カードの作業は自分でしない。
作業は `.claude/agents/board-worker.md` の作業者（サブエージェント）が、まっさらな文脈で行う。
前のカードで読んだコードや決めた事柄を、次のカードの作業に持ち込まないためである。

1 周で作業者に渡す手は **高々 1 つ**。何を渡すかは自分で選ばず、`ai-board status --json` の `next` に従う。
人の判断（着手・承認・否決・中止・並び順・マージ）は代行しない。動作確認（人がブランチを動かして確かめること）も代行しない。

`next.action` は次のどれかである。手の中身は作業者の手順書にあり、監視役は種類を読み分けない。

| `action`      | カードの事情                         | 作業者がすること                                                                                                                      |
| ------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `plan`        | 計画提案中で、まだ何も提出していない | 計画を書いて Draft の PR を出し、`plan 提出` を書く                                                                                   |
| `revise-plan` | 計画提案中で、計画が否決された       | 理由を読んで計画を直し、再提出する                                                                                                    |
| `implement`   | 実装中で、動作確認をまだ頼んでいない | 計画から段を決めて 1 段進める。タスクを倒す / AI レビューの作業者に指摘を書かせる / 動作確認を頼む（飛ばす宣言があれば Ready にする） |
| `revise-impl` | 実装中で、動作確認で否決された       | 理由を読んで直し、動作確認を頼み直す                                                                                                  |
| `ready`       | 実装中で、動作確認を人が承認した     | 計画を archive へ移し、PR を Ready にする                                                                                             |

動作確認を頼んだカードは 動作確認 の列に移り、人が承認か否決をするまで `next` に選ばれない（`waiting` に出る）。

計画提案中 / 実装中 のカードでも、人の判断を待って **止まっている** ものは `next` に選ばれず、`waiting` に出る。
ループはそのカードを飛ばして後ろのカードへ進む。止まりは次の 3 つで、どれも人が判断のボタンか GitHub の操作で解く。

- 作業者が否決を直しきれずに 保留 を書いた（`ai-board card hold`。`## レビュー` に `plan 保留` / `verify 保留` が残る）
- 人の判断の後に、人が PR を Draft に戻した（ループは Ready にし直さない）
- 計画を提出したのに、計画ファイルも Draft の PR も見えない

## 0. 作業中の作業者がいないかを見る

`ListAgents` で、名前が `board-worker-` で始まり、状態が `running` の作業者がいないかを見る（終わった作業者も一覧に残る）。
いれば「作業中: <作業者の名前>（<いつから>）」とだけ伝えて、この周は終わる。

作業者はバックグラウンドで動くので、作業中にも次の周が来る。このときの `status` はまだ同じ `next` を返すため、
ここで止まらないと 2 人目の作業者が同じカードに入る。
「さっき渡した」という自分の記憶ではなく `ListAgents` を見る。自動の要約で記憶が落ちても判定が変わらないようにするためである。

長く動き続けている作業者は、固まっている見込みがある。報告にいつから動いているかを書き、人が `TaskStop` で止められるようにする。

## 1. ボードを読む

メインのチェックアウト（以下 `$MAIN`）で `status` を読む。`dist/` が古ければ先にビルドする。
`status --json` は全カードの全項目を出すので、`next` / `waiting` / `forge` だけを取り出して読む（監視役の文脈を膨らませないため）。

```bash
MAIN=$(git worktree list --porcelain | sed -n '1s/^worktree //p')
# dist/cli.js が無いか、HEAD のコミットより古ければビルドする（stat の書式は OS で違うので node で比べる）
if ! node -e 'const fs=require("fs");const [f,t]=process.argv.slice(1);process.exit(fs.existsSync(f)&&fs.statSync(f).mtimeMs/1000>=Number(t)?0:1)' \
    "$MAIN/dist/cli.js" "$(git -C "$MAIN" log -1 --format=%ct)"; then
  npm --prefix "$MAIN" run build
fi
# パイプでつなぐと status の失敗が絞り込みの JSON エラーに隠れるので、一度受けてから絞る
if out=$(node "$MAIN/dist/cli.js" status --json --root "$MAIN"); then
  printf '%s' "$out" | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const j=JSON.parse(s);console.log(JSON.stringify({next:j.next,waiting:j.waiting,forge:j.forge}))})'
else
  echo "status が失敗した"
fi
```

## 2. 止まる条件（何も渡さずに報告して終わる）

- `status` が失敗した。「不明なオプションです: status」なら、`$MAIN` のコードが `ai-board status` を持たない古いものである。
  `$MAIN` を `origin/main` に更新してビルドし直すよう人に頼む（自分では更新しない）
- `next` が `null`。`waiting` のカードを人に知らせて終わる。
  `waiting` には 計画レビュー（計画を読む）・動作確認（ブランチを動かして確かめる）・PR中（差分を読む）のカードと、AI の列にいても止まっているカード（上の 3 つ）が入る。
  止まっているカードの `reason` には、人が何をすればよいか（実装を直させる / 計画から立て直させる / PR を Ready に戻す / 中止する など）が書かれている。
  どの判断を待っているかを、`reason` のとおりに書く
  `forge.status` が `connected` でないとき（`gh` の未ログイン、問い合わせの失敗、`config.yaml` に `github:` が無い）も、
  `status` は `next` を `null` にする。PR の状態が引けないと、計画レビュー / PR中 のカードが手前の AI の列に落ちて見えるため。
  このときは `forge` の理由を人に知らせる

## 3. 作業者に渡す

`Agent` を次の形で呼ぶ。

- `subagent_type`: `board-worker`
- `name`: `board-worker-<next.cardId の先頭 46 文字>-<HHmm>`（今の時刻）。
  名前は 64 文字までだが、カード ID は 100 文字まで取りうるので切り詰める。
  同じカードには手ごとに何度も作業者を渡すので、時刻を付けて前の作業者と名前がぶつからないようにする
- `description`: `<next.action> <next.cardId>`
- `prompt`: 次の 3 行だけを書く。要約や補足を足さない

```
cardId: <next.cardId>
action: <next.action>
MAIN: <$MAIN>
```

作業者はカード本文・計画ファイル・PR を自分で読み直す。監視役が要約を添えると、監視役の文脈にある前のカードの前提がそこから漏れる。
人がこのセッションで口頭で伝えた補足は作業者に届かない。補足はカード本文の `## 探索メモ` に書いてもらう。

渡したら「<カード ID> の <手> を作業者に渡した」とだけ伝えて、この周は終わる。

## 4. 作業者の報告を伝える

作業者が終わると、完了の通知が届く。この手番では、まず作業者の報告を 3 行以内に縮めて人に伝える。
作業者の主張を確かめ直すことはしない。続けて読む `status` が実態を映す。

伝えた後は、次の cron の周を待たずに、この手番を新しい 1 周として手順 0 から 3 を続ける。
実装中は人の判断を挟まない区間なので、手と手の間で周を待つ理由が無い。
手順 0 の判定は残るので、続けている間に cron の周が来ても、作業中の作業者がいればその周は止まる。

ただし続けるのは、作業者の結果が「進めた」のときと、保留を書いて止まったときだけにする。
保留を書かずに止まったときは続けず、報告だけで終える。
そのカードは次も `next` に選ばれるので、続けると同じ手がすぐに渡り、同じ止まり方を繰り返すためである。

作業者が動作確認を頼んで止まったときは、そのカードが人の番になったことと、PR の URL をはっきり書く。
動かす手順はカードの提出の本文にあり、判断待ちの区画で読める。監視役は手順を読んで書き写さない。

作業者が 保留 を書いて止まったカードは、次の周から `waiting` に出て `next` に選ばれない。ループは後ろのカードへ進む。
報告ではそのカードが判断待ちになったことと、作業者が書いた止まった理由を短く書く。

保留を書かずに止まったカード（ゲートが通らない、未コミットの変更が残っている、カードやブランチが見つからない）は、次の cron の周でも `next` に選ばれ、ループはそこで止まり続ける。
これらは人がワークツリーを直す話で、判断のボタンでは解けないので保留にしない。
人が直すまで他のカードには進まない。報告ではそのカードと、人に何をしてほしいかをはっきり書く。

## ハードルール

- 1 周で作業者に渡す手は高々 1 つ。作業中の作業者がいれば渡さない。完了の通知を受けて手順 0 から続ける手番も、それで 1 周と数える
- カード本文・計画ファイル・差分・PR を読まない。作業者に渡すのはカード ID・手の種類・`$MAIN` だけ
- `Agent` が失敗しても、自分で作業せずに止まって報告する
- `subagent_type: "fork"` を使わない。fork は監視役の会話をすべて引き継ぐので、作業者を切り離す意味が無くなる
- `/code-review` も監視役では走らせない（差分が監視役の文脈に入るため）。作業者の中で行う
- カードへの書き込みはしない。`startedAt` / `rank` / `skipGates` や承認 / 否決 / 中止（plan と verify のどちらでも）を書かず、PR をマージしない。
  `## レビュー` に AI が書いてよい 提出 / 再提出 / 保留 も、書くのは作業者だけで、監視役は書かない
- 止まっているカード（`waiting` に出たもの）を、監視役の判断で作業者に渡さない。PR を Ready に戻したり、保留を解いたりもしない
