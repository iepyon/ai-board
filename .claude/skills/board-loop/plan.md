# plan / revise-plan — 計画提案中のカードを 1 手進める

`board-loop` の手順で、`next.action` が `plan` / `revise-plan` のときに、本筋のセッションが自分で行う手順である。

`$MAIN/.claude/skills/board-loop/rules.md`（以下、共通の決まり）が文脈に無ければ、始める前に読む。
呼び名、カードの読み書き、ワークツリーへの入り方、タスクの数え方、保留の書き方、共通のハードルールはそこにある。

以下、`<id>` は `next.cardId`、`$MAIN` はメインのチェックアウトのパスである。

## 1. カードのワークツリーに入る

共通の決まりの「ワークツリーに入る」に従う。

## 2. `plan` — 計画を書いて提出する

1. カード本文（アイデア / 背景 / 論点 / 探索メモ）と関係するコードを読む
2. `.ai-board/plans/<id>.md` に計画を書く。Plan モードのツールは使わない（承認待ちで止まる。人の確認は Draft の PR で行う）。
   次の構成で書く。書きぶりは `.ai-board/plans/archive/` の計画にならう。日本語で書く。

   ```markdown
   # 題

   ## 人に判断してほしいこと

   ## 提案

   ### Why / ### What Changes / ### Impact

   ## 設計

   ### Decisions
   ### 仮定
   ### 退けた代案
   ### Risks / Trade-offs
   ### Non-Goals

   ## 探索メモとの対応

   ## 動作確認の手順

   ## タスク
   ```

   方針は「決めて記録する」である。迷ったら根拠の強い方を選んで進み、その選択を `### 仮定` に書く。
   人に聞くのは、人にしか決められないこと（製品の意図・互換を壊してよいか・優先度）だけにする。
   - `## 人に判断してほしいこと`: 題の直後に置き、人が計画レビューで最初に読む。人にしか決められないことだけを、1 項目ずつ、何を決めてほしいかと AI が置いた既定（決めなければこう進む）で書く。
     無ければ `- なし` と書く（節を省くと書き忘れと区別できないため）。この節の中身を、そのまま 4 の PR の本文の「判断してほしい点」と 5 の `--reason` に渡す。
     人が答えたら、問いは消さずに、その項目の下に `  - → 回答（<日付>、<出どころ: plan 承認 / plan 否決 / PR のコメント / チャット>）: <人の言葉>` の行を足す。
     追記は、答えを受けた後に計画を触る手（`revise-plan`、`implement` の最初の節、`fix-pr`）が行う。答えは人の言葉のまま写し、言い換えない。
     末尾の `## AI レビュー` 節の `### 人に判断してほしいこと`（`board-reviewer` が実装の後に書き、PR中 で決めてもらうもの）とは別の節で、答えの残し方は同じにする
   - `### Decisions`: 何をどう作るかを書く。仮定と退けた代案はここに混ぜない
   - `### 仮定`: 人に聞かずに AI が決めたことを、根拠（コード・ADR・探索メモ・前の計画）と一緒に書く。人は計画レビューで読み、違えば否決で直させる
   - `### 退けた代案`: 考えて捨てた案を 1 行ずつ、捨てた理由と一緒に書く。実装とレビューの側が「なぜこうしないのか」を追えるようにする
   - `## 探索メモとの対応`: カードの `## 探索メモ` の段落か箇条を 1 項目として、上から番号を振って表に並べる。
     列は「#」「探索メモ（短い引用）」「反映した先（計画の節の名前）」「反映しなかった理由」で、反映した項目は理由を空ける。
     番号は計画の側だけで振り、カードの探索メモには書かない。着手の会話などで人と決めた、カードに書かれていないことも「人と決めた（日付）: …」の行として足す。
     探索メモも人と決めたことも無ければ `- 探索メモなし` と書く
   `## 動作確認の手順` には、実装後に動かして確かめる手順（起動のコマンド、見る画面、期待する結果）を書く。
   締めの段で「確かめたこと / コマンド / 結果」の表の 1 行にできるよう、1 つの手順に 1 つの確かめること・コマンド・期待する結果を書く。
   AI が動かせない手順（画面の見た目、共有のカードへの書き込みなど）は、そうと分かるように書く（表では `走らせていない` 行になる）。
   `implement` の締めの段で AI が動かせるところを動かし、結果を PR の本文に書く。人は PR中 でそれを読み、必要なら手で動かす。
   古い archive の計画にはこの節が無いので、`.ai-board/plans/archive/verify-gate.md` を手本にする。
   `## タスク` は次の決まりで `### <番号>. <題>` の節に区切る。節は `implement` の手で品質ゲートを通してコミットする単位で、止まってよい区切りである。
   `implement` の手は残りの節を上から順に倒し、品質ゲートとコミットは節の終わりごとに 1 回だけ行う
   （節の決め方は共通の決まりの「タスクの数え方と `## AI レビュー` 節」）
   - 節の切れ目は、その節までを倒し終えたら品質ゲートが通るところに置く
   - 節の途中のタスクの後では、ゲートが通らなくてよい。型を壊す変更と、それを受け止める箇所（呼び出し側やテストの切り替え）は同じ節に入れる
   - 1 つの節は、区切りで止まっても次の周が続きから始められるよう、1 つの節だけで倒し切れる大きさにする。目安はタスクが数個、変わるファイルが十数個まで
   - 小さなカードなら、節が 1 つだけでもよい
3. 提出の前に、次を自分で確かめる。満たされなければ計画を直してから進む。確かめた結果は計画にもコミットにも書かない
   - カードの `## 探索メモ` の項目が、すべて `## 探索メモとの対応` の表にある
   - `## 人に判断してほしいこと` の中身と、5 で渡す `--reason` が同じである
4. コミット（`docs: 〜の計画を立てる`）→ `git push -u origin <branch>` → `ai-board pr create --draft --head <branch> --title "<題>" --body-file <ファイル>`
   （本文に計画ファイルの場所、概要、判断してほしい点（計画の `## 人に判断してほしいこと` の中身）。ファイルは `$WT` の外（スクラッチパッドなど）に作る）
5. `ai-board card branch <id> <branch>` → `ai-board card submit <id> --reason "<計画の ## 人に判断してほしいこと の中身>"`（`- なし` なら「判断してほしい点なし」）

## 3. `revise-plan` — 否決された計画を直して再提出する

1. `ai-board card show <id>` の `## レビュー` の最新の plan 否決 の理由と、`ai-board pr view <mr> --comments` を読む
2. 計画を直す。否決の理由が読み取れない、または直し方に人の判断が要るときは、手を付けずに共通の決まりの「直しきれないとき」に従い、`--gate plan` で保留を書いて止まる。
   直すときは、中身の直しに加えて次も行う
   - 否決の理由を `## 探索メモとの対応` の表に「plan 否決（日付）: <理由の短い引用>」の行として足し、反映した先を書く
   - 直した後の計画の `## 人に判断してほしいこと` を読み直し、否決の理由で答えが出た項目には、消さずに `→ 回答（<日付>、plan 否決）` の行を足す
   - archive から戻した古い計画など、`plan` の 2 の構成に足りない節があれば足す

   ここまで済んだらコミット（`docs: 〜の計画を直す`）→ push する
3. `ai-board card submit <id> --resubmit --reason "<直した点と、残った判断してほしい点>"`。
   理由は「直した点:」と「判断してほしい点:」の 2 段にする。「判断してほしい点:」には、直した後の計画の `## 人に判断してほしいこと` のうち、回答の行がまだ無い項目をそのまま渡す（無ければ「判断してほしい点なし」）。
   再提出を読む人が、ボードの判断待ちの理由だけで、何が変わり何を決めればよいかを読めるようにする

`## レビュー` に、その否決より前の plan 承認 があるカードは、人が実装の途中から「計画から立て直させる」を選んだものである。
`skipGates` に `plan` があるカード（plan を飛ばす宣言のカード）では、その否決より前の plan 提出 / 再提出 も同じに扱う
（宣言のあるゲートでは 提出 / 再提出 が承認と読まれ、plan 承認 のエントリは無いため）。
ブランチには前の実装が残り、計画のタスクには `[x]` が付いている。計画を直すときに次も行う。

- 作り直すタスクの `[x]` を外すか、新しいタスクを `- [ ]` で足す。`[x]` のままのタスクは、次の `implement` で倒し済みとして飛ばされる。
  このときも `plan` の 2 の節の決まり（切れ目はゲートが通るところ、節の途中は壊れてよい、節の大きさの目安）を守る。
  `[x]` を外したタスクや足したタスクが、ゲートの通らない切れ目で節を終えないように、必要なら節を区切り直す
- 前の実装のうち、残すものと捨てるものを計画に書く
- 計画が `.ai-board/plans/archive/<id>.md` にある（`implement` の締めの段で Ready にした後に人が Draft に戻した）なら、
  直す前に `git mv .ai-board/plans/archive/<id>.md .ai-board/plans/<id>.md` で戻す。新しく `plans/<id>.md` を作って二重にしない
- 計画に `## AI レビュー` 節（あるかの決め方は共通の決まりの「タスクの数え方と `## AI レビュー` 節」）があれば、節ごと消す（archive から戻した計画も同じ）。
  見出しの行から、次の `## ` の見出しの手前（無ければファイルの終わり）までを消し、中の `### 見送った指摘` と `### 人に判断してほしいこと` も一緒に消す。
  節が残っていると、作り直した実装を倒し終えたときにレビューの段を飛ばし、前の実装へのレビューのまま締めの段へ進んでしまう。
  消すのはコードブロックの外にある見出しの節だけで、例の中の `## AI レビュー` には触らない。
  作り直した後のレビューの段で、新しい差分に対して `board-reviewer` が改めて節を書く

## 4. 手の終わり

手を終えたら、`結果:` を次のどれか 1 つに決める（`SKILL.md` の手順で `loop finish` の `--result` と、続けるかどうかに使う）。

- `進めた`: 計画を提出した、または直して再提出した
- `保留して止まった`: 否決を直しきれず、`--gate plan` で保留を書いた
- `止まった`: それ以外で止まった（ワークツリーに未コミットの変更が残っている、ブランチが既にある、品質ゲートが通らない など）

人には、何をしたか、人が見るもの（PR の URL、判断待ちになったカード）、止まったときは理由と人にしてほしいことを伝える。

## ハードルール

共通の決まりの「ハードルール」に加えて、次を守る。

- 計画ファイルだけを書く。コードは書かない
- カードに書いてよいのは、`ai-board card branch` と、`## レビュー` への 提出 / 再提出（`ai-board card submit`）と 保留（`ai-board card hold`）だけ。どれも plan ゲートだけに書く
- PR を Ready にしない
