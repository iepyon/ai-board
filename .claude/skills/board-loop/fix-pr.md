# fix-pr — PR中 のカードで、人の指摘に応える

`board-loop` の手順で、`next.action` が `fix-pr` のときに、本筋のセッションが自分で行う手順である。

PR中 のカードは人の番だが、人が PR に指摘（コメント）を書き、その後に修正コミットも AI の返信も無いときだけ、AI の番になる（`src/shared/pr-feedback.ts` の `awaitsPrFix`）。
この手は、PR を Ready のまま修正を push するか、直すものが無い理由を 1 件返信して、カードを人の番（判断待ちの区画）に戻す。
ステージは PR中 のまま変わらない。

`$MAIN/.claude/skills/board-loop/rules.md`（以下、共通の決まり）が文脈に無ければ、始める前に読む。
呼び名、カードの読み書き、ワークツリーへの入り方、指摘の分け方、動かして確かめるときの決まり、共通のハードルールはそこにある。

以下、`<id>` は `next.cardId`、`<mr>` はカードの `mr`、`$MAIN` はメインのチェックアウトのパスである。
「止まって報告する」は、`止まった` で手を終え（4 の「手の終わり」）、理由を人に伝えることを言う。

## 1. カードのワークツリーに入る

共通の決まりの「ワークツリーに入る」に従い、カードの `branch` のワークツリーに入って `git pull --ff-only` する。
`branch` か `mr` が null、ワークツリーに未コミットの変更が残っている、`git pull --ff-only` が失敗した、のどれかなら、何も変えずに止まって報告する。

## 2. 指摘を読む

1. `ai-board pr view <mr> --comments` で、PR のコメントを読む。
   応えるのは、ブランチの最新コミットと、AI の最新のコメント（本文に `_Generated by [Claude Code](https://claude.ai/code)_` を含むもの）の、どちらよりも後に人が書いたコメントである
2. カード本文と、計画（`.ai-board/plans/archive/<id>.md`）の `## 設計` の Decisions / Non-Goals を読む。計画は書き換えない
3. 指摘ごとに「直す / 直さない」を決める。決め方は共通の決まりの「指摘の分け方」の「直す / 見送る」と同じで、迷ったら直す。
   次のときは直さず、返信で人に聞く
   - 直すと計画の Non-Goals に踏み込む
   - 直し方が 2 つ以上あり、どれを採るかで振る舞いが変わる
   - 指摘が質問や承認（「LGTM」など）で、直すものが無い

## 3. 応える

### 3.1 直すものがあるとき — 修正を push する

1. 直す。振る舞いを変えたら `src/**/__tests__/**/*.test.ts` にテストを足す。バグの直しは、先にテストを書いて直す前に落ちることを確かめる（`implement.md` の 2.1 の 3 の 5 と同じ）
2. 品質ゲート `cd "$WT" && npm run typecheck && npm run lint && npm run format:check && npm test` を通す。通せなければコミットせず、変更を残したまま止まって報告する
3. `fix: PR の指摘に応える` のコミットにする。本文に、応えたコメントの URL を 1 行ずつ並べ、直した / 直さなかった（理由）を添える。
   直さない指摘が混ざっていても返信はしない（push で人の番に戻り、人はコミットの本文を読む）
4. `git -C "$WT" push origin <branch>`
5. `ai-board pr checks <mr> --wait --sha "$(git -C "$WT" rev-parse HEAD)"` で CI を確かめる。扱いは `implement.md` の 2.2 の 2 と同じ
   （赤なら直すのはブランチのコミットの本文の `CI を通すための直し` の行で数えて 2 回まで、`pending` やチェックを読めないときは直さずに止まる）

### 3.2 直すものが無いとき — 理由を 1 件だけ返信する

1. 応えるコメントそれぞれに、直さない理由（質問なら答え、人に判断してほしいことならその問い）を書いた 1 件の返信を、`$WT` の外（スクラッチパッドなど）のファイルに作る
2. `ai-board pr comment <mr> --body-file <ファイル>` で書く。CLI が本文の末尾に Claude Code のフッターを補い、ボードはそれを AI の返信と読む。
   `gh` で直接書かない（フッターが付かないと、人の指摘として数えられ、AI の番に戻る）

## 4. 手の終わり

手を終えたら、`結果:` を次のどれか 1 つに決める（`SKILL.md` の手順で `loop finish` の `--result` と、続けるかどうかに使う）。

- `進めた`: 修正を push して CI が通った（または `none`）、または返信を書いた
- `止まった`: それ以外で止まった（ブランチや PR が無い、未コミットの変更が残っている、品質ゲートや CI が通らない など）

止まった後にカードがどこへ行くかは、push の前か後かで分かれる。

- **push の前に止まった**（品質ゲートが通らない、未コミットの変更が残っている、ブランチや PR が無い）: カードは AI の番のままで、次の周も `next` に最優先で選ばれる。
  人がワークツリーを直すまで、ループはここで止まる
- **push の後に止まった**（CI が赤のまま直しきれない、`pending`、チェックを読めない）: push で最新コミットが人の指摘より後になるので、
  カードは判断待ちの区画に「再レビュー待ち」で戻り、ループはもう選ばない。人は区画だけでは CI が通っていないことに気づけないので、
  CI の結果（チェックの名前・結果・URL）と PR の URL を必ず人に伝える

人には、応えたコメントの件数、push したコミットか書いた返信の URL、CI の結果、止まったときは理由と人にしてほしいことを伝える。

## ハードルール

共通の決まりの「ハードルール」に加えて、次を守る。

- PR中 のカードに触ってよいのは、この手の中だけ。してよいのは、カードのブランチへの修正の push と、`ai-board pr comment` での返信 1 件だけ
- PR を Draft に戻さない、Ready に触らない、マージしない。PR の本文（`## 動作確認の結果` など）を書き換えない
- 計画（archive 済み）とカードに書かない。`ai-board card` の CLI は使わない
- 返信は直すものが無いときの 1 件だけにする。指摘ごとに返信しない
- `board-reviewer` を立てない（AI レビューは実装の後の 1 回だけ）
