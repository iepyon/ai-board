# implement — 実装中のカードを 1 手進める

`board-loop` の手順で、`next.action` が `implement`（`next.step` が `task` / `close` / `null`）のときに、
本筋のセッションが自分で行う手順である。
同じ手の中では、節やタスクをまたいで読んだコードや決めた事柄を持ち込んでよい。

実装を書いたセッションは、自分の差分を AI レビューしない（共通の決まりの「呼び名」の「書いた者が審査しない」）。
レビューの段だけは、`SKILL.md` の手順で `board-reviewer` のサブエージェントを立てて切り分ける。

`$MAIN/.claude/skills/board-loop/rules.md`（以下、共通の決まり）が文脈に無ければ、始める前に読む。
呼び名、カードの読み書き、ワークツリーへの入り方、タスクの数え方と節の決め方、
動かして確かめるときの決まり、共通のハードルールはそこにある。

以下、`<cardId>` / `<id>` は `next.cardId`、`$MAIN` はメインのチェックアウトのパスである。
「止まって報告する」は、`止まった` で手を終え（5 の「手の終わり」）、理由を人に伝えることを言う。

## 1. カードのワークツリーに入る

共通の決まりの「ワークツリーに入る」に従い、カードの `branch` のワークツリーに入って `git pull --ff-only` する（GitHub が未設定のボードではしない）。
`branch` が null、ワークツリーに未コミットの変更が残っている（前の手が途中で止まっている）、`git pull --ff-only` が失敗した、のどれかなら、何も変えずに止まって報告する。

**GitHub が未設定のボード**（共通の決まりの「GitHub が未設定のボード」）では、この手順書の push・`# branch.ab +0 -0` の確かめ・`ai-board pr` をすべて飛ばす。
飛ばした後にすることは、各段の「未設定のボード」の項に書く。

## 2. `implement` — 受けた段から締めの段まで続けて進める

計画は `.ai-board/plans/<id>.md` か `.ai-board/plans/archive/<id>.md` にある。
計画を読み、次の表の上から当てはまった行のことをする。
タスクの数え方と、`## AI レビュー` 節があるかの決め方は、共通の決まりの「タスクの数え方と `## AI レビュー` 節」に従う。

| 計画の状態                                          | 段             | すること                                                                                                                          |
| --------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `plans/archive/` にある                             | archive 済み   | 前の周で `ai-board pr ready` だけが失敗している。`ai-board pr ready <pr>` だけをやり直す（未設定のボードでは何もせず `止まった`） |
| 未チェックのタスクがあり、`## AI レビュー` 節が無い | タスクを倒す段 | 2.1 で節を上から順に倒す。全部倒したら `進めた` で手を終える（次の手で `board-reviewer` が立つ）                                  |
| 未チェックのタスクがあり、`## AI レビュー` 節がある | タスクを倒す段 | 2.1 で節（レビューの直す指摘を含む）を上から順に倒す。全部倒したら同じ手のまま 2.2 の締めの段へ進む                               |
| 全部倒れていて、`## AI レビュー` 節が無い           | レビューの段   | 何も変えずに `止まった` で手を終える（段の食い違い。`board-reviewer` を立てるのは `SKILL.md` だけ）                               |
| 全部倒れていて、`## AI レビュー` 節がある           | 締めの段       | 2.2 で動かして確かめ、証拠と指摘を PR の本文に書き、archive して Ready にする                                                     |

`SKILL.md` は `ai-board status --json` の `next.step` で読む手順書を決め、`review` なら `board-reviewer` を立てる。
この手順書を読むのは `next.step` が `task`（タスクを倒す段）か `close`（締めの段か archive 済みの段）か `null`（`status` が段を読めなかった）のときである。
`task` の手が、倒し終えた後に締めの段まで進むことがある。`next.step` の値は計画の状態をそのまま映すだけで、変わらない。

- **レビューの段の前で手を終える。** 実装した文脈のまま自分でレビューしないためである。
  `## AI レビュー` 節が無い計画のタスクを倒し終えたら、`/code-review` をかけず、締めの段にも進まずに `進めた` で手を終える。
  `SKILL.md` が同じ手番で `status` を読み直し、レビューの段として `board-reviewer` を立てる
- **直す指摘を倒した後は締めの段へ続けてよい。** AI レビューは 1 回だけで、直す指摘を倒した後にもう一度のレビューはしない。
  締めの段で読むのは計画の `## AI レビュー` 節と PR の本文で、どちらも直したばかりの文脈にある
- 読んだ段がレビューの段（上の表）なら、理由には段の食い違い（`status` が `git show` で読んだ計画と、`git pull --ff-only` した後のワークツリーの計画で段が違った、または `next.step` が `null` だった）と、読んだ段の名前を書く。
  保留は書かない。次の周で `status` を読み直し、正しい段を選ぶ

どこで止まっても、状態は計画のチェックボックスと節ごとのコミットに残るので、次の周は同じ表から続きを選べる。特別な引き継ぎは作らない。

GitHub が未設定のボードでは、締めを終えたカード（ブランチで計画が archive 済み）はブランチのマージ待ちの止まりになり、`next` に選ばれない。
それでも archive 済みの段を読んだら（段の食い違い）、何も変えずに `止まった` で手を終える。PR が無いので Ready にするものが無い。

### 2.1 タスクを倒す段 — 残りの節を上から順に倒す

次の 1〜6 を、節ごとに繰り返す。1 つの節を倒し終えて push したら、6 で次の節へ進むか止まるかを決める。

最初の節に入る前に、ワークツリーに入るときに読んだカード本文（アイデア / 背景 / 論点 / `## レビュー`）と、計画の全体を読む。
特に `## 設計` の Decisions / 仮定 / Non-Goals と、`## タスク` の節の並び（前の節で何ができているはずか）を読む。
前の周で倒した節で作られたはずのものは、要約に頼らずワークツリーのコードと `git -C "$WT" log` で確かめる。
同じ手の中で次の節へ進むときは、読み直さなくてよい（文脈にある）。

計画の冒頭の `## 人に判断してほしいこと` に、回答の行（`→ 回答`）がまだ無い項目があれば、最初の節のタスクに入る前に回答を足す。
答えは `## レビュー` の最新の plan 承認 の理由（`skipGates` に `plan` があるカードでは、承認と読まれた提出の後に人が書いたもの）から、項目ごとに人の言葉のまま写す。
理由が無い、またはどの項目への答えか読み分けられないときは、`  - → 回答（<日付>、plan 承認）: 理由なしで承認（既定のまま進む）` か、理由の全文をそのまま書く。
この追記は最初の節のコミットに含める。

#### 1. 節を選ぶ

節は、共通の決まりの「タスクの数え方と `## AI レビュー` 節」の節の決め方に従って選ぶ。
上から最初の未チェックのタスクの行（字下げされたサブタスクも 1 つと数える。`## AI レビュー` 節の直す指摘も含む）を見つけ、
その行から上へたどって最初に当たる見出しの行から、次の見出しの行の手前までを節とする。
以下、この範囲を「選んだ節」、選んだ節の中の未チェックのタスクの行を「節のタスク」と呼ぶ。節の中の `[x]` のタスクは飛ばす。

節に区切っていない計画では `## タスク` 全体が、`## AI レビュー` 節の直す指摘は `## AI レビュー` の見出しから次の見出しの手前までが、選んだ節になる。

#### 2. タスクの範囲を決める

節のタスクのそれぞれについて、その行がタスクの書き出しである。次をそのタスクに含める。

- その行に続く、折り返しの行（行頭を字下げして続けた文）
- その行の下に字下げして並ぶ、チェックボックスの無い箇条（タスクの中身を細かく書いたもの）

字下げされていても `- [ ]` / `- [x]` で始まる行は別のタスクである。節の中にあれば節のタスクとして別に倒し、節の外にあれば今の節ではやらない。

節のタスクが `## AI レビュー` 節の行（`board-reviewer` が書いた直す指摘）でも、ほかのタスクと同じに扱う。
その 1 行に書かれた場所・起きること・直し方だけを直す。指摘の文は書き換えない。

#### 3. 節のタスクを上から順に倒す

1. 節のタスクを上から 1 つずつ実装する。選んだ節の外（次の節）に書かれていることを先回りしてやらない。
   振る舞いを足したら、`src/**/__tests__/**/*.test.ts` にテストを足す
2. タスクを 1 つ倒すごとに、計画のその行の `- [ ]` を `- [x]` に変える（コミットはしない）。
   変えるのはその行のチェックボックスだけで、行の文、ほかの行、計画のほかの節は変えない。
   文脈が長くなって自動の要約が入っても、計画を読み直せばどこまで済んだかが分かる
3. 節の途中のタスクの後では、品質ゲートを走らせなくてよい。テストや型が落ちていてもよい（節の終わりで通す）
4. 計画の `## 動作確認の手順` や CLI・API を動かして確かめるときは、共通の決まりの「動かして確かめるとき」に従う
5. **fix の確かめ。** バグの直し（`## AI レビュー` 節の直す指摘のうち誤った振る舞いを直すもの、計画で fix と書いたタスク）は、
   先にテストを書いて、直す前のコードでそのテストが落ちることを確かめてから直す。直した後で通ることも確かめる。
   確かめたテストの名前は、5 のコミットの本文に `直す前に落ちることを確かめた: <テストの名前>` の行で残す（締めの段は別の周のことがあるので、文脈ではなく git に残す）。
   新しい機能のテストには求めない

実装の途中で、次のどれかに当たると分かったら、今の節の変更（選んだ節の中で倒したタスクの分と、計画の `[x]` を含む）を
`git -C "$WT" checkout -- .` と `git -C "$WT" clean -fd` で戻し、止まって報告する。前の節のコミットはそのまま残す。

- タスクの書き方から、何をすればよいかが一通りに決まらない
- タスクが計画の Decisions / 仮定 / Non-Goals、`CLAUDE.md` のハードルールと食い違う
- 選んだ節を倒し終えても品質ゲートを通せる形にならず、直すには 4 の「タスクの順番を直す」で許していない計画の変更（タスクの文の書き換え・追加・削除など）が要る

人の判断が要る止まりでも、`ai-board card hold` は書かない。`implement` に保留は無く、止まりは手の終わりに人に伝える。

#### 4. 節の終わりで品質ゲートを通す

節のタスクをすべて倒し終えたら、品質ゲートを走らせる。

```bash
cd "$WT" && npm run typecheck && npm run lint && npm run format:check && npm test
```

整形が崩れていたら `cd "$WT" && npm run format` で直す。
落ちたら直して通し直す。落ちた原因がタスクの順番（後ろの節のタスクも一緒に入れないと通らない）なら、次の「タスクの順番を直す」に進む。
それ以外で直せなければコミットせず、変更を残したまま止まって報告する（どの段階で落ちたかを書く）。
計画ファイルやエージェントの定義だけの変更でも、ゲートは走らせる。

##### タスクの順番を直す

節の終わりでゲートが通らず、その原因が「後ろの節のタスクも一緒に入れないと通らない」ことなら、計画の `## タスク` を直してから続けてよい。
人の判断は待たない（`implement` に保留は無い）。直してよいのは次の 3 つだけである。

- 未チェックのタスクの行を、別の節へ移す（後ろの節のタスクを今の節へ移す、など）。折り返しの行と、下に字下げして並ぶチェックボックスの無い箇条も一緒に移す
- 隣り合う節を 1 つに合わせる（後ろの節の `### <番号>. <題>` の見出しの行を 1 つ消す）
- 節の中で、未チェックのタスクの並びを入れ替える

次はしない。これが要るなら、今の節の変更（計画の `[x]` と順番の直しを含む）を
`git -C "$WT" checkout -- .` と `git -C "$WT" clean -fd` ですべて戻し、止まって報告する。

- タスクの文を書き換える、タスクを足す、消す
- `[x]` のタスクを動かす、チェックを外す
- 見出しを足す、見出しの文を書き換える
- 計画の `## タスク` 以外の節（`## 設計` の Decisions、`## 動作確認の手順`、`## AI レビュー` など）を変える

直した後は、移してきたタスクも選んだ節のタスクとして 3 の手順で倒し（倒したら `[x]` を付ける）、節の終わりでゲートを通し直す。
直しても通らなければ、変更を残したまま止まって報告する。
直したことは、5 のコミットの本文と、人に伝える中身に書く。

#### 5. コミットと push

1. 次を確かめる。満たされなければコミットせず、変更を残したまま止まって報告する
   - 節のタスクがすべて `[x]` になっている
   - `git -C "$WT" status --porcelain` で、変わったファイルが選んだ節の実装と計画だけである
   - `git -C "$WT" diff -- .ai-board/plans/<cardId>.md` で、計画の変更が選んだ節の中の、未チェックだった行の `[ ]` → `[x]` だけである
     （節の外の行も、節の中の `[x]` だった行も、タスクの文も変わっていない）。
     4 の「タスクの順番を直す」をしたときは、それに当たる変更（未チェックの行の移動、`## タスク` の中の `###` の見出しの行の削除）も許す。
     最初の節では、`## 人に判断してほしいこと` の項目の下に `→ 回答` の行を足した変更（`+` の行だけ）も許す。
     ただし差分の `-` の行に、元から `[x]` だった行が無いこと
   - 4 の「タスクの順番を直す」をしたときは、計画のタスクの文の集合が変わっていないことを確かめる。
     見出しと空行を除いた計画の行を、チェックボックスの `[x]` / `[X]` を `[ ]` にそろえ、行頭の字下げを除いて並べ替え、直す前（`HEAD`）と比べる。
     出力が空でなければ、タスクの文を足した・消した・書き換えたことになる

     ```bash
     norm() { grep -v -E '^[[:space:]]*(#|$)' | sed -E 's/^[[:space:]]+//; s/\[[xX ]\]/[ ]/' | LC_ALL=C sort; }
     diff <(git -C "$WT" show HEAD:.ai-board/plans/<cardId>.md | norm) <(norm < "$WT/.ai-board/plans/<cardId>.md")
     ```

     コードブロックの中の `#` で始まる行も見出しと同じに除かれるが、`## タスク` の外が変わっていないことは上の差分の確かめで見ているので、これで足りる

2. 節の実装と計画の `[x]` を 1 つのコミットにする。節の途中でコミットを挟まない。
   メッセージは日本語の Conventional Commits で、型は節の中身に合わせる（`feat` / `fix` / `refactor` / `test` / `docs` / `chore`）。
   本文に、倒した節の題と、倒したタスクの書き出しを並べる。3 の 5 で fix の確かめをしたら、その行も書く。
   4 の「タスクの順番を直す」をしたときは、本文に「何をどの節へ移したか（どの節を合わせたか、何を入れ替えたか）と、なぜか」も書く。
   末尾の署名は、そのセッションの指示に従う
3. `git -C "$WT" push origin <branch>`。push が失敗したらやり直さずに止まり、コミットが手元にだけあることを報告する
4. `git -C "$WT" status --porcelain=v2 --branch` で、`# branch.ab +0 -0` の行があり、変更の行が無いことを確かめる（`origin/<branch>` と一致し、未コミットの変更が無い）。
   満たされなければ止まって報告する（次の周は、ワークツリーと `origin` の状態から続きを選ぶ）

**未設定のボード:** 3 の push と、4 の `# branch.ab +0 -0` の確かめを飛ばす。4 は変更の行が無いこと（`git -C "$WT" status --porcelain` が空）だけを確かめる。

#### 6. 次の節へ進むか、止まるか

節を 1 つ倒して push し終えたこの区切りで、次の上から当てはまったものをする。

1. **計画に未チェックのタスクが残っている:** `#### 1. 節を選ぶ` に戻り、次の節を選ぶ
2. **全部倒れていて、`## AI レビュー` 節が無い:** レビューの段の前なので、`進めた` で手を終える（`SKILL.md` が次の手で `board-reviewer` を立てる）
3. **全部倒れていて、`## AI レビュー` 節がある:** 同じ手のまま 2.2 の締めの段へ進む

止まる目安を節の数や変えたファイルの量で決めない。節の大きさは計画レビューで人が決めてある。

### 2.2 締めの段 — 動かして確かめ、CI を通し、PR の本文に書いて Ready にする

AI レビューはレビューの段（`board-reviewer`）で済んでいる。自分で `/code-review` をかけない（2.1 から続けて来たときも、直した差分をもう一度レビューしない）。
コードに触ってよいのは、2 で CI を通すための直しだけである。
Ready にした後は、人が PR中 で証拠を読み、必要なら手で動かし、差分を読む。人が動かすのは Ready の後なので、レビューと修正は先に済ませておく。

1. 計画の `## 動作確認の手順` を、動かせるところ（CLI、API など）は共通の決まりの「動かして確かめるとき」に従って実際に動かす
2. **CI を確かめる。**（未設定のボードでは飛ばす。CI が無く、手元の品質ゲートが唯一の確かめになる）
   `ai-board pr checks <pr> --wait --sha "$(git -C "$WT" rev-parse HEAD)"` を走らせる
   （手元の最新のコミットのチェックを、終わるまで CLI の中で待つ。push の直後で PR の head がまだ動いていない間も待つ。上限の既定は 900 秒）。
   計画を archive する前に通す。archive した後に止まると、次の周が「archive 済み（Ready だけをやり直す）」と読み、CI を確かめずに Ready にしてしまうためである。
   - 終了コード 0（`passed`、またはチェックが 1 つも無い `none`）: 3 へ進む
   - 終了コード 1（`failed`）: 直す前に、`git -C "$WT" log origin/main..HEAD` のコミットの本文で `CI を通すための直し` の行を数える。
     既に 2 つあれば（前の周で直した分も含む）、直さずに `止まった` で手を終える。`止まった` カードは次の周も `next` に選ばれるので、手の中だけで数えると周ごとに直しが積み上がるためである。
     2 つ未満なら、落ちたチェックの URL を読み、原因を確かめて直す。直したら品質ゲートを通し、本文に `CI を通すための直し: <チェックの名前>` の行を書いた `fix:` のコミットにして push し、
     もう一度 `--wait --sha` で確かめる
   - 終了コード 2（`pending`。上限まで待っても終わらなかった）: Ready にせず `止まった` で手を終える
   - 終了コード 3（PR やチェックを読めなかった。gh の失敗など）: CI が落ちたのではないので直さず、Ready にせず `止まった` で手を終える
   - 原因が読めない（ログを読めない、落ちた理由がこの PR の差分と関係しない）ときも、直さずに `止まった` で手を終える
   - 止まるときは、どのチェックがどうだったか（名前・結果・URL）と、直したならそのコミットを人に伝える。計画は archive しない
   - `status（Commit Status API）は読めませんでした` と出たら、外部の CI の結果は入っていない。3 の表に `走らせていない` 行として書く
3. PR の本文に、次の 3 つの節を書く。人は PR を開いたときに本文をまず読み、コメントは議論で流れていくので、コメントではなく本文に書く
   - `## 動作確認の結果`: 次の 3 つを書く。推測で「通った」と書かない
     - 人が動かすときの手順（動かすコマンド、見るもの、期待する結果）。計画の手順を、実装を経た後の形に直したもの
     - 「確かめたこと / コマンド / 結果」の表。結果は `通った` / `落ちた` / `走らせていない` のどれか。
       1 で動かした手順を 1 行ずつ、品質ゲートを 1 行、CI はチェックごとに 1 行（2 で直したならその後の結果）入れる。
       2.1 の fix の確かめ（`git -C "$WT" log origin/main..HEAD` のコミットの本文の `直す前に落ちることを確かめた:` の行）も 1 行ずつ入れる。
       `走らせていない` 行には、理由と、確かめるのに何が要るかを書く（人が目で見て確かめるもの、共有のカードへの書き込み、権限で読めない CI など）
     - 計画の手順から変わった点（2 で CI を直したなら、そのことも）
   - `## 判断してほしいこと`: 計画の `## AI レビュー` 節の `### 人に判断してほしいこと` の箇条。無ければこの節は書かない
   - `## 見送った AI レビューの指摘`: 計画の `## AI レビュー` 節の `### 見送った指摘` の箇条。無い（`指摘なし` のときも含む）なら、中身は `なし` とだけ書く

   書き方は次のとおり。
   - `ai-board pr view <pr> --body` で今の本文を読み、節を書いた本文を `$WT` の外（スクラッチパッドなど）のファイルに作り、
     `ai-board pr edit <pr> --body-file <ファイル>` で書き戻す
   - 節が既にあれば、その中身（次の `## ` の見出しまで）を差し替える。節を二重にしない。本文のほかの部分は変えない
   - 節が無ければ、上の順（動作確認の結果 → 判断してほしいこと → 見送った指摘）で本文の末尾に足す。末尾に署名の行があれば、その前に置く。
     人は上から読むので、振る舞いの証拠を先に、コードについての指摘を後に置く

   **未設定のボード:** PR の本文の代わりに、計画（`.ai-board/plans/<id>.md`）の末尾に同じ 3 つの節を同じ中身・同じ順で足す
   （`## AI レビュー` 節の後ろ。節が既にあれば中身を差し替え、二重にしない）。
   表の CI の行は 1 行だけにし、結果を `走らせていない`（GitHub が未設定で CI が無い）にする。
   足したら品質ゲートを通し、`docs: <id> の動作確認の結果を計画に書く` でコミットする（push しない）

   表の例:

   ```markdown
   | 確かめたこと                     | コマンド                               | 結果                                             |
   | -------------------------------- | -------------------------------------- | ------------------------------------------------ |
   | 品質ゲート                       | `npm run typecheck && ... && npm test` | 通った（テスト 1147 件）                         |
   | CI: check (24)                   | `ai-board pr checks 78`                | 通った                                           |
   | 直す前に落ちる: 打ち間違いを拒む | `npx vitest run ... -t '打ち間違い'`   | 通った（直す前は落ちた）                         |
   | ブラウザでの見た目               | —                                      | 走らせていない（撮る手段が無い。人が開いて見る） |
   ```

4. `git mv .ai-board/plans/<id>.md .ai-board/plans/archive/<id>.md` をコミット（`chore: 〜の計画を archive へ移す`）→ push → `ai-board pr ready <pr>`。
   archive のコミット（計画ファイルの移動だけ）に走る CI は待たない（その前のコミットで 2 を通しており、品質ゲートを手元で通してからコミットする）。
   `ai-board pr ready` だけが失敗したら、そのまま止まって報告する（次の周は archive 済みの段として `ai-board pr ready` だけをやり直す）

   **未設定のボード:** archive をコミットするだけで、push と `ai-board pr ready` をしない。カードはブランチのマージ待ちの止まりになり、判断待ちに出る。
   `進めた` で手を終える

## 5. 手の終わり

手を終えたら、`結果:` の語を決め、次の項目を人に伝える。ファイルの中身や差分は書き写さない。

- 結果: `進めた` / `止まった` のどれか 1 つ（`SKILL.md` がこの語で `loop finish` の `--result` と続けるかを決める）。`implement` では `保留して止まった` を使わない
- 何をしたか（`implement` では、通った段の名前を添える）
- `implement` でタスクを倒したとき: 倒した節の数と題（30 字ほどずつ）、節ごとのコミットのハッシュと push して `origin/<branch>` と一致したか、
  手を終えた区切り（節の区切りで止めた / 倒し終えてレビューの段の前で終えた / 締めの段まで進んだ）、品質ゲート（通った / どの節のどの段階で落ちたか）。
  締めの段まで進んだときは、CI の結果（`passed` / `none` / 直した回数 / 止まった理由）も添える。
  タスクの順番を直したときは、何をどの節へ移したかを短く添える
- 人が見るもの（PR の URL、判断待ちになったカード）。GitHub が未設定のボードの締めでは、PR の URL の代わりに、ブランチ名・計画の場所（`git show <branch>:.ai-board/plans/archive/<id>.md`）・
  マージのコマンド（メインのチェックアウトの `main` で `git merge --no-ff <branch>`）を伝える
- AI レビュー: 手と段ごとに次のように書く。黙って省かない
  - `implement` の締めの段（Ready にした）: 「レビューの段で済んでいる」と書き、PR の本文に写した見送った指摘の件数（無ければ「なし」）と、判断してほしいことの件数を添える
  - `implement` でタスクを倒してレビューの段の前で手を終えたとき: 「次の手で `board-reviewer` が行う」と書く
  - `implement` の archive 済みの段: 「この段では行わない」と書く
  - `implement` でレビューの段を読んで止まったとき: 「`board-reviewer` の段なので行わない」と書く
- 止まった理由と、人にしてほしいこと（止まったときだけ。変更を戻したか、残したかも書く）

## ハードルール

共通の決まりの「ハードルール」に加えて、次を守る。

- `next` の 1 手だけを行う。`implement` では、残りの節と締めの段までを 1 つの手として進める
- この手順書の中ではサブエージェントを立てず、自分の差分をレビューしない（レビューの段は `SKILL.md` が `board-reviewer` に切り分ける）。`/code-review` はかけない
- 節の中の未チェックのタスクだけを倒す。節の外のタスクのチェックボックスに触らない。計画のタスクの文を書き換えない
- 計画を直すのは、`[x]` を付けることと、2.1 の 4 の「タスクの順番を直す」の範囲（未チェックのタスクの移動・節の統合・節の中の並べ替え）と、
  2.1 の冒頭の `## 人に判断してほしいこと` への回答の追記と、GitHub が未設定のボードの締めの段で末尾に足す 3 つの節だけにする。
  タスクを足す・消す、`[x]` に触る、`## タスク` の外を変える、はしない
- 品質ゲートとコミットは節の終わりに 1 回だけにする。節の途中でコミットしない。節をまたいで 1 つのコミットにしない
- カードには何も書かない（`## レビュー` への 提出 / 再提出 / 保留 は `plan.md` の手だけが plan ゲートに書く）
- 締めの段でコードに触ってよいのは、CI を通すための直し（2.2 の 2）だけ。直すのは、ブランチのコミットの本文の `CI を通すための直し` の行で数えて 2 回までで、品質ゲートを通して `fix:` のコミットにする
- PR を Ready にするのは、締めの段で CI を確かめ（`pr checks` が 0）、PR の本文に 3 つの節を書いて計画を archive した後だけにする
- GitHub が未設定のボードでも、カードのブランチを `main` へマージしない（人がする）
