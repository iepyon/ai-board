# adr — 設計判断を ADR として残す

`docs/architecture.md` は**今どう作られているか**を書く。`docs/specs/` は**何を満たすか**を書く。
ADR は**なぜそう決めたか、何を捨てたか**を、決めた時点の文脈ごと 1 判断 1 ファイルで残す。
後から読む人（人も AI も）が「この不変条件を外してよいか」を決めるための材料であり、実装の説明書ではない。

## 置き場所と名前

- `docs/adr/NNNN-<英小文字のケバブケース>.md`。番号は 4 桁の連番で、**決めた日の順**に振る。
  空き番号を作らない。既存の番号は振り直さない（リンクが切れる）。
- 一覧は `docs/adr/README.md` の表。ADR を足したら、置き換えたら、必ず表も直す。
- ひな形は同じディレクトリの [`template.md`](template.md)。

## 何を ADR にするか

ADR にするのは、**元に戻すのに手間がかかり、外から見て理由が分からない**判断。目安:

- 不変条件を作った・崩した（例: ステージを保存しない、トークンを扱わない、外部コマンドは shell を介さない）
- データの置き場所・形・正本を変えた（ファイル → SQLite → データ用ブランチ）
- 外部への依存を足した・捨てた（OpenSpec、GitLab、`gh pr`）
- 人と AI の権限の境界を引いた（AI が書ける判断の種類、`board-decide`）
- ループやサブエージェントの役割分担を変えた
- 有力な代案があり、それを退けた

ADR にしないもの: 文言・見た目・バグ修正・テストの追加・リネームだけの変更。
それらは計画とコミットで足りる。迷ったら「半年後に誰かがこれを元に戻そうとしたら、止める理由を書いておきたいか」で決める。

## 書き方

- **日本語**で書く。見出しはひな形のとおり。リポジトリの言葉（ステージ・ゲート・提出・否決・監視役 など）を使う。
- **1 ファイル 1 判断。** 2 つの判断が絡むなら別の ADR にして互いにリンクする。
- **状況** は決めた時点の事実を書く。今の作りの説明を混ぜない。困っていたこと・制約・先にあった案を書く。
- **決定** は「〜する」「〜しない」と言い切る。
- **検討した代案** は、実際に検討された案だけを書く（計画の Decisions・Non-Goals・閉じた PR・中止したカード・否決の理由に出てくるもの）。
  それぞれ退けた理由を 1〜3 行で。検討された形跡が無ければ「記録なし」と書き、**代案を発明しない**。
- **結果** は良いことも悪いことも書く。決定で生まれた不変条件・新しい制約・残った課題・後で置き換えた事実。
- **根拠** にコミット（短いハッシュ）・PR 番号・計画ファイル・仕様のパスを並べる。ここに無いことは本文に書かない。
- 長さの目安は 40〜100 行。実装の手順・API の一覧・テストの話は書かない（それは architecture と計画にある）。

## 状態

| 状態       | 意味                                                               |
| ---------- | ------------------------------------------------------------------ |
| 提案       | まだ決まっていない（計画レビュー中など）                           |
| 採用       | 今も効いている                                                     |
| 置き換え済 | 後の ADR が上書きした。`置き換え先: [NNNN](...)` を書く            |
| 廃止       | 判断そのものが不要になった（機能ごと消した など）。理由を 1 行書く |

一部だけ上書きされたときは `採用（一部を [NNNN](...) が置き換え）` とし、`置き換え先: [NNNN](...)（一部）` も書いて、どこが変わったかを結果の節に足す。
新しい方の `置き換え元` にも `（一部）` を付ける。

## 既存の ADR を直すとき

- **決めた内容を書き換えない。** 判断が変わったら新しい ADR を書き、古い方は状態と `置き換え先` だけを直す。
  新しい方には `置き換え元` を書く。
- 誤字・リンク切れ・根拠の追加は直してよい。

## 新しい判断を記録するとき

1. 番号を決める: `ls docs/adr/ | sort | tail -3` で最後の番号を見て +1。
2. `template.md` を写して埋める。根拠には、その判断を入れたコミット・PR・計画を書く。
3. 置き換える ADR があれば、その状態を直す。
4. `docs/adr/README.md` の表に 1 行足す。
5. 判断が不変条件を作ったなら、`CLAUDE.md` の「設計の不変条件」や `docs/architecture.md` の該当節から ADR へリンクする。

計画（`.ai-board/plans/<id>.md`）の `### Decisions` に、ADR にすべき判断があれば、マージの前後で ADR に起こす。
計画は archive へ移って読まれなくなるが、ADR は残る。

## 履歴から書き起こすとき

材料は次の順に当たる。上ほど「なぜ」が書いてある。

1. **計画**: `.ai-board/plans/archive/*.md`（`### Why`・`### Decisions`・`### Non-Goals`・`## AI レビュー`）。
   `git log --all --format='%h %ad %s' --date=short -- .ai-board/plans/<id>.md` で計画の書き直しも追える（否決で変わった案が分かる）。
2. **仕様**: `docs/specs/*/spec.md`（`## Purpose` と MUST / SHALL NOT の理由文）。
3. **git log**: `git log --reverse --no-merges --format='%h %ad %s' --date=short`。
   `feat!:`・`refactor:`・「廃止」「移す」「やめる」「切り替える」を含むコミットが判断の候補。
   クローンが浅いと最初の判断が抜けるので、先に `git rev-parse --is-shallow-repository` を見て、`true` なら `git fetch --unshallow origin main`。
4. **今のドキュメント**: `CLAUDE.md` の不変条件、`docs/architecture.md`、`README.md`。結果の節の裏付けに使う。
5. 消えたファイル（OpenSpec の change など）は `git log --diff-filter=D --name-only` で探し、`git show <hash>^:<path>` で読む。

手順:

1. 候補を日付順に並べ、上の「何を ADR にするか」でふるう。同じ判断を何度も直したコミットは 1 つの ADR にまとめる。
2. 後の判断が前の判断を上書きしているものは、両方を書いて `置き換え` でつなぐ（古い判断も残す価値がある）。
3. 1 つずつ書く。**根拠に挙げた材料に書かれていないことは書かない。** 推測で理由を補いたくなったら、
   「記録なし」と書くか、`## 状況` に「計画には理由の記述が無い」と書く。
4. 一覧を作り、`CLAUDE.md` の「読む場所」から `docs/adr/` へリンクする。

## 品質ゲート

ADR は Markdown なので `npm run format:check` に掛かる。書いたら `npm run format` してから、
`npm run typecheck && npm run lint && npm run format:check && npm test` を通してコミットする。
コミットは `docs: 〜の判断を ADR に残す` の形。
