## アイデア

auto モードで回しているループが、手順書どおりの操作で分類器に拒まれて止まらないようにする。

- **起きたこと。** 2026-11-03、`decide-guard` の締めの段（動作確認を飛ばす宣言があったので Ready にする手）で、`board-worker` が
  計画を archive へ移すコミット → `git push origin decide-guard` → `ai-board pr ready 73` を 1 回の Bash でまとめて走らせ、
  auto モードの分類器に「Unrequested Commit in a Connected App」として拒まれた。作業者は `git mv` を戻して `止まった` を返した
- **直す方向の候補。**
  - 手順書の操作を分ける（archive のコミットと push、`pr ready` を別々の Bash にする）。分類器が「頼まれていない」と見た理由が束ね方にあるかを確かめる
  - 分類器が止める操作だけを `allow` に足す（ADR 0012 の「手順書に操作を足して分類器がそれを止めるなら、その操作だけを `allow` に足す」）
  - 分類器に手順の文脈が届くよう、手順書の書き方や報告の形を変える
- **確かめ方。** 決まった題材のカードで締めの段（Ready にする手）を auto モードで 1 回通し、止まらないことを確かめる

## 背景

ADR 0012 は「ループは auto モードで回す前提で、手順書のふつうの操作（commit / push など）は分類器に任せる」と決めている。
今回は、その前提のふつうの操作が拒まれた。拒まれると作業者は `止まった` を返し、カードは次の周でも `next` に選ばれ続けるので、人が手で直すまでループが止まる。

人の判断で動いている手（着手・承認の後の手）でも、サブエージェントの中の操作は「人がこの会話で頼んだ」ことが分類器から見えない。
人に頼まれた操作として通る見込みのある本筋のセッションと違い、サブエージェントの操作は手順書だけを根拠にしている。

## 論点

- **原因の切り分け。** 拒まれたのは、操作の束ね方（commit・push・PR の状態変更を 1 本にした）か、PR を Ready にする操作そのもの（外のサービスの状態を変える）か、archive への移動か。分類器の判定は再現しにくいので、どう確かめるか
- **`allow` に足すかどうか。** `ai-board pr ready` や archive のコミットを `allow` に足すと、分類器が危ないと見た操作を黙って通すことになる。足すなら形を狭く（ワークツリーの中、`ai-board pr ready <番号>` だけ）にする
- **ほかの手でも起きるか。** 計画の Draft の PR を出す手、動作確認を頼む手（`card submit`）、`git push --force-with-lease` など、外へ書く操作を棚卸しする
- **止まったときの扱い。** 分類器に拒まれたことを、ほかの「止まった」（品質ゲートが通らない など）と区別して報告するか。`loop-retry-limit`（同じところで止まり続けたら上限で人に回す）と合わせて考える
- **ADR。** 方針が変わるなら ADR 0012 を今の形に書き直す
