## アイデア

GitHub への問い合わせの回数を減らし、ボードとループを回し続けても API の上限（1 時間 5000 回）に当たらないようにする。

- **終わった PR を引き直さない。** マージ済み・クローズ済みの PR は状態がもう変わらないので、一度取れたら引き直さない（前回の結果を使い回す）
- **変わっていない PR を引き直さない。** PR の `updated_at` が前回と同じなら、コメント 2 種・コミット・events を引かない
- **ループの `status` を軽くする。** `ai-board status` が毎回全カードを引き直さず、サーバが持っている最新の結果か、手元に残した結果を使えるようにする

## 背景

2026-10-30、ボードのサーバ（30 秒ごとのポーリング）と、`/loop 1m /board-loop`（毎周 `ai-board status` を走らせる）を同時に回していたところ、
1 時間に 2 回、GitHub API の上限（5000 回）に達した。上限に達すると `gh` は失敗し、`gh auth status` もトークンが無効だと表示するので、ログインが切れたように見える。
上限が戻った直後も、7 分で約 570 回、push と `status` を 1 回ずつ走らせた 1 分で約 240 回を使っていた。

`ForgePoller.refresh` は `mr` か `branch` を持つカードをすべて対象にし、1 枚ごとに `pulls/{n}`、`issues/{n}/comments`（全ページ）、
`pulls/{n}/comments`（全ページ）、`commits/{sha}`、Draft の PR なら `issues/{n}/events`（全ページ）を引く。
マージ済みのカードも毎回この対象に入るので、カードが増えるほど 1 回の引き直しが重くなり、ポーリングの間隔とループの周の数だけ掛け算で増える。

上限に当たると、ボードは PR の状態を引けずに計画レビュー / PR中 のカードを手前の列に落として見せ、ループは止まる。
ボードとループを開きっぱなしで使うのが前提なので、普段の使い方で上限に当たらないことが要る。

## 論点

- **使い回しの置き場所。** 前回の結果をサーバの記憶に持つか、DB に残すか。`status` はサーバと別のプロセスなので、DB に残さないと共有できない
- **マージ済みの判定の確かさ。** マージ済みの PR を引き直さなくても、人が revert して作り直す、などで食い違うことは無いか
- **`updated_at` で足りるか。** コメントや events の追加で PR の `updated_at` が変わるかを確かめる。変わらないなら、条件付きリクエスト（ETag / `If-None-Match`。304 は回数に数えられない）を使う手もある
- **残り回数を見せる。** `gh api rate_limit` で残りを引き、少なくなったら間隔を広げる、画面に出す、などをするか
