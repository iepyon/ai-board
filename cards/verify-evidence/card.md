## アイデア

動作確認を頼むときに、AI が確かめた証拠を PR に付ける。人の作業を「手で動かす」から「証拠を見て判断する」に変える。

- **テストの報告。** 走らせたコマンドと結果を表にする（成功 / 失敗、件数）。変更前のコードでは落ち、変更後で通るテストがあればそれも書く
- **走らせなかったもの。** 確かめられなかった項目と理由、確かめるのに何が要るかを別に書く。走らせていないものを成功と書かない
- **CI の結果。** PR の最新コミットのチェックの結果を引いて、報告に含める。ボードのカードにも要約を出す
- **画面の変更。** 画面が変わる変更では、スクリーンショットを添える
- **置き場所。** PR の本文の節か、PR のコメント 1 件にまとめる。押し直すたびに同じ 1 件を書き換える

## 背景

今の動作確認は、人が手順書（計画の `## 動作確認の手順`）に沿って全部手で動かしている。
人を待つ区間のうち、動作確認がどれだけ長いかは `stage-timeline` の痕跡から読める。

Mastra Factory は、レビュー役が走らせたテストの結果を PR のチェックとコメント（Factory test report）に出す。
環境の失敗は合格としない、走らせていないものを成功と書かない、と決めている。
また、CI の結果ではセッションが起きないので、エージェントがツールで CI を確かめる設計にしている。

## 論点

- **pr-checks との関係。** CI の結果をボードに出すアイデアは、この中に含める。取得の仕組み（`check-runs` と `status` の 2 系統、`--paginate`）は pr-checks の論点をそのまま引き継ぐ
- **誰が書くか。** 実装の作業者が締めの段で書くか、レビューの作業者が書くか。レビューの作業者はコードを変えないので、報告は PR の文面に限る
- **CI が赤のとき。** 動作確認を頼む前に AI の番に戻すか。ステージの導出には使わない方針（pr-checks）と両立させる
- **人の手順の残し方。** 証拠で足りる項目と、人が実際に触らないと分からない項目を、計画の動作確認の手順で分けて書くか
