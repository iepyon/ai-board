#### 人に判断してほしいこと（AI レビューから）

- `src/infrastructure/data-store.ts:28` のロックを待つ上限（5 秒）は、ロックを持ったまま行う fetch と、`transact` の最大 4 回の fetch と push より短い。遅い回線では、サーバの定期の取り直しや画面の書き込みの間に、ループの `card submit` や `status` が `DataStoreLockTimeout` で止まりうる。上限は計画の Decisions（「5 秒待って取れなければ失敗」）で決めた値なので、延ばすか、このままにするか
- `src/infrastructure/data-store.ts:648` の死んだロックの取り直しは、持ち主の pid が死んでいると見てから札を確かめずに `rmSync` する。2 つのプロセスが同時に取り直すと、後の方が先の方の新しいロックを消し、2 つが同じワークツリーで reset と commit を走らせうる。また、作った直後に中身を書けずに残ったロック（空のファイル）は `readLock` が null を返すので取り直されず、以後ずっと待ち切れで止まる。どちらも落ちたプロセスが残したロックがあるときだけ起きる。直すか、どれで直すか（`mkdir` によるロック、ロックの mtime で古さを決める、ロックのライブラリを使う）
