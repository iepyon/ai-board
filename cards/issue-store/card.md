## アイデア

カードの正本を、SQLite から git のデータ用ブランチ（orphan の `ai-board/data`）のテキストに移す。
Claude Code のクラウドのセッションだけでボードを回せるようにする。SQLite は持たない。

- **1 カード 1 ディレクトリ。** `cards/<id>/card.md` に frontmatter（`branch`・`mr`）と本文を置く。形は `ai-board card show` の Markdown にそろえる
- **判断は 1 件 1 ファイル。** 提出・再提出・保留・承認・否決・中止・着手・着手を戻す は、`cards/<id>/log/<時刻>.<gate>.<種別>.md` に追記だけで足す。
  `## レビュー` と `startedAt` はここから組み立てる。`stage-resolver.ts` と `review-log.ts` の入力は変えない
- **並び順は 1 ファイル。** `rank` とアイデアの区切り線は `order.yaml` にまとめる
- **書き込みは CLI が 1 回の操作として行う。** 「取り直し → 検査 → コミット → push」をまとめて行う。
  push が拒否されたら rebase せず、自分のコミットを捨てて取り直し、検査からやり直す。手元の複数のプロセスはロックファイルで直列にする
- **PR の操作は REST に寄せる。** 手順書の `gh pr create / view / edit / ready / comment / diff` を `ai-board pr` に置き換える。
  クラウドでは GraphQL が使えないので、Draft の切り替えはプロキシの `/ccr/ready_for_review` と `/ccr/convert_to_draft` を使う
- **PR の状態の控え。** マージ済みの PR の控えはデータ用ブランチに置く。開いている PR の控えは、git に載せない使い捨ての JSON にする
- **ボードは Artifact で見る。** クラウドには常駐のサーバがない。`ai-board status` から HTML を作り、会話のセッションが Artifact として公開する。
  手元では今の画面が、データ用ブランチのワークツリーを chokidar で見る
- **ループは会話のセッションで回す。** 人が開いたセッションの中で回すのを主にする。ルーティン（最短 1 時間）は、止まっているものを動かす保険にする
- **書き込み境界は緩めない。** 判断を書くのは、人が会話で頼んだときの Claude（`board-decide`）だけにする。
  `.claude/settings.json` の deny ルールで、データ用ブランチのワークツリーへの Edit / Write と直接の push を止める。この設定はクラウドでも効く

## 背景

外出中に、スマホからボードを進めたい。
手元の Mac を動かし続ける前提にはせず、スマホの Claude Code アプリからクラウドのセッションを立ち上げて、人の判断と AI の作業を回したい。
人は GitHub のアプリでは作業しない。

今のカードは `.ai-board/board.db` にあり、git に載らない。
クラウドのセッションは毎回新しい clone から始まり、push したもの以外は残らないので、カードが見えない。

置き場所として GitHub Issues も検討したが、3 つの理由で git のデータ用ブランチを選んだ。
1 つ目に、クラウドでは GraphQL が使えないので、Issues で並び順を置く先にしていた Projects が使えない。
2 つ目に、セッションごとに REST で読み直すと問い合わせが増える。
3 つ目に、人が GitHub の画面で読む、という Issues の利点をこの使い方では使わない。
データ用ブランチなら、clone した時点でカードが揃い、読むのに API を使わない。push の拒否は、そのまま楽観ロックに使える。
判断ごとにコミットが残るので、HIL の痕跡も今より辿りやすくなる。

カードは 2026-09-26 にファイルから SQLite へ移した（`b97280b`）。そのときの狙いは、書き込みを `ai-board card` の CLI に絞ることだった。
テキストに戻すと、ファイルを直接書き換える道がまた開く。
ただし今も、`sqlite3` で直接触らないことは手順書の決まりで守っているだけで、技術的に止めているわけではない。
deny ルールで守る形に変えても、実質は弱まらない。

## 論点

- **手元でのデータ用ブランチの置き場所。** メインのチェックアウトの下に専用のワークツリーを 1 か所置き、どのワークツリーもそこを見る。`git-worktree.ts` の解決をどう変えるかを決める
- **移行。** `board.db` からデータ用ブランチへ書き出す手段（`ai-board import` の逆）が要る。既存の `## レビュー` の時刻を保ったまま、1 件 1 ファイルに分ける
- **ファイル名の衝突。** 同じ秒に 2 件書かれたときの名前の付け方を決める
- **`ai-board pr` の経路。** 手元とクラウドで経路を使い分けるか決める。`/ccr/` の経路は、手元では使えない見込み
- **ルーティンの重複起動。** 1 手が 2 回重なって走っても壊れないことを、テストで確かめる
- **ボードの Artifact の作り方。** CLI が HTML を出すか、Artifact の型を使うかを決める
- **ブランチの後始末。** クラウドからはブランチを消せないので、リポジトリの「Automatically delete head branches」を有効にする
- **`assigned-issues` との関係。** Issue を取り込む案は、別のカードのまま残す
- **当初の動機（チームとの共有）。** データ用ブランチは GitHub で読めるので、共有はある程度できる。Issues に置く案は取り下げる

## 探索メモ

2026-11-01 の壁打ちと、クラウドで試した結果の記録。図入りのまとめは https://claude.ai/artifact/NCAvdHUy4QdpdUBuzy9tiK

- **クラウドの GitHub。** `gh` は最初から入っていて、プロキシ経由で認証される。
  REST は使えるが、GraphQL は 403 なので `gh pr` と `gh issue` は動かない。
  `gh auth status` は「GH_TOKEN が無効」と出るが、`gh api` は動く
- **問い合わせの上限。** クラウドでは 1 時間 15,000 回。ETag を付けた 304 は回数に数えない。`gh` は 304 を受けると終了コード 1 で終わる
- **push とブランチの削除。** push はどのブランチにもできる。ブランチの削除は、`git push --delete` も REST の DELETE も 403
- **Draft の切り替え。** REST の PATCH で `draft=false` にしても Draft は外れない。
  `POST /repos/{o}/{r}/pulls/{n}/ccr/ready_for_review` で外れ、`…/ccr/convert_to_draft` で戻る。
  PR の events にも `ready_for_review` と `convert_to_draft` が残る
- **PR の本文の更新。** REST で本文を更新すると、末尾に「Generated by Claude Code」が自動で付く
- **データ用ブランチへの同時の書き込み。** 別のファイルを 2 か所から書くと、後の push は拒否され、rebase すると両方残る。
  同じ行を書き換えると、rebase は衝突して止まる。
  離れた行の編集は git が黙って混ぜる（`order.yaml` で確認）ので、拒否されたら rebase せずにやり直す
- **ルーティンの重複起動。** `run_once_at` で 1 回だけのはずのルーティンが 3 回動き、1 回目は指定時刻より前だった
- **通知。** ルーティンのセッションから Claude のアプリへのプッシュ通知は届く。今は通知しない方針
- **リポジトリの設定。** 単一リポジトリのクラウドのセッションでは、リポジトリの `.claude/settings.json` の権限とフック、skills、agents が効く（ドキュメントによる）
