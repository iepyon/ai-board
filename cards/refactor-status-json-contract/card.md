## アイデア

`ai-board status --json` の出す形が知らないうちに変わったら、テストと `--only` で止まるようにする。外に出す形を内部のモデルから切り離す（専用の型と詰め替え）のは、React の画面とバックエンドを戻すときに決める。

- **項目名の一覧を 1 か所に置く。** `StatusReport` の最上位の項目と、配列の項目（`waiting` / `working` / `cards` / `ideas`）の要素が持つ項目名を、実行時に読める定数として持つ。
  型（`WaitingCard` / `WorkingCard` / `StatusCard` / `IdeaListRow`）と一覧の食い違いは型検査で落とす（項目を足す・名前を変えると、一覧を直さないとビルドが通らない）
- **C. 形を固定するテスト。** その一覧をテストで固定する（スナップショットか、書き下した期待値）。項目が増えたり減ったり名前が変わったりすると、テストが落ち、PR の差分に出る。直す人は、読む側（下）を確かめてからテストの期待値を更新する
- **D. `--only` を厳しくする。** `--only <key>.<field>` の `<field>` も一覧で検査し、無い名前なら GitHub に問い合わせる前に失敗させる（今は最上位の項目だけを検査し、要素に無い `<field>` は黙って出さない）。
  「カードによって無い項目がある」（例: `prState` が無いカード）は、一覧にある名前なら今までどおり、その要素では出さない
- **読む側を書き出す。** 一覧の近くに、`status --json` を読む側とその項目を書く。今は `board-loop` / `board-decide` のスキル（`--only` で `cards.latestReview`・`cards.prState`・`cards.skipGates` などを読む）と、`board-view` の `render.mjs`（PR #103。`waiting`・`working`・`ideas`・`forge`・`loop`）
- **出力は変えない。** 項目を足す・減らす・名前を変えることはしない

## 背景

画面とサーバは ADR 0017 でいったん外したが、後で React の画面とバックエンドを戻す予定である。ADR 0018 は「画面と共有する API 専用の型を作るかは、サーバを戻すときに決める。今は `StatusCard` が内部のモデル（`BoardCard`）をそのまま出している」と先送りした。
`status --json` を読む側は既に 2 つあり（スキルと `render.mjs`）、React の画面が加わる。内部のモデルはリファクタリングのたびに変わり、そのたびに出力も変わるが、出力の形を決めているものが無いので、テストでは気付けない。
とくに `--only` は、入れ子の項目名を検査しない（`src/board/cli/status-cli.ts` の `parseOnly` / `pickFields`）。内部で `latestReview` の名前を変えると、スキルの `--only cards.latestReview` はエラーにならず項目が消えるだけで、スキルは「判断が無いカード」と黙って読み違える。
2026-11-11 に、外に出す形を守る案を 4 つ比べ（下の論点）、今は安い C と D で読む側の壊れを止め、外に出す形の作りは画面の要る項目が見えてから決めることにした。
`board-view` の見た目を直す 4 枚のカードはどれもこの出力に寄りかかったページを触るので、先に止めておくと手戻りが減る。

## 論点

- **一覧の置き場所。** `src/board/models/status-report.ts` の隣に置くか。`--only` の検査（`status-cli.ts`）と、戻す HTTP の入口の両方から読める場所にする
- **固定のしかた。** vitest のスナップショット（`toMatchInlineSnapshot`）にするか、期待値を書き下すか。書き下すほうが、変えたときに何が変わったかを読みやすい
- **`--only` の誤りの文言。** 無い項目名のとき、指せる項目名を並べて出すか
- **サーバを戻すときに決める案（今はやらない）。**
  - A. 外に出す形を別の Zod スキーマで決め、内部のモデルから詰め替える。内部を自由に変えられ React は型を引けるが、型と詰め替えが 2 組になる
  - A'. 外に出す形（`StatusReport`）だけを Zod で書き、内部のモデルはその型に合わせて組む。定義は 1 つだが、内部が外の形に縛られる
- **選ばなかった案。** B. 内部のモデル（`BoardCard` など）を Zod で書き、型を `z.infer` で引いて、出力はモデルのまま出す。
  定義は 1 つで済むが、内部の名前を変えるとそのまま外も変わるので、このカードの問題が残る。
  また、今の Zod はファイルを読むところ（カードの frontmatter・設定・PR の控え・ループの記録）で外から来る値を確かめるのに使っていて、自分のコードが組んだ値を毎回 parse しても得るものが少ない
- **タイトル。** タイトルは「内部のモデルと切り離して固め」だが、このカードでは切り離さず、変わったら止まるようにするところまでにした
