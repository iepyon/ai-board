## アイデア

PR中 のカードのうち、人がレビューで指摘したあと修正がまだ push されていないものを、
判断待ちの区画から「AI が進めている」区画へ移す。

- **条件。** `mrState.noteCount > 0 && !resubmitted`（指摘があり、そのあとの修正コミットが無い）
- **変えるのは見せ方だけ。** ステージは `pr` のままで、`stage-resolver.ts` には触らない。
  振り分けは `src/shared/dashboard-sections.ts` の `groupBySection` に足し、テストもそこに書く
- **ループの手順。** `board-loop-skill` のハードルール「PR中 のカードに触らない」を、
  「指摘のあとに修正が push されていないときだけ、指摘に応える修正を push してよい」に緩める

## 背景

今は PR中 のカードがすべて判断待ちの区画に並ぶ。人がレビューで指摘を書いたあとは、
修正を出すのは AI の番なのに、カードは人を待っているように見えたままになる。
画面の文言はすでに「レビューの指摘に対する修正を待っています」と出しており、
誰の番かは分かっているのに、区画がそれと食い違っている。

Mastra Factory では、変更を求めるレビューは実装したエージェントのセッションへ戻る。
ai-board でも指摘を受けたカードを AI の区画へ移せば、判断待ちの区画には
本当に人が見るべきものだけが残る。ただし区画を移すだけでは、ループのハードルールが
PR中 のカードに触ることを禁じているので誰も動かない。ルールの緩和と一緒に決める必要がある。

## 論点

- **区画の表との関係。** `SECTION_OF_STAGE` はステージだけを見る表なので、この条件を表せない。
  件数帯のジャンプ先（`PipelineStrip.tsx`）がこの表を直接引いているので、PR中 のマスを押したときの行き先をどうするか
- **並び順。** AI の区画に入った PR中 のカードを、計画提案中・実装中とどう並べるか（`rank` か、指摘の時刻か）
- **指摘の判定の粗さ。** `noteCount` は人のコメントすべてを数えるので、質問や承認のコメントも「指摘」として扱われる。
  GitHub の review state（`CHANGES_REQUESTED`）を引くかどうか

## 探索メモ

着手前に人と決めたこと（2026-11-04、チャットでの問答）。

- **指摘の判定。** `noteCount` で数えるが、AI が人のアカウントで書いたコメント（Claude Code のフッター付き）は数えない。
  PR は人のアカウントで出すので自分の PR に Request changes を付けられず、`CHANGES_REQUESTED` は使わない。
  質問や承認のコメントも指摘として扱われる粗さは受け入れる。
- **ループの手。** PR を Ready のまま、指摘に応える修正を push してよい（ハードルール「PR中 のカードに触らない」をこの場合だけ緩める）。
  カードは PR中 のままで、push したことで再レビュー待ち（`resubmitted`）になる。Draft に戻す道は今のまま残す。
- **並び順。** AI の区画では PR の修正を先頭に出し、ループの `next` でも計画提案中・実装中より優先する（マージに最も近いため）。
- **件数帯。** `SECTION_OF_STAGE` は変えず、PR中 のマスの飛び先は判断待ちのまま。AI に回ったカードは判断待ちの区画に出ないだけ。
