## アイデア

実装中 と PR中 の間に、人が実際に動かして確かめる「動作確認」の列を入れる。

- **`plan` ゲートと同じ仕組みで足す。** `verify` ゲートと `verifying` ステージを足し、`stage-resolver.ts` の `RULES` に 1 本足すだけにする。否決・承認・スキップに専用のルールは足さない
- **流れ。** AI は実装を終えたら PR を Draft のまま `verify 提出` を書く。人は動かして確かめ、承認 / 否決する。承認なら AI が `gh pr ready` で Ready にし、否決なら理由を読んで実装へ戻る
- **確かめられる状態にするのは AI の責務。** 人が動かすための手順（起動のコマンド、見る画面、期待する結果）を、提出の本文に必ず書かせる
- **小さな変更は飛ばせる。** 人が `skipGates` に `verify` を宣言すれば、動作確認の列を通らずに PR中 へ進む

## 背景

今のゲートは 計画レビュー と PR中 の 2 つで、PR中 で人が見るのはコードの差分である。
振る舞いが意図どおりかを確かめるには、人がブランチを手元で動かすしかないが、ボードはそれを「人の番」として示さない。
差分を読んでから動かして食い違いに気づくと、レビューの手間が二重になる。

動作確認 と PR中 の役割を分けたい。動作確認では振る舞いが意図どおりかを見て、PR中 ではコードの質・設計・差分を見る。
動かして確かめた後に差分を読めば、PR のレビューはコードの話に集中できる。

## 論点

- **Draft の PR との関係。** 今は「Draft の PR があれば 計画レビュー の列が立つ」ルールがある。
  「Draft のまま `verify 提出` を書く」とき、`verifying` のルールをどこに置けば計画レビューに巻き戻らないかを確かめる
- **列にするか。** 列を足さずに「PR を Ready にする前に verify 承認を要る」だけにする案もある。
  ただし列にしないと、動かして確かめる番が判断待ちの区画に出ない
- **`latestReview` の一般化。** 「いま待たれているゲートの最新エントリ」にするか、ゲートごとに持つか。`waitingSince` もこれに従う
- **手順の置き場所。** 計画ファイルのひな形に `## 動作確認の手順` を足せば、計画レビューの時点で手順も読める。
  `verify 提出` の本文には、実際に動かした結果と計画からの差分を書かせる
- **ループの扱い。** `board-loop` の作業者は、全タスクを倒したら Ready にする代わりに `verify 提出` で止まる。
  承認後に Ready にする手を `pickNextAction` に足す
- **起動の自動化は別カード。** ボードの UI からブランチのコードを起動すると、書き込み境界と信頼の議論が別に要る

## 探索メモ

2026-10-02 に、当時の main（`00e8ee4`。#26〜#35 より前）の上で計画を書いたが、コミットせずにワークツリーごと捨てた。
その計画で考えた点を残す。

- `stage-resolver.ts` の判定は `pr`（Ready の PR、最優先のまま）→ `verifying`（plan 承認済みかつ verify が submitted）→ `impling`（plan 承認済み）の順。
  verify が none / rejected / approved（PR 未 Ready）のときは `impling` に落ちる。否決の差し戻しも「AI が Ready にする待ち」も、新しい `if` 無しで手前の AI 列になる
- 既存のカードは巻き戻らない。Ready の PR はルール `pr` が先に勝ち、`verify` のエントリが無い実装中のカードは `impling` のまま
- 触る場所の見当:
  - `REVIEW_GATES` を `['plan', 'verify']` に
  - `STAGES` の `impling` と `pr` の間に `verifying` を入れる
  - `card-cli.ts` の `submit` に `--gate <plan|verify>` を足す（既定は `plan`）
  - `dashboard-sections.ts` で `verifying` を判断待ちの区画に入れる
  - `src/web/` で `Stage` / `ReviewGate` を網羅している箇所を直す
- DB の `skip_gates` 列に CHECK 制約があればマイグレーションが要る
- 承認の理由に書かれた「別件の発見」は、AI が `ai-board card create` でアイデアカードに起票する（新しい入口は足さない）
- 承認 / 否決 / 中止の入口を CLI に足さない。`CLAUDE.md` の「やってはいけないこと」に `verify` の承認 / 否決の例を足す
