## アイデア

ループが Ready にする前に人が PR をマージしたカードを見つけ、取り残されたものを人に知らせるか、ループが片付ける。

取り残されるのは次の 2 つ。

- **未チェックのタスク。** マージした時点で倒れていなかったタスク。もう要らないのか、別の PR で続けるべきかは人が決める
- **計画の archive。** 計画が `.ai-board/plans/<id>.md` のまま main に入る。PR の merged で マージ済み は立つので
  ボードの表示は正しいが、`plans/` に残り続ける。GitHub が引けないときや `github:` の無いリポジトリでは、
  このカードが 実装中 に見えてしまう（`board-loop-skill` の計画で archive を同じ PR で移すことにした理由そのもの）

## 背景

2026-10-23 に `gitignore-db-backup` をループで試したとき、ループがタスク 1 を倒したところで、人が PR #30 を Ready にしてマージした。
ループは マージ済み のカードに手を出さないので、タスク 2 の確認と計画の archive が残り、人に頼まれて手で別の PR（#31）を出して片付けた。

`board-loop` の計画では、archive を「Ready にする直前に同じ PR の中で移す」形にし、マージ後の `archive-<id>` の PR をやめた。
ループの手順どおりに進めば取り残しは起きないが、人が先にマージすることは普通にある（変更が小さい、急ぎ、など）。

## 論点

- **見つけ方。** `status` で、ステージが マージ済み（PR の merged）なのに、メインのチェックアウトの `plans/` に計画が archive されずにあるカードを拾う。
  `getBoardQuery` は既に計画の `archived` と `tasks` を持っているので、判定は `next-action.ts` に純関数として足せる
- **メインのチェックアウトの鮮度。** マージした計画がメインのチェックアウトに見えるのは、人が main を更新したあとである。
  ループは main を更新しない方針なので、更新されるまでは見つけられない。それで足りるか
- **ループに片付けさせるか、知らせるだけか。**
  - 片付けさせるなら、次の一手に `archive` を足し、`archive-<id>` のブランチから PR を出す（一度計画に入れて外した形の復活）
  - 知らせるだけなら、`waiting` に「計画が archive されていない（未チェックのタスク n 件）」として出し、人が決める
- **未チェックのタスクの扱い。** archive の PR で未チェックのまま移すか、残りを確かめてからチェックを付けるか。
  確かめずにチェックを付けるのは、やっていない作業をやったことにするので避ける
- **画面。** マージ済みの区画のカードに「計画が archive されていない」の印を出すか
