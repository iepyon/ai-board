## アイデア

AI が計画を立てるときに、計画の Markdown に加えて、UI のモックや図解の付いた読みやすいページ（アーティファクト）を作る。
人は計画レビューで、そのページを開いて計画を読む。

- **計画の正本は今のまま `.ai-board/plans/<id>.md`。** ページは読むための写しで、導出（進捗バー、タスクの数え方）には使わない
- **ページに載せるもの。** 変更の前後が分かる UI のモック（画面に関わるカード）、ステージや処理の流れの図、触るファイルの見取り図、判断してほしい点
- **見つけやすくする。** ページへのリンクを Draft の PR の本文と `plan 提出` の本文に書く。ボードの判断待ちの区画からも開けるようにする
- **作るのは `plan` と `revise-plan` の手。** `board-worker.md` の手順に足す。計画を直したら、ページも作り直す

## 背景

今の計画は Markdown の文章とチェックボックスだけで、Draft の PR のファイル表示で読む。
`verify-gate` の計画は 300 行近くあり、「初心者にもわかりやすく」という理由で一度否決された。
作業者は用語の節と具体例を足して書き直したが、それでも文章だけで状態の遷移や画面の変化を思い描くのは骨が折れる。

計画レビューで人が確かめたいのは、何がどう変わるか、その判断でよいかである。
画面が変わるなら変わった後の画面を、流れが変わるなら流れの図を見るのが一番早い。
文章で読んで頭の中で組み立てるより、絵で見て文章で裏を取るほうが、見落としも判断の時間も減る。

## 論点

- **ページの置き場所。** Artifact（claude.ai に公開。既定は非公開）にするか、リポジトリにコミットする HTML（`.ai-board/plans/<id>.html` など）にするか。
  Artifact は作業者のセッションから公開でき、リンクだけで開けるが、外部のサービスに計画の中身を載せることになる。
  リポジトリの HTML は PR で一緒にレビューでき、マージ後も残るが、GitHub の画面ではそのまま開けない
- **軽い代わりの手。** GitHub は Markdown の Mermaid を図として描く。計画の Markdown に Mermaid の図を入れるだけで足りる場面も多い。
  まず Mermaid を必須にし、UI のモックが要るカードだけページを作る、という段階の付け方もある
- **作業者の道具。** サブエージェントの作業者から Artifact の道具を使えるか、公開の許可をどう扱うかを確かめる
- **いつ作るか。** すべてのカードで作ると手間がかかる。画面や流れが変わるカードだけにするか、作るかどうかを作業者に判断させるか
- **ボードからの入口。** ボードは計画の本文を持たない方針である（`GET /api/plans/:id` は廃止した）。
  ページへのリンクをどこから拾うか（`plan 提出` の本文、PR の本文、カードの列を足す）を決める
