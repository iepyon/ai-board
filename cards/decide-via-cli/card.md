## アイデア

人がチャットで頼んだ判断（承認 / 否決 / 中止、着手 / 着手を戻す、飛ばす宣言、並べ替え）を、`ai-board` の CLI で書けるようにする。
`board-decide` のスキルは CLI を 1 行呼ぶだけになり、サーバを一時的に起動して人の API を叩く手順が無くなる。

- **消えるもの。** `board-decide` の手順 4 の、サーバの起動・起動待ち・URL の読み出し・停止の 60 行ほどのシェル、Windows / MSYS の注意書き（`MSYS_NO_PATHCONV`、`$!` と OS の pid、SIGTERM）、`server.json` を照らし合わせる手順
- **守りの置き場所が変わる。** 今は「AI は構造上、承認を書けない」を CLI の構造で守っている（`src/cards/cli/card-cli.ts`）。
  CLI に入口を足すと、守りは手順書の決まり（人がこの会話で自分の言葉で頼んだときだけ書く）だけになる

## 背景

2026-11-03 に、今の Claude のモデルを前提にハーネスを簡素にする案を話し合い、人がこのカードの起票を頼んだ。

ADR 0007 は「`ai-board card` の CLI に人の判断の入口を足さない」とし、理由を「サブエージェントが日常的に使う道具の境界を崩す」とした。
`loop-single-session`（ループを本筋のセッション 1 つで回し、AI レビューだけを別の文脈にする）が入ると、CLI を日常的に使うのは本筋のセッションになり、この理由は弱まる。
一方で、人の判断を書く手順は `board-decide` の 303 行のうちかなりを、クラウドのセッションに常駐のサーバが無いことへの対応（起動して書いて止める）が占めている。

## 論点

- **HIL の保証をどこまで手放すか。** 研修で伝える人の判断ゲート（HIL）の要は「AI は構造上、承認を書けない」ことだった。手順書の決まりだけで足りるか。
  中間の案として、人の判断の CLI を別のコマンド（例: `ai-board decide`）に分け、`.claude/settings.json` の `ask` に置いて、呼ぶたびに人に確かめさせる形はどうか（auto モードでも `ask` は効く。ADR 0012）
- **レビューのサブエージェント。** `loop-single-session` でレビューのサブエージェントが残るなら、その中から人の判断の CLI を呼べてしまう。手順書の決まりで足りるか
- **画面との関係。** 手元の画面のボタンは今どおりサーバの人の API で書く。CLI と人の API で同じ usecase を通し、書き方がずれないようにする
- **`slim-decide` との関係。** `slim-decide` の「サーバの起動をスクリプトに出す」案は、このカードで要らなくなる。残りの細則の整理だけを `slim-decide` に残すか、まとめるか
- **順番。** `loop-single-session` の後にするか
- **ADR。** ADR 0007 を書き直す

## 探索メモ

2026-11-04 に、着手の前に人がチャットで次のように決めた。

- **HIL の守り。** 「手順書の決まりだけ」にする。`ai-board decide` を `ask` に置く案や `deny` に置く案はとらない。人の判断の入口を CLI に足し、守りは「人がこの会話で自分の言葉で頼んだときだけ書く」の決まりに任せる
- **`slim-decide` との関係。** このカードにまとめる。`board-decide` の手順書の細則の整理（理由の扱いの例外、判断待ちの一覧の聞き方など）もこのカードで行う
