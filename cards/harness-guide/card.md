## アイデア

研修の受講者向けに、このリポジトリのハーネスの読み方の案内を 1 枚書く（例: `docs/harness-guide.md`）。

- **観点ごとに部品をたどる。**
  - 人の判断ゲート（HIL）: ステージの導出、`ai-board card` の CLI の境界、人の API、`board-decide`
  - 文脈の切り分け: 監視役（board-loop）と作業者（board-worker / board-task / board-reviewer）、書いた者が審査しない分業
  - 品質ゲート: typecheck / lint / format / test、CI、カバレッジの閾値、`REVIEW.md`
- **なぜそうしたかを示す。** 各部品について、`.ai-board/plans/archive/` のどの計画で入ったかと、どんな失敗がきっかけだったかをつなぐ
- **自分の題材で回すときの読み順も書く。** CLAUDE.md の読み方、ボードのどこを見るか

## 背景

研修では、受講者がこのリポジトリを fork してループを回す。
回すだけでは、どの部品が何を守っているのかが見えにくい。CLAUDE.md は AI 向けに書かれていて、人が最初に読む案内にはなっていない。
伝えたいのは HIL・文脈の切り分け・品質ゲートの 3 つなので、その観点から部品へたどれる入口がほしい。

## 探索メモ

2026-11-03 に loop-permissions（PR #68）を回して分かった、案内に書きたい点と手順書の改善の候補。

- **ハーネスの設定は AI が書き換えられない。** deny の `Edit(/.claude/settings*.json)` と auto モードの判定で、作業者は `.claude/settings.json` を直せず保留した。人が頼んで Claude（メインの会話）が直した。
  これは境界が狙いどおりに効いた例として案内に書ける。あわせて、設定を触るカードは、計画の段階で「その節は人が行う」と決めておく決まりを `board-planner` の手順書に足すとよい
- **実際の Claude Code での確かめ方。** 作業者のサブエージェントからは、許可ルールが本当に効くかを確かめられなかった。
  メインの会話から、スクラッチパッドの bare リポジトリを `origin` にした clone で `claude -p --permission-mode auto` を起動すると確かめられた。
  照合されない `Write(...)` の deny の警告と、信頼していないワークスペースで allow が無視されることは、この方法で見つかった。動作確認の手順の型として案内に書けるか
