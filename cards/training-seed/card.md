## アイデア

研修の題材になるアイデアカードの一式をリポジトリに置き、fork したチームがコマンド 1 つでボードに取り込めるようにする。

- **置き場所。** 題材は main に置く（例: `training/cards/<id>.md`。`ai-board card show` と同じ frontmatter 付きの Markdown）。fork で必ず写るのは main だけなので、データ用ブランチには置かない
- **取り込み。** `ai-board card` にサブコマンドを足す（例: `ai-board card seed --from training/cards`）。まだ無いカードだけを `card create` と同じ口で起票し、既にある ID は飛ばす。何度走らせても重複しない。`rank`・`startedAt`・`## レビュー` は書かない（並び順と着手は人が決める）
- **取り込んだ後も main の題材は消さない。** `seed` は起票するだけで、`training/cards/` はそのまま残す。何度走らせても重複せず、fork の main が元のリポジトリとずれず、振り返りで原本と見比べられるため。題材は `training/` を触らない改良にする（受講者の PR が題材の原本を書き換えないように）
- **題材は新しく用意する。** このリポジトリの既存のアイデアは使わず、研修のために作る。ai-board 自身への小さな改良で、1 枚を 1 周（計画 → 実装 → PR中 → マージ）30〜60 分で回せる大きさにする
- **伝えたいことごとに選ぶ。** 重点は次の 3 つ
  - 人の判断ゲート（HIL）: 計画レビューで否決したくなる題材と、PR中 で AI が PR の本文に書いた動作確認の結果を読み、人が動かして初めて分かるズレが出る題材
  - 品質ゲート: 型やテストで AI のズレが捕まる題材
  - グリル: わざと曖昧さを残し、着手の前に AI に問い詰められて詰める題材。`idea-grill` ができるまでは予備に回し、研修の順路には入れない
- **枚数。** 2 日の研修で、チームが 1 つの fork を共有して回す。1 日目に 2〜3 周、2 日目に 3〜4 周を目安に、6〜8 枚と予備を用意する
- **研修の資料。** 準備の確かめの項目（元 `setup-doctor`）と、観点からハーネスの部品へたどる入口（元 `harness-guide`）を、研修の資料（README など）の一部として書く。どの順で回すか、どこで何を見るかもここに書く
- **答え合わせは置かない。** 講師用の答え合わせ（各題材で否決したくなる点、捕まるはずのズレ）は、このリポジトリの外（講師用の非公開の資料）に置く。main に置くと fork した受講者に見える

## 背景

研修では、受講者がペアやチームでこのリポジトリを 1 つ fork し、手元の PC で用意された題材のループを回す。2 日間の研修である。

カードの正本は `origin` の `ai-board/data` ブランチにある（ADR 0010）。ところが GitHub の fork は既定で main しか写さないので、fork したリポジトリのボードは空である。
すべてのブランチを写して fork しても、写るのはこのリポジトリ自身のバックログで、研修の題材ではない。
題材を毎回講師が手で起票するのではなく、main に置いた一式から取り込めるようにしたい。

fork の始め方は、今のコードでは次のとおり（README の「新しいリポジトリ」）。

1. `.ai-board/config.yaml` を用意する（git の追跡外。`config.example.yaml` から写す）
2. `ai-board init` で空のデータ用ブランチを作って push する（`config.yaml` もデータ用ブランチの根へ写る）
3. 題材を取り込む（このカードで足す）

## 論点

- **`config.example.yaml` の `github.repository`。** 例が `'iepyon/ai-board'` のままなので、受講者がそのまま写すと自分の fork ではなく元のリポジトリの PR を見る。準備の確かめの項目に入れるか、例を `<owner>/<repo>` のような置き換え前提の値にするか
- **チームで 1 つの fork。** 取り込みは誰か 1 人が走らせる。同時に走らせても重複しないこと（push の衝突は data-store が取り直してやり直す）
- **題材が本体の変更で古くなる。** ai-board 自身が変わると題材の前提がずれる。品質ゲートで気付ける形（題材が触るファイルが存在するか、題材のファイルが `card seed` で読めるか、など）にするか
- **fork に写る雑音。** main にはこのリポジトリの計画の archive（`.ai-board/plans/archive/`）も載っていて fork に写る。ボードの導出には効かないが、受講者が読む資料としては雑音になる。研修の前に片付けるか、そのままにするか

## 探索メモ

2026-11-03 のアイデアの整理で、次の 2 枚をこのカードにまとめた。どちらも研修の準備の一部として扱う。

- `setup-doctor`（準備が整っているかを 1 つのコマンドで確かめる）: コマンドは作らず、確かめる項目の一覧を研修の資料（README など）に置き、足りないかどうかは受講者が Claude に「準備を確かめて」と頼んで調べる形にする。
  項目の候補（auto モード、ワークスペースの信頼、許可ルールの警告など）は `setup-doctor` の本文の探索メモにある
- `harness-guide`（ハーネスの部品の案内）: 研修の資料の一部として書く。部品ごとの説明は Claude に聞けば答えられるので、観点（HIL・文脈の切り分け・品質ゲート）から部品へたどる入口だけを置く。
  案内に書きたい例は `harness-guide` の本文の探索メモにある
