## アイデア

PR の最新コミットに付いたチェック（GitHub Actions などの CI）の結果をカードに出す。
成功・失敗・実行中が、PR を開かずにボードから分かるようにする。

- **取得。** `github-client.ts` の `enrich` は既に `head.sha` でコミットを引いている。
  同じ sha で `gh api repos/{owner}/{repo}/commits/{sha}/check-runs` を引き、`MrState` に結果の要約を足す
- **見せ方だけを変える。** ステージの導出（`stage-resolver.ts`）には使わない。
  チェックが落ちていても PR中 は PR中 のままで、カードにバッジを出す
- **画面のロジック。** 要約（全体で成功 / 失敗 / 実行中 / チェック無し）の判定は純関数にしてテストを書く。
  `src/web/` はテスト対象外なので、`src/shared/` か `src/board/services/` に置く

## 背景

今のカードには、PR のコメントとコミットの日時は出るが、CI の結果は出ない。
チェックが落ちたまま Ready になった PR も、通った PR も、ボード上では同じに見える。
人は PR を開いて初めて、レビューする段階に無いことに気づく。

Mastra Factory は、マージの前に必須チェックを確かめることを人の手順に含めており、
push のあとはチェックの結果も合わせて見直すよう求めている。
ai-board も PR の状態を `gh api` で引いているので、同じ問い合わせにチェックを足すだけで、
人が PR を開く前に「見る価値があるか」を判断できる。

## 論点

- **チェックの出どころ。** GitHub には Checks API（`check-runs`）と古い Commit Status API（`status`）の 2 系統がある。
  外部の CI は後者だけに書くことがあるので、両方を合算するか
- **必須かどうか。** ブランチ保護の「必須チェック」だけを見るか、すべてのチェックを見るか。
  必須の判定にはブランチ保護の設定を引く必要があり、権限によっては読めない
- **件数と問い合わせの回数。** `check-runs` は既定で 1 ページ 30 件。CLAUDE.md の方針どおり `--paginate` で全件引く。
  ポーリングのたびにカードごとの問い合わせが 1〜2 本増える
- **Draft の PR。** 計画レビューの段階の Draft の PR にも出すか。計画しか載っていない時点のチェックは意味が薄い
- **区画との関係。** チェックが落ちた PR中 のカードは、人ではなく AI が直す番である。
  `pr-feedback-ai-turn`（指摘に AI が応える番のカードを区別する）と同じ判定に入れるか
- **`verify-gate` との関係。** 退避した DB にあった「人が実装を動かして確かめたい」カードの前段になる。
  CI が通っていることを、人の動作確認の前提にできる

## 探索メモ

2026-11-03 に `verify-evidence` にまとめたが、2026-11-04 の整理で、ボードのカードに CI の結果を出す部分をこのカードに戻した。
`verify-evidence` は締めの段で Ready の前に AI が CI を確かめる部分だけを受け持つ。ポーリングの問い合わせが増えるので `forge-poll-budget` と合わせて考える。
