## アイデア

データの持ち方（1 カード 1 ディレクトリ、ステージは保存せず導出）は変えずに、終わったカードのぶんの読み出しと問い合わせを減らす。

- **C-1. 中止のカードを GitHub の問い合わせから外す。** 中止のカード（`## レビュー` の最新が中止。`isAborted` でカードだけから分かる）は、控え（`snapshots/<id>.json`）があれば引き直さず、控えをそのまま使う。控えは消さない
- **C-2. `status --json` に、終わったカードを外す指定を足す。** `--active`（名前は計画で決める）を付けると、`cards` から マージ済み と 中止 の区画（`board-sections.ts` の純関数で決める）のカードを外す。既定は今までどおり全件。`board-decide` の手順 1 の読み出しにこの指定を付ける

## 背景

2026-11-07 に、データの持ち方を調べて測った（カード 90 枚。マージ済み 54・中止 30・アイデア 6）。

- カード 90 枚のファイルの読み込みは約 12ms で、問題にならない
- `status` 1 回の GitHub への問い合わせは 3 回で、そのうち 2 回は中止の `loop-dummy` / `loop-worker-dummy` の、マージされずに閉じた PR（#29 / #36）だった。
  `pr-fetcher.ts` の問い合わせの対象は PR 番号かブランチを持つ全カード（`src/infrastructure/pr-fetcher.ts:86`）で、マージ済みは控えで飛ばす（`isSettled`）が、閉じた PR は reopen されうるので毎回引いている
- `status --json` は約 233KB で、`cards` の 98% がマージ済みと中止のカード。`--only` は項目を絞れるがカードは絞れない。
  `board-decide` が手順 1 で読む `--only waiting,ideas,cards.id,cards.title,cards.stage,cards.skipGates,cards.latestReview,cards.prState` は約 69KB で、大半はマージ済みのカードの `prState`

状態ごとのフォルダ分けや、終わったカードを `cards/archive/` へ移す案も比べた。
前者はステージを保存しない不変条件を崩し、後者はデータ用ブランチの形の版を上げる割に、今の枚数では読み込みの速さがほぼ変わらない。実害は問い合わせの回数と AI が読む量なので、出力と問い合わせの側で絞る。

## 論点

- **C-1 の控えの扱い。** 問い合わせの対象から外すだけだと、`forgetUntracked` が控えを消す。「引かないが控えは残す」区別を足す。控えの無い中止のカード（PR を持ったまま一度も控えを取っていない）は、一度だけ引くか、引かないか
- **C-1 で中止を確かに終端とみてよいか。** 中止のカードは、どのステージでも区画が 中止 に固定され（`board-sections.ts` の `sectionOf`）、アイデアに出せる判断も中止だけ。後から PR が変わっても表示と判断は変わらないことを確かめる
- **C-2 の既定。** 既定は全件のまま、指定で絞る（既定で絞ると、`cards` を全件読む箇所が黙って欠ける）
- **C-2 の指定の形。** `--active` か、区画で選ぶ `--section inbox,work,idea` か。`--only` と組み合わせられるようにする
- **書く場所。** C-1 は GitHub の取得の話なので、`docs/architecture.md` の GitHub の取得の節か ADR 0003 に書き足す。ステージの導出（`stage-resolver.ts`）と ADR 0001 には触らない

## 探索メモ

- 2026-11-07 のチャットで、人が C-1 と C-2 を 1 枚で起票するよう頼んだ。`card list` に中止を外す指定を足す案（C-3）は、生きているカードを見る入口を `status` にまとめるため見送った
- `waiting` / `working` / `ideas` は今も生きているカードだけを持つ（`ideas` は中止を含まない）ので変えない
- データ用ブランチの形の版（`ai-board-data.yaml`）は上げない
