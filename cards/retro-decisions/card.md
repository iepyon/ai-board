## アイデア

「振り返りを見せて」と頼むと、人の判断（承認・差し戻し・中止）の記録から、指定した期間の振り返りを Artifact のダッシュボード 1 枚にまとめて出す。

- **判断の件数と率。** 承認・差し戻し・中止の件数、提出・再提出に対する差し戻しの率、1 回目の提出で承認されたカードの割合を出す
- **中止の分け方。** 提出の後の中止と、提出が一度も無いまま中止したアイデアの片付けを分けて数える
- **リードタイム。** 着手から計画の承認、承認からマージまでをカードごとに出し、中央値と長くかかったカードを並べる
- **差し戻しの理由。** 理由の文章を Claude が読んで分類し、分類ごとの件数と全文を並べる（`retro-stop-reasons` をここにまとめる）
- **期間を指定できる。** 研修の 1 周ごとや週ごとに出す
- 集計はページの JS（ダッシュボードの計算）に書く。Claude に毎回数えさせない
- 本体（`src/`）は、判断の記録を 1 件 1 行で出す読み出しの口（`board-events`）だけを使う

## 背景

2026-11-07 に、データ用ブランチの判断の記録 279 件から、探索としてダッシュボードを 1 枚作った（push はしていない）。そこで次のことが分かった。

- **`status --json` は要らない。** カードの `log/` の記録とカードのタイトルだけで、判断の振り返りの数字は全部出せた。`status --json` を読むと、ステージの導出と GitHub への問い合わせが毎回走るうえに、廃止した `verify` のエントリ（37 件）が `reviews` から消える（`RETIRED_REVIEW_GATES`）
- **数字のぶれは、本体に集計を入れなくても解ける。** 集計をページの JS に書けば、同じデータからは同じ数字が出て、式も読み手が確かめられる。`retro-artifact` の論点にあった「本体に純関数として戻すか」は要らなくなった
- **Claude の判断が入るのは、理由の分類だけだった。** 分類を別のファイルとして持てば、数字と理由を 1 枚に同居できる。そのため `retro-stop-reasons` をこのカードにまとめる
- **廃止したゲートの記録に発見があった。** 探索メモの答えの反映漏れによる差し戻し 3 件は、どれも `verify` のゲートだった。廃止したゲートも含めて読む価値がある

## 論点

- **日付の区切り。** 記録の時刻は UTC。日ごと・週ごとの区切りを JST にするか
- **「提出から判断まで」を出すか。** 探索では中央値が約 7 分だった。人がレビューに使った時間というより、その場にいたかどうかを測っている可能性がある。主役は着手からマージまでのリードタイムにして、こちらは参考に留めるか
- **リードタイムの終わりの時刻。** マージの時刻は PR（GitHub）にしかない。判断の記録だけで出せる「着手 → 計画の承認」までにするか、`prState.mergedAt` も読むか（読むなら GitHub への問い合わせが入る）
- **中止の理由。** 中止 30 件のうち 28 件は理由が空で、片付けか不要になったかを分けられない。中止にも短い理由を付ける運用にするか
- **理由の分類の安定。** 分類は Claude の判断なので、頼むたびに変わりうる。一度付けた分類を記録の ID に結んで残し、新しい記録だけを分類するか
- **ページの更新。** 探索のページは控えのファイルで、自動では更新されない。頼まれるたびに `board-events` を読み直して上げ直す、を手順として決める
