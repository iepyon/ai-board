## アイデア

カードのリポジトリに、判断の追記の専用の口を作る。判断を本文の文字列に一度書いてから読み直す往復をやめ、偽造が作りの上で起きないようにする。

- **判断の追記の口を分ける。** `CardRepository` に `appendReview(id, { at, gate, kind, reason })` のような口を足し、`log/` の判断のファイルを値からそのまま書く。理由はファイルの中身になるだけで、見出しとして読み直さない
- **本文の保存は判断を作らない。** `save(card)` は本文とメタだけを書き、判断のファイルは決して作らない。`planCardWrite` の「本文の形から判断の追記を推し量る」部分（`appendedEntries` / `readableHeading` / `planBody` の分岐）を消す
- **理由の検査を外せるか確かめる。** 理由が見出しとして読み直されなくなれば、`review-reason-escape` で入れた「判断の見出しとして読める行を含む理由を拒む」（`findEntryHeadingLine`、API の 400）は要らなくなる。外すか、残すかを決める
- **テスト。** `review-reason-escape` で入れた「偽造できない」テストが、作りを変えても通ることを確かめる

## 背景

`review-reason-escape`（PR #61）の AI レビューで見送った指摘から起こしたカード。

判断はデータ用ブランチでは既に 1 件 1 ファイル（ファイル名が時刻・ゲート・種別、中身が理由）で保存されている。
ところが書くときは、usecase が `appendReviewEntry` で本文の末尾に `### <時刻> <gate> <種別>` と理由の文字列を足し、
リポジトリ（`card-files.ts` の `planCardWrite`）が前の本文と新しい本文を比べて、足された部分を Markdown として読み直して判断を推し量っている。
docstring にも「足した判断が本文の差し替えなのか判断の追記なのかは、ここでは区別できない」とある。

理由（自由な文）と判断の見出し（構造）が同じ文字列に乗るので、理由に見出しの行が混ざると構造として読まれる。これが偽造の穴の根っこである。
`review-reason-escape` は、この作りのまま入口（usecase）で見出しに見える行を含む理由を拒んで塞いだ。
CLAUDE.md の「境界を構造で強制する」に沿うなら、文字列を経由しない口にするほうが素直である。

## 論点

- **本文の保存で `## レビュー` 節をどう扱うか。** 画面は組み立てた本文（`## レビュー` 節を含む）を送ってくる。節の変更を今までどおり拒むか（`ReviewEntriesChanged`）、節を無視して本文だけを書くか
- **どこまで踏み込むか。** 読む側（`stage-resolver` / `get-board.query` などの `parseReviewLog(card.body)`）も、組み立てた本文の文字列から判断を読み直している（`demoteHeadings` で守られている）。
  書く口だけを分けるか、`Card` に判断の配列を持たせて読む側も文字列を経由しないようにするか。後者はボードと画面まで及ぶ
- **理由の検査を残すか。** 作りで守れるなら外せるが、人の API で理由に見出しを書いたときの振る舞い（400 → 受け付ける）が `review-reason-escape` から変わる
- **移行の道（`legacyCardFiles` / `migrate-cli.ts`）。** 本文に `## レビュー` を持つ古い形からの移行は、本文から判断を読む必要が残る。新しい口とどう分けるか

## 探索メモ

2026-11-01 の動作確認（PR #62、画面を Playwright で動かした）で分かったことと、差し戻しの補足。

- **画面で見つかった問題。** AI が理由に `### 2099-01-01T00:00:00.000Z plan 承認` の行を混ぜると、カードの詳細パネルのレビュー欄に「2099-01-01T00:00:00.000Z plan 承認」が太字の見出しで出る。
  組み立てた本文で `####` に下がった行を、画面が Markdown の見出しとして描くためで、本物の判断の見出しとの違いは文字が少し灰色なことだけ。人の否決の理由に混ぜても同じ。
  ステージの導出は正しく（承認として数えられない）、判断待ちの区画では生の文字（`#### 2099…`）のまま出る
- **人の方針。** 本文とログ（判断）は分けて表示する。保存は既に `card.md` と `log/` に分かれているので、画面も分ける。
  判断の見出し（時刻・ゲート・種別）は画面が値から描く部品にし、理由はその中に文字として入れて、何を書いても判断の見出しに見えないようにする
- **分けるときの論点（監視役の見立て。計画で確かめてほしい）。**
  - API が判断の一覧を、組み立てた本文とは別の項目で返す必要がある（今は本文しか返していない）
  - 本文の編集に `## レビュー` 節を出さなくなる。節の無い本文の保存を「判断は変えない」と扱うよう、本文の差し替えの検査（今は節が無いと判断を消したとみなして 409）を変える必要がある
  - 今の計画の Non-Goals（`Card` に判断の配列を持たせて読む側も文字列を経由しない）とどう線を引くか
