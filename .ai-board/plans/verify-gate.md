# PR を見る前に、AI の実装を動かして確かめる列を足す

## この計画で使う言葉

ボードの仕組みを知らなくても読めるように、先に言葉をそろえておく。

- **カード**：やりたいこと 1 件を表す札。アイデアのメモから計画、ブランチ、PR、マージまでを 1 枚で追う。
- **ステージ（列）**：カードがいまどの段階にあるか。画面では横に並んだ列として見える。今は アイデア、計画提案中、計画レビュー、実装中、PR中、マージ済み の 6 つがある。
  ステージはどこにも保存しない。計画ファイル、PR の状態、カードに残った人の判断の記録から、毎回計算して決める。これを「導出」と呼ぶ。
- **ゲート**：人の確認を通らないと先へ進めない関所。今は計画を確かめる `plan` の 1 つだけがある。
- **提出 / 承認 / 否決**：ゲートでのやり取り。AI が「確かめてほしい」と書くのが提出、人が「よい」と書くのが承認、「直して」と書くのが否決である。
  どれもカード本文の `## レビュー` の節に 1 件ずつ追記され、消えない。ゲートの状態は、そのゲートの最新の 1 件で決まる（1 件も無ければ「未提出」）。
- **飛ばす宣言（`skipGates`）**：人があらかじめ「このカードではこのゲートを見ない」と決めておく印。宣言されたゲートは承認済みと同じに扱う。
- **判断待ちの区画**：画面の一番上にある、人が判断すべきカードを集めた場所。
- **監視役と作業者**：AI の側の分担。監視役（`/board-loop` のスキル）がボードを見て次にやる 1 手を選び、作業者（board-worker）にその 1 手だけをさせる。
- **次の一手**：監視役が選ぶ「AI が次にやること」。今は 計画を書く（`plan`）、否決された計画を直す（`revise-plan`）、タスクを 1 つ進める（`implement`）の 3 種類がある。
  `implement` はタスクを全部終えていれば、AI レビューをしてから PR を Ready にする。
- **AI レビュー**：PR を人に渡す前に、AI が `/code-review` で差分を見直して指摘を直すこと。
- **Draft の PR / Ready の PR**：GitHub の PR の 2 つの状態。Draft は「まだ途中」、Ready は「レビューしてよい」を表す。
  今の流れでは、計画を出した時点で Draft の PR を作り、実装を終えたら Ready にする。

## 提案

### Why

今のボードで人がカードを確かめる場面は 2 つある。
計画レビューで計画を読む場面と、PR中 でコードの差分を読む場面である。
どちらも文章やコードを読む確認で、実装を実際に動かす場面はボードの流れに入っていない。

動かして確かめたければ、人が自分でブランチを手元で起動するしかない。
しかしボードはそれを「人の番」として示さないので、気づいたときに気づいた人がやることになる。
すると、差分を読み終えてから動かし、意図と違う振る舞いに気づき、直った後にもう一度差分を読む、という二度手間が起きやすい。

そこで、実装中 と PR中 の間に「動作確認」の列を入れる。
動作確認では振る舞いが意図どおりかだけを見て、PR中 ではコードの質や設計を見る。
先に動かして確かめておけば、PR のレビューはコードの話に集中できる。

### What Changes

使う人から見た変化は次のとおり。

- 列が 1 つ増えて 7 つになる。実装中 と PR中 の間に「動作確認」が入る。人の番の列なので、判断待ちの区画に出る
- AI は実装を終えると、PR を Draft のまま動作確認を頼む（`verify` ゲートに提出する）。
  頼むときは、人が動かすための手順（起動のコマンド、見る画面、期待する結果）と、AI 自身が動かしてみた結果を書く
- 人は手順どおりに動かして、承認か否決のボタンを押す。
  承認すると、AI が PR を Ready にして PR中 へ進める。否決すると、AI が理由を読んで直し、もう一度動作確認を頼む
- 動かすまでもない小さな変更は、詳細パネルの「動作確認を飛ばす」に印を入れれば、この列を通らずに今と同じく PR中 へ進む
- 計画に `## 動作確認の手順` の節が増える。計画レビューの時点で、後で何を動かして見ることになるかを読める

中の仕組みの変化は次のとおり。

- ゲートに `verify` を、ステージに `verifying`（動作確認）を足す
- ステージを決める規則に 1 本だけ足す。「計画が承認済みで、動作確認が提出されている → 動作確認」である。
  否決、承認、飛ばす宣言のための規則は足さない（理由は「設計」で述べる）
- AI の次の一手に 2 種類を足す。動作確認で否決された実装を直して頼み直す `revise-impl` と、承認された実装を Ready にする `ready` である
- CLI の `ai-board card submit` に、どのゲートへの提出かを選ぶ `--gate <plan|verify>` を足す（省略すると今と同じ `plan`）

- 型: `src/cards/models/review.ts`、`src/shared/schemas/common.ts`、`src/shared/stage-labels.ts`、`src/web/types.ts`
- 導出: `src/board/services/stage-resolver.ts`、`src/board/services/next-action.ts`、`src/board/usecases/queries/get-board.query.ts`、`src/board/models/board-card.ts`
- 見せ方: `src/shared/dashboard-sections.ts`、`src/web/components/`（`InboxSection` / `ReviewActions` / `CardDetail` / `parts` / `PipelineStrip` と詳細パネル）
- CLI: `src/cards/cli/card-cli.ts`
- ループ: `.claude/agents/board-worker.md`、`.claude/skills/board-loop/SKILL.md`
- ドキュメント: `CLAUDE.md`、`README.md`、`docs/specs/board-stages/spec.md`、`docs/specs/card-review/spec.md`

  `latestReview` に `gate` が増える。ローカル専用ツールで外部の利用者は無い

## 設計

### Decisions

#### 1 枚のカードは新しい流れをどう通るか

まず具体例で流れを追う。
「カードを絞り込めるようにする」というカードが 実装中 にあるとしよう。

1. 作業者が計画のタスクを全部終え、AI レビューの指摘も直した
2. 作業者は PR を Draft のまま、`ai-board card submit <id> --gate verify` で動作確認を頼む。
   本文には「`npm run dev` で起動し、検索欄に『PR』と打つと PR中 のカードだけが残る」のような手順と、自分で動かした結果を書く
3. カードの `## レビュー` に `verify 提出` の 1 件が増え、カードは 動作確認 の列へ移る。判断待ちの区画に出るので、人は自分の番だとわかる
4. 人は手順どおりに動かし、意図どおりなら承認を押す
5. カードは 実装中 の列に戻る。今度は「承認されたので Ready にする」番で、監視役は次の一手に `ready` を選ぶ
6. 作業者は計画を archive へ移し、`gh pr ready` で PR を Ready にする。カードは PR中 へ進み、人はコードの差分を読む

5 で 実装中 に戻るのは、Ready にするのが AI の作業だからである。
動作確認 の列は「人が動かす番」だけを表し、AI の作業を待つ間は AI の列（実装中）に置く。

この流れには脇道が 2 つある。

- **否決されたとき**：4 で人が否決を押すと、カードは 実装中 に戻る。
  監視役は `revise-impl` を選び、作業者は否決の理由と PR のコメントを読んで直し、もう一度動作確認を頼む（3 へ戻る）
- **飛ばす宣言があるとき**：人が詳細パネルで「動作確認を飛ばす」に印を入れていれば、作業者は 2 で頼まず、今と同じく archive して Ready にする。
  カードは 動作確認 の列を通らない

#### ステージを決める規則のどこに 1 本足すか

ステージは、規則を上から順に調べ、最初に当てはまったもので決まる。
上ほど先へ進んだステージで、新しい規則は PR中 と 実装中 の間に置く。

```
1 merged      計画が archive 済み、または PR が merged
2 pr          PR が opened かつ Draft でない
3 verifying   plan 承認済み かつ verify が submitted      ← 足す
4 impling     plan 承認済み
5 plan-review 計画ファイルか Draft の PR があり plan が none / submitted
6 planning    startedAt が非 null
7 idea        既定
```

前の節の流れは、この 1 本だけで説明がつく。
動作確認のゲートの状態ごとに、カードの行き先をまとめると次のようになる。

| 動作確認のゲートの状態    | ステージ  | 次に動く者                          |
| ------------------------- | --------- | ----------------------------------- |
| 未提出                    | impling   | AI（タスクを進め、終われば頼む）    |
| 提出済み                  | verifying | 人（動かして承認 / 否決）           |
| 否決                      | impling   | AI（理由を読んで直し、頼み直す）    |
| 承認（人が押した）        | impling   | AI（archive して Ready にする）     |
| 承認（飛ばす宣言による）  | impling   | AI（今と同じく、終われば Ready に） |
| どの状態でも、PR が Ready | pr        | 人                                  |

否決や承認のための規則を足さないのは、計画レビューと同じしくみで足りるからである。
否決されるとゲートは「提出済み」でなくなるので、3 の規則が外れ、1 つ下の 4（実装中）に自然に落ちる。承認も同じく 4 に落ちる。
専用の規則を足すと、計画と動作確認で差し戻しの扱いが食い違いやすくなる。

気になる点が 2 つある。

1 つ目は、Draft の PR があると計画レビューへ戻ってしまわないか、である。
5 の規則は「Draft の PR があれば計画レビュー」と読めるうえ、動作確認を頼む時点の PR は Draft のままである。
しかし 5 は計画がまだ承認されていない（plan が none / submitted の）ときにしか当てはまらない。
計画が承認されたカードは 3 か 4 で決まるので、5 まで調べが下りてこない。

2 つ目は、今あるカードの列が変わらないか、である。
Ready の PR を持つカードは、3 より上の 2 で決まる。動作確認を頼んでいない実装中のカードは、3 に当てはまらず 4 のままである。
この変更を入れただけで列が動くカードは無い。

#### AI の次の一手をどう分けるか

今は、実装中のカードに対する手は `implement` の 1 種類しかない。
動作確認が入ると、実装中のカードには「まだ頼んでいない」「否決された」「承認された」の 3 つの事情がありうる。

この 3 つを、計画のタスクの進み具合で見分けるわけにはいかない。
計画ファイルは作業用のブランチにあり、監視役が見ているチェックアウトからは読めないことが多いからである。
そこで、動作確認のゲートの状態で手を分ける。

| 動作確認のゲートの状態        | 手            | 作業者がすること                                                                            |
| ----------------------------- | ------------- | ------------------------------------------------------------------------------------------- |
| 未提出 / 飛ばす宣言による承認 | `implement`   | タスクを 1 つ進める。全部終えていれば AI レビューをして、動作確認を頼む（飛ばすなら Ready） |
| 否決                          | `revise-impl` | 否決の理由と PR のコメントを読み、直して品質ゲートを通し、`--resubmit` で頼み直す           |
| 承認（人が押した）            | `ready`       | 計画を archive へ移してコミットし、`gh pr ready` で Ready にする                            |

表の 1 行目と 3 行目は、どちらもゲートの状態が「承認」である。
ゲートの状態を読む関数（`gateState`）は、飛ばす宣言も人の承認も同じ `approved` で返すからである。
しかし手は違う。飛ばす宣言ならタスクがまだ残っているかもしれないので `implement`、人が承認したなら実装は終わっているので `ready` になる。
この 2 つを見分けるため、次の一手を選ぶ関数に渡すカードの情報（`NextActionCard`）に、飛ばす宣言（`skipGates`）を足す（ボードのカードの情報 `BoardCard` は既に持っている）。

`revise-impl` を `implement` に混ぜず、「直してから頼み直すまで」を 1 手にする理由も述べておく。
`implement` に混ぜると、作業者は「この否決への直しはもう済んだか」を見分ける印が要る。
印が無ければ、否決の 1 件が最新である限り、毎周同じ直しを繰り返しかねない。
1 手で頼み直せば、カードは 動作確認 へ上がるので、同じ手がもう一度選ばれることも無い。
否決された計画を直す `revise-plan` と同じ形である。
直しが 1 手に収まらないほど大きいときは、作業者は止まって報告する。その場合は人が計画から見直す方がよい。

#### 判断待ちの区画に、どのレビューの記録を出すか

判断待ちの区画は、カードごとに「提出の本文」と「待ち始めた時刻」を出している。
どちらもカードの最新のレビューの記録（`latestReview`）から取っており、今は `plan` ゲートの記録に決め打ちになっている。

動作確認の列にあるカードでは、`verify` の提出の本文（動かす手順）を出したい。
ゲートごとに最新の記録を持たせる案もあるが、そうすると画面の側で「このステージならどのゲートの記録を読むか」を毎回分け直すことになる。

そこで `latestReview` は 1 つのまま、意味を「その列が待っているゲートの最新の記録」に変える。
計画レビューの列なら `plan` の最新、動作確認の列なら `verify` の最新、それ以外の列ならゲートを問わず最新の記録にする。
何のゲートの記録かがわかるように、`gate` を足す。
待ち始めた時刻（`waitingSince`）は `latestReview` から取るので、手を入れなくても動作確認の提出時刻が待ち始めになる。

ステージからゲートを引く表（今は画面の側にある `GATE_OF_STAGE`）は、サーバも使うようになる。
そのため、サーバと画面の両方から読める `src/shared/` へ移す。

#### 動かす手順をどこに書くか

手順は 2 か所に書く。

1 か所目は計画の `## 動作確認の手順` の節で、起動のコマンド、見る画面、期待する結果を書く。
人は計画レビューの時点で、後で何を確かめることになるかを読める。

2 か所目は動作確認を頼むときの提出の本文で、実装を経て変わった手順、AI が実際に動かした結果、計画から変わった点を書く。
画面を見られずに確かめられなかった部分は、確かめられなかったと書く。
判断待ちの区画は提出の本文を畳まずに出すので、人は PR を開かなくても手順を読める。

#### AI レビューをいつするか

動作確認を頼む前に済ませる。
人が動かした後で AI レビューの指摘による直しが入ると、確かめた振る舞いが変わってしまうおそれがあるからである。
承認の後の `ready` の手では archive と Ready だけをして、コードには触らない。

#### 動作確認を飛ばす入口をどこに作るか

飛ばす宣言を書く入口は、今は API（`PATCH /api/cards/:id` の `skipGates`）にしかなく、画面にも CLI にも無い。
このままでは「小さな変更は飛ばせる」が実際には使えない。
そこで、詳細パネルに「動作確認を飛ばす」のチェックボックスを足し、`skipGates` の `verify` を出し入れする。

CLI には足さない。
CLI は AI も使う入口であり、AI が自分で飛ばす宣言を書けないことを、入口が無いことで守っているからである。
計画レビューを飛ばすチェックボックスも、今回は足さない。

### Risks / Trade-offs

- **`verifying` という名前の使い回し。** 以前（cecbf0b）廃止した「検証中」の列も `verifying` という名前だった。そちらは AI レビューの列で、意味が違う。
  ステージは保存しないので、古い値とぶつかることは無い。古い意味の `verifying` が残っているのは archive の計画だけである
- **人の手間が 1 つ増える。** すべてのカードで動作確認を待つと、小さな変更でも人を 1 回待つことになる。詳細パネルのチェックボックスで飛ばせるようにして和らげる
- **AI が「動かした結果」を書けないことがある。** 画面の見た目を確かめるのは、エージェントには難しい。
  書けない部分は書けないと明記させ、推測で「確認した」と書かせない
- **このカード自身は今の流れで進む。** 作業者の手順書（`.claude/agents/board-worker.md`）はメインのチェックアウトから読まれるので、この変更がマージされるまでは今の手順書のままである。
  そのため、このカードの実装は今の `implement`（終えたら Ready にする）で進み、新しい流れを通しで確かめられるのはマージ後になる
- **列にしない案。** 列を足さず、「Ready にする前に動作確認の承認が要る」という決まりだけを足す案もある。
  しかし列にしないと、動かして確かめる番が判断待ちの区画に出ない。ボードが人の番を示さないという、もともとの問題が残る

### Non-Goals

- ボードの画面からブランチのコードを起動すること。画面から任意のブランチのコードを動かすには、書き込み境界と信頼についての議論が別に要るので、別カードにする
- 計画レビューを飛ばすチェックボックス
- 承認や否決を書く入口を CLI に足すこと（承認と否決は人だけが書く）
- 承認の理由に書かれた別件を自動で起票するしくみ。作業者が `ai-board card create` で起票すれば足りる

## 動作確認の手順

このカードの実装を人が動かして確かめるときの手順である。
共有の DB を汚さないように、`AI_BOARD_DB` で別の DB を指し、`ai-board card create` で作ったダミーのカードで試す。

1. `npm run build` の後に `node dist/cli.js status` を実行し、`verify 提出` のあるカードが判断待ちに `[動作確認]` として出ることを見る
2. `npm run dev` と `npm run dev:web` を起動し、ブラウザで次を見る
   - 件数帯に「動作確認 ★」の列があり、実装中 と PR中 の間に並ぶ
   - 判断待ちの区画に動作確認のカードが出て、提出の本文（手順）が見える。「PR を開く」のリンクと、承認 / 否決 / 中止のボタンが使える
   - 否決すると AI 作業中の区画（実装中）へ戻る。承認しても実装中に残る（AI が Ready にするのを待つ）
   - 詳細パネルの「動作確認を飛ばす」に印を入れると、提出済みのカードが実装中に落ちる

## タスク

### 1. ゲートとステージ

- [x] `verify` ゲートと `verifying` ステージを足し、導出のルールを 1 本足す。型を壊す変更と受け止める箇所を 1 つのコミットにまとめる
  - `REVIEW_GATES` を `['plan', 'verify']` に、`STAGES` の `impling` と `pr` の間に `verifying` を入れる
  - `Record<Stage, …>` / `Record<ReviewGate, …>` の表を埋める: `STAGE_LABELS`（動作確認）、`SECTION_OF_STAGE`（inbox）、web の `Stage` / `ReviewGate` / `STAGE_OWNER`（human）/ `STAGE_SOURCE`（plan）
  - `stage-resolver.ts` の `toFacts` に `verify` を、`RULES` に `verifying` のルールを足し、docstring の判定表を 7 段に直す
