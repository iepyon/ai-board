# 実装中のタスクを一気に倒し、AI レビューを別の作業者に任せる

## この計画で使う言葉

- **監視役**：`/board-loop` のスキルを動かすセッション。`ai-board status --json` の `next` を読み、作業者に 1 手を渡し、報告を人に伝える。
- **作業者**（board-worker）：監視役から 1 手を受け取り、まっさらな文脈で進めるサブエージェント。
- **取りまとめ役**：この計画で、`implement` の手を受けた作業者が担う役。自分ではコードを書かず、タスクを 1 つずつ別のサブエージェントに渡す。
- **タスクの作業者**（board-task、新設）：取りまとめ役から計画のタスク 1 つを受け取り、実装して品質ゲートを通し、コミットして push するサブエージェント。
- **レビューの作業者**（board-reviewer、新設）：計画と PR の差分を読み、指摘を計画の `## AI レビュー` 節にチェックボックスで書き足すだけのサブエージェント。コードは直さない。
- **段**：`implement` の 1 手の中で、計画の状態から決まる作業の区切り。タスクを倒す段、レビューの段、締めの段の 3 つがある（後述）。

## 提案

### Why

今の `implement` は、1 手で計画のタスクを 1 つだけ倒す。
`board-loop-skill` の計画で「コミットと人の判断の単位を小さく保つ」ために決めた単位で、`loop-fresh-context` で作業者に移したときも、次の手は次の cron の周が選ぶ形のままにした。

2026-10-30 に `verify-gate`（タスク 16 件）をループで実装したところ、1 手は 3〜5 分で終わるのに、タスクごとに 5 分の周を待った。
PR中 になるまでの時間の半分以上が待ち時間だった。
実装中は人の判断を挟まない区間なので、タスクの境目で次の周を待つ理由は無い。
止めたいときは作業者を `TaskStop` で止めればよい。コミットはタスクごとに分かれたままなので、次の作業者が続きから再開できる。

AI レビューにも問題がある。
今は `implement` の最後の手で、作業者が自分で `/code-review` にかけ、指摘を自分で直している。
新しい文脈で読むとはいえ、何を直すかを決めるのは実装した作業者自身である。
レビューを別の作業者に分け、レビューの作業者は指摘を書くだけにし、直すのは実装の側に任せれば、書いた者が自分の書いたものを審査する形を避けられる。

### What Changes

使う人から見た変化は次のとおり。

- 監視役は、作業者の完了の通知を受けたら、次の cron の周を待たずに次の手を選んで渡す
- `implement` の 1 手で、未チェックのタスクを最後まで倒す。タスクごとに新しいタスクの作業者が立ち、コミットと push はタスクごとに分かれる
- タスクを倒し終えると、次の `implement` の手でレビューの作業者が立ち、計画の末尾に `## AI レビュー` 節を書き足す。
  レビューの作業者は指摘を「直す」と「見送る」に分ける。直す指摘は `- [ ]` のチェックボックスで、見送る指摘はチェックボックスの無い箇条で理由を添えて書く。指摘が無ければ「指摘なし」と書く
- 直す指摘のチェックボックスは普通のタスクとして、次の `implement` の手で倒される。ボードの進捗バーにもそのまま乗る。見送る指摘は直さない
- 指摘を倒し終えると、次の `implement` の手で、見送った指摘を PR の本文の `## 見送った AI レビューの指摘` 節に書き、今と同じく動作確認を頼む（動作確認を飛ばす宣言があれば Ready にする）
- AI レビューは 1 回だけ。指摘を直した後にもう一度レビューはしない。その先は人が動作確認と PR で見る
- `revise-impl` の手で作業者が自分でかける AI レビューも、重要な指摘だけを直し、見送った指摘を PR の本文の同じ節に足す

中の仕組みの変化は次のとおり。

- `next.action` に `review` を足さない。`implement` の手を受けた作業者が、ワークツリーの計画を読んで段を決める
- サブエージェントの定義を 2 つ足す（`.claude/agents/board-task.md`、`.claude/agents/board-reviewer.md`）
- `src/` のコードは変えない。`next-action.ts` の docstring だけを直す

### Impact

- ループ: `.claude/agents/board-worker.md`（`implement` の段分け、`revise-impl` の直す指摘の絞り込み、`revise-plan` の `## AI レビュー` 節の扱い、報告の項目）、
  `.claude/agents/board-task.md`（新規）、`.claude/agents/board-reviewer.md`（新規）、
  `.claude/skills/board-loop/SKILL.md`（手順 4 の待たない運転、手の一覧、frontmatter の description）
- コード: `src/board/services/next-action.ts` の docstring だけ。`pickNextAction` の判定と `status` の出力は変えない
- ドキュメント: `CLAUDE.md`（1 周の流れの手順 4 と、ループの手の説明）、`README.md`（AI ループの節と手の表）、
  `docs/specs/board-stages/spec.md`（AI レビューを実装中の内部工程とする記述）
- DB・API・画面: 変更なし

## 設計

### Decisions

#### `review` を次の一手の種類にしない

カードのアイデアでは、レビューを監視役が渡す新しい手（`review`）として描いていた。
しかし監視役は、「タスクを倒し終えたか」「レビュー済みか」を見分けられない。

`next-action.ts` の `judgeImpling` の docstring にあるとおり、実装中のカードの手は計画のタスクの進み具合では分けていない。
計画ファイルは作業用のブランチにあり、ボードを動かすメインのチェックアウトからは読めないことが多いからである。
`plan.repository.ts` もメインのチェックアウトの `.ai-board/plans/` をファイルとして読むだけである。

`status` にブランチの計画を `git show` で読ませる案もある。
しかしサーバと `status` に git の読み取りを持ち込むことになり、計画の「ファイルがあれば列が立つ」という今の読み方とも二重になる。
そこで `next.action` は今のまま `implement` とし、手を受けた作業者がワークツリーの計画を読んで段を決める。

#### `implement` の 1 手は、計画の状態から決まる 1 段だけを進める

作業者は計画を読み、次の表の上から当てはまった段を進めて終える。

| 計画の状態                                | 段             | すること                                                                      |
| ----------------------------------------- | -------------- | ----------------------------------------------------------------------------- |
| `plans/archive/` にある                   | （今と同じ）   | 前の周で `gh pr ready` だけが失敗している。`gh pr ready` だけをやり直す       |
| 未チェックのタスクがある                  | タスクを倒す段 | 取りまとめ役として、残りのタスクをタスクの作業者に 1 つずつ渡し、最後まで倒す |
| 全部倒れていて、`## AI レビュー` 節が無い | レビューの段   | レビューの作業者を立て、`## AI レビュー` 節を書かせる                         |
| 全部倒れていて、`## AI レビュー` 節がある | 締めの段       | 動作確認を頼む。動作確認を飛ばす宣言があれば archive して Ready にする        |

`## AI レビュー` 節の指摘は `- [ ]` で書かれるので、指摘があればレビューの段の次の手は「タスクを倒す段」になる。
指摘を倒し終えれば締めの段になる。
レビュー済みかどうかは節の有無だけで決まり、専用の状態は持たない。

段の境目で手を終えるのは、カードのアイデアの表のとおり、段ごとに作業者の文脈を新しくするためである。
監視役が待たずに次の手を渡すので、境目で手を終えても待ち時間は生まれない。
どの段で止まっても、状態は計画のチェックボックスとコミットに残っているので、次の手は同じ表から続きを選べる。

#### タスクを倒す段：タスクごとにタスクの作業者を立てる

取りまとめ役は自分ではコードを書かない。
上から最初の未チェックのタスク（インデントされたサブタスクも 1 つと数える。今と同じ）を、新しいタスクの作業者に渡す。
渡すのはカード ID、タスクの行そのもの、ワークツリーのパス、`$MAIN` だけにする。
前のタスクの要約は添えない。添えると、まっさらな文脈で書かせる意味が薄れる。

タスクの作業者は計画とカード本文を自分で読み、そのタスクだけを実装し、品質ゲートを通し、計画のその行に `[x]` を付けてコミットし、push する。

取りまとめ役は、返ってきた報告をうのみにせず、次を確かめてから次のタスクへ進む。

- 渡したタスクの行が `[x]` になっている
- コミットが増え、push されている（`origin/<branch>` と一致する）
- ワークツリーに未コミットの変更が残っていない

どれかが満たされないとき、またはタスクの作業者が止まったと報告したときは、そこで止まって監視役に報告する。
未チェックのタスクが無くなったら手を終える。

タスクの作業者の名前は `board-task-<カード ID の先頭>-<連番>` とする。
監視役の手順 0 は `board-worker-` で始まる作業中の作業者を探すので、入れ子の作業者が監視役の判定を乱さない。

#### レビューの段：レビューの作業者は指摘を書くだけ

レビューの作業者は計画、カード本文、PR の差分を読み、`/code-review` にかける（呼べなければ `gh pr diff` を `REVIEW.md` の観点で読む）。
指摘を「直す」と「見送る」に分け、計画の末尾に次の形で書き足し、計画ファイルだけをコミットして push する。

```markdown
## AI レビュー

- [ ] `src/foo.ts` の `bar()` で、空の配列のときに例外になる。空なら早く返す
- [ ] …

### 見送った指摘

- `src/foo.ts` の変数名 `tmp` が意味を表していない。挙動に関わらず、この PR の目的から外れるので見送る
- …

### 人に判断してほしいこと

- 〜は計画の決定と食い違う。どちらに寄せるかは人が決める
```

指摘が無ければ節に「指摘なし」とだけ書く。
直し方に人の判断が要る指摘はチェックボックスにせず、`### 人に判断してほしいこと` に書く。

直すか見送るかは、レビューの作業者が決める。
実装の側に選ばせると、書いた者が自分の書いたものへの指摘を取捨することになり、レビューを分けた意味が薄れる。
判断の基準は `board-reviewer.md` に書く。

- **直す:** 誤った振る舞い（バグ、境界の取りこぼし、例外）、セキュリティ、データの破損や消失、計画の決定やハードルールとの食い違い、振る舞いを足したのにテストが無いこと
- **見送る:** 名前や書き方の好み、振る舞いを変えない小さな整理や重複の除去、この PR の目的の外にある改善

見送る指摘をチェックボックスにしないのは、ボードの進捗バーと段の判定が `- [ ]` を全部数えるからである。
見送る指摘を `- [ ]` で書くと、いつまでも未チェックのまま残り、締めの段へ進めなくなる。
`implement` には保留が無いので、この節の中身は締めの段で動作確認の提出の本文（飛ばす宣言のときは PR のコメント）へ写し、人に届ける。

レビューの作業者がコードを直さないことは、道具の制限では守りきれない。
定義の `tools` から Edit と Write を外しても、Bash でファイルを書けるからである。
そこで、レビューの段を進めた作業者（取りまとめ役）が、レビューの作業者のコミットが `.ai-board/plans/<id>.md` だけを変えていることを `git diff --name-only` で確かめる。
ほかのファイルが変わっていれば、そこで止まって監視役に報告する。

#### 締めの段：今の終わり方のまま

今の `implement` の「全部倒れていて、計画がまだ `plans/` にある」の後半と同じである。
AI レビューは済んでいるので、作業者は自分で `/code-review` をかけない。
動作確認を頼むときは、計画の `## 動作確認の手順` を動かせるところは動かし、提出の本文に `### 人に判断してほしいこと` の中身を足す。

その前に、計画の `### 見送った指摘` を PR の本文の `## 見送った AI レビューの指摘` 節に写す（`gh pr edit <mr> --body`）。
見送った指摘が無ければ、節に「なし」と書く。節が既にあれば中身を差し替え、二重にしない。
締めの段で書くのは、動作確認を頼む道と、飛ばす宣言で Ready にする道のどちらも通るからである。

写す先は PR のコメントではなく本文にする。
人は PR を開いたときに本文をまず読み、コメントは動作確認の否決や議論で流れていく。
本文の節なら、`revise-impl` で見送りが増えたときも同じ場所に足せる。

#### `revise-impl` の AI レビューも、重要な指摘だけを直す

`revise-impl` では、今と同じく作業者が直した差分を自分で `/code-review` にかける（レビューの作業者には分けない。Non-Goals を参照）。
ただし直すのは、レビューの段と同じ基準で「直す」に当たる指摘だけにする。
見送った指摘は、PR の本文の `## 見送った AI レビューの指摘` 節に足してから頼み直す。
基準を `board-reviewer.md` と二重に持たないよう、`board-worker.md` からは `board-reviewer.md` の基準を読むように書く。

#### 監視役は完了の通知を受けたら次の手を渡す

今の手順 4 は「次の作業者は渡さない（次の手は次の cron の周が選ぶ）」としている。
これを「報告を伝えた後、手順 0 から 3 をそのまま続ける」に変える。
手順 0 の `ListAgents` の判定は残すので、通知の直後に cron の周が来ても、作業中の作業者がいればその周は止まる。

#### 計画から立て直させたときは `## AI レビュー` 節を外す

人が実装の途中から「計画から立て直させる」を選ぶと、`revise-plan` の手で計画を直す。
このとき前の周の `## AI レビュー` 節が残っていると、実装を作り直した後のレビューの段が飛ばされる。
そこで `revise-plan` では、計画に `## AI レビュー` 節があれば消す。
archive から `plans/` へ戻すときも同じである。

#### 入れ子のサブエージェントで待てることを最初に確かめる

取りまとめ役も、レビューの段を進める作業者も、それ自身がバックグラウンドのサブエージェントである。
その中からさらにサブエージェントを立て、終わるまで待ってから次へ進めるかは、まだ確かめていない。
2026-10-30 の動作確認では、作業者が `Agent` の道具を持つことまでは確かめた。

そこでタスク 2 で、作業者の中から入れ子のサブエージェントを立て、次を確かめて計画の `## 調べた結果` に書く。

- 入れ子のサブエージェントの完了を、取りまとめ役が自分の実行を終えずに待てるか（完了の通知が届くか、`Monitor` で条件を待つ必要があるか）
- 監視役の `ListAgents` から、入れ子のサブエージェントがどう見えるか
- 取りまとめ役を `TaskStop` で止めたとき、入れ子のサブエージェントも止まるか

待てないと分かったときの代わりの道も決めておく。
タスクを倒す段は、今と同じく作業者が自分でタスクを 1 つ倒して手を終える形に戻す。
監視役が待たずに次の手を渡すので、待ち時間の問題はそれだけで解ける。
レビューの段は、作業者自身がレビューの作業者の手順で指摘を書く。
その作業者はコードを書いていない新しい文脈なので、書いた者が自分を審査する形にはならない。

### Risks / Trade-offs

- **待ち時間は、監視役が待たないことだけでも消える。** カードの動機だった 5 分の待ちは、手順 4 の変更だけで解ける。
  取りまとめ役の層が足すものは、タスクの報告（タスクあたり最大 5 行）を監視役の文脈に積まないことである。
  タスク 16 件なら 80 行で、監視役の文脈を圧迫するほどではない。そのため入れ子が使えなければ、取りまとめ役を諦めてよい
- **1 手が長くなる。** タスクを倒す段は、タスクの数だけ時間がかかる。手順 0 の報告に「いつから」が出るので、人は長さで固まりを疑える。
  止めたいときは `TaskStop` で取りまとめ役を止める。入れ子の作業者が一緒に止まらない場合の扱いはタスク 2 の結果で決める
- **レビューの作業者の制限は、事後の確かめでしか守れない。** コミットの差分で確かめるので、コミットせずに書いたファイルは、取りまとめ役が未コミットの変更として見つけて止まる
- **このカード自身は今の流れで進む。** 作業者とサブエージェントの定義はメインのチェックアウトから読まれる。
  そのため、このカードの実装は今の `implement`（1 手で 1 タスク、最後に自分で AI レビュー）で進み、新しい流れを通しで確かめられるのはマージ後になる
- **一気に倒す案との比較。** 1 手でタスク、レビュー、指摘の修正、動作確認の提出までを続けて行う案もある。
  手は短くならず、段ごとに文脈を新しくする利点も失うので採らない

### Non-Goals

- `revise-impl` の AI レビューを、レビューの作業者に分けること。`revise-impl` は今のまま、作業者が直してから自分で `/code-review` にかける。
  人の否決を受けた直しは小さいことが多く、そこにレビューの段を挟むと 1 手で頼み直す今の形が崩れる。
  直す指摘を重要なものに絞り、見送りを PR に書くことだけは揃える（Decisions を参照）
- 見送った指摘を、別のカードやアイデアとして起票すること。PR の本文に残すだけにし、拾うかは人が決める
- 指摘を直した後の 2 回目の AI レビュー
- `pickNextAction` と `status` に計画の進み具合を読ませること
- 作業者や監視役の動きを画面に出すこと

## 動作確認の手順

作業者とサブエージェントの定義はメインのチェックアウトから読まれるので、通しの流れはマージ後にしか確かめられない。
マージ前に確かめられるのは、品質ゲートと、ワークツリーで起動した Claude Code からの部分的な振る舞いである。

マージ前:

1. `npm run typecheck && npm run lint && npm run format:check && npm test` が通る（`src/` は docstring だけの変更）
2. 計画の `## 調べた結果` に、入れ子のサブエージェントで待てたか、`ListAgents` での見え方、`TaskStop` の連鎖が書かれていることを読む
3. ワークツリーで `claude` を起動し（`.claude/agents/` がブランチの定義になる）、次を見る
   - `board-reviewer` を、実装中のカードの PR に対して立てると、計画の末尾に `## AI レビュー` 節が足され、変わったファイルが計画だけである。
     指摘が「直す」のチェックボックスと `### 見送った指摘` の箇条に分かれ、見送った指摘にチェックボックスが付いていない
   - そのセッションで `/board-loop` を 1 周回し、作業者の完了の通知の後に、監視役が cron を待たずに次の周へ進む

マージ後:

4. 次に 実装中 になったカードで `/loop 5m /board-loop` を回し、次の順に進むことを見る
   - 1 回目の `implement` で、`board-task-` の作業者がタスクごとに立ち、タスクごとのコミットが PR に並ぶ。監視役の手順 0 は取りまとめ役（`board-worker-`）を作業中として出す

## 調べた結果

2026-10-30 に、監視役から `implement` の手で立てられた作業者（`board-worker`、バックグラウンドのサブエージェント）の中から、
`board-task-loop-impl-probe-1` / `-2` という名前で入れ子のサブエージェントを立てて確かめた。
入れ子の作業者には、スクラッチパッドに時刻を書いて返すだけの仕事を渡した。

### 入れ子のサブエージェントの完了を待てるか（確かめた。待てる）

- 作業者の `Agent` の呼び出しは、入れ子でも待たずに返る（「バックグラウンドで立てた」とだけ返り、結果は返らない）
- 入れ子の作業者が終わると、完了の通知と、その作業者の `SubagentHandback` の報告が、呼んだ作業者（取りまとめ役）に届いた。
  どちらも、取りまとめ役が実行を終えずに次の道具を呼んだところで届いた
- 待つあいだの道具の呼び方として、Bash の前景で `until [ 条件 ]; do sleep 2; done` を回すと、30 秒かかる入れ子の作業者の終わりまで止まらずに待てた。
  Bash の `run_in_background` で同じ待ちを回し、その完了の通知を受ける形も通った
- 取りまとめ役が道具を呼ばずに応答を終えたとき（ターンを終えたとき）に、通知で起こされて続きを進められるかは確かめていない。
  応答を終えると作業者の実行がそこで終わるおそれがあるので、試していない

このため取りまとめ役は、タスクの作業者を立てたら、ターンを終えずに待つ。
待つ条件は、渡したタスクの行が `[x]` になるか、タスクの作業者の完了の通知が届くか、のどちらかにする。
前景の Bash の待ちは時間切れ（最大 10 分）があるので、切れたら待ちを掛け直す。
タスクを倒す段の取りまとめ役の形（Decisions の「タスクを倒す段」）はこのまま採り、「代わりの道」には戻さない。

### 監視役の `ListAgents` からの見え方（確かめていない）

- 作業者（サブエージェント）には `ListAgents` の道具が無い（`ToolSearch` で見つからない）。作業者の側からは確かめられない
- 作業者に届く「このセッションで動いている作業者」の一覧に、入れ子の作業者が載るかも、この確かめの間には見えなかった
- 監視役の手順 0 は `board-worker-` で始まる名前だけを見るので、入れ子の作業者が `board-task-` / `board-reviewer-` で載っても判定は乱れない。
  入れ子の作業者が一覧に載るか、載るなら取りまとめ役より長く `running` で残らないかは、動作確認の手順 3 で監視役のセッションから見る

### 取りまとめ役を `TaskStop` で止めたときの連鎖（確かめていない）

- 作業者は自分を `TaskStop` で止められないので、作業者の側からは確かめられない。
  入れ子をもう 1 段深くして代わりに確かめる案は、本番の形と違い、後片付けも要るので採らなかった
- `Agent` の道具の説明には「完了の通知は、その作業者が自分の子の作業者が動いていない状態で止まるたびに届く」とある。
  取りまとめ役の完了の通知は、子が動いている間は届かないと読める
- 連鎖するかは動作確認の手順 3 で監視役のセッションから確かめる。
  連鎖しなければ、人が取りまとめ役を止めるときに `board-task-` / `board-reviewer-` で始まる作業中の作業者も止めるよう、`SKILL.md` の手順 0 に書き足す
