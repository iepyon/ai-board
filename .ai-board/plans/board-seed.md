# カードの変更をデータのマイグレーションとして git に載せる

## 提案

### Why

ワークツリーで並列に作業すると、ワークツリーごとに `board.db` ができ、カードの変更が別々の DB に散らばる。
`board.db` は git に載らないので、ブランチをマージしてもカードの変更はマージされない。
新しいワークツリーではカードが 1 枚も無いボードが開き、メインの DB を手でコピーすると、
コピーし直したときに画面の並べ替え（`rank`）を上書きして失う。

カードの変更を「データのマイグレーション」のファイルとして書き出し、git に載せる。
変更のたびに新しいファイルが足されるので、ブランチをマージしてもファイルは衝突しない。
DB は、まだ適用していないファイルを名前の順に流して追いつく。新しい DB は全部を流し直せば今の状態になる。

### What Changes

- `.ai-board/changes/<UTC 時刻>-<乱数>.yaml` に、カードと区切り線の変更を操作として書く。
  1 ファイルに複数の操作を持てる。
- `ai-board changes [--root <path>]` を足す。適用済みのファイルを空の DB に流し直した状態と今の DB を比べ、
  違う列だけを 1 つの新しいファイルに書き出す。違いが無ければ何も書かない。
- DB を開くとき（サーバの起動、`ai-board card` などのサブコマンド）に、まだ適用していないファイルを名前の順に適用する。
  適用したファイル名は DB に記録する（マイグレーション v5、`applied_changes` テーブル）。
- 今の DB に書き出していない変更があるときは、適用せずに警告し、先に `ai-board changes` を実行するよう促す。
  適用すると、手元の変更を黙って上書きするため。
- `ai-board import` は削除する（最初の `ai-board changes` が全カードを書き出し、新しい DB への取り込みは適用が担う）。
- ツールの `MIGRATIONS` には入れない。`MIGRATIONS` はスキーマの定義で npm パッケージに入り、
  ai-board を使う別のリポジトリの DB にも流れ込むため。データのマイグレーションはリポジトリの側に置く。

### Impact

- server
  - `src/infrastructure/database.ts` — マイグレーション v5（`applied_changes` テーブル）
  - `src/cards/models/`（新規）— 変更ファイルの操作の型と Zod スキーマ
  - `src/cards/repositories/`（新規）— `ChangeFileStore`（`.ai-board/changes/` の一覧・読み込み・書き込み）、
    `AppliedChangeRepository` と SQLite 実装
  - `src/cards/services/`（新規）— 2 つの状態の差分から操作を作る純関数、操作を状態に適用する純関数
  - `src/cards/usecases/commands/`（新規）— `recordChanges`（書き出し）と `applyPendingChanges`（適用）。
    どちらも `Result<T, E>` を返す
  - `src/cards/errors/` — `UnrecordedChanges`・`MalformedChangeFile` などのエラー種
  - `src/cards/composition.ts` — 依存の構成
  - `src/cli-main.ts` — `changes` サブコマンド、`import` の削除、サブコマンドの前の適用
  - `src/server.ts` — 起動時の適用
  - `src/shared/config.ts` — `changesDir` のパス。`cardsDir` の削除
- テスト: 差分と適用の純関数、書き出し、適用（順序・適用済みの読み飛ばし・書き出していない変更があるときの停止）、
  マイグレーション v5、CLI
- ドキュメント: `README.md` / `CLAUDE.md` の「タスクは board.db にある」「書き込み境界」「1 周の流れ」
- `card-markdown.ts` の Markdown 表現は `card show` の出力にだけ残る

## 設計

### Context

カードの正本は `board.db`（SQLite）で、画面・CLI・SSE はすべて DB を読み書きする。
DB に書くのは、画面の操作（着手・並べ替え・承認など）、`ai-board card` の CLI、PR 番号の書き戻しの 3 つ。
スキーマのマイグレーション（`MIGRATIONS`）は `PRAGMA user_version` の 1 本の番号で管理している。

### Goals / Non-Goals

**Goals:**

- ワークツリーごとのカードの変更を、コードと同じブランチのマージでまとめられること
- マージでファイルが衝突しないこと
- 新しいワークツリーで、カードの入ったボードが開くこと
- DB で変えたのに書き出していない変更を、適用で黙って消さないこと

**Non-Goals:**

- 適用の順序の正しさ。同じカードの同じ列を 2 つのブランチで変えると、ファイル名の順で後の方が黙って勝つ。
  DB ごとに適用した順が違えば、最後の状態が食い違うこともある。これは受け入れる（2026-09-27 に人が判断）
- ファイル経由の書き込みの検証。変更ファイルを直接書けば `startedAt`・`rank`・`skipGates`・
  承認 / 否決 / 中止も DB に入る。これは塞がない（2026-09-27 に人が判断）
- 書き出しの自動化。DB に書くたびにファイルを足すことはしない
- カードの削除。DB からカードを消す操作は今も無く、変更ファイルにも持たせない
- 変更ファイルを 1 つのスナップショットに畳む手順

### Decisions

#### 変更は SQL ではなく操作として書く

生の SQL で書くと、スキーマを変えたときに古いファイルが流せなくなる。
たとえば列を落とすと、その列を書いていた古い UPDATE 文は、新しい DB に流し直すときに失敗する。
操作として書き、リポジトリを通して反映すれば、スキーマの変更はリポジトリの実装の側で吸収できる。

```yaml
# .ai-board/changes/20260927T071500123Z-3f9a.yaml
- card: verify-gate
  set:
    title: ユーザは PR を見る前に、AI の実装を実際に動かして確かめたい
    rank: 1788504501903
- card: board-seed
  set:
    title: ユーザはワークツリーで並列に変えたカードを、git のマージでまとめたい
    created: '2026-09-27T07:02:41.027Z'
    body: |
      ## アイデア
      ...
- divider: 1788504502903
```

- `card` の操作は、そのカードに `set` の列を書く。カードが無ければ作る（そのときは `title` と `created` が要る）
- `divider` の操作は、区切り線の `rank` を書く
- 列の名前はカードの Markdown 表現と同じ（`startedAt` / `skipGates` / `branch` / `mr` / `rank` / `body`）
- 形式は YAML にする。本文を複数行のまま読め、差分も読める。`yaml` は既に依存にある

#### 変わった列だけを書く

行をまるごと書き戻すと、無関係な変更を消す。ブランチ A が `rank` を、ブランチ B が本文を変えたとき、
後から流した方が片方を消してしまう。変わった列だけを書けば両方が残り、
後の方が勝つのは同じ列を両方で変えたときだけになる。

#### 差分は「適用済みのファイルを流し直した状態」と比べて作る

基準の状態を別に記録しない。適用済みのファイルを空の状態へ名前の順に流し直せば、
「ファイルとして書き出し済みの状態」が得られる。これと今の DB の差分が、まだ書き出していない変更である。
比べるのも適用するのも純関数（状態 × 操作 → 状態）で行い、流し直しに DB は使わない。

#### ファイル名は時刻と乱数

`<UTC 時刻（ミリ秒まで）>-<乱数 4 桁>.yaml`。名前の順が適用の順になる。
乱数は、同じ時刻に別のワークツリーで書き出したファイルの名前がぶつからないようにするため。

#### 適用は DB を開くたびに行い、書き出していない変更があれば止める

適用済みのファイル名は `applied_changes` に記録し、記録の無いファイルがあれば適用する。
適用は未適用のファイルを足していくのではなく、DB を「全ファイルを名前の順に流し直した状態」に揃える形で行う
（実装で変えた点）。未適用のファイルを後から足すと、マージした順によって DB ごとに勝つ列が変わるが、
揃える形なら、同じ列はどの DB でも名前の順で後のものが勝つ。
反映とファイル名の記録は 1 つのトランザクションに入れる。

適用の前に、今の DB と「適用済みのファイルを流し直した状態」を比べる。違いがあれば適用しない。
手元の変更を上書きしないためである。サーバはそのまま起動して警告を出し、CLI は警告してから本来の処理を続ける。
`ai-board changes` で書き出せば、次に開いたときに適用される。

一度も適用していない空の DB は、比べても違いが無いので、そのまま全部が適用される。
新しいワークツリーや clone は、これだけでカードの入ったボードになる。

#### 既存のマイグレーションツールは使わない

dbmate や golang-migrate の多くはバージョン番号 1 本で管理し、順序が前後したファイルを流せない。
また、依存を増やさないために `node:sqlite` を選んだ経緯がある。今の `MIGRATIONS` の実行部と同じくらいの規模で作る。

### Risks / Trade-offs

- **同じ列の並行編集は後勝ちで消える。** 本文を 2 つのブランチで書き換えると、片方が黙って消える。
  git なら衝突として止まる場面である（Non-Goals）
- **書き出し忘れ。** ワークツリーで `ai-board changes` をせずにコミットすると、カードの変更はブランチに乗らない。
  「1 周の流れ」に、PR を出す前と `git pull` / `merge` の前に `ai-board changes` を実行する手順を書く
- **適用が止まり続ける。** PR 番号の書き戻しも DB の変更なので、書き出すまで適用が止まる。
  止まっていることは警告で分かるが、画面にも出すかは実装で様子を見る
- **適用済みのファイルが手元に無い。** ブランチを切り替えて、適用済みのファイルが作業ツリーから消えると、
  流し直した状態が DB とずれて、関係の無い差分が出る。流し直しは「適用済みで、かつ手元にあるファイル」だけで行い、
  足りないファイルがあれば警告する
- **書き込み境界の迂回。** 変更ファイルを直接書けば、CLI が入口を持たない列も書ける。
  README / CLAUDE.md に「変更ファイルを手で書かない」をエージェントのハードルールとして書き、強制はしない
- **ファイルが増え続ける。** いずれスナップショットに畳む手順が要る（Non-Goals）

### Migration Plan

1. マイグレーション v5 で `applied_changes` を作る
2. メインで `ai-board changes` を実行する。適用済みのファイルが無いので、全カードと区切り線が 1 つのファイルに書き出される。
   これが最初の「初期データ」になる
3. 書き出したファイルをコミットする

ロールバックは、`changes` を使わなければ従来どおり DB だけで動く。`applied_changes` は残っても害が無い。
