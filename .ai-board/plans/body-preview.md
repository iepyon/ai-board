# カードの本文を整形して読めるようにする

## 提案

### Why

カードの詳細パネルは、本文を Markdown の生のまま等幅の textarea に出している（`BodyEditor.tsx`）。
アイデアカードの本文は `## アイデア` / `## 背景` / `## 論点` に分かれ、論点は太字の見出し付きの長い箇条書きになることが多い。
これが記号付きの等幅の文字の塊として並ぶので、どこからどこまでが 1 つの論点なのかを目で追いにくい。

本文を開くのは、着手するか、どこへ並べるかを決めるときが多い。
書き換える場面より読む場面の方が多いので、読む形を既定にする。

### What Changes

- カードの詳細パネルの「本文」を、既定では整形して表示する。
  見出し・段落・箇条書き（入れ子と番号付きを含む）・コードブロック・強調・インラインコード・リンクを整形する。
- 「編集」を押すと今の textarea に切り替わる。保存に成功するか、取り消すと、整形した表示に戻る。
- Markdown を表示用の木に変える処理を `src/shared/` に純関数として置き、テストを書く。
- 依存は増やさない。API と DB は変わらない。

### Impact

- shared
  - `src/shared/markdown.ts`（新規）— 本文をブロックの木に、行内をスパンの列に変える純関数
- web
  - `src/web/components/detail/BodyView.tsx`（新規）— 木を React の要素として描く
  - `src/web/components/detail/BodyEditor.tsx` — 閲覧と編集の切り替え
  - `src/web/styles.css` — 整形した本文のスタイル（ライト / ダーク）
- テスト: `src/shared/__tests__/markdown.test.ts`（新規）
- ドキュメント: `README.md` の詳細パネルの説明
- API・DB・CLI・ステージの導出: 変更なし

## 設計

### Context

本文は人もエージェントも書ける場所である。
エージェントは `ai-board card body` で、人は詳細パネルで書き換える。
そのため、本文の中身をそのまま HTML として画面に流し込むと、本文を書ける者が画面でスクリプトを動かせる。

`src/web/` はテストの対象外なので、判定を含む処理は `src/shared/` に置いてテストする
（`dashboard-sections.ts` と同じ形）。
`src/shared/` は server と web の両方の tsconfig に入るので、DOM にも Node にも依存しない書き方にする。

### Goals / Non-Goals

**Goals:**

- ボードに今あるカードの本文（アイデア / 背景 / 論点 / レビュー）が、記号ではなく構造として読めること
- 本文に何が書かれていても、画面でスクリプトが動かないこと
- 書き換えの操作が今と同じ手数で済むこと

**Non-Goals:**

- CommonMark への完全な準拠。カードの本文で使う記法に絞る
- 表の整形。`|` で始まる行の並びは等幅のまま出す（崩さずに読める形に留める）
- 画像・HTML タグ・脚注・タスクリストのチェックボックスの描画
- 編集中のプレビュー（左右に並べる、など）
- 計画ファイルの表示。ボードは計画の本文を持たない方針のまま

### Decisions

- **ライブラリを入れず、必要な記法だけを自前で変換する。**
  - `marked` / `markdown-it` は HTML の文字列を返すので、`dangerouslySetInnerHTML` とサニタイズ（`DOMPurify` など）を組で入れることになる。
    サニタイズの設定を誤ると、本文を書ける者が画面でスクリプトを動かせる。
  - `react-markdown` は React の要素を返すが、unified / remark 一式の依存が web に入る。
  - カードの本文で使う記法は限られている。木に変える処理を純関数にすれば、テストで記法ごとの振る舞いを固定できる。
- **変換は 2 段に分ける。** ブロック（見出し・段落・箇条書き・コードブロック・等幅の行の並び）と、行内（強調・インラインコード・リンク）。
  どちらも文字列を受け取って木を返すだけで、HTML の文字列は作らない。
  描画は `BodyView.tsx` が木を React の要素に写すだけにする。React はテキストをエスケープするので、本文の `<script>` は文字として出る。
- **リンクは `http:` / `https:` だけを `<a>` にする。** ほかのスキーム（`javascript:` など）は、リンクの文字列をそのまま文字として出す。
  `<a>` は今の PR へのリンクと同じく `target="_blank" rel="noreferrer"` にする。
- **段落の中の改行は、改行のまま出す。** カードの本文は一文一行で書いている。
  Markdown の通常の扱い（改行を空白にして 1 行につなぐ）だと、日本語の文の間に空白が入るか、長い 1 行になって文の区切りが見えにくくなる。
  箇条書きの項目の 2 行目以降（インデントされた続きの行）も、同じ項目の中の改行として扱う。
- **箇条書きの入れ子はインデントの深さで決める。** `-` / `*` / `1.` で始まる行を項目とし、親の項目より深くインデントされた項目を子にする。
  論点の箇条書きにある、項目の下にさらに `-` を並べた形をそのまま入れ子として出す。
- **`## レビュー` も同じ規則で整形する。** エントリの見出し（`### <時刻> plan 承認`）と理由が、見出しと段落として出る。
  判断の履歴だけを別の形で出すことはしない。導出に使う解析（`review-log.ts`）は今のまま触らない。
- **閲覧と編集の切り替えは `BodyEditor` の中の状態にする。** カードを選び直したら閲覧に戻る。
  保存は `onRun` に渡す処理の中で、更新が成功したときだけ閲覧に戻す（失敗したら編集の内容を残す）。
- **閲覧中は外の書き換えに追従し、編集中は書きかけを守る。**
  今は外で本文が変わると、編集中の内容が `useEffect` で上書きされる。
  編集中は上書きせず、「保存されている本文が外で書き換わりました」と出す。書きかけを捨てて読み直すかどうかは人が選ぶ。

### Risks / Trade-offs

- 自前の変換は、記法の取りこぼしがあると崩れて見える → 知らない書き方は段落の文字としてそのまま出す。
  記号が残るだけで、文字が消えたり例外で画面が止まったりはしない。変換の関数はどんな入力にも木を返す（テストで確かめる）。
- 等幅の textarea より、整形した表示の方が縦に長くなる → 詳細パネルはもともと縦にスクロールする。
  コードブロックと等幅の行の並びは、折り返さずに横にスクロールさせる（表や長いコマンドの桁を崩さないため）。
- 編集中に外で本文が書き換わったまま保存すると、外の変更を上書きする → 今も同じ挙動である。
  書き換わったことを画面に出すところまでをこの変更の範囲にする。
