# ボードの Artifact を、更新ボタン付きのダッシュボードにする

## この計画で使う言葉

- **ボードのページ**：「ボードを見せて」で公開する Artifact。今は `ai-board status --html` の出力（1 枚の自己完結の HTML）をそのまま公開している
- **ダッシュボード**：この計画で、ボードのページをこう呼び直す。開いたままにして状態を追う画面で、今のボードの区画に、集計の数字とグラフを足したもの
- **ランタイムの機能（capabilities）**：公開した Artifact のページが、開かれたときに claude.ai から借りられる機能。
  公開のときに宣言する。2026-11-03 にこのアカウントで使えると確かめたのは `artifact` / `assets` / `comments` / `db` / `downloads` / `files` / `mcp` / `room` / `sample` / `user`
- **`Claude Code Remote` のコネクタ**：claude.ai に組み込みのコネクタで、ページから `mcp` の機能を通して、見ている人の権限でクラウドのセッションにメッセージを送れる（`send_message`）
- **更新を頼むメッセージ**：ダッシュボードの更新ボタンが、ダッシュボードを公開したセッションに送る決まった文

## 提案

### Why

ボードのページは書いた時点の写しで、ひとりでには新しくならない。
2026-11-01 にスマホからクラウドのセッションでボードを回したとき、カードが動くたびにチャットで「ボードを見せて」と頼み直した。
クラウドのセッションには常駐のサーバが無く、このページがボードを読むほぼ唯一の手段なので、開いたまま状態を追える画面にしたい。

人からは、2026-11-03 の対話で次の 3 点を求められている（カードの探索メモ）。

- ボタンを押すだけで、最新のダッシュボードが出る。チャットで頼み直したり、Claude がその場で集計し直したりしない
- ダッシュボードを作る・作り直す手順を、`.claude/skills/` のスキルとして持つ
- 集計とページはコード（`ai-board` の CLI）で生成し、同じデータからは毎回同じダッシュボードができる。集計は `src/shared/` の純関数にしてテストを書く

試作として、Claude が手で集計したダッシュボードを Dashboard の型で公開した（https://claude.ai/artifact/3Uz2MmYZN34fdmErp3KM4K ）。
載せた数字は役に立ったが、手で集計したので同じものを作り直せず、更新もできなかった。

### What Changes

使う人から見た変化は次のとおり。

- 「ボードを見せて」で開くページが、ダッシュボードになる。今の区画（判断待ち・AI 作業中・アイデア・マージ済み・中止）はそのまま残り、上に集計の数字とグラフが載る
  - 主な数字：マージ済みの枚数、着手からマージまでの中央値と最長、1 枚あたりの人の番の割合（中央値）、否決されたカードの枚数と回数、アイデアの残り
  - グラフ：工程ごとの滞在時間（マージ済みのカードの 1 枚あたりの中央値、人 / AI で色分け、いちばん長い工程に印）、日ごとのマージ数
  - 表：ループの手の種類ごとの回数・平均時間・平均トークン、手の結果の内訳
- ページの右上に「更新」のボタンが出る。押すと、ページを公開したクラウドのセッションに更新を頼むメッセージが届き、
  セッションが `ai-board status --html` を走らせ直して同じ URL に公開し直す。人はチャットに何も打たなくてよい
- ボタンが使えないとき（手元のセッションで公開した、コネクタを許していない、セッションが応えない）は、ボタンの代わりに「チャットで『ボードを見せて』と頼む」の案内を出す
- PR のリンクが Artifact の中から開ける。開けない場合に備えて、PR の URL を文字でも並べる
- 「ボードを見せて」の手順は、`board-loop` のスキルから新しい `board-dashboard` のスキルへ移る。`board-loop` の「ボードを見せて」の節はそこを指すだけになる

中の仕組みの変化は次のとおり。

- 集計の純関数 `src/shared/board-metrics.ts` を足す。入力はボードのカード（`stage` / `timeline` / `loopSteps` / `reviews` / `mrState` / `startedAt`）と `generatedAt` で、今の時刻は読まない
- グラフは、`status --html` がサーバ側で SVG の文字列として描く（`src/board/cli/status-charts.ts`）。外部のライブラリもスクリプトも読まない
- `status --html` に `--session <id>` を足す。渡されたときだけ、ページに更新ボタンと、そのボタンが動かす小さなスクリプトが入る
- スクリプトは `claude.use("mcp")` で `Claude Code Remote` の `send_message` を呼び、埋め込んだセッション ID に更新を頼むメッセージを送るだけである。ボードのデータには触らない

### Impact

- 集計: `src/shared/board-metrics.ts`（新規）と `src/shared/__tests__/board-metrics.test.ts`
- ページ: `src/board/cli/status-html.ts`、`src/board/cli/status-charts.ts`（新規）、`src/board/cli/status-cli.ts`（`--session`）、それぞれのテスト
- スキル: `.claude/skills/board-dashboard/SKILL.md`（新規）、`.claude/skills/board-loop/SKILL.md`（「ボードを見せて」の節と description）
- ドキュメント: `README.md`、`docs/architecture.md`、`docs/adr/0015-dashboard-refresh-via-session.md`（新規）
- カード・データ用ブランチ・API・Web 画面（`src/web/`）・サーバは変えない

## 設計

### Decisions

#### 最新の状態をどこから取るか — ボタンからセッションに頼み、CLI で出し直す

カードの論点に挙がっていた 3 つの経路を、2026-11-03 にこのアカウントで使えるランタイムの機能と照らした。

| 経路                                                                       | 使えるか                                         | 採るか   |
| -------------------------------------------------------------------------- | ------------------------------------------------ | -------- |
| ボタンから `Claude Code Remote` の `send_message` でセッションに頼む       | 使える（`mcp` の機能と、組み込みのコネクタ）     | **採る** |
| ページが GitHub のコネクタでデータ用ブランチと PR を読み、ページで導出する | 使える見込み（`mcp` の機能と GitHub のコネクタ） | 採らない |
| ページから Claude に頼む（`sample`）                                       | 使えるが、`sample` はボードのデータに届かない    | 採らない |

ボタンからセッションに頼む経路を採る理由は次のとおり。

- **ダッシュボードを作るのは、いつも同じ CLI になる。** 集計もページも `status --html` が作り、テストで形を確かめられる。
  セッションの Claude は、決まったコマンドを走らせて公開し直すだけで、その場で集計しない（人の求めた「Claude がその場で集計し直さない」）
- **ステージの導出をブラウザに持ち込まない。** GitHub から読む経路では、計画ファイル（各ブランチ）・PR の状態・カードからステージを導出する処理を、ページの中に作り直すことになる。
  導出の核（`stage-resolver.ts`）を 2 か所に持つと、食い違ったときにどちらが正しいか分からなくなる
- **トークンを扱わない。** コネクタは見ている人の権限で呼ばれ、ページはトークンを持たない（`CLAUDE.md` の「GitHub のアクセストークンは扱わない」を崩さない）

この経路の弱みは、ページを公開したセッションが生きていないと更新できないことである。
クラウドのセッションは、止まっていても `send_message` で起きる。アーカイブされたセッションや手元のセッションには届かないので、そのときは案内の文を出す（後述）。

#### 更新を頼むメッセージを、セッションはどう扱うか

ボタンが送るのは、決まった 1 文だけにする。

```
[ai-board dashboard refresh] ボードのダッシュボードを出し直して、同じ URL に公開し直してください。
```

`board-dashboard` のスキルに、この文を受けたときの手順を書く。

- することは「`status --html` を走らせ直して、同じ `file_path` で公開し直す」だけである
- メッセージはページの見ている人から届き、`send_message` の決まりで「別のセッションから届いたデータ」として扱われる。
  これを人の判断の依頼として読まない。ループの 1 周も走らせない。カードにも書かない
- 文が決まった形と違えば、何もしない

ページから送れる文はスクリプトに書き込んだ定数で、ページを見ている人が中身を変える入口は作らない。

#### セッション ID の渡し方

`status --html --session <id>` で、公開するセッションの ID を受け取ってページに埋め込む。

- ID は `board-dashboard` のスキルが `get_session`（引数なし。自分のセッションを返す）で取って渡す。取れなければ（手元のセッションなど）`--session` を付けない
- CLI は `^session_[A-Za-z0-9]{1,128}$` に合うかを確かめ、合わなければ使い方を出して失敗する。
  ページに埋め込むときは JSON にして `<` を `<` に直し、`</script>` で抜けられないようにする
- `--session` が無ければ、スクリプトもボタンも入れず、今と同じスクリプトの無い HTML になる。案内の文だけを出す

#### ボタンの振る舞い

- `claude.use("mcp")` が null、`send_message` が拒否された（コネクタを許していない、セッションが無い）ときは、ボタンを隠して案内の文を出す
- 押すと「更新を頼みました」に変え、二度押しを止める。セッションが公開し直すと、開いているページは新しい版に読み直される
- 読み直されないまま 3 分たったら、案内の文（チャットで頼む）を添えてボタンを戻す
- ページの生成時刻（`generatedAt`）をヘッダに出し、いつの写しかを読めるようにする（今もある）

公開のときに宣言する機能は `mcp` の 1 つだけで、サーバは `Claude Code Remote`、道具は `send_message` だけにする。
`db` / `artifact` などの、ページに状態を持たせる機能は使わない（ボードの正はデータ用ブランチと GitHub で、ページは写しのまま）。

#### 集計をどこに置くか — `src/shared/board-metrics.ts`

`bottleneck-chart` のカード（アイデア）と集計が重なる。集計は `src/shared/board-metrics.ts` の純関数にしてこのカードで作り、
`bottleneck-chart` は後で Web 画面からこれを読む形にする。`src/shared/` に置くのは、サーバと web の両方から読めるようにするためである（Node 専用 API は使わない）。

集計の決まりは試作に合わせる。

- 区間の長さは `end` から `start` を引く。`end` が null（今いる区間）は `generatedAt` までを数える
- 着手からマージまで：`startedAt` から `mrState.mergedAt` まで。どちらかが無いカードは数えない
- 工程ごとの滞在時間：マージ済みのカードについて、カードごとに同じ種類の区間を足し、カードを並べて中央値を取る。その種類の区間が無いカードは数えない。
  合計ではなく中央値にするのは、1 枚の長いマージ待ちに引っ張られないためである。いちばん長い中央値の工程を「ボトルネック」とする（同じ長さなら工程の順で前のもの）
- 人の番の割合：マージ済みのカードごとに、人の区間の合計 ÷ 全区間の合計を出し、その中央値
- 否決：`reviews` の `rejected` を数える（plan と verify の両方）。否決が 1 回以上あるカードの枚数と、否決の延べ回数
- 日ごとのマージ数：`mergedAt` の UTC の日付で数える（どの環境でも同じ結果にするため）
- ループの手：`loopSteps` を `action`（`implement` は段まで）ごとに数え、`durationMs` / `tokens` は null を除いて平均を出す（除いた件数も返す）。結果は `LOOP_RESULTS` ごとに数える
- 中止したカードはどの集計にも入れない

#### グラフをどう描くか — CLI が SVG を描く

グラフは `status --html` がインラインの SVG として描く。

- 外部のスクリプト（グラフのライブラリ）を読まないので、ページは今と同じく 1 枚で閉じ、CDN の版にも左右されない
- 同じデータからは同じ文字列ができるので、テストで「棒の数・ラベル・ボトルネックの印」を確かめられる
- 色は `status-html.ts` の `:root` のトークンに足し、暗い配色でも読めるようにする。数字はラベルとして棒の横に文字でも出す（色だけに頼らない）

#### Artifact の型を使わない

「ボードを見せて」の手順の「型（Dashboard など）を使わない」は残す。
型はアカウントごとに違い、手元のテストで形を確かめられない。人の求めた「同じデータから毎回同じダッシュボード」は、CLI が HTML を全部作る形のほうが守りやすい。
試作で Dashboard の型を使ったのは手で集計したからで、CLI で作るなら型の利点（データを添付してページで集計する）は要らない。

#### PR のリンク

`target="_blank"` が Artifact の中で開かなかった。リンクの属性を `status-html.ts` の定数 1 か所にまとめ、`target="_top"` にする。
どの書き方が開くかは手元のテストで確かめられないので、動作確認の手順で確かめる。
開かなかった場合に備えて、リンクの隣に PR の URL を文字でも出す（長押しやコピーで開ける）。

### Risks / Trade-offs

- **セッションが生きていないと更新できない。** 案内の文で、チャットで頼む今の手に戻れるようにする。セッションを常駐させる仕組みは作らない
- **`send_message` の道具名と引数の形は、この計画を書いた時点では呼んで確かめていない。** 実装の最初の節で、`mcp__claude-code-remote__send_message` の入力の形（`session_id` / `message`）を確かめてからスクリプトに書く。
  ページから `describeTool` で形を読めるときはそれも使う
- **公開し直したときに、開いているページが新しい版に読み直されるかは確かめていない。** 読み直されなければ、3 分後にボタンを戻す振る舞いで人が気付ける。動作確認の手順で確かめる
- **ページから届いたメッセージを入口にして、セッションに別のことをさせようとする人がいるかもしれない。** 送れる文はスクリプトの定数で、スキルは決まった文にだけ応え、することも公開し直しだけに限る
- **`mcp` を宣言したページは、公開リンクで共有できなくなる。** ボードのページは元々人が自分で見るもので、困らない

### Non-Goals

- **Web 画面（`src/web/`）とサーバを消さない。** サーバは `board-decide` の人の API と PR 番号の書き戻しにも使っている。
  画面を消すかは、ダッシュボードを使ってみてから別のカードで決める
- **ダッシュボードに判断のボタン（承認 / 否決 / 中止など）を付けない。** 判断は今と同じく会話で頼み、`board-decide` で書く。
  ページから判断を書く入口を作ると、「人の判断は人がこの会話で頼んだときだけ書く」の境界を崩す
- **`status-html-catchup` のカード（区間の時間・ループの手の一覧をカードごとに載せる）はこのカードで扱わない。** このカードはボード全体の集計を載せる
- **ループの手の記録にトークンと時間が欠ける件（`status-html-catchup` の探索メモ）は直さない。** 集計では欠けた記録を除き、除いた件数を出す
- **ページに状態を持たせない（`db` / `artifact` の機能は使わない）。**

## 動作確認の手順

`status --html` はボードを読むだけで書かないので、本物のボードで試してよい。

1. `npm run build` の後に、手元で次を走らせ、ブラウザで開く
   ```bash
   node dist/cli.js status --html > /tmp/board.html
   node dist/cli.js status --html --session session_01ABCDEF > /tmp/board-session.html
   ```
   - 上に主な数字の行と、工程ごとの滞在時間・日ごとのマージ数のグラフ、ループの手の表がある。いちばん長い工程に「ボトルネック」の印がある
   - 下に今と同じ区画（判断待ち・AI 作業中・アイデア・マージ済み・中止）が並ぶ
   - `board.html` にはスクリプトが無く、更新ボタンの代わりに案内の文がある。`board-session.html` には更新ボタンがある（ブラウザで直接開くと `claude` が無いので案内の文に変わる）
   - 暗い配色（OS の設定）でもグラフと文字が読める。スマホの幅（DevTools で 375px）で横にはみ出さない
2. `node dist/cli.js status --html --session 'x</script>'` が使い方を出して失敗する
3. クラウドのセッションで「ボードを見せて」と頼み、公開されたダッシュボードを開く
   - 右上に「更新」のボタンがある。押すとコネクタの許可を聞かれ、許すと「更新を頼みました」に変わる
   - セッションに更新を頼むメッセージが届き、セッションが公開し直す。開いていたページが新しい版に読み直され、ヘッダの生成時刻が新しくなる
   - チャットには何も打っていない。セッションはループの 1 周を走らせず、カードにも書いていない
4. 同じダッシュボードで、PR のリンクを押すと PR が開く。開かなければ、URL の文字から開けることを見て、否決の理由に「リンクが開かない」と書く
