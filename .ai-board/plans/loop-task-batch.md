# 実装中のタスクを、計画の節ごとに 1 つのサブエージェントでまとめて倒す

## この計画で使う言葉

- **監視役**：`/board-loop` のスキルを動かすセッション。`ai-board status --json` の `next` を読み、サブエージェントに 1 手を渡す。
- **タスクを倒す段**：`implement` の手の中で、計画に未チェックのタスクが残っている段。`next.step` が `task` のとき、監視役は `board-task` を立てる。
- **節**：計画の `## タスク` の下を `### <番号>. <題>` の見出しで区切った範囲。この計画で、`board-task` が 1 回の起動で倒す単位にする。
- **品質ゲート**：`npm run typecheck && npm run lint && npm run format:check && npm test`。通らないままコミットしない（`CLAUDE.md` のハードルール）。

## 提案

### Why

2026-11-01 に `review-reason-escape` を board-loop で回したとき、実装中のタスク 6 つに `board-task` が 6 回立った。
1 回ごとに計画・`CLAUDE.md`・関係するコードを最初から読み直すので、1 回で 75k〜106k トークン、1.2〜2.8 分かかった。
タスクの手だけで約 54 万トークンになり、カード 1 枚の全体（約 100 万トークン）の半分強を占めた。
docstring を 1 か所直すだけのタスクでも約 75k トークンを使っており、作業より読み直しの方が大きい。

続けて回した `review-append-port` では、計画の 1 つ目のタスクだけを入れると、まだ古い道を使う usecase のテストが落ちた。
その usecase を新しい口に切り替えるのは 2 つ目と 3 つ目のタスクだった。
`board-task` は品質ゲートを通せずに止まり、人が計画のタスクの順番を直すまでループが進めなくなった。
「タスクごとにゲートを通してコミットする」決まりは、「途中では壊れたままでよい」切り方の計画と合わない。

タスクを 1 つずつ別のサブエージェントに渡しているのは、前の文脈を持ち込まないため（`loop-fresh-context`）だった。
しかし持ち込んで困るのは別のカードの文脈で、同じカードの続きのタスクなら、読んだコードを持ち込む方がむしろ有利である。

### What Changes

使う人から見た変化は次のとおり。

- `board-planner` は計画の `## タスク` を `### <番号>. <題>` の節に区切る。節の切れ目は「その節を倒し終えたら品質ゲートが通る」ところに置く。
  どこで区切るかは、計画レビューで人が確かめる
- `board-task` は 1 回の起動で、最初の未チェックのタスクを含む節を倒し切る。品質ゲートとコミットは節の終わりに 1 回だけで、節の途中ではテストが落ちていてもよい
- 節の終わりでゲートが通らず、原因がタスクの順番なら、`board-task` が計画の未チェックのタスクの順番を入れ替えるか、節を合わせてよい。
  変更は節のコミットに入り、コミットの本文と報告に書くので、PR で人が確かめられる
- `board-reviewer` が書く `## AI レビュー` 節の直す指摘は、節 1 つとして 1 回の `board-task` でまとめて倒れる
- 手順書の「まっさらな文脈」の説明を、「別のカードの文脈を持ち込まないため」と位置づけ直す

変わらないこと:

- 1 周で渡す手は高々 1 つ。`next.action` / `next.step` の種類と意味（`task` は「未チェックのタスクがある」）
- 監視役は計画を読まない。`prompt` は `cardId` / `action` / `MAIN` の 3 行
- 実装する作業者（`board-task`）と、レビューする作業者（`board-reviewer`）は別のまま
- ステージの導出、`status` のコード、サーバ、画面、データ用ブランチの形

### Impact

- ループ: `.claude/agents/board-task.md`（中心）、`.claude/agents/board-planner.md`、`.claude/agents/board-reviewer.md`、
  `.claude/skills/board-loop/subagent-rules.md`、`.claude/skills/board-loop/SKILL.md`
- ドキュメント: `README.md`（AI ループの節）。`docs/architecture.md` と `CLAUDE.md` は食い違う記述があれば直す
- コード: 変更なし。`src/board/services/impl-step.ts` の段の判定は「未チェックのタスクが 1 つでもあれば `task`」のままで、節を知らなくてよい

## 設計

### Decisions

#### まとめる単位は計画の節にする

候補は 3 つあった。

1. 計画の `### <番号>.` の節ごとに、1 つのサブエージェントで倒す
2. 残りのタスクを全部、1 つのサブエージェントで倒す
3. 決まった数かトークンの目安に達するまで倒し、その先は次のサブエージェントに渡す

1 を採る（2026-11-02 の対話で人が決めた。カードの `## 探索メモ`）。

- 区切りがゲートの通る切れ目と重なるので、コミットの単位と品質ゲートの単位がそろう
- どこで区切るかが計画に書かれ、計画レビューで人が確かめられる。3 の「目安」はサブエージェントが決めるので、人から見えない
- 2 は文脈が膨らみやすく、途中で止まったときに失うものが大きい

#### 節の決め方

`board-task` が倒す節は、次のように決める。共通の決まりに書き、`board-planner` / `board-task` / `board-reviewer` が同じものを使う。

- 計画の上から最初の未チェックのタスクの行（数え方は今の「タスクの数え方と `## AI レビュー` 節」のまま）を見つける
- その行から上へたどって最初に当たる見出しの行（コードブロックの外の、`#` で始まる行）から、次の見出しの行の手前までを節とする
- 節の中の未チェックのタスクを、上から順にすべて倒す。節の中の `[x]` のタスクは飛ばす

この決め方から、次がそのまま出てくる。特別な扱いは足さない。

- `### 1. 〜` で区切った計画では、その `###` の節が単位になる
- `## AI レビュー` 節の直す指摘は、`## AI レビュー` の見出しから `### 見送った指摘` の手前までの節になり、まとめて倒れる。
  `board-reviewer` は今も「1 行で品質ゲートを通せる大きさ」で書いているので、まとめても節の終わりでゲートは通る
- 節に区切っていない計画（この決まりより前に書いた計画）では、`## タスク` 全体が 1 つの節になる。
  前の計画はどのタスクの後でもゲートが通るように切ってあるので、まとめて倒しても節の終わりでゲートは通る

#### 品質ゲートとコミットは節の終わりに 1 回

- 節の途中のタスクの後では、品質ゲートを走らせなくてよい。テストが落ちていてもよい
- タスクを 1 つ倒すごとに、計画のその行を `[x]` にする（コミットはしない）。
  文脈が長くなって自動の要約が入っても、計画を読み直せばどこまで済んだかが分かる
- 節を倒し終えたら品質ゲートを通し、節の実装と `[x]` を 1 つのコミットにして push する。コミットの型は節の中身に合わせる
- コミットの前の確かめを、選んだ 1 行から節に広げる。計画の変更が「節の中の未チェックだった行の `[ ]` → `[x]`」だけであること
  （次の「タスクの順番を直す」をしたときは、それに当たる変更も許す）
- 今の「選んだ行と同じ文の行がほかにあれば止まる」は外す。行ごとに見分ける必要が無くなり、確かめは節の範囲の差分で行えるため

節の途中にコミットを挟む案（ゲートが通るタスクの後ならコミットしてよい）は採らない。
コミットの単位がサブエージェントの判断で揺れ、PR の履歴から節の区切りが読めなくなる。

#### タスクの順番がまずければ、`board-task` が計画を直してよい

節の終わりでゲートが通らず、その原因が「後ろの節のタスクも一緒に入れないと通らない」ことなら、`board-task` は計画を直してから続けてよい。
直してよいのは次だけにする（人が対話で決めた範囲。カードの `## 探索メモ`）。

- 未チェックのタスクの行を、別の節へ移す（後ろの節のタスクを今の節へ移す、など）
- 隣り合う節を 1 つに合わせる（見出しを 1 つ消す）
- 節の中で、未チェックのタスクの並びを入れ替える

次はしない。必要なら変更をすべて戻し、止まって報告する。

- タスクの文を書き換える、タスクを足す、消す
- `[x]` のタスクを動かす、チェックを外す
- 計画の `## タスク` 以外の節（Decisions、動作確認の手順など）を変える

直した後は、移してきたタスクも今の節として倒し、節の終わりでゲートを通す。
計画の変更は節のコミットに入れ、コミットの本文に「何をどの節へ移したか、なぜか」を書く。報告にも 1 行で書く。
`review-append-port` のように順番がまずくて止まったカードも、人が計画を直さずに進められる。

`implement` の手には保留が無く（判断のボタンが出ない）、ここで人の判断を待たせると、人がワークツリーで計画を直すしか道が無い。
入れ替えと統合はタスクの中身を変えないので、AI に任せても計画レビューで人が決めたことは変わらない。

#### 同じカードの中なら文脈を持ち込んでよい

まっさらな文脈で立てる理由を、「別のカードの文脈（前のカードで読んだコードや決めた事柄）を持ち込まないため」と位置づけ直す。
同じカードの中で、1 つの `board-task` が節の中のタスクをまたいで文脈を持つのは、むしろ読み直しが減って有利と扱う。

節ごとに新しい `board-task` を立てる形は残す。節をまたいで 1 つのサブエージェントに続けさせる（`SendMessage` で続きを頼む など）ことはしない。
監視役の手順（`status` を読み、手を 1 つ渡す）を変えずに済み、節の区切りで文脈が 1 度リセットされるので、長い計画でも膨らみ続けない。

#### 監視役と `status` は変えない

- `next.step` の `task` は「未チェックのタスクがある」のままで、監視役の渡し先も `board-task` のまま
- 1 手で倒すのが 1 タスクから 1 節に変わるだけで、「1 周で渡す手は高々 1 つ」はそのまま成り立つ
- `status` は節を知らない。どの節を倒すかは、受けた `board-task` がワークツリーの計画を読んで決める

#### `board-planner` の計画の書き方

`board-planner.md` の `plan` の手順に、`## タスク` の書き方を足す。

- `## タスク` を `### <番号>. <題>` の節に区切る。節の切れ目は、その節までを倒し終えたら品質ゲートが通るところに置く
- 節の途中のタスクの後では、ゲートが通らなくてよい。型を壊す変更と受け止める箇所は、同じ節に入れる
- 1 つの節は、1 つのサブエージェントが倒し切れる大きさにする（目安を書く。下の Risks）
- 節が 1 つだけでもよい（小さなカード）

`revise-plan` で「計画から立て直させる」とき、作り直すタスクの `[x]` を外すか新しいタスクを足す。このときも節の切れ目の決まりを守る。

### Risks / Trade-offs

- **節が大きいと文脈が膨らむ。** 自動の要約が入っても、計画の `[x]` とワークツリーの差分から続きを読める。
  それでも長すぎる節は、要約で前のタスクの前提が落ちやすい。`board-planner` の手順書に、節の大きさの目安（タスクが数個、変わるファイルが十数個まで）を書く。
  節に区切っていない古い計画は `## タスク` 全体が 1 節になるので大きくなりうる。実装中の古い計画は少なく、受け入れる
- **途中で止まると、節の分の作業を失う。** 節の途中で何をすればよいか決まらないなどで止まるときは、今と同じく変更をすべて戻す。
  コミットは節の終わりにしか無いので、戻すのは節の中の倒したタスク全部になる。
  サブエージェントが途中で落ちたときは、未コミットの変更が残り、次の `board-task` は今と同じく手を付けずに止まる（人がワークツリーを片付ける）
- **ゲートで落ちたとき、どのタスクのせいかが見えにくい。** 1 つのコミットに複数のタスクが入るので、PR で見る単位が大きくなる。
  節の区切りは計画レビューで人が決めたもので、コミットの本文に倒したタスクを並べれば追える
- **計画を AI が書き換える。** 入れ替えと統合に限り、タスクの文は変えない。変更は計画のコミットに残り、PR の差分で人が確かめられる。
  コミットの前の確かめで、タスクの文の集合が変わっていないこと（`[ ]` → `[x]` の違いを除く）を見る
- **このカード自身は今の定義で進む。** サブエージェントの定義はメインのチェックアウトから読まれるので、このカードの実装は 1 タスクずつ進む。
  そのため、この計画のタスクはどれも単独でゲートが通るように切ってある（手順書と README の文書だけの変更）

### Non-Goals

- `status` / `impl-step.ts` / サーバ / 画面に節を持ち込むこと。進捗バーに節ごとの進み具合を出すこと
- 節をまたいで 1 つのサブエージェントに続けさせること。複数のカードを 1 つのサブエージェントで進めること
- `implement` の手に保留や判断のボタンを足すこと（順番の直しは `board-task` が行う）
- 計画のタスクの文の書き換えや、タスクの追加・削除を `board-task` に許すこと
- `board-reviewer` の分け方（直す / 見送る / 人に判断してほしい）と、AI レビューを 1 回だけにする決まりを変えること
- アーカイブ済みの計画（`plans/archive/`、`loop-fresh-context` を含む）を書き直すこと

## 動作確認の手順

変えるのは手順書と README だけで、サブエージェントとスキルの定義はメインのチェックアウトから読まれるので、通しの流れはマージ後にしか確かめられない。

マージ前:

1. ブランチの差分を読み、`.claude/agents/board-task.md` が「最初の未チェックのタスクを含む節を倒し、節の終わりでゲートとコミット」の手順になっていること、
   順番を直してよい範囲（移す・合わせる・入れ替える）としてはいけないこと（文の書き換え・追加・削除・`[x]` に触る）が書かれていることを見る
2. `grep -rn 'タスクを 1 つだけ\|1 つずつ' .claude README.md docs` で、1 タスク 1 手の前提の古い記述が残っていないことを見る（archive の計画は除く）
3. `npm run typecheck && npm run lint && npm run format:check && npm test` が通る

マージ後（手元かクラウドのセッション）:

4. 節に区切った計画（`### 1.` 〜 `### 3.` など）を持つ実装中のカードで `/loop 5m /board-loop` を回し、次を見る
   - `board-task-` で始まるサブエージェントが節の数だけ立ち、PR のコミットが節ごとに 1 つずつ並ぶ
   - 各コミットの後で計画の節のタスクがすべて `[x]` になっている
   - 1 回の `board-task` のトークンと時間（完了の通知に出る）が、タスクの数で割ると今より小さい
   - タスクを倒し終えると `board-reviewer-` が立ち、直す指摘があれば次の `board-task-` が 1 回でそれをすべて倒す
5. わざと順番をまずくした計画（1 つ目の節だけでは型が壊れ、2 つ目の節のタスクと一緒なら通る）のカードで回し、
   `board-task` が後ろのタスクを今の節へ移して倒し、コミットの本文と報告に移したことが書かれていることを見る
6. 節に区切っていない古い形の計画でも、`## タスク` 全体を 1 回で倒して進むことを見る
