# 「動作確認を飛ばす」のチェックボックスを、動作確認の列をまだ通っていないカードにだけ出す

## この計画で使う言葉

- **ゲート**：人の確認を通らないと先へ進めない関所。計画を読む `plan` と、実装を動かして確かめる `verify` の 2 つがある。
- **飛ばす宣言（`skipGates`）**：人があらかじめ「このカードではこのゲートを見ない」と決めておく印。宣言のあるゲートでは、AI の 提出 / 再提出 を人の承認と同じに読む。
  詳細パネルのゲートの欄（`SkipGateField`）のチェックボックスで出し入れする。
- **ステージ（列）**：アイデア → 計画提案中 → 計画レビュー → 実装中 → 動作確認 → PR中 → マージ済み の 7 つ。計画ファイル・PR・`## レビュー` から毎回導出する。
- **中止**：`## レビュー` の最新が 中止 のカード。ステージはどこでもよく、画面では中止の区画に寄せる（`aborted`）。

## 提案

### Why

今の「動作確認を飛ばす」のチェックボックスは、詳細パネルを開けばどのステージのカードにも出る。
PR中・マージ済み・中止のカードで入れても、そのカードはもう動作確認の列を通らないので、何も変わらない。
押しても効かない操作が画面にあると、使う人は「効いたのか」を確かめるためにボードを読み直すことになる。

`verify-gate`（PR #37）の AI レビューで、出し分けに設計の判断が要るとして直さずに残した指摘である。

### What Changes

使う人から見た変化は次のとおり。

- 「動作確認を飛ばす」のチェックボックスと説明文は、アイデア・計画提案中・計画レビュー・実装中・動作確認のカードにだけ出る
- PR中・マージ済み・中止のカードでは、チェックボックスも説明文も出ない。「計画レビューを飛ばす」はこれまでどおり出る
- 動作確認のカードでは、説明文が「印を入れると、提出済みのこのカードは動作確認を通ったものとみなされ、実装中へ戻って AI が PR を Ready にします。」に変わる。
  押す前に、カードが列を移ることが分かる

中の仕組みの変化は次のとおり。

- 出し分けの判定を、純関数 `offersSkipVerify(card)` として `src/shared/stage-gates.ts` に置き、テストを書く
- `SkipGateField` はその関数で「動作確認を飛ばす」の行を出すかと、動作確認のカード向けの説明文にするかを決める

### Impact

- 判定: `src/shared/stage-gates.ts`、`src/shared/__tests__/stage-gates.test.ts`
- 画面: `src/web/components/detail/SkipGateField.tsx`
- ドキュメント: `README.md`（ゲートの欄とスキップの節）、`docs/architecture.md`（`SkipGateField` の記述）、`docs/specs/card-gate-skip/spec.md`
- 人のスキル: `.claude/skills/board-decide/SKILL.md`（動作確認を飛ばすときの条件の表）
- API・DB・ステージの導出・ループは変わらない

## 設計

### Decisions

#### 出すかどうかをステージの順序で決める

`offersSkipVerify(card)` は次のときだけ真を返す。

- 中止でない（`aborted` が偽）
- ステージの進行度が `verifying` 以下（`stageRank(card.stage) <= stageRank('verifying')`）

引数は `{ stage, aborted }` の形だけを受け取る。`src/shared/` は web からも読むので、サーバの `BoardCard` の型は引かない（`SectionCard` と同じやり方）。

ステージを列挙するのではなく進行度で比べるのは、「動作確認の列をまだ通っていない」をそのまま書けるからである。
列が後で増えても、`verifying` より前か後かで自然に決まる。

止まっている（`hold` がある）カードは、ステージが実装中や計画提案中のままなので出す。保留を見て飛ばすと決めるのは人の判断として自然である。

#### 論点への答え

- **計画レビューより前のカードにも出す。** アイデアの時点で「小さい変更なので動作確認は要らない」と決めたいことがある。
  飛ばす宣言はいつでも外せ、外せば次の 提出 から動作確認の列に入るので、早く決めすぎても取り返せる。
  計画を読んでから決めたい人は、計画レビューのときに入れればよい
- **動作確認のカードでは説明文を差し替える。確認のダイアログは出さない。** 入れた後でも、すぐに外せば `verify 提出` がまた待ちに戻る（宣言を外すとログの読み替えが元に戻る）。
  ただし、外す前にループが `ready` の手で PR を Ready にすると戻らない。ダイアログより先に、文言で押す前に分かるようにする
- **無効表示ではなく、出さない。** 灰色で残すと「なぜ押せないのか」の説明が要り、ゲートの欄が長くなる。
  PR中より後のカードでは、動作確認を飛ばすかはもう決める意味の無い問いなので、問いごと消す

#### `board-decide` のスキルの条件もそろえる

人がチャットで「動作確認を飛ばして」と頼む入口（`board-decide`）も、画面と同じく PR中・マージ済みのカードでは書かずに、効かない理由を返す。
画面に無い操作がチャットからだけできると、効かない宣言がそこから入る。中止のカードは今も条件で弾いている。

### Risks / Trade-offs

- **既に印の入った PR中・マージ済みのカードで、印が見えなくなる。** 宣言の値は残るが、画面からは外せない。
  PR を Draft に戻してカードが実装中に落ちれば、チェックボックスはまた出るので、効く場面では必ず触れる。
  効かない場面で値が残ることに害は無い
- **中止のカードでも出さない。** 中止は終端で、作業も判断も待っていない。中止を取り消す入口は今は無いので、出す理由が無い

### Non-Goals

- 「計画レビューを飛ばす」のチェックボックスの出し分け。実装中のカードで plan の宣言を外すと、提出だけで通っていたカードが計画レビューへ戻るなど、
  「効かない」場面の線引きが動作確認とは違う。要るなら別のカードにする
- API（`PATCH /api/cards/:id`）で PR中 以降のカードへの `verify` の宣言を拒むこと。値が入っても害は無く、出し分けは画面の話にとどめる
- 確認のダイアログ

## 動作確認の手順

共有のカードを汚さないよう、`.claude/skills/board-loop/subagent-rules.md` の「動かして確かめるとき」に従い、`AI_BOARD_DATA` でスクラッチパッドの clone を指す。

1. `npm run build` の後、`AI_BOARD_DATA` を指したまま `node dist/cli.js card create --title ...` でダミーのカードを数枚作る
2. `AI_BOARD_DATA` を指して `npm run dev` と `npm run dev:web` を起動し、ブラウザで詳細パネルを開いて次を見る
   - アイデア・計画提案中のカードでは、ゲートの欄に「計画レビューを飛ばす」と「動作確認を飛ばす」の両方が出る
   - 画面のボタンで計画を承認して実装中にしたカードでも両方が出る
   - `verify 提出` を書いて動作確認にしたカードでは「動作確認を飛ばす」の説明文が実装中へ戻る旨の文に変わり、印を入れるとカードが実装中へ落ちる
   - 中止したカードでは「動作確認を飛ばす」が出ず、「計画レビューを飛ばす」だけが出る
3. PR中・マージ済みのカードは GitHub の PR が要るので、手で作るのが難しければ単体テスト（`stage-gates.test.ts`）の `pr` / `merged` のケースで確かめる。
   本物のボード（`AI_BOARD_DATA` を指さずに起動した画面）で、マージ済みのカードの詳細パネルを開いて見るだけなら書き込みは起きない
